## 1. 结论

540-case 评测中，生产 Skill 选择器通过 506 例，路线决策准确率为 93.70%。它只判断“该不该复用某条路线”，不创建 Linux Task，不读 Artifact，也不审核 Evidence 支持的根因。因此，506/540 不能称为“AI 根因准确率”。

当前工作区的最终 Python 全量回归结果为 **307 passed / 3 skipped / 1 warning**。为避免把阶段性数字混成多个基线，本报告只使用这次最终复核结果。

Windows 上的 Docker Client 可以执行，但它无法连接 `desktop-linux` daemon。本轮没有启动 Control、Linux Agent、MinIO 和故障 demo 的完整拓扑，所以不存在可以声称为 live E2E 的 Task/Attempt/Artifact/Evidence/Report 实测链。

## 2. 540-case 路线盲测

数据来自 `web/public/report-assets/skill-evolution/benchmark-report.json`。生成器使用固定种子 `20260905`，把公开 query 和私有 oracle 分开保存。新 query 没有读取已退役的旧 Case，但诊断类别和正确 Skill 仍由当前 `skills/catalog.json` 派生。这是项目内盲测，不是外部独立数据集。

| 指标 | 数量 | 比例 | 计分规则 |
|---|---:|---:|---|
| 总体通过 | 506/540 | 93.70% | 正例选中指定 Skill，负例弃权 |
| 正例复用 | 334/360 | 92.78% | 选中私有 oracle 标注的 Skill |
| 负例拒绝 | 172/180 | 95.56% | 信息不足、误导或能力/环境漂移时不激活 |
| 误激活 | 8/180 | 4.44% | 负例中选了任意 Skill |
| No-Skill 弃权基线 | 180/540 | 33.33% | 全部不复用；180 个负例得分，360 个正例失分 |

No-Skill 基线不运行另一种 RCA 算法。它的策略是 `ABSTAIN_FROM_ROUTE_REUSE`，用来评估“绝对保守”的路由下界。

### 这层能回答的问题

- 生产混合检索器能否为新描述选中目标 Skill。
- 面对歧义、信息不足和环境漂移时，选择器能否弃权。

### 这层不能回答的问题

- 故障根因服务和根因指标是否判对。
- Collector 是否在 Linux 权限与真实负载下产生可用 Profile。
- `AUTO` 是否比 `DISABLED` 更快拿到首条有效 Evidence，或是否减少 Tool Call。

## 4. 三层测试集

### 第一层：静态盲测

输入是新 query、结构约束和当前 Skill catalog。评测器把公开 Case 与私有 oracle 分开，调用生产混合排名与歧义门禁，输出正例复用率、负例拒绝率和误激活率。

这一层宜放在每次 Skill catalog 和检索器变更的 CI 中。它运行快、结果稳定，所以适合防回归。

### 第二层：受控故障合同/集成

这一层把故障当作有边界的实验对象。每个 Case 要写明：

- 故障 ID、目标、持续时间、自动恢复和预期信号；
- 创建会话的 `skill_policy`、人工干预序列、时间窗口和预算；
- 预期事件、树节点、幂等重试结果与结构化质量错误。

当前仓库已用 SQLite、mock HTTP 和临时 Artifact 覆盖上述合同。Docker 不可用时，这一层仍然不等于完整服务拓扑。

### 第三层：Linux live E2E

真实根因验收需要 Linux Worker、真实目标进程、稳定负载和已标注故障。每个实验臂必须走完：

```text
重置环境 → 启动负载 → 注入故障 → 创建 Diagnosis
→ Tool Call → Task/Attempt → Artifact → Analyzer
→ Evidence gate → Report → 停止故障 → 恢复观测
```

同一 Case 分别运行 `DISABLED` 和 `AUTO`。两臂使用同一故障配置和负载参数，各自重置并重放，不共用上一臂的可变运行状态。记录根因服务/指标命中、首条可用 Evidence 耗时、总耗时、Tool Call 数、空 Profile 率、误根因率和恢复验证。

`scripts/run_live_skill_ab_campaign.py` 会建立两个会话并保存服务端签发的 Diagnosis、Tool Call、Task、Evidence、Report、Skill activation 和树版本。脚本只从环境变量读 API Key，报告对 query 保存 SHA-256。它当前按 `DISABLED` 再 `AUTO` 的顺序执行，也不负责故障注入/重置；运行人或上层 Campaign orchestrator 要补上这部分。

## 5. 测试设计的原始依据

- [Microsoft AIOpsLab 原始仓库](https://github.com/microsoft/AIOpsLab) 和 [AIOpsLab 论文](https://www.microsoft.com/en-us/research/wp-content/uploads/2024/10/arxiv_AIOpsLab.pdf)：把应用、负载、故障、Agent 交互轨迹和 evaluator 分开，用 orchestrator 运行可重放问题。Mini-Drop 的 Linux Campaign 应保存同样的实验元数据。
- [RCAEval 原始仓库](https://github.com/phamquiluan/RCAEval) 和 [RCAEval 论文](https://arxiv.org/abs/2412.17015)：用已标注故障案例评估 root-cause service 与 root-cause indicator，并分开粗粒度和细粒度指标。Mini-Drop 不应只看最终文本是否“像对的”。
- [OpenTelemetry Demo 官方文档](https://opentelemetry.io/docs/demo/) 和 [Feature Flag 场景](https://opentelemetry.io/docs/demo/feature-flags/)：提供可部署的多服务应用与可开关问题，适合补足单进程 demo 无法表达的上下游因果链。
- [Chaos Mesh 官方文档](https://chaos-mesh.org/docs/)、[实验运行契约](https://chaos-mesh.org/docs/run-a-chaos-experiment/) 和 [实验作用域](https://chaos-mesh.org/docs/define-chaos-experiment-scope/)：故障需要显式 selector、持续时间和恢复操作。Mini-Drop 故障广场的白名单、时长上限与自动停止和这类安全约束一致。非 Kubernetes Worker 可参考 [Chaosd 物理机故障文档](https://chaos-mesh.org/docs/simulate-physical-machine-chaos/)。

这些来源用于设计实验分层和可审计字段。它们不会自动为 Mini-Drop 生成 live 验收结果。

## 6. 面试演示脚本

### 演示前检查

1. 在 Linux 演示环境确认 Control、Go API、Diagnosis Worker、Analyzer、MinIO 和 Agent 健康。
2. 启动隔离的 `demo/python-hotspot`，设置 `MINI_DROP_FAULT_LAB_URL`，确认故障广场显示 `READY`。
3. 记录待用 Agent、目标进程和当前时间，预热稳定负载。为 A/B 两臂准备相同的故障重置步骤。

### 8～10 分钟主流程

1. 打开 **AI 诊断 → 验证中心 → 故障广场**，选“CPU 计算热点”，设 120 秒。指出页面只传场景 ID 和时长，服务端决定固定路径。
2. 点击“Skill A/B”，进入“真实 Skill AUTO vs DISABLED”，再启动对比。两侧必须出现不同的 Diagnosis ID；展示真实 Skill 激活、Tool Call、Evidence、轮次和首条证据耗时。
3. 检查 Scope 提示。若页面显示“当前不是严格同 Scope 实验”，只讲两条真实路线如何执行，不比较准确率或速度。严格收益对照应由 Linux Campaign 在每臂前重置故障、固定负载并核对相同 Scope。
4. 打开任一诊断，在探索树点“寻找反证”，或在底部提交“CPU 栈没有主导热点，请切换到 I/O 等待”。展示 intervention 节点、旧假设 `DEPRIORITIZED`、新子假设和树 revision 增长。
5. 沿 Tool Call 打开 Task，查看 Attempt、Artifact 和 Analyzer 结果。如果 Profile 为空，应当演示 `SAMPLE_QUALITY` 失败和重采建议，不展示成功火焰图。
6. 回到诊断页查看 Evidence 引用、Report 验证状态和限制。比较两条会话的 Tool Call、首条有效 Evidence 耗时和总耗时，不只比较最终文字。
7. 停止故障，确认 demo 恢复。结尾时打开 540-case 报告，把“路由盲测”和刚才的 live 链路分开讲。

## 7. 已知限制

1. **本轮没有 Linux live E2E。** `docker version` 返回 `failed to connect to the docker API at npipe:////./pipe/dockerDesktopLinuxEngine`。需在 Linux 或已启动 Docker Desktop Linux Engine 的机器上复跑。
2. **540-case 只测路线。** query 虽然是新生成的，分类体系和 oracle 来自当前 catalog；它不是真实故障数据。
3. **故障广场是 demo 工具。** 当前 7 个场景主要覆盖单机/单进程性能症状，不包含 OpenTelemetry Demo 级别的完整微服务依赖网。
4. **live A/B 脚本不管故障重置、Scope 配对和负载一致性。** 它顺序运行两臂并保存各自目标，但不强制目标/时间窗相同。Campaign orchestrator 需在每臂前重置状态并剔除 Scope 不匹配样本，否则时间漂移和目标差异会污染对照。
5. **旧 Profile 质量字段可能缺失。** 新 Analyzer 会写 `sample_count` 和 `profile_quality`；合同层暂时允许旧产物缺失该字段。质量未知不等于可用。
6. **单个演示不足以给出通用收益。** 需要预先固定根因标签、样本量和验收阈值，再运行多故障、多环境 Campaign。
