# Mini-Drop 21 场景云端真机闭环报告（2026-09-08）

## 结论

发布版本 `/opt/mini-drop-releases/20260908T094648Z` 在同一台 Linux 云服务器、同一个受控演示 Agent 上顺序执行 21 个白名单故障场景，最终 **21/21 通过，0 失败**。Python 7/7、Go 4/4、Java 5/5、C++ 5/5；21 条诊断链和 21 次故障清理全部验证通过。

这是一组真实启动故障、真实调用 Collector、真实写入 MinIO/PostgreSQL 并经过 Analyzer、Evidence Gate 和 Report 的受控 Linux live E2E。它不是 21 个生产事故，也不能外推为生产准确率。

## 通过条件

每个场景必须同时满足以下条件才计为通过：

1. 服务端白名单故障成功启动，并绑定当次 Agent、PID 和时间窗。
2. 决定性 Collector 创建真实 Task/Attempt，产物非空且完整性校验通过。
3. Analyzer 生成结构化结果，并形成至少一条可支撑当前假设的 Evidence。
4. Report 引用对应 SUPPORT Evidence，Diagnosis 进入 `COMPLETED`。
5. `finally` 清理故障并验证停止，不能只完成诊断而遗留负载。

## 缺陷修复与复测

同日前一完整 Campaign 为 20/21，唯一失败是 `go-network-latency`。真实 `sys_metrics` 已采到约 241 ms 的网络延迟和请求增量，但查询同时包含“网络等待”和“下游慢响应”，旧路由器先命中 `DOWNSTREAM_DEPENDENCY`，导致网络信号无法支持错误类别。

修复没有降低证据阈值，而是让首个显式症状句中的具体故障域优先于后续调查/反证文字。修复后先做 `go-network-latency` 定向真机复测 1/1，再在同一新版本上完整重跑 21 个场景并得到 21/21。

## 真实性边界

- Campaign 使用受控 demo，不代表生产事故分布、生产流量或线上准确率。
- 21 个场景顺序执行，避免并发故障污染同一 Agent；它不是随机流量 A/B。
- 当前外部模型账户返回余额不足时，Runtime 会使用可审计的确定性规则兜底。本轮证明真实 Agent 编排、工具调用和证据闭环，不单独证明在线大模型推理质量。
- Skill 的量化提升仍引用独立的 540/500 受控回放报告；不能把本轮 21/21 写成 Skill 带来的准确率提升。
