# 根据面试追问优化 Mini-Drop

日期：2026-09-13。本文是对面试反馈的项目评估与实施建议，尚未实施的内容均不算现有能力；本次没有重新测试云端。

依据：用户提供的《李明远的面试-元宝纪要.txt》、本地源码、CI 配置，以及 9 月 10 日的严格验收记录。纪要是 AI 摘要，不是逐字稿；其中“技术底层不重要”“通过了技术盘问”等评价不作为事实。面试官给的 12306、DeepSeek 是举例，不要求复制真实生产系统，更不能声称得到这些产品的使用背书。纪要里的“生成伪假设”宜改成“提出可证伪假设”。

## 1. 最应该改变什么

建议把下一阶段的主线定为：**让知识库服务的维护者，从一次真实的用户查询变慢出发，找到具体慢在哪一段、有什么证据、如何修复，并在相同请求负载下证明改善。**

你已经介绍了自己的 RAG 办公助手，它比重新开发一个购票系统更适合作为第一个被诊断业务。两个项目可以连接：RAG 负责实际问答，Mini-Drop 负责排查其性能。这里尚未审查另一个 RAG 仓库，不能认定它已经部署了 Milvus、支持哪些索引，或者已经具备下述观测接口。

已有的多语言故障实验室应继续保留，作为采集器和推理边界的回归集。下一阶段优先完成一个业务的三条完整案例，随后再扩展场景数量。

## 3. 第一优先级：做一个能真正使用的业务案例

### 3.1 场景与使用者

业务：员工上传项目文档，然后搜索或提问，系统返回答案和可追溯的文档引用。

异常：同事反馈知识库问答突然变慢，或者导入文件时其他人的查询排队。维护者需要判断是检索、重排、数据库等待还是生成服务变慢，不希望逐台 SSH 猜原因。

输入 Mini-Drop 的问题应类似：

> 今天导入文档后，知识库问答的等待时间明显变长。请检查 knowledge-api 的查询链路，先区分排队、检索、重排和模型生成阶段，再定位主要原因。

问题里只给用户能够观察到的症状，不写“这是锁竞争”“请找某某热函数”。故障开关、正确答案和修复方案放在测试执行器侧，不能送给诊断 Agent。

### 3.2 第一批只选三条不同原因的故障

| 案例 | 用户看到什么 | 故障实现与可观测证据 | 真正的修复实验 |
| --- | --- | --- | --- |
| RAG-01：重排工作量异常 | 文档量或候选数增长后，问答变慢 | 实际重排计算处理过多候选；重排 span、候选数、CPU/Profile 指向同一窗口 | 调整候选策略或批处理，固定输入集和流量比较延迟，同时检查召回/答案质量 |
| RAG-02：导入挤占查询执行资源 | 导入文档时其他人搜索排队 | 在真实请求路径共享有界执行队列；记录队列等待、执行耗时和正在进行的导入量 | 保持相同导入速率和查询流量，分离或限额调度导入工作，检查查询恢复且导入仍有进展 |
| RAG-03：生成依赖变慢 | 检索已结束，但答案迟迟不来 | 下游调用耗时、连接等待、重试次数、超时；业务 CPU 可能正常 | 保持请求负载，落实超时/重试预算及明确降级，区分恢复完整答案与仅恢复可用性 |

前两条应有实际计算或排队机制，不能只在无关后台线程忙等。第三条可使用受控依赖代理模拟延迟，但必须标明“受控依赖”；不能说它证明某个真实模型供应商发生了故障。真实模型冒烟另跑，记录供应商、模型版本、时间和费用。

如果 RAG-03 的修复只能快速返回“暂时无法生成”，应判为“降级可用”，不能拿较短的响应时间当作完整业务恢复。

### 3.3 用什么标准验收

每条案例都完整走：固定数据和负载 → 正常基线 → 业务故障 → 新诊断 → 实施具体变更 → 同负载复测 → 检查质量和副作用 → 清理。

需要保存的数据至少包括：

- 请求集与文档集哈希、随机种子、到达速率、并发上限、预热和采样窗口。
- 业务代码提交、部署镜像、配置、数据规模、检索索引、模型与采集器版本。
- 发起/成功/失败/超时请求数、吞吐、端到端 P50/P95/P99；流式生成另记首 token 时间和完整响应时间。
- 每个阶段的排队与执行耗时、业务进程资源、引用命中率或检索质量；错误请求不能从统计中消失。
- 支持根因与排除替代原因的证据，以及具体修复 diff 或配置变更。

先实测正常基线，再在故障实验前冻结验收阈值。例如恢复窗口 P95 不超过基线的 1.2 倍、成功率和质量不劣于规定容差，可以作为待校准的起点，不能预填成实测成绩。慢依赖等案例应定义自己适用的目标，不能共用一个万能阈值。样本少时不报告稳定的 P99；重复实验保留全部结果，不挑一次最好结果。

保持到达负载一致尤其重要：固定并发的闭环压测在服务变慢后往往自动降低发起速率，容易掩盖排队。记录 offered load 与实际完成吞吐，不只写“并发 10”。

## 4. 第二优先级：补齐业务证据和修复验证

### 4.1 已有追踪基础可以复用，但要分清追踪对象

当前 `apiserver/internal/httpapi/server.go`、`proto/hotmethod.proto`、`server/app/logging_utils.py` 已有 Trace Context 相关代码；不应再说项目完全没有 trace。它们主要关联 Mini-Drop 自身调用。下一步需要观测被诊断 RAG 业务的一次用户请求。

建议业务请求拆为 queue、query rewrite、embedding、retrieval、rerank、generation 等 span，跨服务传播上下文，关联服务实例和时间窗。OpenTelemetry 的 trace/span 与上下文传播正适合表达这种请求关系。并行召回阶段不能简单把各子 span 相加当总耗时，要看关键路径和重叠区间。[OpenTelemetry：Traces](https://opentelemetry.io/docs/concepts/signals/traces/)

由服务注册信息把业务服务/实例解析到 Agent、容器和实际进程，再由现有服务端签发目标绑定。不能让模型凭一个 trace_id 或客户端提交的 PID 自行扩大授权范围。

### 4.2 新证据应沿用现有采集与审计合同

建议新增受控的业务观测适配器，读取授权的 trace、阶段指标、执行计划或慢请求摘要，产出既有 Task → Artifact → Evidence 链。字段需包含目标、时间窗、单位、样本数、采样方式、版本和归属依据。无数据返回不可观测，不伪造 0，也不把主机指标冒充请求证据。

SQL、提示词、文档正文和认证头不要默认整段进入模型上下文；保存必要的摘要、模板指纹与受控引用。测试真值仍与 Agent 输入隔离。

### 4.3 修复验证必须从“热点变化”扩展到“业务结果”

代码中的 `verify_diagnosis_fix()` 目前取两个 Task 的 TopN，然后调用 `compare_before_after()`。页面也提示它只支持 TopN 变化。函数注释写有 same-load，并不意味着实现已经自动校验负载相同。

建议增加负载与环境可比性检查、业务指标比较、质量副作用检查、修复内容和原始证据链接。四种结果分别展示：

| 建议状态 | 何时使用 |
| --- | --- |
| 已验证改善 | 同负载可比、业务指标达到预先冻结标准、质量护栏通过 |
| 仅降级可用 | 减少超时或返回了备用结果，但未恢复完整业务能力 |
| 未通过 | 可比实验完成，但效果或副作用不符合要求 |
| 不可比较/证据不足 | 请求集、负载、实例、窗口或证据不满足比较条件 |

停止故障、业务 CPU 下降、某函数占比下降、诊断会话结束，都不能单独触发“已验证改善”。Profile 比例下降也可能是另一个热点变大，必须结合绝对业务耗时和完成工作量。

## 5. 第三优先级：让测试计划随代码演进

面试官问的不是“让 AI 再写一份测试文档”。需要让需求、风险、测试和运行结果能够互相追溯，并让遗漏在合并前被发现。

现有 CI 已运行 Python、Go、Web、C++ 测试，并检查生成合同漂移。保留这些基础，在其上增加版本化业务验收计划。可以借鉴 Spec Kit 的 Spec → Plan → Tasks → Implement，但工具不会自动保证规范正确；Spec Kit 属于规范驱动开发工具，不能与 BDD 完全画等号。[Spec Kit 官方说明](https://github.github.com/spec-kit/)

### 5.1 建议的计划合同

以下是待实现结构示例，不是现有文件或已经运行的测试：

```yaml
id: RAG-02
requirement: 文档导入期间查询仍满足响应目标
owner: business-runtime
risk: shared_queue_starvation
affected_paths:
  - demo/rag-service/**
  - server/app/drop_insight/**
test_layers:
  - contract
  - integration
  - business_e2e
runner: scripts/run_business_acceptance.py
dataset_id: rag-query-v1
load_profile_id: concurrent-ingest-query-v1
oracle_id: private/rag-02
acceptance_contract: contracts/business_acceptance.v1.json
evidence_required:
  - baseline_and_same_load_retest
  - attributed_queue_wait
  - retrieval_quality
```

路径影响映射只能辅助选择，不能证明覆盖完整。共享鉴权、数据合同、调度和证据门禁变化时，应扩大到全部关键链路；定期完整运行作为兜底。

### 5.2 每次 PR 和合并做什么

1. 从 PR diff、合同与依赖图推导受影响的需求和用例，AI 可以提出补测建议。
2. 作者补充行为变化、风险、验收条件；计划和代码在同一 PR 中评审。与需求无关的变更允许明确解释，不能为每行代码机械新增用例。
3. CI 校验用例 ID 唯一、责任人和执行入口有效、引用合同存在、关键改动有覆盖或有依据的说明；基础测试和风险对应的集成测试必跑。
4. 对合并后的组合提交执行关键业务冒烟，记录 source SHA、测试计划 hash、环境和证据。多人分支各自通过不能替代组合版本验证。
5. 发布前跑受影响的真机业务链路；完整 21 场景按资源安排定期运行。新失败、假阳性和错误修复判断阻止对应发布。已有失败要登记原因、负责人和期限，不应通过重写基线永久豁免。
6. 线上或验收中新发现的问题转成回归案例；计划引用失效、执行入口删除、测试被跳过等变化也要显式失败或明确标记，不当作通过。

AI 生成代码和 AI 生成测试可能共享同一种误解。业务真值、可执行断言和独立观测必须由另一条证据来源校核，“两个 AI 都说对”不足以验收。

### 5.3 必须增加的负向案例

无故障时不乱报根因；错误 PID/过期进程绑定拒绝采集；Agent 断线与工具无权限记为不可观测；模型超时可以受控降级；证据目标或时间错位不能支持结论；冷缓存或流量变化时不能假称修复；降低检索质量换速度不得判整体通过；诊断取消与服务重启后不能重复执行故障操作。

当前 21 项原始失败仍需继续修复。它们是有价值的回归资产，不应删掉来提高通过率。

## 6. Agent 应该怎么优化

最值得优化的是“下一次采什么能解决当前问题”。保留现有 LATS 和证据门禁，先补齐业务输入和观测能力。

| 改动 | 落地规则 | 检验方法 |
| --- | --- | --- |
| 业务上下文结构化 | 入口、症状、时间窗、基线、近期变更、实例范围分别保存；未知就留空 | 同一句“变慢”在不同阶段证据下应走不同取证路线 |
| 缺口驱动下一步 | 每次探针声明要覆盖哪个未满足判据，及成功后可观察到什么 | 检查每轮是否增加有效信息，不能只数调用次数 |
| 优先选择合适采集器 | 请求等待优先看阶段耗时、wall/锁/队列/依赖；计算主导再看 CPU | 等待型场景不能反复用无样本 CPU Profile 耗完预算 |
| 区分不可观测与反证 | 采集失败不等于假设被推翻；替代工具需满足归属和样本要求 | 无权限、低样本、断线时仍不生成错误确定结论 |
| 稳定的证据判据 | 将时间、目标、单位、指标变化等转成明确合同，减少自由文本关键词猜测 | 同义改写、负例及分支冲突测试 |
| Skill 复用有边界 | 优先复用已验证的取证路线；环境、版本、能力变更时重新检查，当前事实重新采 | 留出整个故障类型或变体，比较有/无 Skill 的结果 |

诊断指标至少分开记：工具可用率、可归属证据率、具体根因命中、证据不足率、错误肯定率、耗时、工具/模型成本、诊断对业务造成的额外开销。不要只优化“绿色报告比例”。

评估 Skill 时固定基础模型、预算和数据条件；按完整事故分训练/开发/留出集，不能把同一场故障的文本改写分散到各集合。对照实验先防记忆泄漏，再讨论样本量与统计效应，不能认为每臂达到某个固定次数就自然证明有效。

## 7. Milvus、PostgreSQL 与操作系统要补到什么深度

### 7.1 面试中如何回答“RAG 为什么慢”

应先说明自己会量什么：排队时间、向量化、检索、重排、生成首 token 和总耗时，再结合请求追踪判断主要耗时在哪一段。QPS 是吞吐指标，“QPS 变慢”表述不准确，应说吞吐下降或延迟上升。

如果检索阶段慢，再查实际后端、数据规模、过滤条件、索引、搜索参数、加载状态、并发与资源。若本地实际运行的是 SQLite FTS5，要如实说目前验证的是全文检索；FTS5 是全文检索扩展，不能把它描述为 Milvus 向量索引的等价替代。若另有向量存储或向量算法，必须分别说明。[SQLite FTS5 官方文档](https://sqlite.org/fts5.html)

### 7.2 用一次向量检索实验补技术深度

先固定实际 Milvus 版本和数据类型，再比较它支持的 FLAT、IVF_FLAT、HNSW 等索引。FLAT 可作为相同向量与距离定义下的精确近邻参照；IVF_FLAT 的 nlist/nprobe 与 HNSW 的 M、efConstruction、ef 体现构建、内存、搜索耗时和召回之间的取舍。类型与参数以部署版本为准。[Milvus 索引概览](https://milvus.io/docs/index-explained.md)、[IVF 等内存索引说明](https://milvus.io/docs/index.md)、[HNSW 参数](https://milvus.io/docs/hnsw.md)

实验产出必须同时包含 Recall@K、P95 延迟、吞吐、内存与构建时间。降低 ef/nprobe 后查询更快，可能只是少查了候选；向量近邻召回提高也不自动等于答案正确率提高。文档数不是唯一升级依据，还需测切分后的向量条数、维度、并发、过滤、内存和延迟目标。没有性能拐点证据，不应报出一个拍脑袋的“超过多少文档必须换 Milvus”。

### 7.3 基础知识与项目实操对应

| 领域 | 必须亲手验证的事情 | 面试追问 |
| --- | --- | --- |
| 操作系统 | CPU 计算与睡眠等待两条业务请求，分别查看 profile、RSS、上下文切换和 I/O | CPU 不高为何 P95 高？RSS 增长一定泄漏吗？ |
| 计网 | 拆 DNS、建连、TLS、连接池排队和服务处理时间，记录超时及重试 | 服务端处理快，为何客户端仍慢？重试会怎样放大负载？ |
| PostgreSQL | 在隔离实验里看执行计划、估计与实际行数、缓冲访问、锁等待和连接池等待 | 索引为何未使用？是慢 SQL 还是等连接？ |
| RAG | 固定问题集比较检索候选、重排工作量与答案引用，分别统计质量和耗时 | topK 降低是否真的优化？如何判召回丢失？ |
| Agent | 按每轮假设、证据、反证和预算说明选择理由，复现一个错误并加回归 | 为什么用 LATS？固定流程能否更便宜地达到同等效果？ |

PostgreSQL 的 `EXPLAIN ANALYZE` 会真正执行语句，不能无差别对生产写操作运行；先在隔离数据上建立实验。计划阅读应区分估算成本、实际时间、rows、loops 和缓冲访问。[PostgreSQL：Using EXPLAIN](https://www.postgresql.org/docs/current/using-explain.html)

## 8. 页面与现场演示怎么改

建议在现有 AI 工作台上增加业务案例入口，保持单主视图。首页先解释“知识库用户等答案太久”，展示正常/异常业务指标和受影响阶段；树、Skill 和模型过程由用户展开查看。

建议五分钟演示流程：

1. **40 秒：正常业务。** 发起一次真实查询，看到答案和引用，说明使用者是谁。
2. **40 秒：业务异常。** 开始受控故障和固定负载，展示用户实际等待与阶段耗时。
3. **90 秒：诊断。** 从这次请求进入 Mini-Drop；说明绑定了哪个服务，收集到哪些能归属的证据。
4. **60 秒：解释结论。** 指出具体路径、支持证据、排除的替代原因和未确认内容。
5. **70 秒：修复与对照。** 展示已准备好的实际变更、同负载结果及质量护栏，最后再展开一条有价值的 Agent 分支。

真实诊断可能超过演示时间。现场可以显示真实采集中状态，再切换到明确标注日期与版本的已完成案例；不能把回放装成刚刚实时完成。

报告第一屏要回答：哪里变慢、影响什么用户、定位到哪一层、证据是否足够、是否实施了修复、复测改善了什么。修复 Task 选择最好由本会话的有效任务自动筛选，避免新用户手输两个未知 ID。

产品价值由实测证明：排查用了多久、人工切换几台机器/执行几条命令、少走了哪条错误路线、采集带来了多少业务开销。没有测过就不写“提升 80%”。

## 9. 一个月四个人的实施顺序

这是建议排期，不是对既有完成度的承诺。四个角色：A 业务与负载，B 观测与采集，C Agent 与证据，D 前端与验收；每周围绕同一个可验收案例共同交付，避免等基础组全部做完 AI 组才接入。

| 周 | 主要交付 | 可检查的退出条件 |
| --- | --- | --- |
| 第 1 周 | 审查现有 RAG 实际依赖；固定请求集；打通正常问答与阶段观测；建验收计划合同 | 从一次请求看到实例和各阶段耗时；有可重复正常基线；计划校验进入 CI |
| 第 2 周 | 优先闭环 RAG-01；业务证据接入现有 Evidence；支持同负载修复比较 | 一条案例从症状到具体原因、实际变更、业务及质量恢复完整通过；无故障负例不乱判 |
| 第 3 周 | 增加 RAG-02/03；完善等待工具降级、故障隔离、版本绑定；PR 影响映射 | 三类原因可区分；采集失败不作反证；降级与完整恢复分开展示；共享变更触发关键回归 |
| 第 4 周 | 重复独立实验、无 Skill 对照、留出变体、五分钟演示及复盘 | 有版本化结果和全部失败记录；新人能复现；能解释收益、成本与未完成项 |

建议把 Milvus 索引对比作为第 3～4 周的可选专项：只有前面的业务闭环已稳定才加入。资源不足时先串行执行、缩小数据集并保留真实机制，无需先购买更大集群。要评估规模效应时再按实际容量实验安排资源。
