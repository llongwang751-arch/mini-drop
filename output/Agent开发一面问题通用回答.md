# Agent 开发一面问题：通用回答

> 这份内容不绑定任何具体项目。面试时建议先讲结论，再讲方法或链路，最后补充取舍和边界。涉及个人数据、模型名称和实际指标的地方，只能替换成自己真实做过的内容。

## 一、综合 Agent 问题

### 1. 用户量显著增长时，项目瓶颈在哪里，如何扩展？

我不会先假设瓶颈，而是按请求链路做压测和 Trace，拆分网关、业务服务、模型调用、检索、数据库、队列和第三方接口的 P95/P99、吞吐量、错误率和资源利用率。Agent 系统常见瓶颈是模型限流与长尾延迟、向量检索和 Rerank、长任务占用连接、状态持久化以及工具执行队列。

扩展时先将 API 无状态化并水平扩容，把长任务改成消息队列加 Worker；对模型调用做限流、背压、超时、缓存和降级；数据库补索引、分区或读写隔离；大文件进入对象存储；按租户设置并发和 Token 配额。扩容后还要重新压测，避免瓶颈只是从应用转移到数据库或外部模型。

### 2. 平时用大模型做哪些任务？哪些擅长，哪些不擅长？

大模型适合自然语言理解、分类、信息抽取、查询改写、规划、总结、内容生成和从非结构化资料中找线索。它不适合直接承担精确计算、权限判断、事务一致性、不可逆操作和最终事实认定，因为输出存在随机性和幻觉。

我的原则是：模型负责语义和不确定性判断，程序负责数据、权限、状态和副作用。涉及真实世界动作时，模型只能提出结构化调用请求，服务端必须再次校验并保留审计记录。

### 3. 另一个项目的核心目标与整体架构是什么？

这题使用固定结构回答：“项目服务谁、解决什么问题；入口请求如何经过路由、核心能力、数据层和外部依赖；我负责哪一段；最后用什么指标验证。”不要从技术栈列表开始。

可套用表达：“这个项目面向某类用户，解决某个高频问题。整体分为接入层、业务编排层、核心能力层、数据层和可观测层。一次请求从接口进入，经过鉴权与路由，调用核心服务和外部工具，状态与结果持久化后返回。我主要负责其中的某两层，并通过自动化测试、链路验收和业务指标验证。”

### 4. 项目更偏“生成文档”还是“生成核心代码”？取舍是什么？

文档生成容错空间更大，可以通过引用和人工审核后交付；核心代码会直接影响系统行为，必须经过编译、静态检查、单元测试、集成测试、代码审查和发布门禁。因此在系统早期，我更愿意先让模型生成草稿、测试或局部代码，而不是直接修改核心逻辑并上线。

如果业务必须生成代码，应限制仓库和目录范围、隔离执行环境、控制依赖安装、展示 Diff，并要求自动测试和人工批准。取舍标准是失败的影响范围以及结果能否被低成本验证。

### 5. 如果落地失败，如何复盘与调整方向？

先明确原目标和验收标准，再用数据还原实际结果，把问题拆成需求、数据、模型、工具、工程、交互和评测七层。通过 Trace 和失败样本定位根因，区分偶发故障、能力不足和方案方向错误。

短期先止损和降级，中期修复根因并加入回归集，长期重新判断投入产出。如果简单工作流已经能满足需求，就不应为了“Agent 化”继续增加规划和多 Agent；如果失败来自数据和评价标准缺失，则先补数据闭环，而不是继续调 Prompt。

### 6. 记忆模块怎么设计，如何让 Skill 更好发挥？

记忆应分为会话内短期状态、跨会话长期事实和稳定偏好。短期状态保留当前目标、最近对话和工具观察；长期记忆只保存有复用价值、来源明确的事实；偏好使用白名单字段确定性注入。所有记忆都要有用户作用域、来源、时间、更新和删除机制。

Skill 保存的是可复用流程和工具使用知识，不应保存某次任务的既定答案。运行时先用元数据做轻量匹配，命中后再加载完整 Skill，检查环境、工具和权限是否满足。Skill 的发布要经过离线评测和人工审核，执行结果仍需本次任务重新验证。

### 7. 模型选型依据是什么？

我会先定义任务集，再比较任务成功率、结构化输出合法率、工具调用正确率、上下文长度、P95 延迟、吞吐、Token 成本、限流稳定性、数据合规和部署难度。生成、Embedding、Rerank 目标不同，通常应分别选择和评测。

选型不是追求最大模型，而是在质量门槛满足后选择成本和延迟更合适的方案。低风险分类可用小模型，复杂规划可升级大模型；敏感数据可考虑本地模型。最终通过同一数据集做配对测试，而不是凭主观体验决定。

### 8. 如何理解与治理幻觉？服务化后有哪些衍生问题？

幻觉包括编造事实、引用、工具、参数以及“已经执行”的结果。治理需要四层：使用可信检索和工具提供事实；用 JSON Schema 约束输出；在程序中校验权限、参数和业务状态；证据不足时拒答或转人工，并给出可核验引用。

服务化后还会出现提示注入、知识过期、跨用户数据泄漏、工具重复执行、错误在多轮中累积、缓存污染和模型升级漂移。因此要保存 Prompt、模型和数据版本，建设 Trace、回归集、线上监控、灰度与回滚机制。

### 9. 项目能否本地运行？环境、依赖与可复现性怎么保证？

核心服务应能够通过容器或明确脚本本地启动；外部模型、短信、搜索等依赖可以使用测试账号或 Mock。通过锁定依赖版本、容器镜像、环境变量模板、数据库迁移、健康检查和固定测试数据降低环境差异。

每次实验还要记录代码版本、模型版本、Prompt 版本、数据集版本、随机种子、硬件和参数。别人能够按文档重跑并得到同口径结果，才叫可复现，而不是“我电脑上运行成功”。

### 10. RAG 的优缺点与适用边界是什么？

RAG 能接入私有和动态知识，更新知识不必重新训练，答案还可以提供引用。缺点是链路长，解析、分块、召回、重排和生成都会引入误差、延迟和成本；如果关键内容没有被召回，生成模型通常无法补救。

它适合知识问答、客服、研究和企业文档场景。不适合替代事务数据库、权限系统和规则引擎，也不能保证复杂逻辑计算绝对正确。稳定行为风格可考虑提示或微调，精确事实应查询结构化系统，真实动作必须通过工具执行。

### 11. 多任务相关模型适合哪些业务场景？

适合任务共享底层语义且数据相关的场景，例如客服中的意图识别、槽位抽取和风险分类，文档中的分类、实体抽取和摘要。共享编码可以降低推理和维护成本，并让数据较少的任务受益。

任务无关、标签分布差异大或优化目标冲突时可能出现负迁移。需要分别监控每个任务指标，调整采样和损失权重，必要时采用共享骨干加独立任务头，或者拆成不同模型。

### 12. 常见 Agent 产品有哪些通用特质？

通用模块包括目标输入、上下文构建、路由或规划、工具、执行循环、记忆、状态持久化、权限和 Guardrail、人工审批、Trace、评测和停止条件。

真正区别于普通聊天的是：Agent 会根据环境反馈选择后续动作，并可能修改外部状态。因此它必须能限制权限、处理失败、恢复中断、避免重复副作用，并让用户看见当前进度和最终依据。

### 13. 发现模型执行失败时，从监控到定位再到兜底怎么做？

先按 Trace 确定失败发生在路由、检索、模型、工具、持久化还是渲染阶段；再检查输入上下文、模型版本、Token、延迟、输出 Schema、工具参数和依赖状态。使用同一输入和环境快照离线回放，构造最小复现。

模型超时可有限重试或切备用模型；格式错误可修复一次后降级；工具失败要区分网络故障和业务失败；权限拒绝不能通过重试绕过；无法获取依据时应拒答或转人工。修复后把案例加入回归集，并监控同类失败率。

### 14. 长期记忆设计要关注什么？

要定义写入触发、数据结构、检索策略、更新冲突、遗忘机制和访问权限。长期记忆不能等于永久保存所有聊天，应只记录有复用价值且来源清楚的信息，并保存主体、类别、时间、置信度和过期策略。

还要支持用户查看、纠正和删除，敏感数据加密并严格隔离。密码、Token、工具权限和未经验证的推断不应写入记忆。

### 15. 从整体设计看长期记忆，会从哪些维度评估与取舍？

我会评估任务收益、写入准确率、Recall、误召回、新鲜度、延迟、Token 成本、隐私、可解释性和删除能力。记得越多并不越好，错误或过期记忆会长期污染决策。

稳定偏好可以确定性注入，普通事实按需检索，临时任务状态只留在会话。高风险记忆要求来源或人工确认，低价值内容自动衰减。

### 16. 长期记忆还有哪些优化点？

成本方面可异步抽取、批量 Embedding、冷热分层和缓存；命中方面可做关键词加向量的混合检索与 Rerank；漂移方面保存时间与来源并检测新旧冲突；遗忘方面使用 TTL、重要度衰减、容量限制和用户删除。

评测应比较开启和关闭记忆后的任务成功率，同时关注误注入、跨用户泄漏和陈旧事实影响，不能只看“召回了多少条”。

### 17. 怎么看 Agent 领域发展趋势？

趋势正在从“会调用工具的 Demo”转向可恢复执行、上下文工程、Skill、工具协议、权限隔离、Trace 和多轮评测。单 Agent 仍应是默认方案，只有子任务可并行、需要不同权限或上下文隔离时，才增加多 Agent。

另一个趋势是把模型规划与执行环境分离：模型负责决定下一步，受控运行时负责凭证、沙箱、审批、Checkpoint 和副作用。评测也从只看最终文本，发展到检查工具轨迹、环境状态和任务结果。可参考 Anthropic 的[有效 Agent 构建原则](https://www.anthropic.com/engineering/building-effective-agents)、[Agent 评测方法](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)和 OpenAI 的[Agent 构建工具](https://openai.com/index/new-tools-for-building-agents/)。

## 二、腾讯类 Agent 开发问题

### 1. 实习经历深挖：做了什么、难点、产出？

使用 STAR 回答：一句话交代业务背景和目标；明确自己负责的模块和边界；选择一个最难的问题，说明如何定位、做了哪些方案比较、最终如何实现；最后给真实指标和未完成项。

建议表达：“我负责的是某条核心链路，不是整个系统。难点在于某个约束，我通过监控或实验确认根因，比较方案后选择某实现，最终将某指标从 A 改善到 B。这个结果在某环境和某数据集验证，尚不能外推到其他场景。”没有实习就直接说主要工程经历来自项目，不要虚构公司经历。

### 2. 项目经历深挖：架构、链路、你负责的部分？

先用一张请求链回答：客户端请求进入网关，经过鉴权与路由，进入核心业务或 Agent Runtime，调用检索和工具，状态进入数据库，过程通过事件流返回，最终结果持久化。然后解释每层为什么存在。

个人职责要落到文件、接口或模块：负责设计什么、实现什么、联调什么、验证什么；团队已有或别人完成的部分明确说“参与联调”，不要说成独立完成。

### 3. 检索是否基于向量？搭一个完整 RAG 需要哪些组件？

完整 RAG 包括文档加载、解析清洗、分块、Embedding、索引、查询理解或改写、召回、融合、Rerank、上下文组装、生成、引用、拒答、Trace 和评测。向量检索擅长语义，BM25 擅长专有名词和编号，图检索适合关系和多跳信息。

不一定必须全部使用。数据量小或术语精确时，BM25 可能足够；是否增加向量和 Rerank，应通过同一评测集的质量、延迟和成本对照决定。

### 4. 文档上传与分块如何实现？

上传后先校验类型、大小和权限，保存原文件与版本；再解析正文和版面，清理乱码、异常空白和重复元素；然后按标题、段落或语义边界分块，并设置合理重叠。表格、代码和图片应使用专门解析方式。

索引时保存文档 ID、版本、页码和块位置，生成向量并建立关键词索引。可以使用小块检索、大块回填上下文：小块提高命中精度，大块保证回答完整。索引构建最好异步，并支持失败重试、幂等和从权威原文重建。

### 5. 向量检索单次耗时是多少？是否引入 Rerank，怎样评估收益？

耗时必须实测，不能凭经验编数字。我会拆分查询 Embedding、向量数据库、关键词检索、融合和 Rerank 的耗时，预热后在固定数据规模和并发下统计 P50/P95/P99。

Rerank 的收益通过消融实验验证：同一标注集比较召回加不加 Rerank 时的 MRR、nDCG、答案正确率和引用支撑率，同时比较 P95 和调用成本。如果排序质量提升很小但延迟明显增加，就应减少候选数、使用小模型或取消 Rerank。

### 6. 如何评估召回内容与问题匹配度？

离线数据包含问题和标准证据集合，使用 Recall@K 判断正确证据是否进入候选，Precision@K 判断噪声，MRR 看第一个正确结果的位置，nDCG 处理多级相关性。生成侧再看答案正确性、忠实度、引用支撑和无答案拒答。

线上使用无结果率、改写重试、引用点击、人工纠错和用户反馈作为弱信号，再把高价值失败样本脱敏后加入离线集。关键结论不能只依赖模型自评。

### 7. 如何定义 Agent？核心模块有哪些？

Agent 是围绕目标，根据上下文和环境反馈选择动作、调用工具并维护多步状态的系统。核心包括模型、上下文、路由或规划、工具、执行循环、记忆、状态持久化、Guardrail、人工审批、Trace、评测和停止条件。

固定代码路径属于工作流；模型动态决定下一步更接近 Agent。实际产品可以组合两者，明确流程用工作流保证稳定，开放任务才让模型自主决策。

### 8. 是否了解 ReAct？项目里怎么用？

ReAct 是 Reasoning 与 Acting 交替：模型根据当前信息选择 Action，工具返回 Observation，模型基于新事实继续判断，直到完成或触发停止条件。它比一次性规划更能适应环境变化。

工程实现不能暴露无限循环，需要限制步骤、Token、时间和工具次数；每次调用要做 Schema、权限和副作用校验；失败时记录原因，必要时重试、换工具或转人工。

### 9. Agent 循环一般多少步能收敛？达到最大步数仍失败怎么办？

没有统一步数，要通过任务分布和评测确定。简单工具任务可能两三步，复杂研究任务会更多，但必须设置最大迭代、工具调用、Token、时间和费用预算，并检测重复动作和无进展。

达到上限仍失败时，返回已完成步骤、当前证据、缺失信息和可恢复状态，不能编造完成。低风险任务可请求用户补充后继续，高风险任务应转人工。

### 10. Agent 接入了哪些工具？工具接口和权限怎么治理？

回答时按类别说明真实接入的工具，例如检索、数据库、文件、浏览器、代码执行和业务 API。每个工具使用清晰名称、描述和 JSON Schema，服务端校验字段、范围、用户权限和资源作用域。

治理原则是最小权限、凭证不进 Prompt、读写权限分离、高风险操作审批、沙箱隔离、超时与配额、调用幂等和全量审计。模型只能申请动作，不能自行扩大权限。

### 11. 如何约定并约束模型做正确工具调用？

用清晰工具说明和少量示例提高模型选择概率，用 JSON Schema 规定类型、枚举和必填字段；服务端再次检查工具是否存在、参数是否合法、目标是否授权、状态是否允许。格式错误可以有限修复，仍失败则拒绝或降级。

提示词是软约束，程序校验和权限系统才是硬边界。工具结果还应带稳定错误码，帮助模型判断该重试、改计划还是停止。

### 12. 推流是否使用 SSE？为什么选 SSE？

如果场景主要是服务端向浏览器推送 Token、日志和任务进度，SSE 很合适：基于 HTTP、浏览器原生支持、实现简单并有自动重连语义。客户端发起任务、取消和审批仍使用普通 HTTP。

工程上要增加事件 ID、心跳、断线去重和状态补偿。SSE 不是持久消息系统，断线后最终状态应从数据库重新读取。

### 13. 编排里是否有 Plan 阶段？Plan-Execute 如何实现？

Plan 阶段将目标拆成结构化节点、依赖、预期输出和停止条件；执行器校验依赖无环，按拓扑顺序调度，独立节点并行，失败节点按策略重试。状态持久化后可以取消和恢复。

Retry 表示计划正确但某次执行偶发失败；Replan 表示根据已有结果发现后续计划不再合适，只调整未完成部分。计划本身不是权限，执行每个工具仍需经过安全校验。

### 14. SSE、WebSocket、HTTP 的差异、场景与取舍？

HTTP 是一次请求一次响应，适合 CRUD 和提交任务；SSE 是服务器到客户端单向推送，适合流式文本和进度；WebSocket 是全双工长连接，适合游戏、协同编辑和高频双向控制。

Agent 聊天通常使用 HTTP 提交请求、SSE 接收过程。只有确实需要持续双向低延迟通信时才使用 WebSocket，因为连接治理和扩容更复杂。

### 15. 为什么限制每个用户只能上传一个文件？

这通常是 MVP 的产品和一致性约束，不是技术极限。先限制单文件，可以降低批量上传的部分成功、重复文件、配额、跨文档权限、多索引补偿和回滚复杂度，快速验证核心价值。

后续支持多文件时，应增加批次 ID、单文件状态、去重、幂等、配额、失败重试和索引重建。面试时应坦诚它是阶段性取舍。

### 16. 图像识别怎么做？为什么不用多模态大模型，而用传统方案？

如果目标只是扫描文字识别，传统 OCR 通常成本低、速度快、输出稳定，并能提供字符位置和置信度。多模态模型适合复杂版面、图表和图片语义，但成本更高、输出更难确定性验证。

合理设计是 OCR 先处理常规页面，低置信度或复杂图表再路由到多模态模型，同时保留页码和区域坐标。是否采用要根据识别准确率、延迟、成本和数据合规评测。

### 17. 项目用到哪些大语言模型？选型原因是什么？

这题必须替换成真实模型。回答结构是：“生成模型负责什么、Embedding 负责什么、Rerank 是否独立；为什么选；与哪些方案比较；目前有什么边界。”

不要只说价格便宜。至少说明任务成功率、结构化输出、上下文、延迟、成本、稳定性和部署。没有做完整横评时就说“当前是工程基线，不宣称最优，后续会用同一评测集比较”。

### 18. Go 并发与其他语言并发模型的关键差异是什么？

Go 使用 goroutine、channel 和运行时调度器。goroutine 初始栈小，由运行时调度到较少 OS 线程上；channel 提供通信式协作，`context` 负责取消和超时。相比直接创建线程，适合大量 I/O 并发；相比单线程事件循环，代码结构更接近同步写法。

但共享变量仍会产生数据竞争，channel 也会死锁或泄漏。要使用有界 Worker Pool、`context`、WaitGroup、锁和 Race Detector，避免无限创建 goroutine。

## 三、字节类 Agent 开发问题

### 1. 项目端到端流程、关键实现细节与整体架构取舍？

按“请求进入—鉴权路由—上下文—规划—工具—状态—结果—观测”讲完整链路。每到一层说明输入输出和失败处理，再选择两个关键细节深入，例如幂等、权限或恢复。

取舍要回答为什么没有采用更复杂方案。好的表达是：“先用最简单方案满足核心指标；只有评测证明质量不足，才增加 Rerank、多 Agent 或复杂图编排。每增加一层都会带来延迟、成本和故障面。”

### 2. 项目有哪些缺陷？如果重来如何改进？

不要说“没有缺陷”。可以从评测集不足、监控不全、过早引入复杂架构、异常链覆盖不足、成本和安全边界中选择真实问题。说明它造成的具体影响，以及为什么当时会做这个取舍。

重来时先定义成功指标和失败集，做最小闭环，再逐层增加能力；提前设计事件、幂等和可观测；对新组件做消融实验，收益不足就不引入。

### 3. 遇到模型输出偏离指令时如何处理？给具体案例与对策

例子可以是模型返回非法 JSON、编造工具名或遗漏必填参数。处理方式是先记录原始输出和 Trace；用 Schema 校验；只允许一次有限格式修复；校验工具名、参数、权限和状态；仍不合法则拒绝或走确定性 fallback。

修复后把案例加入评测集，统计 Schema 合法率和工具调用成功率。不能只在 Prompt 后面继续加一句“请严格遵守”，因为提示词不是强制边界。

### 4. 关注的前沿 Agent：举例并解释核心机制

可以讲 OpenClaw。它以长期运行的 Gateway 作为本地控制面，连接多种消息渠道，维护会话、工作区、记忆、模型和工具；通过 binding 将不同渠道或账号路由到隔离 Agent；Skill 用 `SKILL.md` 描述能力，并按环境、依赖和 allowlist 过滤。

值得关注的是 local-first、多渠道、持久状态、Skill 和多 Agent 路由的组合。它面向可信操作者，不应直接当作对抗性多租户安全边界。可参考其[官方架构](https://docs.openclaw.ai/architecture)、[Skill 文档](https://github.com/openclaw/openclaw/blob/main/docs/tools/skills.md)和[安全说明](https://github.com/openclaw/openclaw/security)。

### 5. 如何理解 Claude Code “memory 三层”设计？

常见的三层说法是：用户级 `~/.claude/CLAUDE.md` 保存跨项目个人偏好；项目级 `./CLAUDE.md` 保存团队共享规范；本地项目级 `CLAUDE.local.md` 保存不提交仓库的个人环境信息。分层解决作用域、共享范围和优先级问题。

按当前官方实现，还包括组织托管策略、路径范围规则和 Claude 自动维护的 Auto Memory，因此不能机械地说永远只有三层。`CLAUDE.md` 是上下文指导，不是强制安全策略；禁止操作应使用权限设置或 Hook。参考 [Claude Code Memory](https://code.claude.com/docs/zh-CN/memory)。

### 6. 是否使用过 AI 编程工具？团队内如何使用并规避风险？

可以用于代码阅读、方案草稿、局部实现、补测试、重构和定位问题，但开发者对最终代码负责。团队需要限制数据和目录范围，不把生产密钥放入上下文；所有修改看 Diff，经过代码审查、静态检查和自动化测试后才能合并。

风险包括错误代码、秘密泄漏、依赖与许可证问题、提示注入、大范围误改和生成测试自证实现。高风险操作要最小权限和人工审批，禁止 Agent 自动推送生产。

### 7. Cursor 上下文过长是否出现性能下降？如何监控与缓解？

上下文增长会增加输入 Token、首 Token 延迟和成本，也可能让关键指令被无关历史稀释。监控输入 Token、首 Token 时间、总耗时、缓存命中、截断或压缩次数、工具失败和任务成功率。

缓解方法包括不同任务使用新会话、只加载相关文件、按需检索、压缩旧过程但保留约束与未完成状态、限制工具输出、将稳定规则放项目指令或 Skill，并对长短上下文做同题评测。

## 四、百度类 Agent 与单元测试问题

### 1. 项目核心目标、技术栈、线上指标与瓶颈？

回答顺序是：一句业务目标；一条端到端链路；核心技术栈；两项真实指标；一个瓶颈和下一步。指标最好覆盖业务效果与工程质量，例如任务成功率、P95、错误率和成本。

所有数字都要说明数据集、环境和时间范围。离线评测不能说成线上准确率，自动化测试通过也不能替代业务效果。

### 2. 提示词模板如何设计与迭代？怎样判断真的变好？

模板应明确角色、目标、输入可信级别、输出 Schema、工具、禁止事项、停止条件和失败处理；动态信息作为结构化字段注入，Prompt 和模型都做版本管理。

使用固定评测集比较任务成功率、Schema 合法率、工具选择正确率、越权率、引用正确率、工具次数、P95 和成本。先离线配对评测，再做小流量 Shadow 或 A/B；同时看改善和退化案例，不能凭语言是否流畅判断。

### 3. 单 Agent 与多 Agent 的取舍点是什么？

默认使用单 Agent 加清晰工具，因为共享上下文容易、延迟和成本低、调试简单。子任务可以并行、需要不同专长或权限、上下文需要隔离时，再考虑多 Agent。

多 Agent 会增加调用、协调、重复工作和冲突合并成本。采用前应通过任务成功率、延迟、Token 和失败率证明收益；固定流程可能直接用工作流更合适。

### 4. 如何确定任务拆分粒度和停止条件？

每个节点应有清晰输入、单一可验证输出、明确副作用和失败边界。过粗不利于并行、重试和定位；过细会增加模型调用和状态传递成本。一般按一次工具调用、一个外部依赖或一个独立验收点拆分。

停止条件包括目标完成、验证门通过、没有新信息、连续重复、预算耗尽、无可用工具和需要人工确认。停止由程序判断，不只依赖模型说“完成”。

### 5. 上下文如何组织，避免信息污染和无关信息挤占窗口？

按可信度和用途组织：系统约束、用户目标、当前状态、工具说明、相关知识和最近观察。外部文档与工具结果标记来源，不能覆盖系统指令；知识按当前步骤检索并去重，工具长输出先结构化或摘要。

保存实际上下文快照和 Token 分布，方便定位污染。其他用户数据、敏感字段和无关历史必须在进入模型前过滤。

### 6. 窗口不够时优先保留哪些信息？依据是什么？

优先保留安全与权限约束、当前目标、不可变事实、未完成状态、最近工具结果和与当前步骤最相关的知识。普通寒暄、重复内容、已完成的详细过程和低相关资料可以压缩或删除。

依据是信息丢失后对安全和任务正确性的影响，而不是简单按时间先后。原始材料保留引用，必要时再按需读取。

### 7. AST、调用图等结构化信息如何融入模型输入或检索？

先解析代码得到符号、定义引用、调用边、文件和行号，并按函数或类建立索引。查询时先通过符号和语义找到入口，再沿调用图扩展有限跳数，把相关代码、签名、关系和测试送入模型。

AST 提供精确结构，调用图处理跨函数影响，向量检索处理自然语言。三者融合时要限制图扩展范围并保留出处，避免把整个仓库塞进窗口。

### 8. 哪些代码不适合自动生成单测？如何识别与过滤？

强依赖硬件或生产环境、随机与时间敏感、第三方副作用、并发竞态、视觉效果、没有稳定契约的遗留代码，以及支付和删除等高风险逻辑，不适合直接自动生成完整单测。

检测外部依赖、全局状态、非确定性和危险副作用后，可以只生成测试骨架并要求人工提供 Oracle，或者先重构依赖注入；剩余部分使用集成、契约或端到端测试。

### 9. 覆盖率高但质量差，如何定义“好单测”？

好单测验证可观察行为和关键不变量，覆盖正常、边界、异常和状态迁移；稳定、隔离、快速，失败时能指出问题；不复制实现细节，也不只有“方法被调用”这种弱断言。

除覆盖率外，还要看 Mutation Score、历史缺陷复现率、断言质量、Flaky 率和失败定位时间。覆盖率只是发现盲区的信号，不是最终目标。

### 10. Mock 的边界：什么时候必须 Mock，什么时候会掩盖问题？

网络、时间、随机数、第三方 API、昂贵模型和危险副作用适合在单元测试中 Mock，以保证快速和确定。自己的核心业务逻辑、SQL 行为、序列化和协议契约不能全部 Mock，否则只证明 Mock 能按预期返回。

关键边界需要 Fake、临时真实依赖、契约测试和集成测试补充。Mock 的 Schema 也要与真实接口同步，避免接口已经变化而测试仍通过。

### 11. 依赖 DB/RPC 的函数，如何让生成单测稳定运行？

通过依赖注入抽离 Repository、RPC Client、Clock 和 ID Generator。单元测试使用内存 Fake 或 Stub，固定时间、随机数和 ID，覆盖成功、超时、重试、重复请求和错误映射。

事务、唯一约束和 SQL 使用临时数据库或容器做集成测试；RPC 用契约测试验证兼容性。测试数据独立准备和清理，不依赖执行顺序，异步逻辑用事件等待而不是固定 `sleep`。

### 12. 除覆盖率外，单元测试还有哪些指标？

可以看分支与条件覆盖、Mutation Score、关键需求覆盖、历史缺陷复现率、断言强度、测试耗时、Flaky 率、失败定位时间和维护成本。

最重要的判断是：故意改坏关键逻辑时测试是否稳定失败；只做不影响行为的重构时，测试是否仍然稳定。前者衡量发现缺陷能力，后者衡量测试是否过度绑定实现。

## 五、使用建议

1. 每题先练 30 秒版本，再准备一个可展开的例子。
2. 涉及数字时必须说清样本、环境、指标定义和限制。
3. 不知道具体耗时时，回答测量方法，不要编毫秒数。
4. 面试官继续追问时，用“为什么这样选、替代方案是什么、怎样验证”展开。
5. 不要为了显得复杂，强行把所有系统说成多 Agent、向量检索或动态规划。
