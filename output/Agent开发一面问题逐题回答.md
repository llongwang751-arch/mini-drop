# Agent 开发一面问题逐题回答

> 适用方向：AI 应用开发、Agent 开发、测试开发、AI 后端实习。
>
> 回答原则：先给结论，再讲链路或取舍，最后说证据和边界。下面的答案按 30～90 秒设计，不要逐字背；涉及尚未完成的评测时必须如实说明。

## 一、综合 Agent 问题

### 1. 用户量显著增长时，项目瓶颈在哪里，如何扩展？

我会先根据监控定位瓶颈，而不是直接说“加机器”。AGI-Saber 的潜在瓶颈依次是外部模型限流和延迟、多路检索与 Rerank、文档解析和多索引写入；Mini-Drop 则可能是任务调度、Agent 心跳与租约、Artifact 上传和 Analyzer 队列。重点观察各阶段 P95/P99、队列长度、错误率、数据库连接池和资源利用率。

扩展时把 API 做成无状态服务并水平扩容，把解析、采集和分析改成队列驱动的 Worker；对模型调用做限流、背压、超时和缓存；数据库补索引、分区和读写隔离；对象存储承接大文件；最后增加租户配额、幂等键和全链路 Trace。先消除单点和状态耦合，再扩容计算资源。

### 2. 平时用大模型做哪些任务？哪些擅长，哪些不擅长？

我主要让模型处理语义理解、查询改写、候选假设生成、任务规划、工具选择、信息归纳和报告解释。这些任务允许一定表达差异，适合模型发挥。

模型不适合直接承担权限判断、精确计算、数据库一致性、不可逆操作、目标身份绑定和最终事实认定。Mini-Drop 中模型可以提出根因假设，但不能直接执行 Shell，也不能把自己的判断写成 Evidence；确定性程序负责工具白名单、参数、预算、状态机和证据门禁。原则是让模型处理不确定性，让程序控制事实、权限和副作用。

### 3. 另一个项目的核心目标与整体架构是什么？

如果先讲 Mini-Drop，另一个项目 AGI-Saber 可以这样介绍：它是个人办公 Agent，目标是让用户基于 PDF、Markdown 等私有资料可靠问答，并完成有限的工具任务。架构分为文档入库、RAG 查询和通用执行三条链。入库侧做解析、清洗、父子分块和多索引；查询侧做向量与 BM25 召回、RRF、Rerank、父块回填和引用；执行侧做路由、任务规划、状态调度、工具调用和 Trace。

如果先讲 AGI-Saber，则用 Mini-Drop 回答：React 页面访问 Go API，Go 负责鉴权、范围和任务编排，C++ Control/Agent 负责跨机下发白名单采集器，Python Analyzer 生成火焰图和结构化指标，Diagnosis Worker 使用 LangGraph、LATS、RAG 和 Skill 完成证据驱动诊断，PostgreSQL 与对象存储保存状态和产物。

### 4. 项目更偏“生成文档”还是“生成核心代码”？取舍是什么？

AGI-Saber 更偏私有知识问答和受控任务执行，文档是可能的交付物，但不是让模型直接生成并上线核心代码。文档生成风险相对较低，能通过引用和人工复核验收；核心代码会产生更大副作用，需要仓库上下文、编译、静态检查、单元测试、代码审查和权限隔离。

当前已移除重复且过度特化的专用报告工作流，生成报告可以作为通用执行链中的一种任务。取舍是减少特殊分支和维护成本，但保存文件仍必须经过明确工具、路径隔离和幂等控制。

### 5. 如果落地失败，如何复盘并调整方向？

我会把失败拆成需求、数据、模型、工具、工程和评测六层，先用 Trace 找到失败发生在哪一层，再区分偶发故障和系统性缺陷。复盘记录目标、实际结果、关键假设、证据、根因、修复方案和防复发测试。

项目中的一个例子是专用报告工作流：它增加了固定路线和额外维护成本，但通用执行链已经能覆盖大部分生成任务，收益不足以支撑复杂度，因此后续移除专用路由，保留通用执行与文档能力。另一个例子是 RAG 缺少足够真实标注集，因此不能把演示成功当质量提升，而应先补评测集和消融实验，再决定是否继续增加图检索或模型调用。

### 6. 记忆模块怎么设计，如何让 Skill 更好发挥？

记忆要区分短期上下文、长期事实和稳定偏好。AGI-Saber 的短期记忆是最近对话窗口；长期记忆先提炼值得保存的事实，连同类别、重要度等持久化，再按当前问题相关性召回；偏好应使用白名单字段确定性注入。当前没有把中间对话做摘要压缩，属于可改进项。

Mini-Drop 中，诊断事实、Evidence 和报告以 PostgreSQL 为权威，模型短期消息由 Checkpoint 管理；Skill 保存的是经过验证的调查路线，不保存旧事故根因。为了让 Skill 发挥作用，先用轻量目录检索，命中后才加载完整正文；再做运行时、环境和工具能力门禁；最终必须通过离线评测和人工发布。Skill 只能影响“先查什么”，不能替代本次取证。

### 7. 模型选型依据是什么？

我会在同一评测集上比较任务能力、结构化输出和工具调用成功率、上下文长度、P95 延迟、Token 成本、限流稳定性、数据合规和部署方式，而不是只比较榜单分数。

Mini-Drop 当前云端通过 OpenAI 兼容接口使用 `deepseek-chat`，模型不可用或输出非法时有确定性兜底。AGI-Saber 的聊天、改写、规划和远程 Rerank 当前主要复用火山方舟上的 DeepSeek V4 Flash；文档 Embedding 使用豆包多模态向量模型，输出 2048 维，但当前只传文本；联网搜索可选 Tavily，没有单独接 Cross-Encoder Rerank。选择原因可以说成本、延迟和接入一致性合适，但没有完成全面模型横评，不能宣称它一定最优。

### 8. 如何理解与治理幻觉？服务化后有哪些衍生问题？

幻觉不仅是“答案说错”，还包括编造工具、参数、数据来源、引用和已执行结果。治理分四层：输入侧只提供可信上下文并隔离外部指令；输出侧使用 Schema 和字段校验；执行侧使用白名单、权限、预算和人工审批；结果侧使用 Evidence、引用和拒答门槛。

服务化后还会出现提示注入、知识过期、引用与正文不一致、工具重复调用、多轮错误累积、缓存污染、模型版本漂移和跨用户数据泄漏。因此要保存模型版本、Prompt 版本和 Trace，按失败类型监控，使用离线回归、线上小流量和可回滚发布，而不是只调提示词。

### 9. 项目能否本地运行？如何保证环境、依赖和可复现性？

两个项目都能在本地启动核心服务，但完整能力有外部条件：Mini-Drop 的真实 `perf`、eBPF、py-spy 等采集需要合适的 Linux 权限和运行时；模型调用需要配置 Provider。AGI-Saber 的 Milvus、Elasticsearch、Neo4j 等可通过容器启动，模型和搜索依赖相应密钥；扫描 PDF 当前只提示需要 OCR，并不内置 OCR。

可复现性通过固定依赖版本、Docker Compose、环境变量模板、数据库迁移、健康检查、固定随机种子、公开输入与私有 Oracle 分离、测试 Fixture 和机器可读报告保证。任何性能或准确率结论都要附带代码版本、模型版本、数据版本、预算和运行环境。

### 10. RAG 的优缺点与适用边界是什么？

优点是能接入私有和更新频繁的知识，回答可以带引用，更新知识时不必重新训练模型，成本通常低于微调。缺点是链路长，解析、分块、召回、融合、重排和生成任何一层都可能出错；召回不到时模型也无法凭空恢复，检索还会增加延迟和上下文成本。

RAG 适合知识密集、答案需要出处、知识经常变化的场景。不适合把稳定行为规则完全交给检索，也不适合精确事务、权限判断或必须执行真实动作的任务。后者应使用结构化数据库、规则引擎和工具接口；固定风格或行为能力有时更适合提示模板或微调。

### 11. 多任务模型适合哪些业务场景？

适合多个任务共享输入和底层语义、标签相互促进的场景，例如客服中的意图识别、槽位抽取和风险分类，文档中的分类、实体抽取和摘要。共享编码可以减少重复计算和维护多个模型的成本。

如果任务相关性低、标签规模差异大、优化目标冲突或某个任务风险特别高，多任务训练可能出现负迁移。此时要监控每个任务的独立指标，调整损失权重，必要时使用共享骨干加独立头，或者直接拆成不同模型。

### 12. 常见 Agent 产品有哪些通用特质？

通用模块包括：目标与交互入口、上下文构建、规划或路由、工具注册与调用、短期和长期记忆、执行状态与 Checkpoint、权限和 Guardrail、人工审批、Trace 与评测。

产品层面的共同点是任务通常跨多步、能读取环境反馈、允许失败恢复并有明确停止条件。真正的工程价值不在“能调用模型”，而在工具接口是否清晰、状态是否可恢复、行为是否可审计、失败是否可降级。

### 13. 发现模型执行失败时，怎样从监控到定位再兜底？

先根据请求 ID 或 Trace 定位失败阶段：路由、检索、模型、工具、状态持久化还是输出渲染。然后检查输入上下文、模型版本、Token、耗时、结构化输出、工具参数和依赖状态，使用同一快照离线回放，构造最小复现。

失败类型不同，兜底也不同：模型超时可重试或切备用模型；非法结构可修复一次后走确定性 fallback；工具失败要区分可重试故障和业务失败；权限拒绝不能重试绕过；证据不足应该拒答或换证据域。修复后必须把该案例加入回归集，并观察线上失败率和退化指标。

### 14. 长期记忆设计要关注什么？

需要回答五个问题：什么内容触发写入，保存什么结构，如何检索，如何更新或遗忘，谁有权读取和删除。不能把所有聊天直接永久保存，更不能把密码、Token、旧 PID、工具权限和未经验证的根因写入长期记忆。

建议保存来源、主体、时间、类别、重要度、置信度和过期时间；写入前去重和冲突检测；检索时同时考虑相关性、时效性和权限；提供查看、修改和删除入口；敏感字段加密并按用户隔离。

### 15. 从整体设计看长期记忆，如何评估和取舍？

我会从记忆价值、准确性、新鲜度、召回命中、误召回、延迟、成本、隐私和可解释性评估。写得越多不一定越好，错误或过期记忆会持续污染决策；检索越激进，噪声和 Token 成本越高。

因此稳定偏好可确定性注入，普通事实按需召回，临时任务状态只保留在会话中。高风险事实需要来源和人工确认，低价值信息自动衰减。核心取舍是“记住的收益”是否大于错误记忆和隐私风险。

### 16. 长期记忆有哪些优化点？

成本方面做异步抽取、批量 Embedding、冷热分层和缓存；命中方面做混合检索、重排和按任务类型选择记忆；漂移方面保存时间和来源，发现新旧事实冲突时不直接覆盖；遗忘方面使用 TTL、重要度衰减、容量上限和用户删除。

评测不能只看召回率，还要看记忆是否真的改善任务成功率、是否误注入不相关内容、是否泄露其他用户信息，以及关闭记忆后的消融差异。

### 17. 怎么看 Agent 领域发展趋势？

我的判断是重点正从“做出一个会循环调用工具的 Demo”，转向可恢复执行、上下文工程、Skill 复用、工具协议、权限控制、Trace 和多轮评测。单 Agent 仍是默认方案，只有并行研究、隔离上下文或角色能力确实不同，才值得增加多 Agent；复杂度必须由评测收益证明。

另一个趋势是把模型的“脑”和执行环境的“手”分开：模型规划，受控运行时处理凭证、沙箱、审批、Checkpoint 和副作用。Agent 评测也从只看最终答案，发展到同时检查轨迹、工具调用、环境状态和任务结果。这个判断与 Anthropic 的[有效 Agent 构建原则](https://www.anthropic.com/engineering/building-effective-agents)、[Agent 评测方法](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)以及 OpenAI 的[Agents SDK 与可观测能力](https://openai.com/index/new-tools-for-building-agents/)一致。

## 二、腾讯类 Agent 开发问题

### 1. 深挖实习经历：做了什么、难点、产出？

如果没有正式实习，不要虚构。可以说：“我的主要工程经历来自两个完整项目。”然后用 STAR：背景是手工性能诊断难复现；任务是负责 AI 诊断主链；行动包括 Agentic RAG、Skill、LATS、Evidence Gate 和全链路验收；结果是五百组同题同预算回放中，Skill 将证据型根因 Top-1 从 41.20% 提升到 68.00%，并完成多运行时真实链路验收。最后说明回放不等于五百次线上故障。

### 2. 深挖项目经历：架构、链路、负责部分？

Mini-Drop 的完整链路是：用户描述问题，服务端发现并绑定 Agent、PID、启动时间和命名空间；RAG 提供知识先验，Planner 产生可证伪假设；LATS 用 UCT 选择分支；语义工具经过能力、权限、参数和预算门禁后转成 Task；C++ Agent 执行采集器并上传 Artifact；Analyzer 转换为结构化数据；Evidence Gate 判断支持、反证或不可观测；系统继续搜索或生成带引用报告。

个人职责建议表述为：负责 AI 诊断方案调研、假设搜索与推理编排、知识和 Skill 路线、证据约束以及全链路联调验收。不要把所有 C++ Agent、Go API 和采集器都说成自己独立完成。

### 3. 检索是否基于向量？完整 RAG 需要哪些组件？

AGI-Saber 使用向量检索：子块通过豆包 Embedding 生成 2048 维向量写入 Milvus，查询也生成同维向量；同时使用 Elasticsearch 的 BM25，并可按需加入图谱关系。完整 RAG 包括文档加载、解析清洗、分块、Embedding、索引、查询改写、召回、融合、Rerank、上下文组装、生成、引用、拒答和评测。

Mini-Drop 不使用向量数据库。知识 RAG 是本地 BM25；Skill 召回使用运行时硬门禁，再融合 BM25、本地 512 维哈希 n-gram 特征和结构化上下文。

### 4. 文档上传与分块如何实现？

AGI-Saber 上传 PDF 后会尝试多种文本解析器；提取不到有效文本就返回需要 OCR，文字过少会标记需要 OCR，项目本身没有实现 OCR。清洗只处理换行、空字符、跨行连字符和多余空白，不能说已经智能删除所有页眉页脚。

之后保存文档和版本，再做 Small-to-Big：默认子块约 200 字符、重叠 50；父块取子块四倍和 600 中较大者，因此默认约 800 字符、重叠 100。对子块生成向量和关键词索引，查询命中子块后回填父块。PostgreSQL/SQLite 保存权威记录，Milvus、Elasticsearch 和 Neo4j 是可重建检索投影。

### 5. 向量检索单次耗时多少？是否引入 Rerank，怎样评估收益？

不要编一个毫秒数。可以答：“当前没有一组经过固定环境、多次重复后可公开的单阶段 P95，因此我不会给未经验证的数字。正确做法是在 Trace 中拆分查询 Embedding、Milvus 检索、BM25、融合、Rerank 和生成耗时，预热后统计 P50/P95/P99。”

项目引入远程 Rerank，当前复用聊天模型打相关性分；失败时熔断到本地重排或保留 RRF 顺序。收益要在同一标注集上比较“无 Rerank”和“有 Rerank”的 Recall@K、MRR、nDCG、答案正确率、P95 和成本，只有质量增益覆盖额外延迟和费用才保留。

### 6. 如何评估召回内容与问题匹配度？

离线数据至少包含问题、标准证据块、标准答案和无答案标签。检索层看 Recall@K、Precision@K、MRR 和 nDCG；如果存在多个等价证据，要用证据集合标注，不强制唯一块。生成层看答案正确性、忠实度、引用支撑率和拒答准确率。

线上不能直接看到标准答案，因此观察无结果率、用户追问改写率、引用点击、人工纠错、失败率和延迟，并把高价值失败样本脱敏后回流离线集。模型判分只能辅助，关键案例需要规则或人工复核。

### 7. 如何定义 Agent？核心模块有哪些？

Agent 是能够围绕目标，根据上下文和环境反馈选择下一步动作、调用工具并维护多步状态的系统。一次 Prompt 返回文本不够构成完整 Agent。

核心模块包括模型、上下文、路由或规划、工具、执行循环、记忆、状态持久化、权限与 Guardrail、人工审批、Trace、评测和停止条件。工作流路径由代码预定义，Agent 则允许模型动态选择动作，两者可以组合。

### 8. 是否了解 ReAct？项目里怎么用？

ReAct 把 Reasoning 与 Acting 交替进行：模型根据当前信息选择动作，工具返回 Observation，模型再决定下一步，直到满足停止条件。它的价值是让推理不断接收外部事实，而不是一次性猜完整答案。

AGI-Saber 的通用执行链属于 ReAct-style：模型选择注册工具、读取结果并继续，但复杂任务还会先形成任务图，不是无边界自由循环。Mini-Drop 中 LangChain 负责模型和语义工具循环，LATS 负责多个根因假设之间的树搜索；两者职责不同。

### 9. Agent 循环多少步能收敛？达到最大步数仍失败怎么办？

步数不是越多越好，应该按任务风险、工具成本和成功标准配置最大迭代、工具次数、Token 和时间预算。每一步都要判断目标是否完成、是否有新信息、是否重复动作以及是否需要人工输入。

Mini-Drop 实时诊断最多四个产品轮次，搜索默认最多六次迭代并受最多十二次工具调用等更严格预算约束。达到上限仍未形成充分 Evidence 时，返回“证据不足”和已完成步骤，而不是编造根因；可保存 Checkpoint，允许人工补充后继续。

### 10. Agent 接入哪些工具？接口与权限怎么治理？

Mini-Drop 接入系统指标、`perf`、py-spy、Go pprof、JVM Profile、eBPF 等受控采集能力。模型只看语义工具名和结构化参数，服务端映射为固定 TaskKind；再检查目标 binding、Agent capability、运行时、参数 Schema、风险等级、权限、预算和审批，最终由 C++ Agent 执行白名单 Collector。

AGI-Saber 的工具通过注册表暴露，文件和命令工具受沙箱、路径、超时和资源限制。通用原则是最小权限、凭证不进入 Prompt、写操作显式审批、调用幂等、结果审计、不同用户目录隔离。

### 11. 如何“约定并约束”模型做正确的工具调用？

第一层用清晰的工具名称、说明和 JSON Schema，让模型知道何时调用和参数含义；第二层在提示中声明可用工具、停止条件和禁止事项；第三层在程序中重新校验工具名、字段类型、范围、枚举和目标权限；第四层只对可重试的格式错误允许有限修复，仍失败则拒绝或走确定性回退。

提示词只能提高概率，不能成为安全边界。真正的权限、目标绑定和副作用控制必须由模型之外的代码强制执行。

### 12. 推流是否使用 SSE？为什么选择 SSE？

项目使用 SSE 将节点开始、工具调用、进度、错误和最终结果从服务端持续推送到浏览器。这个场景主要是服务端单向推送，SSE 基于普通 HTTP，浏览器原生支持、实现简单，并具备断线重连语义，比 WebSocket 更贴合需求。

需要注意事件 ID、心跳、重连后的去重和状态补偿；SSE 不是可靠消息队列，最终状态仍应从数据库重新读取。客户端向服务端提交取消或人工干预，继续使用普通 HTTP 请求。

### 13. 编排里是否有 Plan 阶段？Plan-Execute 如何实现？

有。AGI-Saber 的 Planner 输出任务节点和依赖，TaskGraph 负责校验无环、保存依赖和节点状态，GraphRuntime 按拓扑层执行，同层任务可并行，并处理超时、重试、取消和快照。Retry 是同一节点重新执行；Replan 是基于已完成结果修改尚未执行的后续计划。

Mini-Drop 的 Planner 生成可证伪假设和允许工具，LATS 再选择下一分支；领域服务负责真正的工具、Evidence 和持久化。计划不是权限，所有执行仍需通过服务端门禁。

### 14. SSE、WebSocket、HTTP 的差异与取舍？

普通 HTTP 适合一次请求一次响应，例如创建任务、查询结果和提交审批。SSE 是服务端到客户端的单向长连接，适合日志、Token 和任务进度流，使用简单且能复用 HTTP 基础设施。WebSocket 是全双工连接，适合高频双向交互、游戏、协同编辑和实时控制，但连接管理、心跳和扩容更复杂。

Agent 对话通常是“HTTP 提交指令 + SSE 接收过程”；只有需要持续高频双向控制时才考虑 WebSocket。

### 15. 为什么限制每个用户只能上传一个文件？

如果当前产品确实有这个限制，应说明它是 MVP 的产品和一致性约束，不是技术上只能处理一个文件。单文件可以先保证解析、版本、删除、索引重建和引用定位完整，避免批量上传时出现部分成功、重复文档、跨文档权限和多索引补偿问题。

扩展到多文件时，要引入批次 ID、单文件独立状态、幂等、配额、去重、失败重试和索引补偿，并允许部分成功和重新构建。不要把临时限制包装成系统优势。

### 16. 图像识别怎么做？为什么不用多模态大模型？

当前 AGI-Saber 没有真正完成图片理解：PDF 提取不到有效文本时会返回“需要 OCR”。如果只需要识别扫描文字，传统 OCR 更便宜、延迟低、结果稳定、便于定位页码和字符置信度；多模态模型适合理解复杂版面、表格、图表和图片语义，但成本和结果不确定性更高。

合理路线是先用 OCR 做文字和版面提取，对低置信度页面或复杂图表再调用多模态模型，并保留页码、区域坐标和原图引用。面试时不要说当前已经支持完整多模态入库。

### 17. 项目用到哪些大语言模型？选型原因是什么？

参考第一部分第 7 题。补充一句：生成模型和 Embedding 模型目标不同，不能互相替代；Rerank 最好单独评测 Cross-Encoder，但当前 AGI-Saber 复用聊天模型，属于成本优先的实现，尚未证明是最优方案。

### 18. Go 并发与其他语言并发模型有什么关键差异？

Go 使用 goroutine、channel 和运行时调度器。goroutine 初始栈小，可由运行时在少量 OS 线程上调度；channel 适合通过通信协调状态，`context` 负责超时和取消。相比 Java/C++ 直接使用线程，创建和调度成本通常更低；相比 Python `asyncio`，Go 可以更自然地同时表达阻塞式代码和并发任务。

但 goroutine 不是自动安全：共享变量仍会发生数据竞争，channel 也可能死锁或泄漏。工程上要使用有界 Worker Pool、`context`、WaitGroup、互斥锁、Race Detector，并避免无界创建 goroutine。

## 三、字节类 Agent 开发问题

### 1. 项目端到端流程、关键实现和架构取舍？

使用第二部分第 2 题的 Mini-Drop 主链。取舍重点补三句：知识 RAG 和 Skill 使用本地轻量检索，因为规模小且需要可复现；模型不直接执行 Shell，因为权限和目标不可控；实时环境使用有预算的 LATS，而不冒充可以回滚环境的完整树搜索。

### 2. 项目有哪些缺陷？重来会如何改进？

Mini-Drop 的不足是架构较复杂，真实故障评测成本高，当前五百组主要是受控回放；实时 LATS 不能复位现场；模型短期 Checkpoint 降级到内存时可能无法跨 Worker 重启恢复。重来会先建立更小的证据型主链和真实评测集，再逐步加入 Skill 与 LATS，并更早建设统一事件协议和故障注入环境。

AGI-Saber 的不足是真实 RAG 标注集不足，父子块大小、RRF 权重、图检索、Rerank 和无答案阈值缺少充分消融；多数据库增加了一致性成本。重来会先使用 PostgreSQL 加一种检索引擎完成基线，建立评测后再决定是否增加 Milvus、Neo4j 和复杂 Runtime。

### 3. 模型输出偏离指令时如何处理？

Mini-Drop 中模型曾可能返回非法 JSON、以英文长段落代替规定字段，或选择不兼容工具。处理方式不是继续相信模型，而是用 Pydantic/JSON Schema 校验、规范化枚举、验证 binding 和 allowed tool；格式错误只允许有限修复，仍失败就生成可审计的中文确定性规划兜底。工具最终还会经过服务端能力和权限门禁。

这个案例说明提示词只是软约束。正确方案是“提示 + Schema + 程序校验 + 权限门禁 + fallback + 回归测试”，并在 Trace 中区分模型结果和确定性兜底。

### 4. 关注的前沿 Agent，举例并解释核心机制

可以讲 OpenClaw：它是 local-first 的个人 Agent 基础设施，核心是一个长期运行的 Gateway 连接 Telegram、Slack、WebChat 等消息入口，维护会话、工作区、记忆、模型和工具，并把不同渠道或账号通过 binding 路由到隔离 Agent。Skill 使用 `SKILL.md` 描述工具使用方法，加载时按环境和 allowlist 过滤；工具权限、沙箱和执行环境由 Gateway 控制。

它值得关注的不是“又一个聊天壳”，而是本地控制面、跨渠道会话、持久记忆、Skill 和多 Agent 路由的组合。边界是它面向可信操作者，不应直接当作对抗性多租户安全边界。依据可参考 OpenClaw 的[官方架构](https://docs.openclaw.ai/architecture)、[Skill 文档](https://github.com/openclaw/openclaw/blob/main/docs/tools/skills.md)和[安全边界](https://github.com/openclaw/openclaw/security)。

### 5. 如何理解 Claude Code “memory 三层”设计？

面试中的“三层”通常可以解释为：用户级 `~/.claude/CLAUDE.md` 保存跨项目个人偏好；项目级 `./CLAUDE.md` 保存团队共享的架构、命令和规范；本地项目级 `CLAUDE.local.md` 保存不提交仓库的个人环境信息。分层的目的是让作用域、共享范围和优先级明确，避免所有规则塞进一个全局文件。

按当前官方实现，还要补充：Claude Code 现在包含组织托管策略、用户、项目、本地和路径范围规则，并有 Claude 自动维护的 Auto Memory，因此严格说不是固定三层。`CLAUDE.md` 是用户编写的行为指导，不是强制安全策略；真正禁止工具应使用权限设置或 Hook。参考 [Claude Code Memory 官方文档](https://code.claude.com/docs/zh-CN/memory)。

### 6. 是否使用过 AI 编程工具？团队内如何使用和规避风险？

可以真实回答使用 Codex、Claude Code 或 Cursor 辅助阅读代码、生成初稿、补测试、重构和定位问题，但最终变更由人负责。团队使用时不给模型生产密钥和无边界权限；敏感仓库遵守公司数据策略；每次改动走代码审查、静态检查、单元和集成测试；重要设计和生成来源可追踪。

主要风险包括错误代码、依赖或许可证问题、提示注入、秘密泄漏、大范围误改和测试“自证正确”。因此要求最小权限、限定目录、先看 diff、禁止自动推生产、测试与实现分开审查，并让关键业务逻辑由人工理解后合并。

### 7. Cursor 上下文过长是否导致性能下降？如何监控与缓解？

会出现成本、延迟和质量问题，但不要把所有变慢都归因于上下文。上下文过长会增加输入 Token 和首 Token 延迟，相关信息被噪声淹没后还可能降低指令遵循；工具输出、重复文件和旧对话也会污染决策。

监控输入 Token、首 Token 时间、总耗时、缓存命中、截断或压缩次数、工具失败和任务成功率。缓解方法是新任务开启新会话、只加载相关文件、用检索按需取上下文、压缩旧过程但保留约束和未完成状态、限制工具输出、把稳定规则放入项目指令或 Skill，并对长短上下文做同题评测。

## 四、百度类 Agent 与单测问题

### 1. 项目核心目标、技术栈、线上指标和瓶颈？

建议用 Mini-Drop 回答：目标是把跨机器手工采集和经验式性能诊断变成安全、可复现、可审计的证据闭环。技术栈包括 React、Go、C++、Python、PostgreSQL、MinIO、LangChain/LangGraph，以及 `perf`、eBPF、py-spy、pprof、JVM 工具。

指标必须按证据口径说：五百组同题同两次工具预算回放中，Skill 将证据型根因 Top-1 从 41.20% 提升到 68.00%，提升 26.80 个百分点；136 组改善、2 组退化，187 组更早到达关键采集器。这是受控回放，不是五百次公网故障。系统瓶颈主要在真实采集成本、外部模型延迟、Analyzer 队列和跨服务状态一致性。

### 2. 提示词模板如何设计与迭代？怎样判断真的变好？

模板要明确角色、输入可信级别、任务目标、输出 Schema、允许工具、禁止事项、停止条件和失败处理；把动态事实作为结构化字段注入，不把用户文本直接提升成系统指令。模板和模型版本都要记录。

迭代依赖固定评测集：比较任务成功率、Schema 合法率、工具选择正确率、越权率、证据和引用正确率、平均工具次数、P95 延迟和成本。先离线配对评测，再小流量 Shadow 或 A/B；同时看改善和退化案例。不能用“输出看起来更顺”作为唯一标准。

### 3. 单 Agent 与多 Agent 如何取舍？

默认选择单 Agent 加清晰工具，因为上下文共享简单、延迟低、成本和调试难度小。任务存在可并行且相对独立的子问题、需要不同权限或专长、单个上下文容易污染时，再考虑多 Agent。

多 Agent 的成本包括更多模型调用、信息同步、重复工作、冲突合并和更复杂评测。是否采用应通过任务成功率、延迟、Token 和失败率对照证明，而不是因为架构听起来先进。固定流程也可能直接使用工作流，不必包装成多个 Agent。

### 4. 如何确定任务拆分粒度与停止条件？

一个节点应有清晰输入、单一可验证输出、明确副作用和失败边界。过粗会难以重试、并行和定位；过细会增加模型调用、状态传递和调度成本。通常按工具调用、外部依赖、可并行性和可独立验收点拆分。

停止条件包括目标已满足、验证门通过、没有新信息、连续重复动作、预算耗尽、无可执行工具、风险需要人工确认。Mini-Drop 最终是否停止由 Evidence、反证检查、轮次和工具预算决定，不由模型自己宣布完成。

### 5. 上下文如何组织，避免信息污染和无关信息占窗口？

先按可信度和用途分层：系统约束、用户目标、当前任务状态、必要工具说明、相关知识、最近观察。外部文档和工具结果标记来源，不允许其中的指令覆盖系统规则。只检索当前步骤所需内容，做去重、排序和 Token 预算裁剪。

长工具输出先结构化或摘要，原文通过引用按需读取；已经完成的过程压缩成状态，不重复塞全部历史；敏感信息和其他用户数据在进入上下文前过滤。还要记录实际上下文快照，便于复现污染问题。

### 6. 窗口不够时优先保留什么？依据是什么？

优先级通常是：安全和权限约束、用户当前目标、不可变业务事实、未完成任务状态、最近工具观察、与当前步骤最相关的知识、普通对话和表达性内容。不能为了省 Token 删除 Evidence、幂等状态或审批结果。

依据是删除后对任务正确性和安全性的影响，而不是简单按时间顺序。稳定规则可以放项目指令，详细资料按需检索，历史过程压缩成结构化摘要，原始大文件保留引用。

### 7. AST、调用图等结构化信息如何融入模型输入或检索？

先用解析器生成符号、定义引用、调用边、文件路径和行号，再按函数或类建立结构化索引。查询时先根据符号和关键词找到入口，再沿调用图扩展一到两跳，将相关代码片段、签名、调用关系和测试一起送入模型。

AST 适合精确定位语法和符号，调用图适合跨函数影响分析，向量检索适合自然语言语义。三者可以混合，但要限制图扩展深度并保留文件和行号，避免把整个仓库塞进上下文。

### 8. 哪些代码不适合自动生成单测？如何识别与过滤？

不适合直接自动生成的包括强依赖硬件或生产环境、随机和时间敏感、第三方副作用、并发竞态、UI 视觉、遗留代码无稳定契约、以及涉及真实支付、删除和权限的代码。生成器很容易 Mock 掉真正风险，得到“能通过但没有价值”的测试。

识别时检查外部依赖、全局状态、不可控时间、非确定性、危险副作用和缺失需求。对这些代码可以只生成测试骨架，要求人工补 Oracle；或者先重构依赖注入，再生成单元测试，剩余行为放到集成、契约或端到端环境验证。

### 9. 覆盖率高但质量差，怎样定义好单测？

好单测应验证可观察行为和关键不变量，失败时能指出问题；同时覆盖正常、边界、异常和状态迁移，具备确定性、隔离性和较快速度。它不应该复制实现细节，也不能只有“函数被调用过”这种弱断言。

质量控制包括需求到用例映射、Mutation Testing、分支和条件覆盖、缺陷发现率、失败可诊断性、Flaky 率和评审。覆盖率只是发现未测试代码的信号，不是质量目标。

### 10. Mock 的边界：什么时候必须 Mock，什么时候会掩盖问题？

单元测试中，对网络、时间、随机数、第三方 API、昂贵模型和危险副作用应 Mock，以保证快速、稳定和可控异常。自己的核心业务逻辑、数据映射、SQL 契约和序列化边界不应全部 Mock，否则只证明 Mock 按预期工作。

正确做法是少量单元测试使用 Mock，大量关键边界使用 Fake 或本地真实依赖，再用契约和集成测试验证 DB、RPC 和对象存储。Mock 必须遵循真实接口 Schema，并通过契约测试防止接口演进后失真。

### 11. 依赖 DB/RPC 的函数，如何让生成单测稳定运行？

先通过依赖注入把 Repository、RPC Client、Clock 和 ID Generator 从业务逻辑中抽离。单元测试使用内存 Fake 或受控 Stub，固定时间、随机数和 ID，覆盖成功、超时、重试、重复请求和异常映射。

数据库语义、事务、唯一约束和 SQL 不能只靠 Mock，应使用临时数据库或容器做集成测试；RPC 使用生成的接口和契约测试验证请求响应兼容性。每个测试独立准备和清理数据，禁止依赖执行顺序，异步逻辑使用可等待事件而不是固定 `sleep`。

### 12. 除覆盖率外，怎样评估单元测试？

可以看分支和条件覆盖、Mutation Score、历史缺陷复现率、关键需求覆盖率、断言强度、测试耗时、Flaky 率、失败定位时间和维护成本。Mutation Testing 特别有价值：如果故意修改条件或返回值后测试仍然通过，说明断言可能没有验证真正行为。

最终目标不是测试数量，而是改坏关键逻辑时测试能稳定失败，正确重构时测试不会因实现细节变化而大面积损坏。

## 五、面试前最小背诵清单

1. 两个项目各准备 90 秒介绍：问题、链路、个人职责、难点、指标、边界。
2. 熟练画出 AGI-Saber 的“解析 → 父子块 → 多路召回 → RRF → Rerank → 父块 → 引用”。
3. 熟练画出 Mini-Drop 的“Scope → 假设 → LATS → Tool → Task → Artifact → Evidence → Report”。
4. 能解释为什么模型不能直接执行 Shell，为什么 Artifact 不等于 Evidence。
5. 能解释 Skill A/B 的正确率口径，以及为什么 68% 不能外推成线上准确率。
6. 测试题必须掌握等价类、边界值、状态迁移、接口测试、Mock 边界、P95/P99 和性能压测流程。
7. 不记得精确数字时先讲指标含义和取舍，不要现场编造。

## 六、容易说错的地方

- Mini-Drop 的知识 RAG 是本地 BM25，不是 Milvus；Skill 的 512 维向量是本地哈希特征，不是神经 Embedding。
- AGI-Saber 才使用 Milvus，Embedding 当前是豆包多模态向量模型，实际只传文本，不是 BGE。
- BM25 是关键词排序，不是向量检索；RRF 是排名融合，不是 Rerank 模型。
- AGI-Saber 当前没有完整 OCR，也没有经过充分消融证明 Rerank、图谱和阈值一定提升质量。
- Mini-Drop 的 Skill 是调查先验，不是 Evidence；知识文档也不是本次事故证据。
- LIVE 路径是 `BUDGETED_LATS`；只有可复位的冻结快照路径才能称为 `FULL_LATS`。
- 自动化测试通过只能证明相应代码和契约，不能替代真实模型质量或线上性能结论。
