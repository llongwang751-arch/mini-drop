## 页面负责观察，任务负责继续运行

现在回到任务详情。后台已经有一项 CPU 采集在运行，你打开页面，看见时间线和分析状态。过一会儿你关掉标签页，这项工作应该继续。原因很直接：task、attempt、状态和事件都在服务端持久保存，React 组件只是读它们。页面是否挂载，不能决定目标机器上的采集器是否继续工作。

从一个简单但容易出错的方案开始想：组件发起请求，然后用本地计时器把状态依次改成 RUNNING、UPLOADING、SUCCESS。这样的页面看起来很顺畅，却只是在播放预定动画。一旦采集失败、后台重启或用户从另一个窗口取消，本地状态就与事实分离。Drop 的进度来自真实持久状态，前端只能决定怎样及时、清楚地展示。

本章沿 `web/src/views/TaskDetail.tsx` 往外读三条线：REST 读取当前任务；SSE 提醒缓存刷新；Worker 下载和处理较大的分析制品。最后再回到火焰图，亲手算几组数字。前半段避免把别人的结果写进当前页面，后半段避免把正确的结果解释错，两者都属于前端正确性。

贯穿案例仍是“联系人接口 CPU 升高”，但本地 smoke 的证据是 PROC_CPU 线程计数。页面能画出一棵树，不表示它知道 Python 函数名。读组件时始终带着 kind、unit 和 source，别让漂亮的图形替输入增加它没有提供的信息。

## 先找真实调用者：REST 是账本，SSE 是通知铃

`TaskDetail.tsx` 的第一份 `useQuery` 使用 `queryKey: ["task", id]`，通过 ``api(`/tasks/${id}`)`` 读取详情。请求把查询提供的 `signal` 继续传下去；轮询间隔交给 `pollingInterval`，活动任务正常情况下以五秒为基础间隔刷新，终态不再按同样方式继续轮询。

同一组件的 effect 为非终态任务调用 `subscribeTaskEvents(task.id, ...)`。收到 `task_status` 时，它没有直接把事件 JSON 塞进任务对象，而是执行下面这句实际调用：

```typescript
qc.invalidateQueries({ queryKey: ["task", id] });
```

来源：`web/src/views/TaskDetail.tsx / 订阅任务事件的 effect`。缓存失效会让查询重新读取授权的服务端详情。这样，事件只负责“有变化，去看一眼”，REST 负责“现在究竟是什么”。即使某个中间通知重复或错过，重新读取仍能拿到当前事实，不需要浏览器自己完整重演数据库状态机。

想象通知铃坏了，账本仍在。SSE 断开后，REST 轮询继续工作，用户可能晚几秒看见结果，却不应该看见任务被改成 FAILED。反过来，流连接显示 live 也不保证采集正常，它只证明观察通道当前连通。`connecting、live、polling、paused` 描述连接，collection/analysis 描述任务，界面文案应把这两类状态分开。

## 一次网络 read，可能只有半个汉字

读 `event-stream.ts / EventStreamDecoder` 之前，先看一个教学用事件。下面是协议文本示例，数字是合成游标，不是某项真实任务的序号。事件末尾的空行也是内容的一部分：

```text
id: 9007199254740993
event: task_status
data: {"stage":"采集完成"}

```

网络不会按照这三行整齐送达。第一次 read 可能只到 `event: task_`，第二次从 `status` 接上；UTF-8 的“采”有多个字节，也可能恰好被分到两次 read。若每次 read 都单独 `JSON.parse`，就会把正常网络分块误认为坏数据。若每次都新建 TextDecoder，还可能把一个完整字符拆成替换符号。

实际解码器把 TextDecoder、未完成行、data 列表、事件类型和 pendingId 都保存在实例里。`push` 喂入字节，按流解码后继续积累，遇到换行处理一行，遇到空行才提交事件。CRLF 也可能切成两块，`afterCR` 专门记录这个边界，不能把一个 Windows 风格换行当成两个事件分隔。

这里有个小细节影响恢复：看见 id 行时只是记住候选游标，完整帧结束才提交。如果连接在 data 中间断开，这个半事件应丢弃，不能推进断点。否则重连说“我已经读到这个 ID”，服务端就可能跳过浏览器其实还没处理过的事件。解码器还有整帧字节上限，注释心跳和无用字段也计入，不能只限制 JSON 正文。

## 重连该从哪里开始，为什么要用 BigInt

沿刚才的合成事件继续推演。浏览器完整收到序号 9007199254740993，把它作为字符串保存；下一事件只收到一半，网络就断了。重连请求应携带前一个完整序号的 `Last-Event-ID`。服务端从这个位置之后继续读，尚未完成的事件才有机会重新到达。

为什么不把游标转换成 JavaScript number？因为超过精确整数边界后，不同整数可能变成同一个值。例如 9007199254740992 与 9007199254740993 转换后可能无法区分。ID 不是用来做近似统计的数值，丢一位就可能让任务路由、事件去重或缓存命中指向错误对象。

来源：`web/src/event-stream.ts / subscribeTaskEvents`，实际去重节选如下：

```typescript
if (cursor && BigInt(event.lastEventId) <= BigInt(cursor)) return;
cursor = event.lastEventId;
failures = 0;
options.onEvent(event);
```

字符串负责保存原值，BigInt 负责比较大小，前面还要校验它是不是合法 int64 范围的正整数。相同或更小序号被丢弃，只有有效新事件才刷新回调并清零失败次数。暂时失败使用有上限的指数退避；401 和部分不可恢复错误停止盲目重连。退避解决故障时的连接压力，去重解决恢复时的重复，两者不能互相代替。

## 离开 A 页面后，A 的回调为什么还会回来

现在想一个比断网更隐蔽的问题。你先打开任务 A，A 的请求还在等响应，就立刻切到 B。B 已经显示在屏幕上，此时 A 的旧回调开始执行。若它直接更新一个通用状态，页面可能把 A 的结果盖到 B 上。代码没有抛异常，用户却在研究错的证据。

`subscribeTaskEvents` 为每条连接保存自己的 AbortController，并用 `current(controller)` 检查当前身份：订阅没有被清理、active 仍指向这个控制器、信号也没有取消，回调才有资格继续。effect 清理会设置 disposed、移除事件监听、清除定时器并取消活动连接。A 不只是“被要求停下”，它还失去了继续回写的资格。

为什么已经 abort 还要检查身份？因为取消请求是尽早节省资源，不能让所有已经排队的 Promise 回调凭空消失。网络响应可能刚到，事件循环里已经排好下一步。身份检查负责处理这段时间差，和后端发布时再查 attempt 的思路相似：开始时正确，不代表完成时仍然属于当前对象。

缓存 key 也承担身份职责。完整火焰图 key 包含 task、attempt、artifact ID 和 SHA；不能只写 `flamegraph.json.gz`，因为新一轮采集也会用同一个文件名。任务重试以后，旧成功图仍可作为历史证据，却不能自动变成当前 attempt 的分析结果。读这里的 key，比只看请求 URL 更容易发现跨轮次误复用。

## 标签页隐藏以后，连接和任务各做什么

浏览器后台标签页可能被限速，也可能休眠很久。一直维持 SSE 再密集重连没有太大收益。实现监听 `visibilitychange`，隐藏时清理连接和重连定时器，显示 paused；重新可见时，从已经提交的游标建立新连接。游标跨连接保留，当前控制器身份则会更换。

可以按三个时间点检查：隐藏前最后一个完整事件已经处理；隐藏期间后台任务继续推进；恢复后重连和详情查询重新对齐。最容易漏掉的是“旧连接的 finally 晚到”：它不能清掉新连接的 active 或定时器，所以 finally 也先判断 `active !== controller`。保护不能只放在成功回调，清理路径同样会写共享状态。

短暂离线练习适合验证这一点。在自己的独立本地栈打开已有任务，用浏览器开发者工具临时切换离线，再恢复网络。预期是连接状态变化、详情恢复读取，后台任务不会因为浏览器离线而被标记失败。任务本身若恰好执行失败，要看服务端错误证据，不能仅凭两个现象同时发生就认定断网导致采集失败。

这个练习也有边界：观察浏览器恢复，不等于验证 Agent 断网恢复或 Analyzer 持有租约时崩溃恢复。它们发生在不同进程、不同持久化边界，需要各自的故障证据。前端可以诚实显示“实时连接恢复中”，同时继续展示最后一次成功读到的业务状态和更新时间。

## 大火焰图为何要经过专用 Worker

一份 gzip 文件下载很小，展开后可能很大；树节点很多时，JSON 解析和遍历也会占住主线程。如果把所有工作放进渲染组件，用户可能连“停止加载”都点不了。`profile-loader.ts` 管理专用 profile Worker 的生命周期，`profile.worker.ts` 在后台完成制品授权、受限下载、解压和结构校验。

并不是所有网络请求都被搬进 Worker。`loadAnalysisResult` 在主线程限额读取结果响应，再把 ArrayBuffer 转移给 Worker 解析；`loadFlameArtifact` 则把任务和制品身份交给 Worker，由它重新申请下载授权。区分这两条路径，才不会把注释中的“避免主线程解析大文件”读成“主线程完全不下载任何数据”。

当前压缩制品上限为 16 MiB，展开上限为 32 MiB，总期限 30 秒，错误正文也单独设限。不能先无限展开再检查大小，那时资源已经消耗了。主线程在成功、失败、超时和 signal 取消等路径都会终止专用 Worker，离开页面后不会把它留着慢慢解压。

类型定义也不是网络校验。`validateFlameTree` 继续检查 name、children、安全整数、非负权重、节点数、深度，以及重复或循环引用。它先校验整棵树，再做显示过滤；否则坏分支恰好被隐藏，就可能绕过限制。性能优化的目标是把同样严格的工作放到合适线程，不能为了流畅而少检查输入。

## 申请下载权限，与下载文件是两个请求

页面不能根据 artifact ID 自己拼长期 MinIO 地址。`profile.worker.ts / artifact` 先请求当前任务制品的 download 接口，应用 Cookie 只用于这个同源授权请求；后端此时检查当前用户与任务权限，再发放短期地址。拿到地址后还要校验同源 `/objects/` 路径，并拒绝重定向。

真正请求对象时使用 `credentials: "omit"`，也设置不发送 referrer。应用会话不该跟着对象请求走。短期地址只留在这次下载流程内，不能写进组件长期配置、错误信息或日志。地址过期时允许受控地重新申请一次；无限刷新只会掩盖权限或部署问题。

下载之后核对实际压缩大小与登记大小，展开后的树再做结构校验。这里需要理解权限与输入安全的区别：一份文件可以是你有权读取的，内容仍然损坏或过大；一个格式完全正确的文件，也可能属于你无权看的任务。因此授权、地址检查、体积限制和树校验要分别存在。

撤权时，已经显示在用户屏幕上的信息不会被浏览器自动抹去，这不代表可以继续获取新数据。每次重新申请授权都要受当前权限约束，前端缓存也不能被当成永久访问凭据。阅读制品链路时，尤其要避免把“拿到过一次链接”写成“以后永远可读”。

## 手算 total 和 self，再决定哪块最值得看

下面仍是合成教学数据，不是联系人服务的真实测量。main 的 total=100、self=10；它下面 parse 的 total=90、self=20；parse 下面 decode 的 total=self=70。宽度最大的 main 包含全部后代，直接执行权重最大的却是 decode。total 帮你找路径，self 帮你找直接消耗，不能用同一列回答所有问题。

来源：`web/src/components/flame-analysis.ts / validateFlameTree`，核心关系是：

```typescript
let inclusive = node.self;
for (const child of node.children) inclusive += child.value;
if (inclusive !== node.value) throw new Error("调用树总计与自身权重不一致");
```

在上面的树里，parse 满足 `20+70=90`，main 满足 `10+90=100`。如果有人把 parse 的 total 改成 95，其余不动，校验应拒绝，不能让渲染器按一个不守恒的数值继续画图。显示层不会因为“差一点也看不出来”就自动补齐，因为补在哪里都会改写测量含义。

再看递归：两条 folded 路径 `main;walk;walk 4` 和 `main;walk 6`，外层 walk 的 total=10、self=6，内层 walk 的 total=self=4。切换按函数自身开销聚合后，walk 的 self 合计是 10；不能把两个 total 相加成 14，当作独立观测。Analyzer 的 inclusive TopN 对单条路径中的同名函数去重，火焰树则保留递归层级，读两种展示时要知道各自保留了什么。

## 隐藏、搜索和聚焦，都不能悄悄改证据

“隐藏系统帧”如果只是删掉节点和全部后代，会把真实业务调用也删掉；如果把系统 self 全算给下面的业务函数，又会夸大业务开销。`prepareFlameTree` 删除明确识别的系统框时，把后代提升到上一层，被隐藏框自己的 self 另行记到展示根节点，并返回 hiddenSelf 与 hiddenFrames。

用一个较小的合成例子手算：总根下 main 权重 100，其中系统框 total=30、self=5，下面业务 decode 权重 25，其余路径权重 70。隐藏系统框后，decode 的 25 仍在，系统自身的 5 也仍留在总权重里。假如展示根是外层 all，main 可见子树成为 95，all 的 self 接住 5，整棵展示树仍是 100；这不表示 all 真的是一个耗 CPU 的业务函数。

搜索只是标记符合名字的框，不能把未命中框当成没有执行。点击聚焦则放大一棵子树，当前布局的分母也可能随选中的根变化。前面 decode 在整棵 100 权重树中是 70%，聚焦到 parse 的 90 后是约 77.8%；同样的 70 变宽了，不代表性能恶化。重置应能回到完整输入。

`functionRelations` 从完整树计算调用者与被调用者，而不是只检查当前 SVG 中渲染出的框。大图会按可见深度减少 DOM，当前屏幕上没有某一层，不代表源数据里没有。过滤、聚焦和虚拟渲染都是观察方式，原始树要作为独立证据保留，才有办法复核一处交互究竟改变了什么。

## 同一个热点比例，可以对应完全不同的 P95

再用一组明确合成的请求记录把区别算到底。假设二十个请求里，十九个各耗时 10 毫秒，另一个耗时 1000 毫秒。为便于手算，这里约定使用最近秩百分位：先排序，再取向上取整的 `0.95 × 请求数` 所在项。第二十项是慢请求，第十九项仍是 10 毫秒，所以这份小样本的 P95 为 10 毫秒。

若另一次观察是十八个 10 毫秒、两个 1000 毫秒，同样规则下第十九项变成 1000 毫秒。两个窗口的 Python 栈采样仍可能显示 decode 占 70%，因为慢请求可能在等下游，也可能来自少数输入；CPU 热点比例没有保存每个请求开始和结束的记录，无法反推出这个耗时分布。

这里的数字不是性能基准，最近秩也不是要求项目所有系统都换用这个算法。它帮助你看见 P95 需要另一份数据、样本量与计算约定，小样本的尾部分位还会很不稳定。真实监控若采用直方图或其他分位估计，应该沿它自己的定义核对，不能把两种口径的数字直接相减。

因此做页面文案时，不要把样本占比标成“请求耗时占比”，也不要从两次图宽变化生成“P95 提升”。应显示测量单位，并把业务延迟留给真正的请求指标。需要关联时，继续核对服务身份、采集窗口、负载与请求数量；把两个图放在同一页，只是便于观察，尚未建立二者之间的因果关系。

## 实验：给一种已存在的指标补一句人能看懂的解释

选一个可回滚的本地前端练习：在任务结果区域为 `cpu_ticks` 补一句“线程 CPU 计数增量，不含函数栈”，为 `samples` 显示“采样权重，不等于请求耗时”，未知单位明确显示“单位未知”。先找实际 `summary.unit` 与 `summary.source` 的使用处，再决定文案放哪里，不要为了展示例子伪造线上任务。

写代码前先定四个预期。PROC_CPU 显示线程粒度；导入 folded 明确显示导入来源；未知值保留未知；切换两个任务后文案跟着新任务变化。验证这些输入时使用明确标记为合成或导入的既有 fixture，不能把 `kind` 改成 PYTHON_CPU 就声称获得了函数级测量。

在 `web` 目录可以从下面的相关回归开始，然后运行构建。命令供你执行，本章没有替你运行浏览器断网或后端采集：

```powershell
npm test -- src/event-stream.test.ts src/profile-loader.test.ts src/profile-data.test.ts src/components/flame-analysis.test.ts
npm run build
```

先读测试再改，会更容易知道应该保护什么：拆分 UTF-8 仍能还原完整事件，半帧不推进游标，路由取消会终止 Worker，隐藏系统 self 后总量仍守恒。测试若只断言你新写的字符串存在，抓不住单位取错或旧任务结果回写；至少要覆盖与文案有关的真实输入差异。

最后做一次口头验收。火焰图中 decode 从 70% 降到 50%，接口 P95 是否下降？答案仍是不知道：分母、采样时长、负载和线程活动都可能变化，P95 需要真实请求耗时分布。SSE 断开是否要取消采集？不用，观察失败不等于任务失败。聚焦后框变宽是否变慢？没有，先看当前分母。能把这几件事讲清楚，才算把测量正确地交到了用户手里。
