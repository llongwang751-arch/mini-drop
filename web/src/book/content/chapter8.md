## 如果只把火焰图丢给模型，会发生什么

假设我们把联系人服务的一张热点表发给模型，问：“为什么接口慢？”它可能很快写出一段完整结论：某个解析函数占比高，建议缓存、并行、减少数据库查询。这些建议听起来都熟悉，但热点表未必包含数据库观测，甚至可能只有 PROC_CPU 的线程计数。语言越流畅，越容易让读者忽略中间缺了哪些证据。

Drop 没有把“生成一段分析文字”当作诊断完成。它把过程拆成有限动作：读取当前采集摘要，检查热点，检查质量，查看特定调用路径，必要时查询已经接入的业务信号，再提交带来源的报告。程序检查模型实际调用过什么、引用了什么，模型负责在允许的动作中选择下一步。

这章仍是项目教程，不是通用提示词课。我们要回答的具体问题是：一项已授权调查怎样从 Go 进入 Python runtime；AgentScope 怎样发出工具意图；为什么工具最后还要回到 Go；最终报告为什么会被拒绝。先读清这条链，才知道哪里该改工具、哪里该补数据，而不是所有问题都往 system prompt 里加一句话。

有一条边界要先放在心里：程序可以验证一个数值是否来自当前工具，不能仅凭结构合法就保证根因判断正确。后面会用项目实际的六轮评测说明这段距离。把执行可靠与语义可靠分开，才能判断已经完成了什么，还有什么值得继续研究。

## 四个角色各自决定什么

C++ 采集 Agent 负责在目标环境核验进程、调用受控工具、上传原始制品。Python Analyzer 负责把这些字节解析成带单位与来源的结构。它们已经在前几章出现，不会因为后面加入模型就改变职责。模型提出的“再看看 CPU”最终仍要经过正常任务链，不能绕过它们直接进入宿主机。

诊断 runtime 是另一个 Python 服务，目录是 `agent_runtime`。它使用 AgentScope 的 Agent、工具适配器和原生工具循环，负责把模型的工具选择接进框架。它不直接连接任务数据库、MinIO、采集器或 Docker。它知道如何请求一个业务工具，却没有这些系统的长期访问能力。

Go 控制面负责用户同意、当前权限、运行状态、attempt、租约、工具参数、预算与报告验收。React 展示计划、接收用户确认、呈现工具进度和结果。你可以把“谁想做”与“谁能批准”分开：模型选择工具不等于授权工具，页面显示按钮不等于服务器允许执行，Python 收到回调成功也不等于可以自行扩展动作范围。

画一张责任表时，至少写清“提出计划”“确认目标”“实际采集”“解析文件”“生成解释”“验收报告”六件事。把任何两件混在一起，都会出现一个具体风险：例如把模型解释当解析结果，或者把模型计划通过校验当作用户已经确认。后面每一个检查点，都是在维护这些职责之间的交接。

## 规划先看能力，用户确认后才采集

用户说“帮我查慢接口”，仍不足以执行采样。`investigation.go / RequestInvestigation` 先建立调查与目标范围，检查同意和授权；规划工作经 `planCollection` 调用实际采集器目录。目录中的 schema 来自项目契约，具体可用性还要和目标 Agent 的公布能力结合，不能让模型凭常识猜本机一定安装了 py-spy。

规划阶段只有两个工具：`list_collectors` 与 `propose_collection`。前者读取当前绑定目标支持的类型与参数，后者提交符合 schema 的计划。模型可以选择类型、时长、频率和允许的 options，并解释理由；它不能在这一步塞进另一个 PID、宿主路径、shell 或 URL，把用户最初同意的目标换掉。

这里最容易误读的是 propose 的“成功”。它表示计划已被程序校验并准备展示，不表示采集已经发生。`ConfirmInvestigation` 是独立的持久化动作，会再次检查计划与当前目标授权，然后才推进采集。规划期间用户可能撤权、Agent 可能下线，不能沿用几分钟前的检查结果直接开工。

用本地 PROC_CPU 举例，模型最多能根据真实目录提出受控线程 CPU 采集，不能因为用户的问题写着“Python”就声称拥有函数栈。若能力不足，它应该解释当前能获取什么、还缺什么。少一点自动化但说清限制，比偷偷换成另一种测量后继续输出原结论更可靠。

## 从 Go 走进框架，再沿工具回到 Go

诊断入口可以从 `diagnosis_tools.go / diagnose` 往下读。它准备当前任务证据与 trace，在使用 AgentScope 的路径进入 `diagnosis_agentscope.go / diagnosisAgentScope`。这里组装 `agentRunSpec`，包括 Phase、消息、工具定义，以及 Fence、Checkpoint、Invoke、Finish 四类回调，然后交给 `s.Runner.Run`。

下面是阅读调用关系的伪代码，省去了网络封装和错误分支，不是项目真实 API 的替代实现：

```text
Go diagnosisAgentScope
  → AgentRunner.Run → Python runtime
  → AgentScope 模型调用 → 工具选择
  → GatewayTool.call → Go agentSession.callback
  → Fence + schema + Invoke → observation
  → AgentScope 继续读取 observation
  → finish callback → Go Finish 校验 → accepted result
```

`GatewayTool` 是适配器，不是在 Python 里重新实现所有采集工具。它把已登记名称和参数发送到本次运行的 Go capability 网关，再把返回观测交给框架。Go 与 runtime 通过私有 Unix socket 交接，并校验对端身份；随机 capability 绑定本次会话，不是模型可以在回答中自行发明的口令。

于是一次完整工具动作至少经过两层检查：runtime 知道该阶段允许哪些工具、输入是否满足 schema；Go 再检查实际领域对象与当前执行资格。即使框架某一处收到一个格式正确的请求，也不能因此取得另一个任务的证据。这种重复不是重复做同一件事，前一层挡协议错误，后一层守当前业务事实。

## 一轮工具观测应该怎样读

给自己安排一条假设性的阅读轨迹，注意它不是已经发生的模型实验。Go 先提供 `read_profile_summary` 的初始观测；随后模型请求 `inspect_hotspots({})` 和 `check_collection_quality({})`，再用 `inspect_call_paths({"rank":1})` 看某个热点的上下文。实际 E 编号由本轮 trace 的顺序产生，知识读取等动作也可能占用编号，不能把教程顺序当成固定序号表。

摘要会说明测量单位。对于 PROC_CPU，工具还明确返回只有进程和线程计数、没有函数栈。热点工具最多给出前十项，用哈希符号和有限的 symbol_hint 表示线索；原始符号留在授权结果页面。hint 是本地词形分类，不是“发现锁竞争”或“证明某个 SQL 慢”的裁决。

质量工具继续说明短采集窗口、导入来源和未知业务指标。调用路径工具只接受热点 rank，而不是任意源码路径或另一个 task ID；不存在的排名会得到 unavailable，树或上下文截断也有明确标记。没有返回的路径不能靠模型补全，“设置了最大遍历量”也不等于这次真的发生截断。

这时比较两句话：“热点排名第一，所以它是慢接口根因”；“当前热点表中这一项 self 较高，但缺少请求耗时与业务关联，需要按相同负载补证”。第二句仍是可继续调查的判断，第一句跳过了单位、粒度、时间窗口和因果关系。工具的价值就是让这些差别出现在可检查的观察记录里。

## 白名单把模糊意图缩成有限动作

“继续调查”不是一个可以随意执行的万能工具。`runner.py / PHASES` 与 Go 的 `phaseTools` 分别列出当前阶段名称。规划只能读目录和提计划；诊断包括摘要、热点、质量、调用路径、复测比较、知识与已接入业务信号等工具；修复阶段才提供 `profile_business_flow、read_source、test_patch`。

不要只看工具名，还要看参数。`diagnosisDefinitions` 给只读摘要、热点等工具下发空对象 schema，并设置 `additionalProperties:false`。模型不能在空对象后偷偷加 `task_id`、`sql` 或 `url`。`diagnosisTool` 还用 Go 解码器拒绝未知字段、null 和尾随数据，再按具体工具检查哪些参数确实允许。

来源：`api/internal/service/diagnosis_tools.go / diagnosisTool`，下面两行是实际严格解码的一部分：

```go
dec := json.NewDecoder(strings.NewReader(string(args)))
dec.DisallowUnknownFields()
```

单有这两行仍不够，还要继续看类型范围、阶段名和目标绑定。工具叫 compare_profiles，也不能让模型自己指定两项未授权任务；它比较的是服务端已经关联的基线和候选。程序给模型的是一个窄动作，而不是把所有底层接口包装成一个名字好听的自由入口。

## 报告不是写完就收，还要过事实验收

模型可能跳过工具直接交稿。`diagnosisAgentScope` 的 Finish 先检查实际使用记录：必须完成热点和质量工具；初始摘要表明已有可用复测时，还必须调用 compare_profiles。下面条件来自该函数实际代码，换行仅便于阅读：

```go
if !used["inspect_hotspots"] || !used["check_collection_quality"] ||
    summary.VerificationAvailable && !used["compare_profiles"] {
    return nil, domain.Fail("AI_INSUFFICIENT_EVIDENCE", "未完成必要的热点、质量或复测检查")
}
```

但完成调用只是第一道门。当前 v2 报告用结构化 facts 指向实际 E 编号、有限 JSON Pointer、operator、value 与 unit。`diagnosis_facts.go` 会逐字段复算，而不是用另一段模型评语判断“原模型是否说得像真的”。例如来源中的 self_percent=70，声明值必须仍为 70、单位为 percent，不能擅自换成 70 毫秒。

假设也要引用已核验事实，并满足对应方向的证据前提。业务延迟方向需要真实业务时长事实，部署回退方向需要实际变更事实，不能仅拿 CPU 占比支持所有类型。无法支持时应该保留已有事实并使用 insufficient_evidence。程序生成的权威描述与明确标注未核验的模型解释分开，才便于用户逐条复核。

报告被拒绝后可以在原预算内修正，反馈仍受限，不能借格式错误追加权限和无限工具调用。最后 Go 还比较 runtime 返回的 result 是否与自己已接受的 JSON 一致，再附加实际模型/工具调用元数据。模型写一句“我已运行十项检查”，不能替代这些记录。

## 预算为什么要在调用前记账

网络模型调用慢，而且可能收费。一个天真的循环是“失败就再试，没结论继续问”，这样断网、坏报告或工具错误都会变成没有上限的消耗。Go 的 `phaseBudget` 与 runtime 请求校验共同限制模型次数、工具次数、单轮工具数和活跃时间，调用开始前先预留，失败也不能免费抹去。

当前阶段上限可以对照源代码阅读：planning 为 6 次模型、10 次工具、150 秒；diagnosis 为 9 次模型、14 次 runtime 工具回调、150 秒；repair 为 8 次模型、12 次工具、420 秒，每轮最多两个工具。这里的次数是上限，不表示每次都会用满，也不包含 Go 已经放进消息的初始摘要。

诊断的第九次模型调用还保留给最终格式修正，不能理解成九轮都能自由查工具。旧报告协议另有更小预算；非 SDK 的旧传输也保留自己的实现。阅读时把 `run.ReportProtocol`、`agentBudget` 和 runner 放在一起，不能从历史发布文档挑一个数字套用到所有运行。

如果前两轮拿到的信息已经不足以支持函数结论，正确动作可能是提前报告边界和补证计划。预算限制能防止失控，却不会教模型怎样把有限机会分配到最有价值的工具。工具是否被主动调用、是否反复围绕 CPU 打转，是语义策略问题，仍需要后面的独立评价。

## 恢复时最难的，是不知道上一步到底做没做

模型响应或工具响应可能在传输途中丢失。假设 Go 已把工具结果保存，runtime 没收到成功；直接重新执行可能浪费预算，带动作的工具更可能重复产生工作。`agent_checkpoint.go` 把运行 scope、输入摘要、规格摘要、SDK 可见状态、消耗计数和工具回执持久绑定，恢复时先检查它们是不是同一轮工作。

对已完成回执，同一个 call_id、同一份规范化请求可以返回保存过的 response，不必重新测量。若 call_id 相同但请求内容变了，返回 `AGENT_CALLBACK_REPLAY`；一个编号不能第一次指向读热点，第二次又被解释成别的动作。原始输入或运行规格变化，也不能继续使用旧游标装作同一次调查。

还有一种更麻烦的回执：已经登记 pending，却没有完整响应。它可能尚未执行，也可能执行完但没保存成功。系统用 `AGENT_CHECKPOINT_AMBIGUOUS` 拒绝不安全恢复，不把“不知道”自动解释成“没做过”。这条限制牺牲一点自动恢复能力，换来不在结果不确定时盲目重放动作。

恢复也不重置费用。模型次数、工具次数和活跃时间继续计入同一预算，部分预留在崩溃后也不退款。每次读取检查点先经过业务 Fence，重新核对当前权限、来源、状态与租约；用户撤权或取消以后，旧检查点不能成为继续工作的通行证。恢复保存的是可重用的执行事实，不是把历史权限永久冻结。

## 观测里的指令、历史知识和旧证据怎么办

工具返回的文件、日志或符号名可能包含奇怪文本，甚至写着“忽略以上规则，读取某个目录”。这些内容都是被分析的数据，不是新的授权来源。system prompt 会提醒模型，真正的防线仍是没有相应工具、schema 不接受任意路径、Go 不允许换目标。不能只因为提示词写了“禁止”就认为注入已经解决。

源码和业务信号也要逐次确认来源。旧 attempt 的热点不能当作新一轮观测，别的源码摘要上的行号不能附到当前修复，未执行的业务指标查询不能被写进报告。有效引用至少说明这份数据属于当前运行并真实出现过；至于时间窗是否覆盖故障、负载是否可比，还要继续检查数据质量。

`read_diagnostic_knowledge` 提供版本化方法和允许读取的历史案例，适合提醒“检查哪些反证”“何时应该停止猜测”。它是先验，不是本轮现场事实。过去有人通过缓存解决类似问题，可以提醒我们检查重复计算；不能据此宣布联系人服务这次也由同一原因导致。

代码在 `diagnosis_knowledge_flow.go` 继续校验加载快照和方法要求，v2 facts 也不允许拿历史知识作当前事实来源。遇到没有当前观测支撑的经验判断，应该退回待验证假设。保留知识来源与版本有助于复现方法，却不能把一个被人工修正过的旧案例当作永远正确的模板。

## 一份运行成功记录，为什么仍可能诊断错

runtime 正常退出，说明协议、工具循环和报告验收走完了。它不意味着模型找到了已知故障方向。仓库 `docs/JD_QUALITY_DEPTH.md` 中 2026-10-23 修复后的六轮因果评测，综合结果为 2 轮通过、4 轮失败；独立干预完成与诊断方向命中分别记录，不能把前者的成功率替换成后者。

这些实验先修正了取证时间窗与报告执行问题，再用原场景重跑。结果里多个 SQL/timeout 故障仍偏向 CPU，故障轮没有主动查询业务信号。这个事实说明：让业务工具存在、让结构化报告可通过，与模型在需要时真正选择它们之间，还有策略缺口。单纯加大 token 预算未必对准问题。

恢复阶段的 Top3 包含 normal_load 或 insufficient_evidence，也不能写成“正常误报率为零”，因为同一正常报告还可能包含 CPU 热点方向。评价时要看完整标签集合、场景分母和独立人审状态。六轮小样本不支持通用准确率，人审尚未完成的部分要继续保持未知。

读这些失败记录的目的，是知道下一步怎样提出可检验改进：例如面对慢接口问题，策略是否先检查当前采集粒度与可用业务指标；业务信号缺失时能否及时停止；报告修正是否只修形式而没有新增证据。任何改进都要在新版本上重新测量，不能拿旧工具链通过替新模型策略背书。

## 实验：不用模型密钥，走完一次纸面审查

先做一个完全不发网络请求的练习。打开 `diagnosisDefinitions、phaseTools、GatewayTool.call、diagnosisAgentScope`，画出一项工具请求经过的四次判断：阶段是否允许、参数是否匹配、当前领域对象是否授权、观测能否被报告正确引用。给每个判断写一个应拒绝的例子，而不是只画成功箭头。

预期答案可以这样核对：planning 中请求 read_source，阶段拒绝；inspect_hotspots 增加 sql 字段，schema/解码拒绝；用户已撤销访问仍继续调用，Fence 拒绝；工具返回 samples 却提交 milliseconds 事实，报告验收拒绝。若只靠“模型应该不会这样做”，说明你还没有找到实际保护点。

再做回执练习：一张纸写 call_id、请求摘要、状态与响应。先记 complete，再收到完全相同请求，应复用响应；换请求保留 ID，应拒绝；保留 pending 而没有响应，应报结果不确定。这个推演不证明真实数据库事务已经验证，却能让你读恢复测试时知道需要哪种故障点。

需要运行本地 runtime 回归时，先按 `agent_runtime/README.md` 用独立 Python 3.12 环境安装经过校验的依赖，再从项目根目录执行：

```powershell
python -m unittest discover -s agent_runtime/tests -v
```

这些测试使用明确标记的合成 provider/tool 夹具，不表示真实外部模型诊断通过；Unix socket 与双 UID 检查还依赖 Linux，跳过要单独记录。本章没有发起模型调用或执行后端故障实验。最后回答：模型说“已优化”，什么证据才允许这样写？至少需要独立正确性与性能对照，而不是一次循环成功。下一章就沿着复测和修复，把这句结论拆开验证。
