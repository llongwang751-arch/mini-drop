## 先说清这一章到底新增什么

假设你已经跑通 mini-drop，也能解释它的受控进程 CPU 计数，现在想增加一个带明确来源的新结果版本。最容易的做法是在 React 下拉框加一个名字，再让 Analyzer 认一个字符串；结果可能是页面能提交、Agent 却不认识，或者树能画、单位却悄悄换了。这一章要从契约开始，把这种跨服务变化拆成可以逐项验收的改动。

前置条件是完成 mini 的 C++→Go→Python→React 链，理解任务与 attempt，以及第 15 章的权重边界。实际可执行练习是 `tutorials/labs/analysis.py / validate_lesson_contract`，case 名为 contract-evolution。它只验证合成 v1/v2 数据，不启动采集、不修改生产 catalog，也不声称新增 Runner 已经交付。

我们把拟议的教学类型命名为 `LESSON_SELF_CPU_V2`。它不在当前 `contracts/task-kinds.json` 中，以下新增类型示例都必须按“待实现设计”阅读。课程模块确实接受这个名字，是为了有一份能运行的契约实验；这与完整 Drop 已拥有同名采集能力是两回事。

章节结束时，你应交出三份东西：一组正反夹具与版本矩阵，一张跨服务改动表，一个能说明哪些检查实际通过的收据。真正接入生产类型仍要在独立分支实现所有参与方、跑相应构建与回归，再按部署流程交付，不能用本地验证器通过代替整条采集链。

## 用一句话固定测量对象与单位

先写验收定义：“这个教学类型描述受控进程自己的 CPU 计数增量，单位 cpu_ticks，不提供函数栈；没有执行采集的输入必须标明 synthetic 或 import，缺失来源保持 unknown。”这句话决定后续数据字段、图形说明和负例。若团队对它都不能达成一致，先不要讨论字段缩写。

mini 真实实现使用 `source=controlled_self`，并保留 clock_ticks_per_second。Linux 等平台的 CPU 计时与 Windows 的 GetProcessTimes 计数口径不同，具体值也可能因分辨率为零；同样叫 tick，不能跨平台直接相减。课程 contract case 的三十七则是指定的合成权重，不是从你的机器采来的数字。

为什么新版本要明确来源？旧结果若只存一个 weight，下游可能不知道它是用户导入、测试夹具还是受控自采。新增 provenance 能表达身份，但不能追溯性地替旧记录编造身份。兼容读取旧版本时应填 unknown，而不是“为了界面统一”填 controlled_self。

同理，不能看到一个树就默认它是 CPU samples。cpu_ticks、samples、bytes 可以使用相似可视化结构，测量含义不同。契约至少要把 kind、版本、单位、权重与来源组合起来校验；仅检查一个字符串存在，不足以保证新类型仍然回答原来的问题。

## 先读现有真源，再写拟议条目

正式工程的契约入口是 `contracts/task-kinds.json、contracts/drop.proto、SQL migrations` 与 `docs/CONTRACT.md`。任务目录约定 runner、pipeline、格式、文件名、工具要求、参数 schema 与边界；proto 约定 Go 与 Core 的控制消息；SQL 保存状态和身份；公开文档说明 REST 与兼容行为。它们负责不同部分，不能互相替代。

读一个已存在的 PROC_CPU 或 PYTHON_CPU 条目，列出输入到输出的路径：前端怎样获得参数，Go 怎样归一化与授权，C++ 怎样公布能力并执行，Analyzer 怎样选择解析管线，结果怎样带上单位。先找到这些真实入口，才知道拟议类型需要改哪些地方，而不是在全仓库替换一个名字。

下面仅是教学类型设计摘要，不是可直接复制到生产 catalog 的完整条目。缺失的工具、目标与资源策略必须在实现前补齐：

```json
{
  "proposed_kind": "LESSON_SELF_CPU_V2",
  "measurement": "controlled process CPU counter delta",
  "unit": "cpu_ticks",
  "function_stacks": false,
  "wire_versions_to_read": [1, 2],
  "new_output_version": 2
}
```

这里故意使用 proposed_kind 而不是假装已有真实 id。草案是讨论输入，不能让它混进自动加载目录以后被 UI 当成已实现能力。设计文档、已实现类型与目标 Agent 当前可用能力是三层不同事实，只有最后一层通过目标侧探测，才允许用户真正选择执行。

## 把跨语言变化拆成一张接力表

新增类型不能只是“后端支持”。至少有以下参与者，每一行都应写出一个可检查的输入与输出：

| 层              | 要实现的工作                       | 应保留的边界             |
| --------------- | ---------------------------------- | ------------------------ |
| 契约目录        | 参数、格式、单位与工具声明         | 新旧消费者如何识别       |
| React 表单      | 读取 schema、显示能力与单位        | 隐藏按钮不代替授权       |
| Go 服务         | 归一化、校验、资源授权、任务持久化 | 不接任意命令或目标变更   |
| Core 与 Agent   | 协议、能力协商、固定 Runner        | 目标身份、argv 与预算    |
| Python Analyzer | 格式适配、解析与结果元数据         | 有界输入、未知来源不推断 |
| 结果页面        | 展示来源、单位、限制与失败         | 不把新权重翻译成旧指标   |

把每行的完成条件写具体。例如“Analyzer 能处理 v2 合成夹具并拒绝错误单位”是解析证据；“目标 Agent 实际公布并执行新 Runner”是现场能力证据；二者不能用同一个绿色勾概括。跨服务失败常发生在交接处，单模块测试都绿也可能接不起来。

目录变更还可能经过生成、嵌入或测试校验进入各语言包，读当前加载实现再改，不要假设所有服务都会运行时直接读取同一个 JSON。需要重新构建谁、旧镜像保留什么能力，也应写进交付计划。一个文件看起来是“共同真源”，并不意味着部署时没有版本差。

## 参数 schema 不允许用户偷偷变成命令

假设新类型需要 iterations。先规定整数上下限、默认值与是否必填，再决定它在哪个层转换成工具参数。mini 当前创建请求只接受一千到一千万的 iterations，并用固定路径启动固定 C++ 程序；它不接受用户传 collector 路径、shell、任意 argv 或下载 URL。

在正式 Drop 里也保持这种类型化方式。React 按 schema 展示字段，Go 做严格校验与授权，C++ Runner 把已允许的参数组装成 argv。新增一个 options 字段仍要讨论类型、范围、未知字段策略与工具对它的解释，不能因为包在 options 里面就变成无界自由字符串。

负例应覆盖布尔冒充整数、浮点数、负数、超范围、重复 JSON 键、尾随对象以及未知字段。Python 中 True 是 int 的子类，所以课程验证用 `type(value) is int`；JavaScript 的 number 还需检查安全整数。跨语言的“看起来是数字”不是足够精确的协议定义。

路径和目标更不能靠 schema 形式正确就放行。一个合法 PID 仍可能属于别人的进程，一个合法 URL 仍可能指向不应访问的服务。正式实现继续核验用户资源权限、Agent 本地策略与进程身份。参数校验负责格式和范围，授权负责允许操作谁，两层都必须存在。

## v1 与 v2，明确谁读得懂谁

课程定义 v1 有 schema_version、kind、unit、weight；v2 再要求 provenance.source。两版都使用同一个拟议 kind 名，名字里的 V2 不自动充当 wire version，真正的解析分支由 schema_version 决定。这样可以单独讨论“采集类型变了”与“同一种类型的封装升级了”。

新 reader 读 v1 时只补 unknown 来源，不补采样频率、不补目标身份；读 v2 时要求来源为明确枚举。旧 reader 只声明支持版本一，面对版本二应报 UNSUPPORTED_VERSION，而不是忽略新增字段后继续宣布兼容。是否允许忽略字段是版本策略，不是所有 JSON 都天然向后兼容。

| 输出方      | 读取方    | 预期               |
| ----------- | --------- | ------------------ |
| v1 fixture  | 新 reader | 接受，来源 unknown |
| v2 fixture  | 新 reader | 接受，保留显式来源 |
| v2 fixture  | 旧 reader | 明确拒绝版本       |
| v2 错误单位 | 新 reader | UNIT_MISMATCH      |

这个矩阵适合部署前讨论。先发新 writer、让旧 reader 碰运气，是最容易造成局部成功的顺序。通常应先让消费者理解新版本，再逐步启用新输出；仍要根据实际协议与回滚能力决定具体顺序，不能把一句“先后兼容”当成已验证计划。

## 写出两份正例，再写一组必须失败的反例

课程使用的输入如下。legacy 的零是合法计数，不表示有函数栈；current 的三十七明确是 synthetic，不代表控制进程真的测到了该值：

```python
legacy = {
    "schema_version": 1, "kind": "LESSON_SELF_CPU_V2",
    "unit": "cpu_ticks", "weight": 0,
}
current = {
    **legacy, "schema_version": 2, "weight": 37,
    "provenance": {"source": "synthetic"},
}
```

反例每次只改一个字段：把 unit 改成 samples，应该在单位检查失败；把 weight 改成 True，应被拒绝为 INVALID_WEIGHT；增加 command 字段，应得到 INVALID_FIELDS；source 写 guessed，则是 INVALID_PROVENANCE。不要把所有错误塞进一份文件，否则测试只能证明“至少有一处错”，无法说明每个边界是否存在。

还有一个特别重要的兼容负例：用只支持版本一的 reader 读取 current，必须拒绝。若测试只拿新版 reader 跑所有夹具，就没有验证混合部署中的旧消费者。写测试时把读取能力作为显式输入，才能有把握讨论发布顺序与回滚范围。

这些夹具可以来自手写，也可以导入真实工具产物，但身份必须跟着文件保存。测试目录里的真实文件仍是离线导入证据，不是平台本次刚完成的现场采集；SHA 只能帮助确认同一份字节，不能自动证明文件是谁、在哪个目标、何时采来的。

## 验证器为什么检查字段集合

打开 `validate_lesson_contract`。它先确认输入是对象、版本是支持的整数，再根据版本决定允许字段集合，然后验证 kind、unit、weight 与来源。检查顶层 key 的完整集合，能够同时拒绝缺字段和未知字段；不能只对认识的字段逐个取值、把剩下内容静默丢掉。

下面代码从仓库根目录可直接调用课程实现，不连接任何服务：

```python
from tutorials.labs.analysis import validate_lesson_contract

legacy = {
    "schema_version": 1, "kind": "LESSON_SELF_CPU_V2",
    "unit": "cpu_ticks", "weight": 0,
}
new_reader_result = validate_lesson_contract(legacy)
print(new_reader_result["provenance"]["source"])
print(new_reader_result["weight"])
```

预期标准输出两行，先是 `unknown`，再是 `0`。这两个值代表一种诚实的兼容行为：没有的来源不推断，合法的零不填成一。若为了让火焰图看得见而把零改成最小样本，就已经修改了数据，不能再称为相同测量结果。

错误控制可以在临时副本中删除字段集合检查，再给 current 加 command。若回归仍然通过，测试没有保护未知字段；若原本的负例失败，就说明它确实检查了边界。恢复代码后再继续，不要让学生为了让示例“更宽容”而把生产风格的拒绝规则全部拿掉。

## JSON 变成字典之前，还有一次验收

刚才的验证函数接收 dict，但原始输入通常是 JSON 字节。这里还有一个容易漏掉的边界：重复键在普通 json.loads 之后可能只剩最后一个值，验证器已经看不见它曾经出现两次。比如来源同时写 synthetic 与 controlled_self，不能让不同语言各自挑一个解释以后继续运行。

课程模块因此另有 `decode_lesson_json`。它先限制八 KiB，严格解码 UTF-8，用 object_pairs_hook 在建字典时拒绝重复键，并拒绝 NaN 等不属于标准 JSON 的常量。解析完成才调用版本与字段验证。把字节解码、JSON 结构和领域契约分开，错误发生在哪一层就能说清楚。

```python
from tutorials.labs.analysis import decode_lesson_json

try:
    decode_lesson_json(b'{"weight":1,"weight":2}')
except ValueError as error:
    print(error)
```

预期标准输出为 DUPLICATE_KEY。再试不完整 JSON、尾随另一个对象或非法 UTF-8，都不能变成一个看起来可接受的空字典。对于已经进入 Python dict 的数据，重复键信息不可恢复，所以不要把字段校验测试当作字节解码也已覆盖的证据。

这一层不会因为使用 JSON 就自动解决所有输入风险。嵌套、正文大小、字符串长度与数值范围仍要有边界，输出也要限制；课程只处理小型封装，正式 HTTP 与制品解析分别面对自己的字节预算。共享语法方便交接，严格接受规则才真正形成契约。

## 用混合版本时间线检查发布与回滚

先写一个四阶段发布表。开始时 writer 与 reader 都只用 v1；第二阶段先发布能同时读 v1/v2 的 reader，但输出仍为 v1；第三阶段在明确能力范围内启用 v2 writer；最后才考虑收紧旧格式支持。每一步都要检查实际消费者是否已经更新，而不是只看主分支代码已合并。

为什么先更新 reader？因为新字段一旦写进对象或数据库，不会随容器回滚自动消失。如果 v2 已产生，再把 reader 回滚成只懂 v1，旧结果仍能读，新结果可能明确拒绝。可行回滚计划要保留新格式读取能力，或暂停新输出并说明受影响记录怎样处理，不能把解析失败伪装成空报告。

再看 Agent 混合版本。即使 Go 理解新任务，旧 Agent 不具备 Runner，也必须在派发前根据真实能力拒绝；不能把任务先发出去，期待旧程序忽略陌生字段后“尽量做点什么”。字段兼容只说明消息能否解码，执行兼容还要看目标语义、工具与权限。

把故障点加进时间线：新 writer 上线一半、某个 reader 暂时离线、计划生成后用户撤权、分析完成但发布租约已过期。每一项都要问谁重验当前事实，哪些旧数据保留，用户看见什么错误。这样部署计划才和状态机连起来，而不是一张只画服务启动顺序的图。

课程没有实际部署这些版本。你运行的是固定的合成接受矩阵，能够验证 reader 的明确行为；真实混合部署还需独立测试环境和版本镜像。把两者分开记录，既能复用课程的反例，也不会把纸面时间线写成现场验收结果。

## 控制面、采集端和分析端分别改什么

Go 的任务创建先归一化，再进行目录与参数校验，继续检查用户对 Agent 与目标的授权，最后原子建立任务、attempt、事件与派发待办。若新类型需要额外身份或预算，先确定它属于哪个契约层；不能把新字段塞进日志字符串里，再指望 C++ 从文本解析。

C++ 端要有真正的 Runner 分支和能力探测。工具存在与实际可运行是两回事：路径、版本、权限、平台、目标策略都要检查。参数必须经过固定 argv 交接，不拼 shell。目标执行前后仍核对身份，结果上传仍围绕当前 attempt，不能因新增类型就跳过原有安全与恢复边界。

Analyzer 则要登记实际 pipeline 与接受格式，核验 RAW 大小和摘要，在有界环境解析，公开结果保留单位、来源与限制。若只是新来源的 folded，也要讨论它的权重究竟是什么；若是新二进制格式，解码器、压缩预算、错误分类和测试夹具都要单独实现。

最后是页面。创建表单应基于真实能力与 schema，结果区应显示新单位和粒度，失败时能区分采集与分析。一个新下拉选项不等于新能力交付，结果页面能渲染也不等于语义正确。每一层的“已完成”都要配自己的测试或真实执行证据。

## 哪些变化需要迁移，哪些不该重排

新增 catalog 条目未必需要数据库加列；新增持久化语义则可能需要 migration。先检查当前 schema 能否表达新事实，再决定迁移，不要为了让一个 JSON 字段有名字就创建一列，也不要为了省迁移把必须查询和约束的身份混进不受控文本。

若新增 protobuf 字段，使用未占用编号，保留已有编号含义，不能因为想让字段排列整齐而重排。旧 Agent 可能忽略新字段，这不自动表示它能够执行依赖该字段的任务。能力协商要说明哪些版本真正理解新语义，Go 派发时据此拒绝不兼容目标。

数据库迁移也要考虑旧代码仍在运行的阶段。约束收紧前检查旧记录，新增状态前检查所有读取方，避免新代码写入旧服务不理解的值。任务双状态与 attempt 不能因为一个新类型被简化成另一套随意流程，否则恢复与事件一致性会出现只在该类型发生的例外。

写一个具体回滚问题检验计划：如果新 Analyzer 产出 v2，随后回滚到只读 v1 的镜像，已生成的结果怎么办？答案必须落到保留消费者能力、暂停新输出或明确拒绝与重新处理策略，不能写“回滚应该没问题”。数据版本不会随着容器回滚自动倒退。

## 从纯夹具走到真实链路，分三层验收

第一层是本章标准库 case，验证版本矩阵、单位、来源和负例；第二层是各语言实现的构建与针对性回归，验证协议与代码边界；第三层才是在独立本地环境执行真实采集、上传、分析和页面读取。前一层通过是进入下一层的依据，不是跳过下一层的理由。

```powershell
python -m tutorials.labs --case contract-evolution --json
python -m unittest tutorials.labs.test_analysis -v
```

预期 case 中 legacy_normalized 的来源 unknown、weight 为零，current_accepted 的来源 synthetic、weight 为三十七，并明确 production_catalog_changed=false。旧 reader 拒绝新版、错误单位、布尔权重、未知 command、无效来源的检查都应通过；观察的是程序确实拒绝了这些输入，不是报告里手写一串成功文字。

如果学生真正实现拟议类型，接下来 Go 用 gofmt 并跑相关测试，C++ 以 warnings as errors 编译，Python 跑对应 parser/worker 回归，前端构建并验证表单与结果。生命周期、授权、并发或恢复变化还要补相应真实数据库与故障回归，不能用很多纯函数测试替代这些风险。

独立环境里保留 task、attempt、RAW 摘要、结果单位、事件与实际命令，异常时保留失败记录。不要用生产注入故障或删除数据卷完成课堂验收；本地栈与教学 workdir 已经足够开始验证。没有真实执行的 Runner 和平台应列为未验证，不能从代码存在推断能力通过。

## 给评审者一份能逐项核对的交付说明

先写用户会观察到的变化，例如“新版结果显示明确来源，旧结果保持未知，不再默认为现场采集”。再写输入与兼容矩阵，列出涉及的目录、proto、迁移、Runner、Analyzer 与页面。说明顺序围绕最终行为，不需要把所有试错过程写成流水账。

验证部分只列实际执行过的检查，分开合成夹具、导入数据与现场采集，给出版本与环境。若新类型只在课程验证器里存在，直接写“生产 catalog 未改，Runner 尚未实现”；若完成某个平台的真实链路，也不要扩展成其他平台和所有工具都通过。部署与限制变化按仓库约定更新开发日志和交付矩阵。

自测一：页面下拉出现新名字，是否可以交付？不可以，还缺执行和分析链。自测二：新版 reader 读旧记录，为什么不能把来源补成 controlled_self？旧记录没提供这种证据。自测三：给 proto 字段重新编号只是重排吗？不是，它改变线上编码含义。

最后把整章缩成一次具体动作检查：拿到一种真实输入，能指出谁验证参数、谁批准目标、谁采集、谁解释单位、谁发布当前 attempt、谁展示局限。每个箭头都有代码与测试支撑，才是一种新增采集类型；只有一个漂亮名字和一张成功图，还只是一个尚未接完的想法。
