## 10.1 学完以后，先别急着给自己加一排技术标签

如果现在让你介绍 Drop，你可能会列 C++、Go、Python、React、gRPC、PostgreSQL、MinIO、AgentScope。列完还不能证明你理解了项目。更好的检验是给出一个具体错误情景，再指出系统在哪个边界拒绝它，以及什么测试能防止以后改坏。

这一章就做这样一项小工作：给“未知单位不能参与自动比较”补一条回归保护。它比重新写一个管理页面更小，也不需要碰真实采集器。我们会从规则、生产判断、反例、修复和验证范围走一遍，而不是看完代码以后直接宣布学会分布式系统。

先说明练习方式：下面的新测试与故意变异都只用于你自己的学习分支或纸面推演，本章没有替仓库提交比较器改动，也没有执行这些 Go 命令。生产源码当前已经拒绝空单位与 unknown；练习补的是回归证据，再用短暂坏实现验证这条证据是否真的会报警。

已有测试越多，越要问新测试增加了哪一种观察。重复断言同一个正常例子，数量会上涨，风险覆盖却没变化。针对一个明确边界做出能复现、能解释、能撤销的改动，才是这套教程希望你完成的学习成果。

## 10.2 把需求写成一句会失败的话

先写验收句：“即使两侧都写相同的未知单位，系统仍不能把它们当作同口径测量。”为什么特意强调两侧相同？因为最容易写出的错误判断是 `left.unit == right.unit`。空字符串等于空字符串，unknown 也等于 unknown，但两个不知道不等于知道它们可比。

构造最小输入：同一任务类型、同一 Agent、同一参数、两侧各 2000 权重、相同 Top 数据，只改变两侧单位为 `""` 或 `"unknown"`。其他条件尽量满足，让拒绝原因只来自正在研究的规则。不要同时换 PID、改类型、删 Agent，否则测试可能因为无关错误通过。

现有 `TestDiagnosisComparisonDoesNotInventCausality` 已测试不同 PID、samples 对 bytes、样本量不足，以及较大占比变化不冒充因果。我们新增的两个用例填的是“两个单位一样，但它们都未知”的空缺，不是把旧测试复制一份换名字。

纸面预期也写清楚：函数可正常返回业务比较结果，`Comparable=false`，`RootCauseStatus=not_tested`。这里不要求抛出 HTTP 500，因为不可比是一种可解释的领域结果。需求若写成“不能比较”，却没有规定返回什么，测试作者和实现者很容易各理解一套。

## 10.3 顺着源码找到唯一该改的边界

打开 `api/internal/service/diagnosis_verify.go` 的 `compareProfiles`。它先限制输入大小、解码结果与参数，然后检查任务类型、Agent、目标、来源、单位，之后才设置 `Comparable=true` 和计算差异。下面是实际条件中的连续摘录：

```go
p.Source == "import" || q.Source == "import" || out.Unit == "" || out.Unit == "unknown" || out.Unit != y.Summary.Unit
```

请把它逐项翻译。导入数据不进入这条现场自动比较路径；左侧单位缺失或明确 unknown 就拒绝；两侧单位不相同也拒绝。右侧为空、左侧已知会被最后一项挡住；两侧都为空则需要前面的未知判断，不能靠不等式侥幸拦住。

这里不该去改 React 按钮，也不该在模型提示词里加一句“请不要比较未知单位”。所有调用比较器的后端流程都应该得到同一规则，模型也不能拥有绕过它的特权。把正确性放到共享的领域边界，前端再解释结果，职责才不会倒过来。

同样，不要为了这项小练习重构整个 profile 类型，或者顺便改比较门槛。范围越大，失败越难归因。先让一个不变量有清晰证据，后续确需扩大单位体系时再协调契约与调用方；共享字段和真实单位不是各服务可以随意重命名的内部细节。

## 10.4 实验：新增一条能抓住坏实现的测试

下面是建议练习代码，当前仓库没有这个名为 `TestLearningComparisonRejectsUnknownUnits` 的新函数。可在学习分支追加到 `investigation_test.go`；该文件已经导入了 testing、encoding/json 和 domain。不要复制进生产分支后直接宣称门禁已通过，先理解每个输入和断言。

```go
func TestLearningComparisonRejectsUnknownUnits(t *testing.T) {
    aid := "learning-agent"
    task := domain.Task{
        Kind: "PERF_CPU", AgentID: &aid,
        Parameters: json.RawMessage(`{"pid":7,"scope":"process"}`),
    }
    for _, tc := range []struct{ name, unit string }{
        {"missing_unit", ""},
        {"unknown_unit", "unknown"},
    } {
        t.Run(tc.name, func(t *testing.T) {
            raw, err := json.Marshal(map[string]any{
                "total_samples": 2000,
                "summary": map[string]string{"unit": tc.unit},
                "top_functions": []map[string]any{{"name": "learning_hotspot", "self_percent": 50}},
            })
            if err != nil {
                t.Fatal(err)
            }
            got, err := compareProfiles(raw, raw, task, task)
            if err != nil {
                t.Fatal(err)
            }
            if got.Comparable || got.RootCauseStatus != "not_tested" {
                t.Fatalf("unknown unit accepted: comparable=%v root=%q", got.Comparable, got.RootCauseStatus)
            }
        })
    }
}
```

两侧使用同一份 raw 是有意的：排除内容差异，专测未知单位。设置 2000 权重是为了避开“小样本碰巧被降级”的干扰，但测试没有要求 outcome，因为单位未知首先影响比较资格。输入名字带 learning，明确这是合成测试数据，不是某次真实采样函数。

在准备好依赖的本地 `E:\tx-drop\api` 执行下面命令；不需要设置数据库连接。预期输出包含新测试的两个子用例和旧比较回归通过。若代码尚未追加，命令只能运行旧例子，不能把没有匹配到新名称误记为成功。

```powershell
go test ./internal/service -run '^(TestDiagnosisComparisonDoesNotInventCausality|TestLearningComparisonRejectsUnknownUnits)$' -count=1 -v
```

遇到编译错误先修正练习文件的语法与导入；那不是你想验证的业务失败。测试开发也需要分清“测试跑不起来”与“它成功抓到了错误实现”。两者都可能让命令非零，但提供的证据完全不同。

## 10.5 故意改坏一次，看看测试究竟有没有牙齿

只在学习分支，把前面条件中的 `out.Unit == "" || out.Unit == "unknown" ||` 暂时去掉，保留两侧单位不等检查。不要改测试预期，也不要同时修改其他条件。再运行相同命令，两个新子用例应失败，因为未知单位终于被错误地当作 comparable。

这一步叫受控变异：我们知道引入了什么错误，用它检查测试是否会报警。现有正常单位和混合单位用例可能仍通过，正好说明新增负例补上了什么空白。若新测试仍通过，先检查它有没有实际运行，再查输入是否被其他拒绝条件挡住。

随后恢复生产条件，重新跑同一组测试。预期通过，并用 `git diff` 核对最终只剩新增回归，没有遗留故意删除的保护。源码格式使用 gofmt。这个过程的学习成果应包括“原实现通过、变异实现按预期失败、恢复后通过”三份可分辨记录，而不是只留最后一张绿图。

别把这个练习描述成发现并修复了线上 bug：源码原本正确，是你为了验证回归而短暂注入错误。简历或学习日志可以写“为未知测量单位补充负例，并用定向变异检验测试”，不能把自己制造的故障说成既有生产事故。

如果改完以后还想增加空白、大小写等单位规则，先回到契约讨论接受集合。不要让一次局部教学变异变成各处自己 trim、自己猜单位，最终形成三种看似友好的不一致行为。

## 10.6 挑验证范围，依据改动跨过了什么边界

这个练习改的是纯比较规则的回归，不需要一上来构建所有镜像或运行付费模型。先跑指定纯测试，确认练习有效；若实际修改比较器，再运行相关 service 测试和 Go 静态检查。没有新的疑点，不必机械重复一整套大测试来换安全感。

若改的是 HTTP 绑定、认证或 CSRF，纯比较测试就不够，需要真实路由的请求/响应和无副作用断言；若改 SQL 谓词、锁顺序、事务事件，就需要 PostgreSQL；若改 C++ 子进程收尾，则要覆盖进程组、取消和 Linux 资源约束。测试层次服务于失败机制，不是一个人人照抄的固定金字塔。

前端文字或教程布局主要检查渲染、导航、响应式和构建，不能因为页面没动后端就声称重新验收了采集链。反过来，后端纯函数通过，也不能证明移动端能阅读长代码。报告时把改动、风险和验证一一对应，读者才知道哪些结论可以接受。

有价值的测试通常会在某种合理坏实现下失败。若断言只是把刚赋值的字段重新读出来，或用与实现相同的公式复制一遍，很可能只是在证明两段代码同样写错。先想反例、状态不变量和独立预期，再选择工具。

## 10.7 真 PostgreSQL 验证的是锁和事务，不是换个数据库名称

`api/internal/testutil/postgres.go` 从显式 `TEST_DATABASE_URL` 或对应文件读取独立测试连接，为每次测试创建随机 schema，执行真实迁移，结束后清理。未配置时明确 skip，连接失败则 fail，不偷偷回退内存数据库，也不寻找生产连接。

所以 `go test` 退出为零但日志含 skip，不能说数据库竞态通过。项目的协议风险门禁会检查指定场景是否实际执行，跳过、删除或改名都不算完成。生产 DSN 也不能用来凑验收，随机 schema 并不会把错误的连接选择变成合理做法。

读 `TestPostgresExhaustedDispatchCannotOverwriteConcurrentLifecycle` 时，重点不是它创建了多少 fixture，而是 RPC 回调尚未返回时，让另一事务提交 QUEUED、CANCELED 或新 attempt，再模拟响应丢失。它检测的是旧快照不能覆盖新事实，这恰好需要真实事务交错，而不是仅有一个 mock error。

`TestPostgresLifecycleRandomizedProperties` 用固定种子驱动真实 Repository 的操作序列，每一步核对 attempt 单调、授权失效、事件等不变量。出错时保存 seed 和失败前缀，才能重放。随机不等于没有预期，确定性也不等于只测一条正常路线。

这两种测试与纯 `Dispatchable` 测试互相补充：纯测试快速解释规则，真实 PG 检查锁等待和原子提交。它们都不能证明物理断电恢复、多节点容灾或所有隔离级别组合，承诺范围要跟实际执行范围一样大。

## 10.8 导入、mock、真实 Runner、完整 E2E，分别证明什么

明确标记的导入 folded 文件很适合复现解析边界，mock S3 也能稳定制造上传失败。它们不是低价值测试；问题在于把它们写成“真实采集已通过”。如果输入不是本次 Runner 产生的，就应在任务、fixture 和报告里保留 import 或 synthetic 来源。

`scripts/quality/protocol/run-live-chain.sh` 使用真实 C++ PROC_CPU Runner、MinIO 和 Analyzer，验证 RAW 字节、单位与结果提交。这比 mock 更接近实际，但它不覆盖 Go HTTP 建任务、Agent gRPC、浏览器和模型，所以文档明确不把它称为完整平台 E2E。

`scripts/quality/system/lab.py` 才创建独立 Compose 项目，从浏览器真实登录、创建任务，经 Go、mTLS Core/Agent、存储、分析，再把真实 gzip 结果加载回来。浏览器可以限制同源请求，不能用填充假响应来冒充链路成功；独立客户端还会下载制品核对 SHA。

同一条 E2E 选择 PROC_CPU，证明的是这一受控目标与 pipeline。它不自动覆盖 Java heap、BPF 权限或 Python 内存附加。用“全链路”描述调用范围可以，但不要把“全”悄悄扩成所有采集类型、所有平台、所有负载。

学习展示时可以把每条证据后面补一个动词：构造、导入、模拟、实际采集、实际下载、人工审阅。词选准以后，就很难把一份合成文件无意间包装成整机性能结论。

## 10.9 Fuzz 和消毒器擅长抓边界，替不了业务答案

项目的 Go Fuzz 入口包括任务规范化/校验、诊断观测对象与精确数值。Fuzz 能生成你没手写的坏输入，帮助找崩溃、超限和断言失败。它没有穷举所有输入，更不会因为执行几十万次，就知道模型说的根因是否符合真实事故。

发现失败输入要保留原字节、seed 或 corpus、实际退出码和源码版本。固定时长预算也可能遇到预算退出问题；不能因为没有留下反例就自行宣布“没有 bug”。项目将预算与实际执行数分开记录，并保留原失败轮次，不靠多跑几次挑一个绿色覆盖掉。

C++ sanitizer 目标启用 ASan/UBSan 和警告即错误，覆盖 domain、json、catalog、lifecycle、sampling、protocol_properties 六个 CTest。它能发现运行到的内存错误和未定义行为；没有报告并不等于未运行路径也安全。发布镜像与插桩镜像更不能混作同一性能环境。

覆盖率也是线索。协议门禁检查 Cancel、Retry、DispatchOne 的生产语句覆盖，是为了防止已有关键风险回归，不是全仓分支覆盖率，也不是正确率。新增分支应增加对应场景；直接调低阈值让 CI 过关，会让指标失去原本的保护作用。

把这些工具放在正确问题旁边：parser 边界看 Fuzz，指针/整数等运行错误看 sanitizer，授权副作用看真实请求与数据，模型语义看独立评审。工具本身再高级，也不能替你定义什么叫对。

## 10.10 故障测试先写清窗口，再决定怎么注入

“测过恢复”太笼统。Agent 在采样中被杀，与 RAW 已 PUT 但确认未到，是两个不同窗口；Analyzer 还没领任务，与已持 lease 后崩溃，也不是一件事。先列阶段、持久事实和应有结果，再选工具注入故障，才能避免一刀切地重启整套服务。

| 故障窗口                   | 需要观察的不变量                     | 当前应怎样解释证据                     |
| -------------------------- | ------------------------------------ | -------------------------------------- |
| 创建提交前退出             | task/attempt/event/outbox 不出现半套 | 事务回滚验证                           |
| Core 接受后丢回包          | 旧失败处理不覆盖 QUEUED              | 真实 PG 派发竞态用例                   |
| 采集中 Agent 强杀          | 不盲目重采，明确恢复或失败           | 独立整链已包含此受控场景               |
| Analyzer 领取前停止        | COLLECTED/PENDING 可留存并继续       | pending 队列持久性，不是 lease 崩溃    |
| Analyzer 已领 lease 后失联 | 过期接管、旧 owner 不能发布          | 结合租约回归，现场崩溃范围另记         |
| PUT 后确认丢失             | 复用结果，不换测量窗口               | 上传与 Notify 边界，不能只检查对象存在 |
| 数据库短断                 | 会话、历史结果、新采集可恢复         | 单机短断，不是数据库 HA                |

这些是读源码与设计测试的矩阵，不是宣称每个格子都已经执行。当前整链明确验证 Agent 强杀/journal、Analyzer 领取前停止、PostgreSQL 短断；全部原生 probe 的强杀、所有 lease 已领取崩溃窗口仍有未覆盖项。

真正运行故障实验时，只使用工具创建并标记归属的隔离容器和目标。清理也逐个核对标签与不可变身份，不按一个模糊项目名前缀删除未知资源。不要把教材中的时间线直接变成生产 kill 命令，更不能用删除数据卷“修复”恢复失败。

## 10.11 一条通过记录，必须知道它属于哪份代码

昨天的镜像通过，不代表今天工作区改完也通过。测试报告至少绑定源码提交或明确脏工作区状态、实际二进制/镜像 ID、契约/迁移版本、输入摘要、命令、时间、退出码、通过/失败/跳过计数，以及关键限制。只有 tag 字符串，没有不可变镜像身份，容易在重打标签后认错版本。

质量摘要的契约是 `contracts/quality-run.schema.json`。发布器只投影白名单数据、检查计数与状态，使用原子发布保存不可变记录，相同 ID 不同字节不能覆盖。API 只读挂载这些文件，不提供“点按钮运行任意测试”的 HTTP 执行入口。

SHA 帮助确认摘要、收据或制品的字节一致，不证明独立人审身份，也不是签名。人审指标尚未评审就保留 null，不能填零，更不能把结构匹配率换名叫根因准确率。一次模型 API 调用成功与一次解释正确，在记录里应分成两个指标。

重跑也保留历史。假如第一个前端 CI job 因依赖下载超时取消，后来单独重跑成功，应写“跨 attempt 完成”，不能回头描述成首次全绿。三十分钟持续窗口如果对应修复前 API，就不能挂到新 API 上；新版本短整链通过，也不能借用旧时长。

学习分支的小收据可以很简单：一个文本文件写三次练习结果与最终 diff，注明使用的合成输入。没有执行的检查写“未运行”，没有环境的项目写“跳过/待验收”。少几项漂亮数字，往往比一张无法追到代码的全绿截图更有说服力。

## 10.12 交付一项你能独立解释的学习成果

现在把练习整理成四段：规则是什么；原测试漏了哪种反例；新增回归怎样在定向坏实现下失败；恢复保护以后跑了哪些检查、还有什么没跑。附上最终测试 diff 与版本绑定记录。读者应能照着复现，不需要相信你说“我看懂了”。

如果想再深入一层，下一个小任务可从已有边界选择：为晚到消息补一个状态组合，为坏 profile 保留权重写一个性质测试，或解释 SSE 断线后怎样按事件序列续读。每次只选一个能独立验收的问题，顺着实际调用链做；不必为了显得高级，先把项目拆成更多服务。

介绍工程时也应保留现实尺度。当前文档记录部署在四核八 GB 单机，多日长稳、最大容量、多节点/ARM 和全部 Runner 开销仍有验收边界。用了多语言与网络协议，说明存在跨进程协作，不自动证明已经承受海量流量或拥有容灾能力。

AI 部分同样如此：修复后的独立六轮因果评测综合为 2/6，十二次诊断执行成功没有变成十二次准确定位。可以诚实说实现了受控工具、证据校验、复测和隔离补丁，不能说已经可靠自动处理任意生产事故。已知失败是下一轮研究材料，不是需要藏起来的污点。

最后回到“这个项目是不是 CRUD”。数据库仍然在增删改查，真正值得学的是那些 UPDATE 之前必须成立的条件：用户仍有权限、轮次仍是当前、租约仍有效、输入仍是同一份、结果仍满足契约。你能为其中一个条件给出反例、源码和有效回归，就已经开始做实际的工程工作了。
