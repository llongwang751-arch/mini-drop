## 21.1 把“看起来更快”拆成四个可以否决的问题

这一章先不让模型评价自己。我们建立四道独立检查：改动是否修复预先定义的问题，未涉及的行为是否保持，输出类型和值是否符合契约，对照数据是否稳定且达到接受门槛。任何一道失败，都不能因为一张漂亮比值表而宣布采纳。

实现入口是 `tutorials/labs/diagnosis.py` 的 `paired_gate` 与 `controlled_comparison_case`。运行 `python -m tutorials.labs --case controlled-comparison --json`，你会看到功能红绿断言、错误输出拒绝、类型变坏拒绝、sham 漂移拒绝、无改进拒绝等真实执行结果。

先强调实验材料：六组成本数字是人工指定的合成整数，不是 CPU、纳秒或请求延迟。代码没有调用计时器、profiler 或外部程序。我们用这些数值练习接受逻辑，绝不能拿 47/40 写成“本机实测提升百分之十七点五”；它只是一道已知输入的算术结果。

毕业项目里会另有 C++ 实测自身受控计算，但那条链的 cpu_ticks 也不能替这份配对实验补真实性。不同材料各证明各的事。先把“代码确实计算了结果”和“数据确实来自真实测量”分开，才有能力审查真实优化报告。

## 21.2 先冻结答案，再写候选实现

用一个小需求做载体：输入姓名字符串列表，输出去掉两侧空白并进行 casefold 的新列表。冻结输入 `[' ALICE ', 'bob']`，预期 `['alice','bob']`。旧实现只 casefold，不去空白，因此第一个元素错误。新实现补 strip，这个行为差异与需求直接对应。

```python
# 来自教学实验的实际函数定义，不是性能测试。
baseline = lambda rows: [row.casefold() for row in rows]
candidate = lambda rows: [row.strip().casefold() for row in rows]
defect_input = [" ALICE ", "bob"]
expected = ["alice", "bob"]
```

正确答案不能从 candidate 的返回值反推。若写 `expected=candidate(input)`，候选函数无论怎么错都能“符合自己”。这里的 oracle 来自先写下的需求，baseline 应失败、candidate 应通过；测试的裁决权不在被测试对象手里。

同样要说清需求边界：这个小函数没有中文姓名规则、地区化排序、空值容错或数据库写入。casefold 也不等于所有语言环境下的身份规范化。不要顺手把例子包装成通用用户身份清洗器，否则原本能判断的问题又变成没有定义答案的大问题。

练习时先在纸上写两个新输入及预期：一项全空白和一项本来没有空白。是否保留空字符串、是否保持输入顺序要先决定，再写测试。遇到歧义时补契约，而不是让候选实现的当前行为自动成为产品规则。

## 21.3 红绿回归检验缺陷，冻结样例检验没有顺手改坏

controlled_comparison_case 直接计算 baseline 和 candidate 在同一缺陷输入上的返回，要求旧版不等于 expected、新版等于 expected。这是具体的红绿证据，没有让调用者传一个 functional_ok=true 冒充测试成功。

但是缺陷修好不等于其他行为没坏。实验另外使用已经规范的 `['alice','bob']`，要求两版相同，示范冻结未受影响样例。你可以继续增加顺序、重复元素、空列表和不修改输入的断言；每一项都要对应已经声明的行为，而不是随便凑数量。

一个关键区分是，缺陷输入本来就应该让两版输出不同，所以不能要求所有输入前后 hash 一致。对于允许改变的错误行为，用独立正确答案；对于应该保持的行为，用冻结回归和对照。若把这两种检查混在一起，要么合法修复永远不能通过，要么所有变化都被当成修复放行。

这也解释真实通用 Python harness 为什么先要求同一新增测试在 baseline 断言失败、candidate 通过，再运行原 build/test 和输出契约。旧版导入失败或测试被 skip 不算复现缺陷，测试错误与业务断言失败有不同含义。

纸面负例：候选把全部姓名直接返回 `['alice','bob']`，会蒙过当前一个样例。新增含第三个姓名的冻结例子就能揭穿它。不要为了追求“每行都覆盖”忽略输出泛化，测试应尝试区分正确算法与几种合理坏实现。

## 21.4 值相同也可能违约：类型、可变性与对象归属

如果候选返回 tuple，打印出来和 list 很像，元素也一样，但调用方依赖 append 就会失败。paired_gate 明确要求 expected_output 与 candidate_output 都是 list，内部元素都是字符串，再比较具体值。类型不是一个为了舒服可以随意变化的展示细节。

```python
# 教学门禁中的输出契约，布尔短路使错误类型直接失败。
contract = (
    type(expected_output) is list
    and type(candidate_output) is list
    and all(type(value) is str for value in expected_output + candidate_output)
    and expected_output == candidate_output
)
```

这里没有声称完整处理任意嵌套 Python 对象，它只服务这项小需求。生产契约若允许别的返回类型，应该重新定义；不能拿教学 gate 随便验证一个 DataFrame 或数据库游标，再因为不匹配就说业务实现错了。

可变性还比类型多一层：缓存同一 list 实例，每次返回的值当时都对，但第一个调用者修改它以后，第二个调用者看到污染。教学新函数用列表推导创建新对象，学习扩展可主动修改一次返回值再调用，检查另一份结果未被影响。

真实通用测量器保留 output_type 和 mutable_output_isolated 检查，就是防止候选用共享可变缓存换表面性能。候选不能为了通过基准把 list 改 tuple，或在测试结束后偷偷恢复类型。输出 hash 相同只代表某种编码字节相同，不能独自证明所有 Python 调用契约都保持。

## 21.5 六组配对材料从哪里来，必须写在表旁边

教学 gate 接收 pairs 和 sham 各六组，每组两个一到十亿之间的正整数。排除 bool、零、负数和浮点，是为了让除法、门槛与输入范围有明确含义。下面是实验实际使用的数据，每一项都是人为指定的成本单位。

```python
# 固定合成成本，不含真实计时，也不应写成 nanoseconds。
pairs = [(120,100), (119,100), (118,100),
         (117,100), (116,100), (115,100)]
sham = [(100,100)] * 6
```

左边作为 baseline，右边作为 candidate。每组先算自己的比值，保持配对关系；不要把六个左值与右值打散、挑最好一边，也不要只报告中位数却删掉最差一组。原始配对数据是别人核算与发现噪声的材料，不是结果确定后可以整理掉的草稿。

真实实验中，配对需要匹配输入 seed、构建、目标、负载和采集条件，还要记录先后顺序。教学 pairs 没有这些执行来源，所以即使公式与生产 harness 类似，也只能称固定数据的门禁验证。这一点必须随着结果一起展示，不能藏到另一个页面角落。

你可以改变第六组为很差的值，观察五组改善与中位数怎样共同决定接受。不要先看结果，再决定哪些组“似乎有噪声”删掉。排除规则需要事先定义并保留原因，否则实验会变成从许多结果中挑自己最满意的一份。

## 21.6 用 Fraction 保留精确边界，别让格式化替你做决定

paired_gate 使用 `Fraction(left,right)` 得到有理数，再对六个比值取 median。当前数据中间两项是一点一八和一点一七，中位数为 47/40。收据保持这个精确分数，展示层如需小数可以另做格式化，但接受判断先使用原值。

```python
output.append(Fraction(pair[0], pair[1]))
improved = sum(ratio > Fraction(105,100) for ratio in ratios)
accepted = contract and stable and median(ratios) >= Fraction(11,10) and improved >= 5
```

为什么要专测边界？109999/100000 约为一点零九九九九，显示保留两位可能都是一点一零，但它并没有达到一点一零门槛。回归 `test_threshold_is_not_rounded_across_acceptance_boundary` 要求这个输入拒绝，而 110000/100000 恰好达到时允许。

还要分清严格与非严格：至少一点一零用大于等于；超过一点零五用严格大于。若你把两个操作符写反，门槛边缘会有不同结果。这种差异应该由测试固定，不能让图表四舍五入后看起来差不多就算了。

中位数也不是万能统计量。它减少极端值对中心的影响，但不告诉你方差、样本独立性和分布。当前门禁使用它作为预设工程规则，不是自动置信区间；后续如果引入统计推断，必须另写假设、估计方法和适用条件。

还有一类错误是提前取整每组比值，再求中位数。它与先求精确中位数、最后展示小数不是同一个计算。请保留输入到最终判定的类型流：整数对、Fraction 比值、Fraction 中心、布尔门禁、可选展示字符串。把格式化放在最后，前端字号和小数位变化就不会悄悄改变接受结果。

可追加一个排序检查：六组原始配对的排列次序变化，计算结果应保持；但把左右两侧交换，所有比值会取倒数，不能还得到相同结论。这个正负性质能检验你的实现是否真的使用了方向，而不是只取两数较大者除较小者，把变慢也算成“改善”。

## 21.7 sham：让“没改任何东西”也接受同样的审视

sham 负控把完全相同的 baseline 当作两侧，理想情况下比值靠近一。如果原版对原版都稳定显示一点三，候选的一点一八就很难解释成改动收益。实验将 sham 中位数限定在九成到一点一倍之间，漂移超限便否决接受。

controlled_comparison_case 用六组 130/100 构造噪声负例。pairs 再漂亮、输出再正确，noisy 的 accepted 仍为 false，sham_stable 为 false。这个测试验证负控确实能否决结果，而不是把负控信息写在旁边、最终照常给绿灯。

这里的 sham 是固定数据模型，不是真的观察到机器噪声。真实测量需要运行同一冻结 baseline，使用同组输入并记录环境。直接把 sham 填成六个一会让门禁永远通过，和人为指定“环境稳定”没有区别。

当前教学 gate 只检查 sham 中心漂移，不检查所有组离散程度。中位数接近一却两头极端跳动的材料仍可能通过，因此不能声称它是完整噪声检测器。学习扩展可以增加预先定义的离散约束，先写能抓住高波动但中心正常的负例，再实施规则。

不要因为增加一个负控就删除其他条件。sham 稳定没有证明候选输出正确，输出正确也没有证明测量稳定。独立否决条件的意义，正是让不同错误没有机会借另一项好结果蒙混过去。

## 21.8 工程接受门槛如何组合，拒绝原因也应该能复查

当前接受规则是四项同时成立：输出契约满足，sham 稳定，成本比中位数至少一点一零，六组至少五组严格超过一点零五。实验返回这几个子结果，让读者能分清是输出坏、环境漂移还是没有足够改善，不只得到一个 accepted 布尔值。

另外构造 pairs 全为 100/100。输出完全正确，sham 也稳定，门禁仍拒绝，因为没有观测到改进。不要把“运行没错”当成“优化有效”，也不要因为候选代码看上去聪明就放宽事先写好的门槛。

反过来，功能修复可能很有价值，但性能没有改善。这时可以单独接受正确性修复，前提是产品目标允许、变更描述如实说明；不能为了把同一修复归为性能成果，挑换统计口径。本教学 gate 的 accepted 专指这套合成比较条件，不代表所有工程变更都必须达到同一个倍率。

同样，门槛不是通用行业标准。真实 Saber preset 使用特定的六组规则；通用 Python 项目从管理员 manifest 读取门槛与负控范围。不同项目的容许开销、噪声与收益目标可能不同，不能把某个一成规则无条件套到请求延迟、内存和吞吐。

练习答案应列出一个二维反例：输出正确但无性能变化，性能比值漂亮但输出错误。两者的处理理由不同。如果你的报告只能写“失败”，没有说明失败在哪一条可检查条件，下一位维护者很难决定要修代码还是修实验。

## 21.9 重复、置信与因果，不是三个程度不同的绿色图标

重复测量回答“这个现象能不能在相近条件下再出现”。统计置信回答“在明确采样假设下，估计的不确定程度多大”。因果问题则问“改变这个机制，是否造成了结果变化”。它们有关联，但不能把执行六次自动解释成同时解决了三件事。

固定数据门禁没有随机采样，因此没有频率学意义的置信区间。真实六组配对也不能无条件当作六个独立同分布样本：进程缓存、温度、相邻负载会让它们相关。不要给一个没有定义分布的结果旁边随手加“置信百分之九十五”。

若以后真的估计区间，需要保留每组值、配对关系、预定统计方法、处理离群和重复尝试的规则，并说明样本量限制。区间再窄也不排除共同偏差：两侧都测错单位或选错目标，可能稳定得到同一个错误答案。

教学结果刻意保留 `root_cause_status=not_tested`。通过成本门槛只说明给定数据满足规则，不能反推 normalize 的 strip 改动确实减少 CPU，因为我们根本没有计时。这个字段的克制是程序约束，不是依赖作者记得在结尾加免责声明。

请把实验收据中的 source 和 unit 也一起检查。若你写可视化，把 synthetic_cost_units 显示成 milliseconds，就制造了新的错误事实。前端不参与测量，也有责任保持单位与未知信息，而不是为了图看起来专业帮它补一个熟悉标签。

## 21.10 要讨论因果，至少明确改了什么与什么没变

真正的受控改动需要一份可证伪假设。例如“重复归一化在特定长查询上消耗 CPU，缓存一个有界纯结果会降低这部分成本”。随后固定输入、输出契约、构建和测量环境，只改变登记模块中的对应实现，并保留撤销改动后现象是否回归的观察。

若一次同时增加缓存、换数据库、降请求量、改限流，很难将改善归给某一机制。随机化或交替 A/B 可以减少部分时间偏差，sham 可以暴露一些漂移，撤销与洗脱可以检查可逆性，但仍需结合业务信号与真实负载。工具不会自动替你消除所有混杂因素。

本章 normalizer 练习是功能修复，配对成本是另外指定的合成材料。两者放在同一个门禁里，是为了学“功能与性能都应独立核查”的结构，绝不构成这个函数的因果性能实证。请在自己的学习报告里保持这两个来源分开，避免顺着故事就把它们连成真实测量。

如果做真实实验，补丁 SHA、原版 SHA、镜像 ID、输入 seed、A/B 顺序、CPU 与墙钟、输出 hash 和限制都需要保存。只给一个比值，别人无法判断分母是什么、是每组比值中位数还是两个总量相除，也无法发现某组功能已经失败。

现场根因还更难：被测业务可能同时受到上下游和资源竞争影响。一个组件基准改善不等于生产请求 P95 改善。若问题是 SQL 等待，CPU 火焰图高占比可能只描述剩下的活动部分，不能凭图形热度宣告原因已经找到。

## 21.11 对照真实修复链，程序怎样限制候选的自由度

真实 `api/internal/service/code_repair.go` 要求先 profile_business_flow，再 read_source，最后 test_patch，且限制实际测试次数。源码片段与补丁都绑定原 SHA 和登记项目；模型不能指定任意宿主命令或镜像，也不能改原测试、权限与测量 harness 来为自己创造通过条件。

`ops/code_executor.py` 对路径、文件摘要、唯一上下文、重叠补丁和 AST 做校验，再创建隔离 candidate。容器无网络、UID 一零零零一、capabilities 清空、只读根目录、有限资源；取消核对本 job 的标签、镜像与不可变容器 ID，不能按相似名字删除别人的工作。

真实 `integrations/generic-python/harness/run_job.py` 在同一新增 unittest 上检查 baseline 断言失败与 candidate 通过，然后运行原检查、比较值与类型及可变输出隔离。六组基准交替 baseline→candidate 和 candidate→baseline，另跑冻结 baseline sham，输出实际测量回执。

```text
登记源码/镜像 → 原 profile 与行号 → 读同 SHA 源码
             → 隔离补丁 → 红绿与原回归 → 输出契约
             → 交替配对与 sham → 有界结果/patch bundle
```

这条图是阅读实际调用职责，不是本章已经发起的运行。旧 CRM/Saber preset 与通用协议的验收细节不同，历史记录不能倒填新规则。项目真实产物也只作用于隔离快照，production_deployed=false；测试接受与原仓库合并、发布生产分别是后续动作。

## 21.12 实验：让四种坏候选分别被正确拒绝

先运行完整 controlled-comparison，再在学习分支一次只变异一处。候选去掉 strip，应在独立答案检查失败；返回 tuple，应在输出契约失败；把 sham 改成六组 130/100，应在稳定性检查失败；把 pairs 改成六组 100/100，应在改善门槛失败。

这四个失败都不需要网络或 Docker，适合先建立确定性理解。它们也不代表真实环境的四次性能测试，只是检验给定输入能否击中指定规则。测试名和报告要写 synthetic，不要把这些数字编进真实运行历史。

```powershell
python -m unittest tutorials.labs.test_diagnosis.TeachingDiagnosisTests.test_output_contract_and_sham_can_each_veto_good_ratios -v
python -m unittest tutorials.labs.test_diagnosis.TeachingDiagnosisTests.test_threshold_is_not_rounded_across_acceptance_boundary -v
```

接着扩展一个“中位数很好，但只有四组超过一点零五”的负例，验证五组条件确实参与决定。构造时先在纸上核算，别给出一个同时中位数也失败的材料，否则删掉五组判断测试仍可能通过，证明力不够。

一个可用思路是让两组等于一点零五，其余四组足够高，使排序中间两项仍超过一点一零。精确边界与整数配对要一起写清。完成后暂时去掉 improved>=5，确认新增测试失败，再恢复实现，这样你才知道测试不是被别的条件代劳。

## 21.13 交付结论时，给数据、判断和未知各自留位置

这章最小交付包含：冻结需求与独立正确答案、红绿和未受影响回归、原始六组材料、sham、输出契约、门槛及负例、最终结果来源说明。读者应能自行计算 47/40，也能看出这不是任何机器的测速。

学习报告可以写“实现固定合成数据的精确配对接受器，并用错误输出、类型变化、漂移负控和边界值证明其拒绝行为”。不能写“优化代码提升一点一七五倍”。如果随后真的运行 profile，也要另起收据，绑定本次源码、输入与环境，不覆盖这份教学结果。

真实项目的效果同样看范围：组件基准曾有改善，也有 BOLT 未观察收益的记录；独立六轮因果评测修复后综合二比六，流程执行成功不等于语义正确。没有人类独立审阅的指标保持未知，不能根据一份结构完整报告反算准确率。

下一章把前面的工作装成可以检查的毕业作品：一条四语言最小实链、十二个有负例的机制实验、你自己的单项改动与一份有版本的证据包。目标是让另一个人从空终端走到相同可解释结果，而不是收集更多听起来高级的组件名字。
