## 故障实验先写“不允许发生什么”

现在你有一条能运行的最小链路。下一步不是随机关几个进程，看它能不能重新亮绿，而是先写出要保护的不变量：同一创建意图不增加第二项工作；旧轮次不能发布到新轮次；失去租约的执行不能提交；状态和对应事件要一起出现。

这些句子都指向一个具体反例，因此能设计可重复的实验。如果目标只是“重启后正常”，你可能永远没有撞到最危险的窗口；如果目标是“RAW 已生成但成功提交尚未完成时重启”，就知道该安排怎样的顺序、检查哪些记录。

本章使用两类材料。Mini Drop 的 Go 测试验证真实文件 journal 与本地状态入口；`tutorials.labs` 的这些 case 使用临时 SQLite 真实事务和人工指定的交错顺序，接收端去重等环节则是受控模型。它们不调用真实采集、不连接生产，也不代表 PostgreSQL、网络或模型服务已经验收。把层次分清，实验才有可解释的结论。

课程命令从仓库根目录执行，Python 3.11+ 即可。四个重点 case 都可独立运行，不需要 Docker、凭据或语言模型密钥。它们是手工构造的教学输入，不是导入的现场 profile，更不能作为业务性能数据引用。

## 先把执行链切成可以指定的窗口

回顾最小任务：创建 journal、送入内存队列、提交 RUNNING、运行 collector、保存 RAW、运行 analyzer、核验结果、提交终态。把每一个“然后”都想成可能中断的位置，才不会把一次连续成功误当全部可靠性。

| 中断前最后的持久事实 | 可能已经发生的副作用         | 合理恢复方向                         |
| -------------------- | ---------------------------- | ------------------------------------ |
| QUEUED               | 尚未允许工具执行             | 重排同一工作                         |
| RUNNING              | 工具可能没开始，也可能已完成 | 明确中断，不能盲目补采               |
| RUNNING 且有 RAW     | 真实计量已完成               | 保留原始文件，仍不能凭存在发布成功   |
| RUNNING 且有结果     | 分析可能已完成但未接纳       | 核对执行资格与完整性，再讨论恢复策略 |
| SUCCESS              | 当前轮结果已经发布           | 重启后保留终态，不重新执行           |

本参考对 RUNNING 统一选择明确失败，是有意收紧恢复保证。正式 Agent 有更细的 journal、helper token、上传回执，才能恢复其中某些阶段。更细状态需要更多持久事实支持，不能只改一个 if 就获得安全重放。

先用自己的话补一列“我需要看到哪些证据”。例如 RAW存在还不够，要知道所属轮次和字节摘要；结果存在还要知道它绑定哪份输入。每一列都能对应回源码，而不是凭文件修改时间猜执行历史。

## lifecycle-outbox：提交任务与发送通知之间

运行第一项机制实验：

```sh
python -m tutorials.labs --case lifecycle-outbox --json
```

它帮助理解任务已经持久保存、通知尚未可靠送达的窗口。观察教学轨迹中哪一步代表持久事实，哪一步只是发送尝试，再看恢复如何继续处理同一身份。你要检查的是不丢单与允许重放的关系，而不是计算“网络只发送了一次”。

Mini Drop 的 journal QUEUED 加启动恢复，覆盖了单进程内存队列丢失的情形。正式 `api/internal/repository/postgres.go:CreateTask` 同事务写 task、attempt、event、Outbox；后台 `DispatchOne` 再投递。它们都先保存工作，但后者还面对独立 Core、网络 ACK 和多个 dispatcher。

纸面推演最关键的一步是：接收方已接受、响应丢失，发送方看到超时。若直接用新身份再发，就可能制造新的执行。正确思路是保留消息身份、接收端幂等，并在推进失败前重读当前事实。

实验通过只能说明这个教学模型里的断言成立。再读正式派发恢复测试时，要找真实事务的竞争窗口和连接要求。只有模型没有网络，就不能用它证明真实 RPC 超时后的 PostgreSQL 锁顺序没有问题。

## attempt-fence：让旧取消消息失去写入资格

第二项命令是：

```sh
python -m tutorials.labs --case attempt-fence --json
```

这个 CLI 实验的实际顺序是：先取消轮次一，再创建轮次二，随后重放轮次一的 CANCEL。JSON 的 observations 显示 protected_status 为 CREATED；去掉轮次条件的坏更新则使 broken_status 变成 CANCELED。它演示旧取消误伤新执行，不发送旧成功结果。

另一种旧消息由 Mini Drop 的 Go 测试单独覆盖：`TestOldAttemptCannotPublishAfterRetry` 把轮次二推进 RUNNING，再提交轮次一的 finish。`finish` 在 mutex 内核对 ID、attempt 和 RUNNING，拒绝旧结果。让新轮也处于 RUNNING，才能避免状态检查掩盖缺失的 attempt 条件；去掉轮次判断时，负例应真正失败。

正式系统还需要在 Server 结果入口、取消、派发与分析发布分别守住身份。只在页面按钮处检查一次远远不够，因为旧网络消息不经过当前页面。只检查 task_id 也不够，因为多个 attempt 共享同一业务任务。

记录实验时不要只写“加了栅栏”。写清栅栏条件、检查发生在哪个最终写入边界、失败后保留谁的状态。这样以后新增一种异步回调，你才能判断它是否也需要携带同样的执行资格。

## 重试请求自己也需要幂等

用户说“再跑一次”，会建立新 attempt；浏览器没收到这次 retry 的响应，又传一次，是同一个 retry 意图的网络重放。两种动作看起来都叫重试，状态机必须把它们分开。

在 Mini Drop 中，终态才允许新增轮次，retry 使用新键，事件追加 TASK_RETRIED，结果和当前错误清空，旧目录保留。相同 retry 键重放不再增加轮次；把创建键换个路径使用，则与原动作冲突。这样每个意图都有可解释的归属。

请在工作台做一次正常 retry，再用终端重发同一请求。检查 attempt 是否只增加一次，事件里是否没有多出另一次 TASK_RETRIED。若只看当前状态，短任务可能已经完成，容易漏掉重复执行；历史事件和目录更适合检查副作用。

这也提示一种测试设计：同时检查返回值、当前轮次、队列数量和事件数量。只断言 HTTP 200，错误实现也可能通过；只断言 task 数量不变，重复采同一 task 仍可能漏掉。选观察点要对应你要保护的副作用。

## lease-handover：轮次相同，执行者也会过期

第三项命令：

```sh
python -m tutorials.labs --case lease-handover --json
```

这里的教学顺序与 attempt 不同。任务仍是同一轮，但分析 worker A 暂停，租约过期，worker B 取得新的执行资格。随后 A 醒来，不能因为“我算完了”就发布。task/attempt 没变，仍需要租约身份来区分过期执行者。

Mini Drop 只有一个 worker，没有 lease。它通过重启明确结束 RUNNING，不处理多执行者接管。这个模型实验是在为正式 `analyzer/drop_analyzer/repository.py` 做准备：领取、续租、完成时都要确认当前资格，失去租约的子进程结果最多成为未发布产物。

模型里可以控制时间与顺序，让过期接管稳定出现；真实环境用随意 sleep 常常不可靠，机器一慢就错过窗口。测试设计应允许把 A 停在明确位置，再让 B 接管，最后检查 A 的发布被拒绝。不能只验证 B 能完成，而漏掉 A 醒来后的旧写入。

最后用一句话区分两个 fencing：attempt 挡住旧业务执行轮次，lease 挡住同一轮中已经失效的处理者。它们可以同时需要，不能用“有一个任务版本号了”概括掉所有接管场景。

### 租约到期，不等于旧进程已经停止

再推演一个容易漏掉的事实：B 取得租约时，A 可能仍在另一个 CPU 上计算。租约是数据库授予的发布资格，不是操作系统替你发出的 kill。停止旧子进程可以减少浪费，但即使停止通知延迟，最终写入仍必须自己拒绝过期资格。把“发了取消”当成“不会再收到旧结果”，会重新打开同一个漏洞。

续租失败也不能一概重置计时从头开始。旧执行应及时停止产生新副作用，已算出的结果保留为未发布状态；新的执行在自己的资格下继续。真实部署还要考虑时钟来源、网络延迟、数据库不可用以及续租和完成竞争。教学模型控制了这些条件，只有把它们逐项带回真实测试，才能扩大结论范围。

给本次案例补两列观察：谁当前有资格、谁实际上还活着。它们可能一段时间内不一致，系统仍应保持安全。你会因此更容易看懂正式 Analyzer 为什么在上传、续租和最终 SQL提交处多次检查，而不只在 claim 的第一秒确认一次 owner。

## atomic-events：状态与事件怎样一起成功或失败

第四项命令：

```sh
python -m tutorials.labs --case atomic-events --json
```

先设想一个坏顺序：把任务状态写成 SUCCESS，事件写入时失败。用户详情看见成功，事件流却没有相应事实；另一个依赖事件推进的模块也可能永久等待。反过来先写事件、后改状态失败，会留下没有对应状态的成功公告。

这个 CLI 的实际注入点在创建事件之后、Outbox 插入之前。异常后 observations 的 after_injected_failure 里，tasks、attempts、events、outbox 计数都应为零；它验证四种创建记录一起回滚，还检查参数化 SQL 把看似攻击的名字按数据保存。Mini Drop 的 commitLocked 则用文件快照提交；正式系统在 SQL事务里写 task/attempt 与 task_events。

文件级原子替换不是分布式事务。RAW 文件、对象存储和数据库仍是不同交接，不能由这项实验推出“所有东西一起回滚”。它证明的是被放进同一提交的事实，外部副作用需要额外身份、恢复和对账。

做观察笔记时，写提交前后的状态、事件数与当前 attempt，不必只贴 passed。想一想哪种坏实现会让这三个值不一致，再去测试里找到能够识别它的断言。这样你可以判断实验有没有真正覆盖“原子”这个词的含义。

## 读 JSON 收据，别只看最上面的 passed

每项机制实验都可追加 `--json`。输出包含 passed、case_count、check_count、cases；每个 case 有 name、summary、checks 和 observations。checks 中有断言名称与 passed，observations 保存帮助解释过程的观察。

```sh
python -m tutorials.labs --case attempt-fence --json
```

先核对 cases 中的名称，确认运行的是你想看的实验，再读每项检查及观察。顶层 true 是摘要，不是你理解机制的替代品。四项实验的断言数量可以不同，因为每个窗口要保护的事实不同；断言多也不自动代表语义覆盖更深。

Windows 普通终端可直接阅读中文摘要。若用程序捕获输出并需要统一 UTF-8，可按运行环境设置 PYTHONIOENCODING=utf-8，再解析 JSON。不要因编码显示异常就把实验里的中文删掉，也不要把无法解析的文本当作“没有失败”。

收据里还应记录代码版本、命令、运行环境和时间。代码改变后，旧 passed 仍属于旧版本；把旧文件复制到新目录，不会自动构成一次新验证。这个规则与正式质量记录相同，模型实验也不能免除来源追踪。

## 稳定复现比“多试几次总会撞到”更有用

线程竞争经常被写成两个 goroutine 同时跑，再循环一千次期待出错。它可以发现问题，但失败不稳定时很难定位，测试也可能在 CI 偶发红。机制实验先固定交错点，让旧消息晚到、租约先过期，再检验结果。

Mini Drop 的 Go 测试使用 store 入口控制顺序：create、begin、finish、retry，然后再次旧 finish。它没有真实并发，也没有声称验证所有调度，却能稳定检查最终写入条件。另一个重启测试真正写临时 journal，再重新打开，覆盖文件恢复这一段。

正式数据库测试还需要不同连接、事务锁与可控阻塞点。纯模型里的 mutex 或字典，不能证明 PostgreSQL 隔离级别、锁等待后的重读和跨进程行为。反过来，真实数据库接通也不能替代一个能抓住旧消息的断言。

把测试分工写出来：模型检查规则，单元测试检查本地入口，集成测试检查真实交接，端到端检查用户路径。各自成本与结论不同，选择组合而不是彼此冒充。通过更多随机次数，无法弥补根本没有观察旧结果发布的测试缺口。

## 真服务重启时，先承认你看到了哪个窗口

想验证本地服务重启，可以先完成一项任务，关闭自己启动的 Go 终端，再按原 flags 和 workdir 启动，检查任务和文件保留。这验证终态读取与身份延续，不是采集中断恢复。

若你恰好在 RUNNING 时停止进程，重启后应看见 INTERRUPTED_RESTART，新轮次要由用户明确 retry。受控循环很短，手工操作可能抓不到 RUNNING。抓不到时如实记录，不要用终态重启的成功替采集中断背书；确定性 Go 测试可以稳定覆盖前述状态入口。

只停止自己启动、知道用途的服务，不按进程名扫机器后批量杀进程。目录和端口也要对应原实例。启动到新 workdir 时看不见旧任务，首先是实例选择变化，不应立刻判断持久化丢数据。

更深入的真实崩溃注入需要专门夹具，把程序停在已标记阶段，再回收指定子进程，并保留输出。正式性能工具可能影响目标，不能为了课程故障练习去随意中止生产采集。本参考与模型提供安全边界内的第一步，剩余验收要单独准备环境。

## 解析与完整性失败，也应该停在正确阶段

拿自己保存的教学 RAW 副本，先改一个协议字段，例如 unit，再单独运行 analyzer。预期拒绝输入；它不应该生成成功树。再读 Go 的结果校验测试，观察错 SHA 和错单位都被挡住。合法 JSON 只是开始，测量含义仍需匹配。

不要用“修改已经成功任务目录里的 result.json，然后刷新页面”来证明发布校验。Go 当前任务保存的是被接纳的结果快照，后改文件并不会自动触发一次新分析。没有把坏字节放进真实消费入口，就不能说你测试了那个入口。

同理，把 collector 文件移走再新建任务，可能观察到启动失败，但这不是解析失败。报告应写最后成功边界：程序没启动、RAW 未通过、analyzer 退出非零、result 完整性失败，或者 journal 发布失败。一个笼统的 FAILED 不足以定位实验覆盖。

正式 `registry.py` 还处理不可信格式、大小、深度、二进制附件和隔离进程。课程的七字段协议让错误容易看清，并没有替代那些解析器。扩展输入格式时，应继续按“哪种坏输入、在哪个入口、应产生什么有限错误”设计回归。

## 从文件 journal 迈向 PostgreSQL，需要新增哪些保证

假设你希望两个 worker 共同处理队列。现在本机 channel 和 mutex 不够：进程 B 看不到 A 的锁，两份 journal 副本还可能互相覆盖。首先要有共享持久队列和原子领取，再定义执行资格多久有效、怎样续租、怎样阻止过期发布。

如果又把采集控制面拆成独立服务，还需要处理提交任务与网络派发的缝隙。正式 Outbox 把待发送事实纳入 SQL提交，下游按 task/attempt 幂等接受；发送端在耗尽时重读当前状态，防止把已接受任务写成失败。多个机制分别填上不同窗口，不能只安装一个消息队列就概括完成。

再加事件读取、授权、对象制品和保留期，每次交接都要回答身份与失败问题。SQL 参数化、事务范围、锁顺序和当前租约条件，比选择哪一个 ORM 更接近保证本身。参考没有这些能力，就明确标为后续设计，而不使用“生产级”一词替代实现。

纸面作业可以画三张图：单进程文件参考；两进程共享数据库；控制面、节点、分析器分离。给每张图标出已经解决和新出现的窗口。你会发现架构拆分不是单纯增加模块数量，它也增加需要持久身份和恢复证据的交接。

## 为整个实验写一份有分母的记录

把四个 case 分别运行，记录成功、失败与跳过，而不是只留下最后一次绿色输出。再运行本地 control 的 Go 测试和一项真实四语言任务，让三类证据并排出现：机制规则、真实本地入口、完整受控链。

| 记录             | 可以支持                                | 仍不能支持                     |
| ---------------- | --------------------------------------- | ------------------------------ |
| 四项机制 case    | 人工指定窗口中的规则断言                | 真实网络、数据库、采集权限验收 |
| control Go 测试  | 参考实现的输入、journal、轮次与结果检查 | 正式服务全部并发路径           |
| 一项本地成功任务 | 本机固定工具到页面的受控链              | 联系人业务根因、所有平台和长稳 |
| 失败原始记录     | 指定边界的实际拒绝行为                  | 没有发生过的其他故障窗口       |

每行都写版本和运行条件。若某项失败，报告它的阶段与错误，不需要为了凑“全通过”删除。先修正假设、代码或环境，再在新版本重跑对应部分，保留前后关系。教学课程也应该练习这种证据纪律。

最后用一个反问检查措辞：“看到这份记录的人，会不会以为我验证了更多东西？”如果会，就补上范围。诚实的限制不会削弱成果，反而让别人知道它能作为哪一项后续判断的可靠输入。

## 结课作业：新增一个坏实现一定会暴露的断言

选一条你最熟悉的不变量，在自己的教学副本中写一个负例。可以选择旧 attempt 回来时当前事件不增加、journal 写失败时内存任务不出现，或相同键冲突时队列长度保持不变。先说明哪种错误实现会违反它，再写断言，不从当前代码每一行机械复制预期。

随后故意移除对应保护，观察测试确实失败，再恢复。这个步骤叫负控：它回答“我的测试有没有能力发现我担心的错误”。若坏实现仍然通过，应调整观察点，而不是把测试数量当作安全感来源。改动只在自己的参考副本，不触碰正式工程与运行数据。

参考答案可以用五句话组织：保护的是谁；消息或结果来自哪一轮；哪个事实先提交；坏实现怎样覆盖它；测试从状态、事件还是文件读出了差异。能把这五句讲清，比背诵幂等、Outbox、lease 和 fencing 四个名词更接近会实现。

这四章的产物应是一条能运行、能拒绝坏输入、能解释失败的本地链，以及一组来源明确的实验记录。继续向正式 Drop 迁移时，每新增一种真实目标或并发能力，就重新列出它改变了哪些边界。下一部分将把这样的实验方式用于分析与页面，让数据从字节到图形的含义同样经得起检查。
