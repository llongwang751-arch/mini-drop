## 从能讲清调用链，到亲手把它接起来

前十章沿正式工程阅读：请求怎么入库、采集怎样运行、结果怎么发布、模型怎样使用证据。现在换一种学习方式。我们亲手接通一条小链路，让终端里真正出现原始数据，让分析器真正读文件，再让页面读到自己创建的任务。这样，前面那些交接词就有了可以指认的对象。

参考源码在 `tutorials/mini-drop`。它不导入正式 API 的包，也不连接 PostgreSQL、MinIO 或部署环境。你可以单独编译、单独运行，故意给它错误输入，再观察它在哪个阶段停住。正式系统有很多生产约束，第一次自己搭链路时把所有组件一起搬过来，往往会让一个 JSON 编码错误也难以定位。

这一部分的完成标准有三层：先让一条合法请求成功；再让一个坏输入明确失败；最后能解释重启和重试留下的文件。只看到绿色成功按钮不算完成全部课程。每个实验都要保留来源、命令和观察，教程的预期不能代替你本机的记录。

我们的联系人慢接口仍然作为问题背景，但这份参考不会附加联系人服务。采集器只计算自己的受控循环。它测到了真实的自身 CPU 计账，却没有测到真实接口，后面的每一段结果都必须保留这个范围。

## 给最小系统划一圈可以守住的边界

Mini Drop 使用四种语言：C++ 生成受控工作并计量自身 CPU；Go 接 HTTP、安排一次执行、保存任务；Python 校验和分析原始字节；React 展示这些事实。四种语言不是作业评分要求，而是让你实际经历一次跨进程交接：类型在离开一个进程后会变成字节，另一个进程必须重新检查。

只允许一个输入：iterations，范围是一千到一千万的整数。用户不能在页面填可执行文件、脚本、PID、URL 或工作目录。工具路径由启动 Go 时的本机命令行固定，HTTP 请求无权更换。这样你可以先把任务正确性学清楚，而不用同时处理任意外部进程采集的权限。

另一个边界是运行位置。Go 只绑定数字回环地址，默认端口 4330；阅读器在 4322，经本地代理访问。这个设计适合个人学习，不提供账号体系，也不是可公开部署的多人服务。把监听改成所有网卡，并不会让缺少的资源授权自动出现。

最后限定可靠性范围：一个进程、一个 worker、一个私有 workdir。它保存文件 journal，最多排队一百项；没有数据库锁、跨机器租约或高可用。把这些边界写在开始处，后面我们就能准确回答：某个机制在参考里已经做到哪一步，正式 Drop 为什么还需要更多代码。

## 先约定交接物，再写调用命令

打开 `collector.cpp`，输出协议是一个 JSON 对象。下面是字段示意，数值是教学占位，并非一次实际测量：

```json
{
  "schema_version": 1,
  "source": "controlled_self",
  "unit": "cpu_ticks",
  "clock_ticks_per_second": 1000000,
  "total_ticks": 2400,
  "iterations": 1000000,
  "checksum": "0123456789abcdef"
}
```

source 说明被测对象是采集器自己；unit 说明 total_ticks 的单位；clock_ticks_per_second 给出换算尺度。若想得到秒，要用计数除以尺度，不能只看 total_ticks 的数字大小。Windows 的计量尺度与 Linux 可能不同，跨平台比较更不能直接减 tick。

checksum 来自确定的受控计算，目的是让计算结果被使用，帮助读者确认工作量输入参与了执行。它不是 RAW 的 SHA，也不是软件签名。RAW 的输入摘要要由分析器对整份实际字节计算，两者解决的问题不同。

schema_version 用于拒绝自己不理解的协议。即使这里只有七个字段，仍然值得显式约定；等数据跨过 C++ 输出、Go 保存、Python 解析、Go 验收四处边界，隐含假设就会变成真实错误。先写出协议，也会逼我们想清楚零值、单位和缺省行为。

## 第一段实验，只编译和观察采集器

依赖是支持 C++17 的编译器、Go 1.23+ 和 Python 3.11+。独立参考只使用 C++17 特性，正式 core 仍按自己的 C++20 配置构建。完整的平台命令放在 `tutorials/mini-drop/README.md`。先从最小步骤开始，在仓库根目录用自己的编译器执行：

```sh
g++ -std=c++17 -O2 -Wall -Wextra -Wpedantic -Werror tutorials/mini-drop/collector.cpp -o collector
```

Windows 的输出文件通常命名为 collector.exe；如果使用 MinGW，可按 README 加静态运行库链接选项。编译器不在 PATH 时，用实际完整路径调用，而不是因为“找不到 g++”就去改项目源码。警告即错误保留着，先弄清警告涉及类型转换还是遗漏检查。

运行 collector 加上 `--iterations 1000000`，应看到一行 JSON。随后分别试 999、10000001 和 abc：预期退出非零，并在 stderr 给出有限的错误码。此时不要接 Go。只有采集器自己的输入输出明确了，才把它交给另一个进程。

记录本机平台、编译参数、iterations 和输出。`-O2` 会影响机器执行方式，CPU 数字也会随平台、调度和分辨率变化。这里不要求每次计数相同；我们要验证的是协议、受控计算与真实计量路径能工作，而非得到教程预先指定的一个漂亮数字。

## 怎样理解真实的零计数

很短的计算可能落在计时器同一个刻度里，结束值减开始值就是零。零并不说明循环没有执行，也不必强行改成一。采集器仍会输出 checksum，分析器保留零，页面应该如实显示计量分辨率限制。

在这份参考里，循环使用无符号整数做有限次混合计算，结果最终写进输出。无符号溢出按语言规则处理，不能把它误写成“程序发生未定义行为”。我们不通过睡眠凑计数，也不启动额外后台负载来保证图有宽度。那样会把练习的观察对象悄悄换掉。

提高 iterations 可以让窗口更长，但它仍然是受控微型工作，不代表联系人服务的请求分布。多跑几次发现结果有抖动，是理解测量的机会：计时器刻度、进程调度、后台争用和编译优化都可能参与。先描述这些条件，再决定是否值得做统计比较。

还要区分 CPU 与墙上时间。Go 等待子进程结束的十秒上限是墙钟限制；C++ 报告的 cpu_ticks 是自身累计 CPU 计量。两者属于不同层。某次任务耗时较长，不能仅凭墙钟就把结果中的 CPU tick 改大；观察等待和观察工作必须各自保存口径。

## 第二段实验，原样保存字节再分析

Python 分析器的接口是 `analyzer.py RAWPATH --output RESULTPATH`。RAWPATH 指向采集器原始 UTF-8 JSON，输出是另一份 JSON。你可以先用一个小脚本捕获 stdout 为字节，再保存；Windows 上尤其不要忽略终端重定向可能改变编码的问题。

下面是独立的教学调用示意，路径需要换成本机编译产物。它不接 HTTP，也不导入业务代码：

```python
from pathlib import Path
import subprocess

collector = Path("你实际编译的 collector 完整路径")
raw = subprocess.check_output([str(collector), "--iterations", "1000000"])
Path("raw.json").write_bytes(raw)
```

再用当前 Python 执行课程 analyzer，指定 raw.json 和 result.json。检查 result 是否包含 input_sha256，以及 summary 中的来源、单位和限制。这个阶段文件由你自己创建，记录它们的位置，避免打开另一个目录里遗留的同名文件。

为什么保存原字节？同一 JSON 对象可以有不同空白和字段顺序。对对象重新序列化后的 SHA，与原始文件 SHA 可能不同，但并不表示对象内容不同。本参考用输入字节摘要建立文件身份，因此必须对实际 RAW 计算，不能在中间“美化一下”却继续沿用原来的摘要。

## 分析器第一件事，是决定哪些输入可以拒绝

打开 `analyzer.py:analyze`，先看长度和解码，再看字段集合与范围。输入最多 32 KiB，UTF-8 必须有效，对象字段必须正好匹配这份小协议；重复键、NaN、错误类型和额外字段不能悄悄穿过去。Python 的 bool 是 int 的子类，所以整数检查使用 `type(value) is int`，避免把 true 当作一个 tick。

这些检查的目的不是预测所有性能文件，而是守住自己承诺接受的那一种输入。Analyzer 没有通用 profile 解析能力，不能把一份正式 py-spy 文件改名为 raw.json 就交给它。扩展格式需要新的解析和验证，不能让异常捕获把所有失败都变成空结果。

再看错误输出。InvalidInput 保存固定代码，CLI 只输出这些安全类别，不把整份坏 JSON 或堆栈塞回 Go。这样处理后，你仍能分辨格式错误、计数范围错误和 I/O 错误，同时不会把数据正文顺手记录到服务日志。

练习时复制一份自己的 RAW，把 unit 改成 milliseconds，再运行分析器。预期非零退出，不产生一份看似成功的新报告。保留原文件以便对照。这个负例比“合法样例能打开”更能检验协议是否真正参与了执行。

## 两层树也要满足计数关系

分析结果的 flamegraph 很简单：根叫 all，下面只有 controlled_process。根 value 等于 total_ticks，根 self 为零；叶子 value 和 self 都等于 total_ticks，没有子节点。这不是函数火焰图，而是一种与现有树形展示约定兼容的进程计账表达。

亲手算一次教学数字：假设 total_ticks 是 2400，那么根和叶子的 value 都是 2400，并不是系统总共消费了 4800 tick。父节点包含子节点，不能把路径上每层相加。根的 self 为零，表示它只是聚合容器，没有另外一份独占计数。

`analyzer.py:analyze` 完成映射后，`atomic_output` 将结果序列化到同目录临时文件，flush、fsync，再 replace 到目标文件。先形成完整内容，再换名字，是为了避免另一个读取者拿到半个 JSON。临时文件只删除本次调用自己创建的那一个，不会递归清理工作目录。

正式 `analyzer/drop_analyzer/registry.py` 面对多种格式和更复杂的树，需要下载完整性、预算、隔离进程和作业租约。参考先把“输入字节、合法结构、聚合关系、输出文件”这四件事串起来。读完以后，再回正式实现，就能看见额外保护具体加在哪一段。

## 第三段，把手工命令交给 Go

手工运行每个工具很适合定位问题，但页面不能每次要求用户进入终端。Go 控制面把它们组成后台任务：接收 iterations，保存 QUEUED，交给单 worker；worker 先持久化 RUNNING，再运行 collector 和 analyzer；最后核验结果，发布 SUCCESS 或 FAILED。

HTTP 创建返回时不等待完整分析。`POST /tasks` 返回 task，`GET /tasks/实际ID` 读取进度。ID 是字符串，attempt 是本任务内的轮次。最初也许很快就完成，所以页面不一定能抓住 RUNNING；事件保留了已经经过的状态。

这里没有把前十章所有状态硬塞进来。参考只有 QUEUED、RUNNING、SUCCESS、FAILED，把采集和分析放在同一轮执行里，错误码指出失败阶段。正式 Drop 为了区分已经收集 RAW、待分析、分析重试等情况，保存采集与分析双轴。二者是不同范围的设计，不能因参考更短就删掉正式状态。

观察 Go 的 runner 时注意：程序路径来自启动 flags，HTTP 只提供受控整数。`exec.CommandContext` 按固定 argv 启动，子进程不继承任意应用环境。这个选择把“服务能调用程序”限定成明确能力，而不是给浏览器一个任意命令入口。

## journal 和逐轮目录，各保留哪一种事实

Go 的 workdir 中有 journal.json，还有按 task ID、attempt 分开的 raw.json 与 result.json。journal 保存当前任务、事件和幂等键，文件保留具体字节。两者并存是为了回答不同问题：当前状态是什么，和这轮实际产生了什么。

`store.go:commitLocked` 先复制内存状态，在副本里修改；序列化后写临时文件、sync、rename，成功才把新快照交给读请求。假如磁盘写失败，进程不会先向页面宣称成功。状态和对应事件在同一份 journal 中发布，也就不会故意制造一个成功状态却没有成功事件的提交。

但文件 journal 没有获得数据库的全部语义。两个控制面进程共用同一 workdir，会各自覆盖快照，内存 mutex 无法协调它们；某些文件系统和断电条件也需要更严格的持久化设计。因此一个 workdir 只启动一个实例，参考不承诺高可用。

重试会增加 attempt，使用新目录，不覆盖旧 RAW。看到 attempt-1 和 attempt-2 时，先对照事件判断哪一轮对应当前结果。重新采样获得新的测量窗口，旧文件有助于解释历史；把所有结果一直写同一个文件名，虽然界面容易找到，却会丢掉这种追溯能力。

## 第四段，页面读的是事实而不是执行权

[Mini Drop 工作台](/book/workbench)经本地代理读取任务。浏览器只知道 iterations、任务 ID、状态、事件和结果，不知道采集器完整路径、Python 路径或 workdir。即使页面被手工改动，请求也不能要求后端换一个程序。

先观察任务表，再看结果。应同时展示 source、unit 和 limitations，尤其说明 controlled_process 是进程计账节点。CPU 计数为零时，页面要保留零值和分辨率说明；如果把零替换成默认宽度，视觉上就制造了不存在的测量。

网络请求失败时，也要保留“任务状态未知”和“任务已经失败”的区别。前者是浏览器暂时没有获得事实，后者是 Go 已经发布终态。刷新或重新 GET 可以恢复观察；再次 POST 新键会创建另一项工作，并不只是刷新画面。

这和正式 `web/src/views/TaskDetail.tsx` 的原则一致：页面离开以后，后台继续执行；页面重开以后，重新读取持久状态。参考暂时不提供 SSE，用轮询观察也能理解职责。等你能解释这一点，再去优化连接方式，比先把动画做得流畅更有价值。

## 完整实验：为一条请求留下四种记录

按 README 编译 collector，分别确认 collector 和 analyzer 能独立工作，再启动 Go。Windows 使用 PowerShell 的 Invoke-RestMethod，Linux 可用 curl。创建请求是以下协议，幂等键每个新意图使用一个新值：

```http
POST /tasks
Content-Type: application/json
Idempotency-Key: lesson-create-001

{"iterations":1000000}
```

等待终态后，保留四种记录：创建请求中的 iterations 和键；返回的 ID、attempt、状态；该轮 RAW 的 SHA；结果中的来源、单位和树值。不记录进程环境，也不复制浏览器无关请求。参考没有凭据，练习仍应养成保留最少必要证据的习惯。

随后用相同键、相同请求再发一次，预期返回已有任务，不多出一项队列工作。把 iterations 改成另一个合法数却继续用原键，应得到冲突。最后发一个新的 retry 键，观察 attempt 增加，旧目录继续保留。具体任务编号由本机产生，不照抄教材示意值。

实验报告不必很长，但要让读者能把四种记录互相对上。若某一步失败，记录最后一个已确认阶段，再检查下一段。这样留下的失败实验也有学习价值，比删除所有文件重新开始更容易发现交接中的误解。

## 管线不通时，把故障缩小到一条边界

现在安排一个排错作业：不改变程序能力，只用自己的文件与运行参数，找出“后端没结果”到底发生在哪一段。先在纸上画六个格子：可执行文件存在、工具退出成功、stdout 合法、RAW 保存成功、分析结果合法、当前任务接纳。每确认一格，记下实际证据，再检查下一格，不凭最后一个红色按钮倒推原因。

第一种常见情形是工具能在原终端运行，Go 却报 TOOL_FAILED。检查你启动 Go 时使用的完整路径，是不是刚才编译的那个产物；Windows 动态运行库是否依赖原终端 PATH；Python 解释器是否为预期版本。参考刻意收窄子进程环境，因此“我在自己的 shell 里能运行”只证明另一组环境成立。按 README 静态链接编译器运行库，比给子进程传进所有应用变量更容易解释。

第二种是手工保存的 RAW 无法解码。用字节方式检查文件开头，确认终端没有写成另一种编码或加上不被当前协议接受的标记；再用字节捕获脚本重新保存。不要先修改分析器去宽松吞掉所有编码。接口原本约定 UTF-8，放宽时需要决定哪些变体可接受、摘要对哪份字节计算以及错误怎样报告，不能只让这一份样例碰巧通过。

第三种是你打开了 result.json，却在页面仍看见旧结果。先核对 task ID 与 attempt，再核对服务启动的 workdir。页面读取的是 Go 已接纳的快照，不会因为某个同名文件被手工修改就自动更新。这个现象并不证明代理缓存坏了，也不应通过不断新建任务来“刷新”。只有找到真正的消费入口，排错动作才有针对性。

再考虑一种较隐蔽的情况：你美化 RAW 后重新运行 analyzer，SHA 变了，但计数没有变。它表示输入字节身份改变，不必立即认定计算错误。把原文件和新文件分别保存，各自计算摘要，再解释“语义一致”和“字节一致”的区别。这个练习可以帮助你理解正式制品校验为什么保留原始字节。

最后整理一份排错表，每行写症状、最后已确认边界、下一步只读检查和实际结论。不要把所有检查一口气同时执行：如果同时换编译器、换 Python、改输入、重启服务，你也许得到成功，却不知道修正了什么。一次只改变一个待验证条件，才能把这份小链路变成自己的实验工具。

保存错误输出时也标注它来自哪个命令。collector 的拒绝、Python 的解析错误和 Go 的任务错误码处在不同层，字符串看起来相近，不代表执行到了同一位置。保留这个归属，下一次排错就能直接从正确边界开始。

## 作业答案要解释为什么，而不只贴输出

第一题：结果树两层都显示同一个 total_ticks，为什么不能相加？参考答案是 value 为包含子节点的计数，根只承担聚合，独占值看 self。第二题：RAW 有 checksum，为什么还要 input_sha256？前者使用计算结果，后者标识传入分析器的实际字节，不能互相替代。

第三题：页面超时后重发请求，该保留什么？同一创建意图保留原幂等键，先 GET 已知 ID；明确新增任务或轮次才使用新键。第四题：分析器运行成功，Go 为什么仍校验摘要和树？进程退出码只说明程序按自己的规则结束，控制面还要确认结果确实属于本轮输入、单位未变、计数关系成立。

请在自己的副本里故意改坏一次结果中的 input_sha256，再阅读 `runner.go:validateResult` 推演它会怎样拒绝。不要改正式代码去跳过校验，也不把一个手工推演写成后台已经实测。真实跑过的命令、纸面预期和源码判断分别标明。
