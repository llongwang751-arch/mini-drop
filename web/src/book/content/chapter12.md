## 先给采集器一项足够窄的工作

这一章只做一件事：让一个可执行程序完成自己拥有的有限计算，报告自身 CPU 计数。源码是 `tutorials/mini-drop/collector.cpp`，支持 C++17，方便现有本地工具链编译；正式 `core` 的语言标准和构建配置保持独立。不要因为教学程序能编译，就宣布正式采集器的 Linux 权限路径也已验证。

为什么暂时不接外部 PID？因为外部目标会立刻带来所有权、复用、namespace、附加权限和运行干扰。它们都值得学，但在还没弄清 stdout 协议时一起加入，会让一次失败有太多解释。先把自身计量做好，再逐项列出扩展目标需要增加什么保护。

参考的输入只有 `--iterations N`。进程没有 HTTP、数据库或对象存储功能；它只管校验输入、运行工作、计量、输出或失败。这样的接口可以手工运行，也可以被 Go 以固定 argv 调用。工具越窄，上层越容易知道一次调用的副作用到底在哪里。

本章的观察对象从头到尾都是这个 collector。联系人服务只是背景案例，不能把受控循环的 checksum 或 CPU tick 填进联系人接口报告。明确对象，是所有后续分析能够成立的第一道条件。

## main 先检查调用形状，才解释数值

打开 `main`，第一道分支检查参数数量和选项名。合法形状必须是程序名、`--iterations`、数值三个元素。缺少数值、换一个标志、追加路径或额外参数，都应该在做任何计算之前退出。

这一步很简单，却决定了接口是否真的有限。如果程序一边说“只接受 iterations”，一边又把多余 argv 交给别的工具，就给上层制造了未知能力。参考不会因为认识前两个参数就忽略后面的内容，也不会尝试从错误输入里猜一个最接近的意图。

输入拒绝信息写到 stderr，退出码为二；计时不可用或输出失败返回三。成功 JSON 写到 stdout。Go 可以把 stdout 当数据通道，把退出码当调用结果，再有界捕获诊断输出。把欢迎语、进度条和 JSON 混在 stdout，会迫使下游按行猜哪一段才是真数据。

独立运行时，先试没有参数，再试合法形状，最后试多一个参数。预期只有合法输入继续执行。你不需要一次把所有错误码背下来，先证明参数个数与名称这两个边界参与了控制流。后面的数值测试才不会混入调用形状错误。

## from_chars 为什么要核对两个结果

`main` 使用 `std::from_chars` 读取无符号整数。它返回转换状态和停止位置：前者说明是否发生错误，后者说明到底读到了字符串的哪里。只检查转换成功，可能把前半段合法、后半段夹杂字符的输入当作完整数值。

参考的判断可以概括为以下实际条件，变量名来自源码：

```cpp
parsed.ec != std::errc{} || parsed.ptr != input.data() + input.size() ||
iterations < 1000 || iterations > 10000000
```

第一个条件拒绝无法转换或越界；第二个拒绝未消费完整输入；最后两个限制业务预算。`1234abc` 不应只取 1234，负数也不应经有符号转换后再绕成巨大无符号值。上层虽然已经校验，独立工具仍应守住自己的入口。

这也是一次跨层校验的具体例子。Go HTTP 只接受整数且有相同范围；C++ 不因此省略检查，因为它还可能被直接调用。重复的是相同契约，保护的是不同入口。若将来调整范围，需要同时协调两边和分析器，不能只让表单变宽。

练习时分别写出非法类型、非法尾缀和合法但超预算的例子，再对应到这三个判断。这样看边界，比只用一个 abc 测试所有失败更清楚。

## iterations 是工作预算，不是性能承诺

一百万次迭代定义了有限工作量，但不会承诺“必须花多少毫秒”。编译器优化、指令集、处理器频率、系统争用和计时分辨率都会影响测量。范围下限与上限帮助实验可控，无法把机器差异消掉。

上限也不是唯一资源保护。C++ 自己限制循环数，Go 外层再给每个工具墙钟超时，捕获输出设置字节上限。每层回答不同问题：输入防止正常代码拿到夸张工作量；超时处理工具异常或运行环境卡住；输出限制避免异常文本撑满内存。

别把这组限制描述成正式沙箱。参考启动的是已固定、本地可信的采集器；它没有处理任意第三方程序或不可信用户脚本，也没有正式 Runner 的进程组追踪和完整隔离。若你把固定 collector 换成一个会递归创建子进程的程序，原来的简单超时语义就不够了。

本章可以做一个纸面推演：如果把最大 iterations 放大一千倍，需要同时重新考虑哪些限制？答案至少包含预期执行时长、超时、计数范围、教学机器负担和测试预算。不是所有参数上限都能孤立修改。

## checksum 让受控计算留下可用结果

循环从固定的无符号种子开始，每轮把当前序号混入状态，再做乘法和位运算，最后把 checksum 格式化为十六进制字符串。它没有访问联系人数据，也不会根据网络返回内容改变循环次数。相同算法与输入应得到相同校验结果，计时则不必相同。

为什么不写一个什么都不做的循环？编译器有理由把无可观察效果的工作消掉。让循环结果参与 stdout，能避免最直接的死代码删除。它仍然不是证明“机器实际执行了某组固定汇编”的证据；编译器可以用保持语义的方法优化，因此记录编译参数仍有意义。

循环使用 `std::uint64_t`。无符号算术按固定模数处理，溢出是这项混合计算的一部分；不要为了追求“数值精确”改成浮点数，再把不同精度的结果放进同一个协议。也不要把 checksum 当密码学摘要，它没有承担防伪或完整性认证。

结果文件的身份由 SHA256 表示，计算对象是 RAW 的完整字节。checksum 与 input_sha256 并排出现时，需要在报告里分别说明“计算结果”和“输入身份”。这份简单参考恰好让你看清，一串看起来像哈希的十六进制文本，并不能凭外观决定其保证。

## own_cpu_ticks 把平台差异收在一处

函数 `own_cpu_ticks` 输出当前进程 CPU 计数和每秒 tick 数。非 Windows 分支使用 `std::clock()` 与 CLOCKS_PER_SEC，先检查不可用返回值。main 在计算前后调用两次，验证结束值不小于开始值、两次尺度一致，再计算差值。

Windows 分支使用 GetProcessTimes，将 user 与 kernel 的 CPU 时间相加，单位为一百纳秒，每秒一千万 tick。这里没有照搬 Windows CRT 的 clock：微软文档明确说明其 clock 测经过的墙钟时间，并建议 CPU 时间使用 GetProcessTimes。这个平台差异会直接改变 unit 的真实性，不能只在界面加一个模糊免责声明。[微软 clock 文档](https://learn.microsoft.com/en-us/cpp/c-runtime-library/reference/clock?view=msvc-170)。

实现里把 FILETIME 的高低位组合成无符号六十四位值，并检查相加溢出。API 失败时返回固定错误，不把一个无意义的零当成功。零测量与失败必须分开：前者可能是分辨率不足，后者表示计量本身没有成立。

把差异收在函数里，main 就可以只关心“获得同一尺度的两个计数”。这是一种有限抽象：它没有宣称所有平台分辨率相同，也没有给不同机器建立可直接比较的性能基线。抽象统一调用方式，测量条件仍应留下。

## 从 tick 换成秒，也不能跳过来源

假设教学输出为 total_ticks=25000、clock_ticks_per_second=1000000，换算得到 0.025 秒的进程 CPU 计量。若另一台机器的尺度是一千万，25000 tick 只有 0.0025 秒。直接按原始计数排序，会把尺度差误当性能差。

进程 CPU 计量也不等于请求延迟。参考没有请求处理链，无法给出 P95、数据库等待或用户体验结论。把这份测量画成两层树，只是为了让课程页面使用统一的 value/self 结构，不会让 controlled_process 自动变成函数节点。

计数为零时也遵守同一规则。可以说明当前工作窗口短于可观察刻度，或建议增加有限工作量重新观察；不能补一个最小正值，再把它当真实 CPU 时间。结果解释与图表布局应共享这种限制。

请把自己的输出抄成一行说明：“在某平台、某编译参数、某 iterations 下，collector 自身记录了多少 tick，每秒尺度是多少。”这句话看似保守，却比“该接口只耗时几毫秒”更完整。后者甚至没有进入本实验的观察范围。

## stdout 协议要稳定，stderr 也要有上限

采集器成功只输出一份 JSON，字段名固定，字符串中不包含用户任意文本，因此不需要临时手拼复杂转义。checksum 只由十六进制字符组成，计数是经过验证的整数。写入 stdout 失败时，进程仍返回非零，不能因为已经完成计算就忽略交接失败。

独立测试时，要同时观察 stdout、stderr 与退出码。没有 JSON 可能是参数拒绝，也可能是时钟不可用，还可能是管道写失败；这些情形都不该在 Go 里变成一个带默认值的“成功结果”。工具退出码是必要信号，但仍需要解析和校验输出。

Go 的 `boundedBuffer` 最多保留 stdout 32 KiB、stderr 8 KiB。越界后返回错误，runner 会给任务一个有限错误码，不将原始诊断文本发给浏览器。参考工具平时输出很少，也应该保留坏输出的边界；“我们的程序不会那样”不是处理异常的完整理由。

正式 `core/src/process.cpp` 同样把公共日志与采集原始输出区分开，并设输出和进程资源限制。回到正式项目时，观察它怎样脱敏、怎样限制读取量，而不要仅凭用了日志库就认为诊断信息天然安全。

## 固定 argv 怎样跨过 Go 与 C++ 的边界

Go 的 runner 调用 collector 时，argv 只有 `--iterations` 和经过整数转换的值。可执行程序来自启动参数，浏览器不能更换。`exec.CommandContext` 直接启动这个程序，不通过 shell 解释字符串。

假设有人提交 `"1000; echo anything"`。它首先不符合 JSON 整数类型，HTTP 就会拒绝。即使在某种普通字符串参数中出现分号，argv 也不会自动把它拆成第二条命令。但你仍要理解工具本身可能有自己的表达式或脚本语义，所以固定选项与输入类型都不可省。

子进程环境也刻意收窄。参考只保留所需的平台变量，Python 使用隔离模式，避免继承任意 PYTHONPATH 和应用凭据。Windows 编译产物若依赖 MinGW DLL，建议静态链接编译器运行库；不能为了让一个工具启动，就把整份服务环境无差别传下去。

练习时沿数据流写出 iterations 的四种形态：HTTP JSON 数字、Go int、argv 十进制字符串、C++ uint64_t。每次形态变化都有检查点。跨语言类型安全需要靠这些边界接起来，编译器无法替另一个进程检查字节。

## 十秒超时到底覆盖哪一段

参考 `runner.go:execute` 为每次工具执行创建十秒 context。collector 最多等待十秒，接下来 analyzer 又有自己的一次十秒窗口；排队时间、文件写入和 HTTP 轮询并不因此获得一个统一的十秒完成承诺。

这很容易在页面里写错。显示“单工具超时十秒”与显示“任务一定十秒内结束”是不同产品承诺。若排队前还有几十项工作，后者明显不成立。用户的等待时间需要单独测量，而不是拿工具预算相加后假装得到精确上界。

取消同样要看范围。本参考没有取消 API，CommandContext 用来处理控制面退出或工具超时，主要面向直接启动的固定程序。它没有正式 C++ Runner 那样持续约束工具进程组、线程数与嵌套子进程，不宜让用户上传任意程序试验逃逸。

正式项目的超时、取消和资源预算分别覆盖采集、附加、收尾等阶段。第二遍读 `core/src/process.cpp` 时，逐一标出创建进程组、发信号、等待收尾和清理残留的位置，再回到参考，才能准确说出小实现为了可读性省去了什么。

## 外部 PID 会把哪些新问题带回来

如果下一项作业是“采 Python 联系人服务”，不能只给 collector 增加一个 PID 参数。你需要确定谁有权选这个目标、PID 属于哪个 namespace、启动时刻是否仍匹配、UID 是否允许，以及采集前后是否还是同一可执行对象。

正式 `core/src/target.cpp:process_identity` 从 procfs 读取身份，`same_identity` 比较多个维度。一个数字 PID 可能被复用；同一文件路径也可能换 inode；容器内部编号不等于采集器可见编号。采集工具可用与目标可附加，也不是同一个检查。

还要重新设计输出来源。controlled_self 不能继续写在一份外部进程测量上；不同采集机制需要不同单位与限制。若采用 py-spy，要说明是 Python 栈采样，保留质量信息；若采用 procfs 线程计账，就不能把线程节点标成函数热点。

这份纸面扩展表至少应有平台授权、目标身份、工具能力、预算、取消、制品来源和分析兼容七项。缺一项就先保留在待实现范围，不用为了让课程显得“完整”而给一个无校验 PID 开口。最小实现的价值，也在于让你看见从受控世界走向真实目标需要付出的具体工程。

## 学生实验：给每个边界一个反例

先按 README 编译，再独立运行四组输入：合法的一百万次、低于下限、超过上限、带非数字尾缀。记录退出码与 stdout 是否为合法协议。不要只贴成功输出，因为那还没有验证输入拒绝发生在计算之前。

再把合法工作量设为最小值，多观察几次计数。可能是零，也可能是很小的正数；两种都应保持单位和尺度。若机器很快，增加至允许范围内的较大值观察，不要求教材与本机得到同一个数字。任何睡眠、后台负载或编译选项变动都写入记录。

最后把一份 RAW 的 total_ticks 改成负数，或将 iterations 改为不在范围内，交给 Python。预期分析器拒绝；Go 自己也会核对 collector 输出的 iterations 与这轮请求一致。进程成功退出却报告别的工作量，不能进入当前任务的成功结果。

这组练习只在自己的目录里创建与编辑教学数据，不需要提升权限，不向外部 PID 发信号。它验证输入、计量和交接，不验证正式 perf、memray 或 helper。把未覆盖项写在报告里，才方便下一章继续扩展。

## 跨语言核对 checksum，确认你跑的是同一项工作

除了时间，我们还有一条不依赖调度的观察：相同 iterations 对应确定的 checksum。可以用一千次迭代在 Python 中独立复写计算，核对 C++ 输出。这个实验验证算法与数据传递，不能验证 CPU 计时精度，更不能把 checksum 相同当成性能相同。

下面是对应当前参考算法的教学代码。它不调用外部工具，最后打印十六进制结果，供你与自己运行的一千次 collector 输出比较。没有在这里预填一个声称已经测过的数字。

```python
mask = (1 << 64) - 1
checksum = 1469598103934665603
for i in range(1000):
    checksum ^= (i + 0x9e3779b97f4a7c15) & mask
    checksum = (checksum * 1099511628211) & mask
    checksum ^= checksum >> 29
print(f"{checksum:016x}")
```

为什么 Python 要手工加 mask？它的整数会继续扩展，不自动在六十四位处回绕；C++ uint64_t 具有固定宽度。只把乘法一字不差抄过去，最后的数值就会不同。这个差异不来自语言“快慢”，而来自数值模型。跨语言实现相同算法时，类型语义本身就是契约的一部分。

为何先选一千次？它足够检查循环、常量、移位与格式，又不让独立 Python 验算变成大负载。逐步扩到另一个允许数值时，也应同时修改两边的输入。若忘记改一边，checksum 不一致首先提示任务条件不同，不要马上归咎于 CPU 架构或编译器错误。

若计数合法但 checksum 不同，先确认编译输入和运行产物是否对应：修改源码后是否重新编译，Go flags 是否仍指向旧路径，当前终端调用的同名程序是哪一个。然后检查常量、循环上下界、整数宽度与移位顺序。每排除一项，保留一条理由，不通过手改输出让它看起来一致。

这个实验还可以区分两种变化。把编译参数从未优化换成 O2，合法实现应保持计算结果，时间则可能变化；把算法常量改变，checksum 也会变化，此时两份时间不再测同一项工作。做性能比较之前先验证功能语义等价，是正式源码修复也必须面对的问题。

最后给报告加一列“工作身份检查”。它可以是这里的确定结果，也可以是正式业务中的 oracle、响应集合或独立正确性断言；不要只记工作量参数和秒数。某个补丁算得更快，却悄悄少做了一部分工作，CPU 下降并不能支持优化成功。当前实验用很小的算法，让这个原则可以亲手检查。

再补一个格式反例：同一个整数可以写成十进制，也可以写成十六进制。协议要求十六位小写十六进制字符串，包含必要的前导零；只比终端显示的数字而忽略表示方式，也会把合法结果误判为不一致。先统一数值与表示，再比较字节。

## 参考答案与下一段实现

为什么同时检查 from_chars 状态和结束位置？因为“读到一个整数”不保证“完整输入就是那个整数”。为什么零不是失败？因为合法计量可能受分辨率限制，失败由 API/返回状态单独表示。为什么 Windows 换一个计量函数？因为单位要由实现支持，接口名字相同不代表各平台语义相同。

为什么不把 std::cout 中的 JSON换成一整段自然语言？因为它是机器交接协议，后续分析需要稳定字段、类型和范围。自然语言说明放在限制和课程正文里，不能让分析器从“这次看起来挺快”猜一个计数。

最后问自己：如果 Go 任务失败，你能否先独立运行 collector，再独立运行 analyzer，把问题缩小到一段？能做到，说明你保留了模块边界；若必须先启动整个正式栈才能知道一个整数是否合法，就还没有用好这份参考。
