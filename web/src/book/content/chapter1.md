## 接到“接口很慢”这句话以后

假设你维护一个 Python 联系人服务：请求带着一批联系人进来，服务为每个人生成摘要，再返回列表。小批量很快，数量增加后，请求要等好几秒，机器 CPU 也升高了。你打开代码，看见一个循环，于是准备把它改成多线程。

先停在这里。你已经看见现象，也找到了一个看起来有关的函数，但还没有证据说明时间花在那里。请求可能在等数据库，可能多次计算相同内容，可能卡在序列化，也可能恰好碰上另一个后台任务。不同原因对应不同动作，改错地方既浪费时间，也可能引入新的问题。

Drop 要把这件事变成能继续追问的过程：选定目标，收集数据，保留原始文件，分析出热点与调用关系，再根据证据调查、复测。学习这个项目，可以先问一个朴素的问题：**一次诊断中的每句话，究竟依据哪份数据？** 后面的状态、事务、制品校验和工具权限，都围绕这个问题展开。

这也是我们的贯穿案例。联系人服务用于教学说明；本章的数字和执行编号都是明确标注的假设，不代表仓库已经完成了对应测量。真正动手会从 [第 2 章](/book/chapter2/) 的本地受控进程开始。

## 把观察、瓶颈和根因分开

“一分钟内有五次请求超过两秒”是一条观察。它可以来自访问日志，能指出发生时间、请求范围和测量口径。“摘要生成占据主要 CPU 样本”是对采样结果的解释，提示了资源消耗集中在哪里。“相同联系人被重复生成摘要”则是一个原因假设，需要结合代码、输入或对照实验验证。

瓶颈还要带着目标来谈。假如我们关心每秒能处理多少批联系人，串行摘要计算可能限制吞吐；如果用户主要在等远端查询，节省一点摘要 CPU 可能几乎不改变响应时间。相同热点，在不同负载和目标下，价值可以不同。

因此，给结论补三样东西：什么负载、什么指标、什么范围。例如“在本次一千条联系人请求中，摘要路径占较高比例的 CPU 样本，值得检查重复计算”，就比“这个函数是根因”更容易验证。它也自然引出下一步：保持输入不变，去掉重复计算，再比较 CPU 和响应时间。

**本章第一个检查点：**如果你只能拿出一张 CPU 曲线，先写“观察到 CPU 升高”。不要顺手把它升级成“某段代码低效”。证据足够时再推进结论，调查才不会被最初的猜测绑住。

## CPU 时间和等待时间，不是一把尺子

用户从发出请求到拿到响应的时间，通常称为耗时或 wall time。CPU 时间则是处理器为进程实际工作的累计时间。单线程可能花很长时间等待网络，却只消耗少量 CPU；多线程并行工作时，进程累计 CPU 时间又可能超过同一段墙上时间。

下面是独立的教学实验，不是 Drop 的业务实现。它只在自己的 Python 进程里做有界计算和休眠，可以用来理解两把尺子的区别：

```python
from time import perf_counter, process_time, sleep

wall_start = perf_counter()
cpu_start = process_time()
checksum = sum(i * i for i in range(1_000_000))
sleep(0.5)
print("wall_seconds", perf_counter() - wall_start)
print("cpu_seconds", process_time() - cpu_start)
print("checksum", checksum)
```

`perf_counter()` 统计经过的时间，包含中间的休眠；`process_time()` 统计当前进程的 CPU 时间，休眠本身不会消耗同等长度的 CPU。预期能看到前者比后者多出明显的等待部分，具体数字取决于机器和调度，教程没有替你运行它。

回到联系人接口：若 wall time 上升而 CPU 时间接近原来，应该优先寻找等待、排队或外部依赖；若两者都随联系人数量增加，就有理由继续调查计算路径。两种指标都不能单独排除其他原因，但它们可以帮你选对下一次采集。

## 火焰图能告诉你什么

CPU 栈采样会在一段时间里反复观察程序正在执行的调用栈，再按路径聚合。某个路径得到很多样本，说明它在这些采样观察中经常出现。火焰图把这种聚合画成宽度，方便你从整体逐步展开。

宽度必须结合单位解释。CPU 样本、线程 CPU tick、分配字节、对象数量都能画成树，却不是同一种测量。父节点通常包含子调用的权重，不能把父子百分比相加；一个父函数很宽，也可能主要是它调用的子函数在工作。图中横向位置用于排布路径，也不应直接当成真实时间先后。

这会影响我们的第一轮操作。仓库的 `PROC_CPU` 使用 `/proc` 线程 CPU 计数，只能看到线程层面的消耗；`PYTHON_CPU` 使用 py-spy，能够取得 Python 栈。两者都可能产出 folded 形式的数据，文件语法相近，证据精度仍有差别。

所以，看见一个叫 `render_summary` 的节点之前，先确认结果来源、输入格式和统计单位。图表的颜色和形状很容易给人确定感，真正限定结论的是采集方法。数据质量、丢样、目标身份和采样窗口，也会影响一张图值得相信到什么程度。

## 先画两条线：控制命令怎样走，文件怎样走

Drop 使用 C++、Go、Python 和 TypeScript，各自承担独立工作。理解它们的分工，可以先画两条线。控制线传递“允许做什么、做到哪一步”；数据线传递真正的性能文件和分析结果。

```text
控制线：浏览器 → Go API → 数据库/Outbox → C++ Server
                                             ↕ mTLS 心跳与回报
                                         C++ 采集 Agent

数据线：采集工具 → RAW → MinIO → Python Analyzer → 结果制品
                      数据库保存制品身份与状态        ↓
                                                浏览器展示
```

这张图做了教学简化，省略了认证、事件流和部分辅助制品。Go 接住用户请求，负责权限、校验和业务编排；C++ Server 负责与节点通信及采集状态交接；Agent 在明确范围里执行工具；Analyzer 解析原始格式；React 让用户看见进度、结果和证据。

为什么文件不全塞进 HTTP 返回值？采样可能持续数十秒，文件可能很大，浏览器也可能中途关闭。把业务状态保存在 PostgreSQL，把大文件放到对象存储，后台就能继续工作。页面重新打开时查询持久事实，而不是依赖上一次页面内存。

控制和文件分开也带来新问题：文件上传成功，数据库登记却可能失败。工程必须处理它们之间的缝隙。这正是后面恢复、幂等和校验代码存在的原因。

## 用一组教学编号追踪完整交接

下面所有编号都是教学用的假设值，不对应线上或本地已有记录。假设用户创建了 task `101`，第一次执行的 attempt 数据库 ID 是 `501`，执行序号为 `1`，要采一个已授权 Python 目标十秒。

| 时刻 | 交接发生了什么                 | 需要留下的事实                          |
| ---- | ------------------------------ | --------------------------------------- |
| 提交 | Go 接收创建请求                | task、attempt、创建事件、审计、派发待办 |
| 排队 | 后台经 gRPC 请求 Core 接受任务 | 当前 attempt 的队列状态与上传授权       |
| 领取 | Agent 心跳收到任务描述         | 已交付给哪个节点、当前执行身份          |
| 采集 | Agent 核对进程，运行 py-spy    | 真实目标、工具与有界执行结果            |
| 回传 | Agent 上传 RAW 并通知 Server   | 制品 key、大小、SHA、采集完成事件       |
| 分析 | Analyzer 领取 job 并处理 RAW   | 租约、分析状态、结果与版本              |
| 展示 | 页面读取结果和事件             | 用户当前权限范围内的持久记录            |

比如 RAW 对象 key 可以是 `raw/tasks/101/attempts/1/python.folded`。其中 `1` 是任务内的执行序号，并不是数据库 ID `501`。只记住“都是 attempt 数字”很容易串错，读代码时要核对字段含义。

创建请求很快返回，也不表示采集已经完成。它承诺平台已经接住这项工作；后续推进由后台、节点和分析进程分别完成。浏览器等待的是同一条业务记录持续出现的新事实。

## task、attempt、artifact 和 run 分别记什么

task 记录用户这项采集请求，包括类型、权限、参数和当前状态。attempt 记录其中一轮实际执行。同一个 task 可以在失败后重试，产生新的 attempt；旧执行的文件和事件仍留在历史里，不能清空后假装从没发生。

artifact 是文件的登记记录，包含所属 task/attempt、角色、对象 key、大小、SHA 和格式等信息。RAW 是一种角色，RESULT、MANIFEST、LOG、BINARY 也各有用途。下载地址只是短期访问方式，不是制品身份；URL 变了，不代表文件换了。

analysis job 记录处理 RAW 的后台工作。分析还可能重试或重新分析，因此还会遇到分析执行和归档 run。它和采集 attempt 不是一回事：重新采样获得新的现场数据，重新分析则可以继续处理已有 RAW。仓库的 `analysis_job_runs` 用于保存分析重跑历史，具体版本与编号要看当前迁移和实现。

以后还会遇到诊断 run、综合任务 run 和源码修复运行。`run` 是常见词，单独一个数字不够用。记录证据时写出“任务 101、采集第 1 轮、某次分析/诊断”，并标明版本，才能回答报告究竟依赖哪份输入。

## 一条任务为什么要有两条状态

采集与分析可以独立失败，所以 task 有 `collection_status` 和 `analysis_status`。正常路径可以用下面的教学进度表理解；它说明可能的推进，不保证页面能抓住每个短暂状态。

| 采集状态  | 分析状态 | 可以怎样理解                     |
| --------- | -------- | -------------------------------- |
| CREATED   | PENDING  | 创建已落库，还未被 Core 接受排队 |
| QUEUED    | PENDING  | 等待节点领取                     |
| DELIVERED | PENDING  | 已交付给 Agent                   |
| RUNNING   | PENDING  | 正在采集                         |
| UPLOADING | PENDING  | 正在回传制品                     |
| COLLECTED | PENDING  | RAW 已登记，等待分析             |
| COLLECTED | RUNNING  | 正在解析和生成结果               |
| COLLECTED | SUCCESS  | 分析结果已发布                   |

这些名字来自数据库契约。`db/migrations/001_initial.sql` 对采集状态作了实际约束：

```sql
CHECK(collection_status IN ('CREATED','QUEUED','DELIVERED',
  'RUNNING','UPLOADING','COLLECTED','FAILED','CANCELED'))
```

`CHECK` 能拒绝拼错的值，却不能独自挡住旧执行覆盖新执行。合法推进还要结合当前 attempt、事务与写入条件。分析 job 表自己的状态使用小写 `pending/running/retry/success/failed`，与 task 上的大写状态属于不同字段，读日志时先认清对象。

## 三种失败，三条不同的排查路

第一种，task 一直停在 `CREATED`。可能是派发待办尚未成功处理，也可能是控制通信不可用。此时还没有证据说明目标进程采样失败，先检查 Outbox 到 Core 的交接。反复在页面新建任务只会增加相同待办。

第二种，采集到 `UPLOADING` 后断网。工具可能已经完成，RAW 仍在 Agent 的有界恢复目录中。恢复应优先继续上传或确认已有结果。重新采十秒会改变测量窗口，不能当作原来那次工作的补交。

第三种，`COLLECTED/FAILED`。数据采到了，但分析失败，可能与格式、完整性、解析预算或发布有关。应该先看分析错误和 RAW 是否可读，再决定重分析还是补采。把采集和分析压成一个“失败”字样，会失去这种排查方向。

还有竞争场景：用户取消后，旧执行才带着成功回来；用户重试后，旧 attempt 才恢复上传。它们都要在写入时确认资格。网络消息会迟到，进程会重启，系统需要把这些情况当作正常输入来设计。

## 它和普通 CRUD 项目差在哪儿

如果你写过用户管理、文章管理或库存列表，熟悉的模式是“校验请求，改一行数据库，返回结果”。这些经验仍然适用：身份、授权、分页、表单和事务，Drop 一样需要。新增的难点在于，一项业务动作跨过多个进程和时间窗口。

| 常见操作     | Drop 里需要继续回答的问题                  |
| ------------ | ------------------------------------------ |
| 新建一行任务 | 任务落库以后，派发进程崩溃会不会丢单？     |
| 更新状态     | 谁正在执行，消息属于哪一轮，迁移是否合法？ |
| 删除或取消   | 远端工具还在运行，晚到结果是否还能发布？   |
| 保存文件地址 | 下载字节是否匹配登记的大小和 SHA？         |
| 返回一份报告 | 输入版本、分析版本和证据引用能否追溯？     |

因此，学这个项目不应只背接口清单。更有用的练习是给每次交接加一句“如果此刻断开会怎样”。普通本地事务覆盖不了整个网络链，工程会通过持久待办、幂等、租约和栅栏，把大问题拆成可恢复的小阶段。

## 两个 Agent 和一个 Analyzer

C++ 采集 Agent 驻留在节点，围绕确定的任务执行工具；Python Analyzer 围绕确定的输入格式计算结果；AgentScope 智能体读取受限证据，提出工具调用并继续调查。三者不能因名字接近而混成一个“大模型后台”。

比如把 folded 解析成树，是明确的计算工作；追问“热点是否来自重复计算”，可能需要智能体读取调用路径、质量摘要或源码。模型提出动作后，Go 仍检查工具白名单、参数、权限、阶段和预算。报告引用合法，也只表示引用通过检查，不自动保证因果解释正确。

源码入口分别是 `core/src/agent.cpp`、`analyzer/drop_analyzer/worker.py` 和 `agent_runtime/drop_agent_runtime/runner.py`。前端的 React 则负责呈现，它与模型的 ReAct 循环只是名字相近：ReAct 指读取观察、选择行动、取得新观察的过程。

第一遍学习先走普通采集，等到 [第 8 章](/book/chapter8/) 再接模型。这样可以清楚地区分“采集和分析链没有接通”，还是“已有证据不足或模型解释有误”。

## 带着三个检查点进入下一章

现在做一个纸面练习：画出联系人服务的调查链，给每一段写上输入和输出；再把“RAW 上传完成、Server 回应丢失”的故障放到图上，圈出应该保留什么记录。这个练习不需要运行环境，也不会创建任务。

读完时应能回答三个问题。**第一，CPU 高能直接说明某个 Python 函数是根因吗？** 不能；先确认目标和窗口，再用适合的采样取得路径，结合代码和对照验证解释。**第二，COLLECTED 是否代表分析成功？** 不代表；还需看分析轴及对应结果。**第三，重采和重分析是否可以混用？** 不可以；它们会改变不同层的输入与执行身份。

你的学习记录可以从四句话开始：我观察到了什么；这份数据怎样得到；目前能支持什么判断；下一步怎样检验。等环境跑起来，再给这四句话加上自己的 task ID、attempt 和制品记录。
