## 这次要保存的，不只是一个返回值

采集器和分析器能独立运行以后，下一步通常是加一个 HTTP 接口：收到 iterations，运行程序，把 JSON 返回浏览器。这样很快能做演示，但关闭页面、重复提交或重启进程以后，用户就不知道上一项工作到底有没有发生。

本章使用 `tutorials/mini-drop/control`，只依赖 Go 标准库。它把一次操作变成有身份、有状态、有事件的任务，HTTP 只负责提出请求和读取事实，worker 负责后台工作。你可以不启动正式 Drop，直接阅读、测试并运行这个模块。

我们保留四个状态：QUEUED、RUNNING、SUCCESS、FAILED。这样已经足以练习提交、执行、终态和重试。正式工程的采集/分析双状态、授权、Outbox 和租约后面再比较；课程不会把文件 journal 包装成 PostgreSQL，也不会声称一个 mutex 可以协调多台机器。

完成这一章时，应能指着一次 POST 说清：哪些检查发生在持久化前，哪些事实必须一起出现，什么时候才允许启动程序，以及响应丢失后拿什么找到同一项工作。这比记住 Gin、GORM 等库名更接近后端编排的实质。

## 先从 main 固定运行位置和工具

`main.go` 接受 listen、collector、python、analyzer、workdir 五类 flags。后四项要求实际的本机绝对路径，监听只接受数字回环地址。启动时先检查程序文件，再打开 journal、进行恢复，最后监听 HTTP 并启动单 worker。

顺序有意义。journal 无法安全读取时应该拒绝启动，而不是当作空环境另建一套编号；端口被占用时应该明确退出，而不是假装在另一个地方提供服务。文件已有但内容损坏，也不是“没有任务”，把两者混同会让历史任务失去身份。

工具路径只从启动参数读取，API 没有这些字段。浏览器即便手工构造请求，也不能换成另一个 Python 文件。参考把“谁启动这个本地服务”作为信任前提，HTTP 请求只使用被授予的有限能力；这和开放一个通用命令执行接口有明显的工程差别。

HTTP server 还设置请求头、读取、写入、空闲超时和头大小上限。它们约束连接资源，不会代替任务执行预算。任务早已交给后台时，浏览器连接结束不应把任务记录删掉。停止整个服务，则由进程 context 通知 worker 与子进程收尾。

## 路由分派之后，还有 Host 与 Origin

`server.go:ServeHTTP` 先检查 Host 是否为带合法端口的回环 IP，再检查 Origin。这样，即使服务只监听本机，也不会把任意 DNS 名称直接当成可信同源。带 Origin 的请求只允许同源及课程使用的两个明确本地地址；无 Origin 的本机 CLI 可以访问。

这不是完整账号授权。它只限制这份本地练习被哪些浏览器页面使用，没有用户、资源组或逐任务访问控制。一个能在同机发请求的程序仍属于当前信任范围。参考适合私有学习，不应把这些条件替换成正式工程的用户权限模型。

随后才分派四类动作：列任务、创建、详情、重试。路径中的 ID 必须是规范的正整数字符串，不能带任意目录片段。HTTP 的 `/tasks/1` 是资源标识，不是让用户选择宿主文件路径。逐轮目录由服务器根据验证后的身份生成。

浏览器通过 [Mini Drop 工作台](/book/workbench)连接本地服务时使用代理，后端不用开放带凭据的跨域读取。遇到 Origin 拒绝，先核对页面地址和代理配置，不要为了省事把允许来源改成星号。拒绝信息本身说明哪一道边界尚未对齐。

## readBody 同时限制大小与结构

创建正文只允许 iterations。`readBody` 检查 Content-Type，再用 MaxBytesReader 把正文限制为一 KiB，读取以后要求顶层对象。过大输入在解析前就停止，避免先把任意大小文本全部放进内存，再“检查一下长度”。

接着 `strictJSON` 做两遍工作。第一遍走 token，限制嵌套深度并拒绝重复键和尾随内容；第二遍用 DisallowUnknownFields 解码到目标结构。只用后者能拒绝陌生字段，但 Go 标准解码对重复键有自己的覆盖行为，因此参考把歧义单独挡住。

例如下面四项都不应创建任务：iterations 是字符串、出现两次、额外提供 command，以及一个合法对象后再附一个对象。它们代表四种不同错误，而不是同一类“坏 JSON”样例。把范围内整数改成很大的合法整数，则应在业务范围检查处被拒绝。

严格输入的意义是避免隐含能力和隐含解释。用户说了一件程序不认识的事，明确拒绝比忽略后继续执行更容易调查。前端可以提前反馈，但服务端必须独立拥有这些检查，因为终端、测试和其他客户端不经过页面表单。

## 幂等键表示同一个意图，请求参数限制这个意图

创建请求需要八到一百二十八个不含空格的 ASCII 字符（码点 33–126）作为 Idempotency-Key。store 保存键对应的动作、task ID 和 iterations。相同创建键、相同参数返回已有 task；同键换参数或换成另一个动作，返回冲突，不新增工作。

参考输入只有一个整数，所以比较规范化后的 iterations 已足够表达创建内容。正式 `api/internal/service/tasks.go` 对更丰富的规范化请求计算摘要，两者是在不同输入规模下实现同一个目标：不能用同一个意图编号偷换要做的事。

网络重发保留原键，主动新增采集使用新键，主动重试某任务也使用新键。重试请求本身若响应丢失，再发仍保留那次 retry 的键。不要用“所有重试都换键”或“所有重试都同键”来记忆，先区分是重传同一个 HTTP 意图，还是明确建立新的执行轮次。

重放返回当前业务任务，不会复制历史轮次的快照。假设任务后来已经进入第三轮，最初创建键仍然指向同一个 task，返回的是当前任务视图。它保证不再创建一项工作，不保证把时间倒回第一次响应；这种接口语义应写清楚，避免客户端把重放当作历史查询。

## 持久事实先出现，队列通知才有意义

`store.go:create` 在 mutex 内检查幂等键、容量和队列空间，构造第一轮 task，追加 TASK_QUEUED，并把键写入同一份新 journal。提交成功后，才向容量一百的 channel 发送任务 ID 与 attempt。

如果先入队再保存，worker 可能已经开始计算，磁盘里却没有这项工作。若保存以后、发送 channel 之前进程退出，journal 仍有 QUEUED，重启可以重新入队。channel 是当前进程的提醒，journal 才是跨重启的事实。这个区分会帮助你理解正式 Outbox。

mutex 让本进程内多个 HTTP 请求按顺序检查状态。它还协调队列容量判断和提交，避免两个请求同时以为最后一个位置仍空闲。worker 可以取走队列项，但它推进状态也需要经过 store。不要把这种局部协调描述成跨进程锁。

容量达到上限时，参考返回明确错误。没有把任务放进持久队列却返回“已接收”，只会让用户永久等待。这里还有任务总数、幂等键和 journal 大小上限；它不是无限历史平台，达到边界后应保留现有证据并选择新的私有实验环境，而不是静默删历史腾空间。

## commitLocked 为什么先改副本

一个容易写出来的错误实现是：先把 map 中状态改成 SUCCESS，再调用保存函数；如果磁盘失败，返回错误，但下一次 GET 已经能读到成功。HTTP 与文件各说各话，重启以后状态还可能倒退。

`commitLocked` 先序列化并复制当前 journal，在副本中调用变更函数。变更成功后再编码，检查字节上限，原子写到 journal.json；只有文件交接成功，才把内存引用切换到新快照。所有写入口都走这条路径，读请求获得的是已经发布的快照。

复制整份状态不是大系统的高效通用方案，但在最多一千项任务的教学参考里，能让提交边界直观可见。它把“准备修改”“尝试持久化”“发布新状态”三步分开，比在任意函数里直接改共享 map 容易审查。

原子写使用同目录临时文件、文件 sync、close 和 rename。它避免普通读取者看见半份 JSON，但没有承诺所有文件系统和断电条件的数据库级持久性。尤其缺少多进程协调、事务恢复日志和更完整的存储故障处理，不能因为函数名里有 atomic 就省略适用范围。

## 状态和事件为什么放在一个提交里

task 含 ID、attempt、iterations、状态、UTC 时间、可选结果/错误和事件数组。`addEvent` 同时更新时间和追加带 attempt 的事件；begin、finish、retry、恢复都在各自 journal 变更中调用它。成功发布以后，状态和对应事件一起可见。

时间戳便于人阅读，但不用来裁决并发身份。两个操作可能在相近时刻发生，决定是否能写的是当前 attempt 和允许的状态。事件里的 attempt 让你知道“这次失败”属于哪一轮，不能只看一串 TASK_FAILED 就推断当前轮也失败了。

参考直接把有限历史放在 task 中，方便页面观察。正式工程将 task_events 单独持久化，事件有全局序号并支持 SSE 续读，更适合较长历史和多个读取者。参考没有伪造一个序号体系来假装兼容正式接口。

练习时找一次成功任务，列出 TASK_QUEUED、TASK_RUNNING 和 TASK_SUCCEEDED 三个事件，再看 retry 后新事件的 attempt。尝试用只读方式解释当前结果与历史，而不修改 journal 来凑状态。日志打印顺序可以帮助定位，却不能代替这一份持久提交记录。

## worker 每拿到一个身份，都重新确认资格

worker 从 channel 取 work，其中只有 ID 和 attempt，不保存可随意变化的整个 task 指针。它调用 `begin`，重新确认任务仍为同一轮 QUEUED，再持久化 RUNNING。只有这次提交成功，才进入 `runAttempt`。

为什么不在 HTTP 创建时检查一次就够？从入队到执行之间，程序可能重启，测试可能推演旧消息，未来功能也可能新增取消。执行边界自己核对身份，能让排队通知只是提示，而不是永久有效的执行许可证。

工具依次运行后，finish 又检查同一 ID、attempt 和 RUNNING。成功不是“子进程说完成了就覆盖状态”，而是“当前执行仍拥有发布权，且结果通过校验”。这道栅栏在单 worker 下也值得保留，因为重试和恢复已经引入跨时间轮次。

文件保存到 tasks/ID/attempt-N，每轮路径隔离。错误码只返回固定类别，不公开工具 argv、stderr 或宿主路径。读到 TOOL_FAILED 时，你需要在本地受控环境检查工具，而不是要求公共 API 返回整份内部异常来帮助调试。

## 退出码、SHA 和树关系，分别负责什么

`runner.go:execute` 用固定 argv 和十秒 context 调工具，并限制 stdout 与 stderr。正常退出只表示程序结束，没有证明它输出的 JSON 正确。Go 随后检查 RAW 的类型、范围、来源、单位与 iterations，原样保存，再调用 Python 隔离模式运行分析器。

分析结果回来以后，`validateResult` 将 input_sha256 与原始 RAW 的 SHA 比较，核对 summary 的来源、单位、计数与尺度，检查根/叶子的 value 和 self 关系，以及限制文本是否在范围内。它不是第二个自由解释器，而是当前小协议的验收器。

这三层不能混用。退出码不能代替数据校验；摘要不能证明原始对象选对了；计数关系一致也不能证明联系人接口根因。对每一项保护写出它能挡住的具体错误，才能避免把“我们校验了 SHA”夸大成“整个诊断可信”。

当 result.json 已生成而 finish 的 journal 写失败时，文件可以留在目录里，但 API 不发布 SUCCESS。下一次启动把原 RUNNING 明确结束为中断，保留证据供观察。文件存在与结果被当前任务接纳，是两种不同事实。

## 重启时，不把不确定状态当成没执行过

`newStore` 有界读取 journal，检查版本、任务身份与状态。`recover` 将 RUNNING 改为 FAILED，错误为 INTERRUPTED_RESTART，并追加中断事件；QUEUED 重新入队，终态保留。它不会看见一个旧文件夹就盲目调用 collector。

这样选择的理由是：QUEUED 持久记录还没有进入工具执行，重新排队能继续原意图；RUNNING 可能在任意工具阶段退出，我们不知道是否已经完成计算或分析。再采一遍会改变窗口，不能继续称为原来那一轮。参考宁可明确失败，让用户用新 attempt 重试。

重新入队的顺序没有实现完整持久优先队列，不要给它附加“重启后仍严格保持原队列先后”的承诺。正式 Drop 在数据库里保存调度事实、优先级、attempt 和 Outbox，可据此协调多个处理者；参考只保存最小恢复需求。

如果 journal 本身读不出来，则拒绝启动。若磁盘失败让 begin 无法提交，工具不应启动，任务保持持久 QUEUED，修复磁盘后重启再恢复。无法保存新事实时，不能靠继续执行制造更多无法解释的副作用。

## 用已有测试找到三个会失败的坏实现

进入 control，执行 `go test ./...`。这组标准库测试不连接正式数据库、不运行真实 collector，也不替代完整四语言演练。先看测试构造，再运行，分清它们验证哪一层。

`TestCreateReplayAndConflict` 检查相同键不新增任务与队列工作、换参数冲突。若坏实现只比较键而忽略内容，冲突用例会抓住；若每次重放又发一次 channel，相同任务数量可能仍为一，队列数量检查还能继续发现重复副作用。

`TestRestartFailsRunningAndRequeuesQueued` 把一项任务推进 RUNNING，再留另一项 QUEUED，重新打开 store。它要求前者明确失败、后者重新排队，防止“所有未成功项都重采”的简化。`TestOldAttemptCannotPublishAfterRetry` 则让旧轮终态后新增第二轮，再尝试旧 finish，检查它不能覆盖当前状态。

最后看 `TestResultHashAndUnitsMustMatch`。合法样例之后分别改坏摘要和单位，验证正常树并不能掩盖来源错误。这个顺序比只有若干合法样例更有用：测试必须有能力抓住你担心的坏实现，才值得在改动后依赖它。

## 真正制造一次保存失败，检查内存是否先说了谎

只读 commitLocked 容易让人觉得顺序显然正确。现在看 `server_test.go:TestFailedJournalWriteCannotPublishMemoryOrQueue`，它故意让最终文件名无法被替换，再检查创建没有泄漏到内存、幂等键、ID 和队列。这个负例验证的，是磁盘提交前后那一道真实边界。

测试创建自己的临时 store，随后在 journal.json 这个最终文件位置创建一个目录。新的临时文件可以正常写入和 sync，但 rename 到已有目录应失败。这样不依赖 Unix chmod 是否有效，也不需要真的填满磁盘；Windows 与 Linux 都可以在隔离目录中复现。测试没有移动现有 journal，更不会触碰你的学习服务或正式数据。

错误返回以后，断言任务列表仍为空、channel 仍为空、键表仍为空、NextID 仍为初始值。为什么连 ID 都检查？因为某些实现会先增加编号，再尝试保存；虽然没有直接执行工具，下一次请求已经观察到未经提交的状态变化。这里希望整项创建在失败时都不发布，而不是只把最显眼的 task 删掉。

若把实现改成先修改共享 map，再保存文件，列表检查就能发现错误。若 map 回滚了却忘记撤销队列，队列检查还能继续发现；若只残留键记录，下一次同键重放可能找到不存在的 task。多个断言共同覆盖一次提交的不同可见面，而不是重复比较同一个布尔值。

这项测试可以从 control 模块运行以下选择器。它是供你执行的命令；实际通过情况记录在自己的运行结果中，不用因为教材提供命令就预写 PASS。

```sh
go test ./... -run TestFailedJournalWriteCannotPublishMemoryOrQueue -count=1 -v
```

测试覆盖普通文件交接失败，不覆盖断电、存储控制器谎报、网络文件系统或跨进程同时写入。rename 成功以后某种文件系统是否已保证所有元数据落盘，还需要不同层的设计和故障验证。把这个范围明确写出，才能既认可当前断言的价值，又不把它夸成数据库持久性证明。

通过 HTTP 调用同一创建入口时，未知的存储错误由 mutationResult 映射为 JOURNAL_UNAVAILABLE。客户端应保留原意图和键，先解决存储问题，再决定重发；服务端没有提交任务，也就不应假装返回一个正在运行的对象。错误码在这里帮助用户理解“暂时无法保存事实”，而不是“目标程序采样失败”。

还可以继续提出两个待实现的测试：旧终态更新时保存失败，原终态和原事件是否保持；retry 保存失败，轮次是否仍为旧值、旧结果是否仍可见。当前创建负例没有自动覆盖它们，应根据各入口实际经过的共同提交函数和差异分支判断是否需要增加。测试范围要从断言推出，不能因为函数名相同就把所有阶段都写成已实测。

这种练习也教你区分程序错误和存储故障：合法迭代数并不会修好不可写目录，换一个新键也不会增加磁盘空间。先找到失败发生的交接，再改变对应条件，避免用不断新增业务请求去试探一个已经明确的环境问题。

## 学生作业：把一项请求追到磁盘

按 README 启动服务，在工作台创建一项任务。记下请求、实际 ID、attempt、终态和事件；再打开对应逐轮目录，比较 RAW 与结果中的 SHA。不要把 journal 直接当数据库编辑器，也不要为了方便把它放进正式数据目录。

接着做三次 HTTP 对照：同键同参数、同键换参数、新键重试终态。应分别观察到重放、冲突、增加轮次。给每项写一句原因，并说明是否新增了文件、事件和队列工作。重试不是把旧目录清空，页面看到新结果时旧证据仍可复查。

纸面扩展题是“允许两个控制面进程同时处理同一 workdir”。答案不能只加 goroutine：至少需要跨进程协调、持久队列领取、执行租约、写入栅栏和原子提交。正式 PostgreSQL 事务与 Outbox 解决的正是这些交接中的一部分，而不是对文件 API 换个名字。

自测最后一问：worker 完成工具以后，为什么仍会收到 STALE_ATTEMPT？因为执行时间与发布时间之间，任务资格可能变化；结果好坏与有没有当前发布权属于两个判断。带着这个区别进入 [第 14 章：主动制造故障，再验证恢复](/book/chapter14/)，我们会把这些判断变成可重复的机制实验。
