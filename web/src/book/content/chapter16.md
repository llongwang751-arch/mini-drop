## 先把“占内存”拆成三个问题

联系人服务这次不是 CPU 升高，而是缓存越积越多。你打开一份堆快照，看见一个很小的 cache 对象和一大批数组。直接按对象自身大小排序，cache 很不起眼；把它能访问到的所有对象都相加，又可能把共享数组算到好几个容器头上。要看懂这种结果，必须先分开对象自己多大、从根还能到哪里、哪些内容只被某个对象留住。

本章前置条件是理解字典、集合和有向图，完成第 15 章的权重手算会更顺利。实际课程实现是 `tutorials/labs/analysis.py / heap_dominators`，回归在 `tutorials/labs/test_analysis.py`。这里用人造对象名和指定的载荷字节，不读真实 HPROF，也不采集 JVM；所有数字都是合成夹具，不能拿来证明业务泄漏。

我们会交出一套能运行的小图算法：从 GC roots 计算可达节点，迭代求支配集合，找直接支配节点，再算 retained。先把算法限制在最多三十二个对象、一百二十八条强引用边的小图，目标是每一步都能复核，而不是声称能用几行集合代码分析任意大的生产堆。

最后再回到 `analyzer/drop_analyzer/hprof.py / analyze_hprof`。生产实现还要解码 HPROF、恢复索引、处理引用类型、控制算法成本，并解释大小口径。纸面小图与生产输入之间这些差别，正是“懂一个概念”与“能交付分析工具”之间的工程内容。

## 先定义对象，别急着定义泄漏

把每个对象看成一个带重量的点，把一个对象的强引用看成一条箭头。GC roots 表示本次快照中垃圾收集器认为仍被外部持有的入口；它们可能不止一个。我们额外加入一个不是真实对象的 `@root`，用零权重箭头连向所有入口，方便算法只处理一个起点。

shallow 是对象自身的大小口径，不沿箭头展开。可达表示从根沿强引用能走到；它回答对象是否仍被根保留，并不回答哪个容器独占它。retained 则与“必须经过谁”有关：如果从根到某对象的所有路径都经过 cache，那么去掉 cache 后，那部分对象会失去这些根路径，才可以纳入 cache 的保留关系。

这里用“去掉”帮助理解，不是要求你真的在运行服务中删除对象测量回收量。真实语言运行时还有栈、原生引用、并发变化和快照口径。我们计算的是这份已建成的强引用图里的关系，不是对下一次 GC 或操作系统 RSS 作预测。

因此“大 retained”首先是一个值得调查的保留候选。缓存按设计保留大量数据，可能完全正常；本应随请求结束释放的对象持续保留，才值得追查生命周期。泄漏判断至少需要预期生命周期、跨时间变化与负载背景，单张图中的一个大数不具备这些信息。

## 把完整合成图摆在桌上

课程 case 使用下面这组对象。数字表示指定的载荷字节，既不包含 VM 对象头，也不是一次真实测量：

```python
objects = {
    "cache": 8, "other": 8, "shared": 40, "owned": 24,
    "cycle_a": 4, "cycle_b": 4, "orphan": 16,
}
edges = {
    "cache": ["shared", "owned"],
    "other": ["shared"],
    "owned": ["cycle_a"],
    "cycle_a": ["cycle_b"],
    "cycle_b": ["cycle_a"],
}
roots = ["cache", "other"]
```

先画两条根路径。第一条经过 cache 到 shared，第二条经过 other 也到 shared。shared 被两个入口共同持有，所以不能把它的四十字节全部说成 cache 独占。另一路 cache→owned→cycle_a→cycle_b 则只有 cache 这个外部入口，尽管后两个对象彼此成环。

orphan 没有根路径。它可能代表快照中不可达的对象，但本课只把它作为算法反例，不推断真实 JVM 为什么还在文件里记录它。所有对象 shallow 相加是一百零四，其中根可达部分是八十八，不可达部分十六。先把这三个数写下，后面每一步都可以对照。

这张图故意同时包含共享引用、独占子树、循环和不可达对象。只用一条单链做实验，几乎所有错误算法都可能碰巧算对；加入共享边以后，普通“递归加孩子大小”的做法就会暴露重复记账，加入循环以后，不带 visited 的遍历还会停不下来。

## 第一步：从根出发，只访问一次

可达性可以用队列完成。先把虚拟根放进队列，取出一个节点，把尚未访问过的后继放入队列；visited 在入队时就更新。这样 cycle_a 再次遇到 cycle_b、cycle_b 回到 cycle_a 时，都不会重复入队，算法会在有限步内结束。

不要把“对象有引用者”当作“对象可达”。两个不连到任何 GC root 的对象可以互相引用，却仍然不可达。课程回归里专门有一个没有根入口的二节点环：只有 rooted 在根列表里，a 与 b 互相引用，结果必须把 a、b 都放进 unreachable。

执行完遍历，课程图可达对象是 cache、other、owned、shared、cycle_a 和 cycle_b；orphan 留在集合外。支配算法只讨论可达部分，否则一个没有任何根路径的对象会让“所有路径都经过谁”变成没有意义的空话。先解决图的边界，再讨论保留关系，是算法前提。

实际输入还要检查悬空引用。教学函数拒绝指向 missing 的边，因为这组夹具声称已经是一张完整对象图。生产 HPROF 的建图规则则要按格式处理记录、引用和不在已解析对象集中的目标，不能把课程的简单规则未经讨论直接搬过去。两者都需要明确规则，但规则来源不同。

## 第二步：什么叫“所有路径都经过它”

如果每一条从根到 x 的路径都经过 d，就说 d 支配 x。每个节点都支配自己，虚拟根支配所有可达节点。cache 支配 owned、cycle_a 和 cycle_b，却不支配 shared，因为 other 提供了绕过 cache 的根路径。这是比“cache 能到达 shared”更严格的关系。

可以拿删除反例检验这个概念：暂时遮住 cache，shared 是否仍能通过 other 到达？可以，所以 cache 不支配 shared。遮住 owned，cycle_a 是否还有不经过 owned 的根入口？没有，所以 owned 支配它。不要被图上的箭头数量迷惑，支配关系问的是整条根路径。

对于一个节点，它必须经过的节点也必须出现在所有前驱的必经集合里。于是得到迭代关系：本节点的支配集合，等于所有前驱支配集合的交集，再加它自己。多个前驱用交集而不是并集，这一点决定共享对象能否被正确处理。

若误用并集，shared 会把 cache 与 other 都认成必经节点，相当于说“走任意一条路遇到谁，谁就支配它”。这与定义相反。稍后的负向实验只删掉一条共享边，就能让两个方案产生不同结论；测试应检查这种结构差异，而不是只检查程序返回了一个整数。

## 第三个完整函数：迭代到支配集合稳定

下面是可执行的算法核心，适合只含本章小图的临时练习。它接收已验证的完整图，graph 包含 `@root`，reachable 包含虚拟根；外部输入的结构与规模限制由课程模块完整处理。这是教学的集合算法，不是生产 HPROF 的直接支配节点实现。

```python
def dominator_sets(graph, reachable):
    parents = {name: set() for name in reachable}
    for source in reachable:
        for target in graph[source]:
            if target in reachable:
                parents[target].add(source)

    dom = {name: set(reachable) for name in reachable}
    dom["@root"] = {"@root"}
    for _ in range(32):
        changed = False
        for name in sorted(reachable - {"@root"}):
            common = set.intersection(*(dom[p] for p in parents[name]))
            updated = {name} | common
            if updated != dom[name]:
                dom[name] = updated
                changed = True
        if not changed:
            return dom
    raise ValueError("DOMINATOR_LIMIT")
```

初始把普通节点的集合设为整个可达集合，看似很宽，实际是在不断去掉“不是必经”的候选。根固定为自己，不参与这种猜测。集合逐步缩小，直到一轮没有变化。课程实现保留三十二轮上限，不能把“理论上会收敛”作为接收无界输入时不设预算的理由。

手算 shared 的关键一步：cache 一侧最终只有根与 cache，other 一侧只有根与 other，交集只剩根，加上 shared 自己。因此 shared 的集合里没有 cache，也没有 other。owned 的前驱只有 cache，于是集合保留根、cache、owned；环内节点则在迭代中逐步消除错误候选，不需要递归沿环一直走。

## 直接支配节点，把必经关系整理成一棵树

一个节点可能被根、cache、owned 多个节点支配，但直接支配节点只取最近的那个。对 cycle_a 而言，根和 cache 都是必经点，owned 距离它更近；所以 idom(cycle_a)=owned。对 shared 而言，没有更近的独占入口，idom(shared)=@root。

课程算法从严格支配集合中选出那个被其余严格支配者支配的候选。换句话说，候选位于这些必经节点最靠近目标的一端。每个非根可达节点应有唯一直接支配者；无法得到唯一答案，说明图前提或算法关系出了问题，不能随便选名字最靠前的一个掩盖错误。

本图的预期关系是：cache 与 other 的 idom 都为 @root；owned 的 idom 为 cache；cycle_a 为 owned；cycle_b 为 cycle_a；shared 为 @root。把这些关系画出来会发现，原引用图有共享边和循环，支配关系却整理成了一棵树。两张图回答的问题不同，不能互相替换。

这也解释为什么结果叫 dominator tree，而不是“把原引用图去重以后随便画成树”。如果原图里的 shared 随机挂到 cache 下面，看起来也能形成树，却会误导用户认为 cache 独占四十字节。树形展示必须由支配关系推导，不能让布局算法替分析算法作决定。

## 沿支配关系累计 retained

现在为每个对象 d 累加它支配的所有可达对象 shallow。cache 包含自身八、owned 二十四、cycle_a 四、cycle_b 四，得到四十；shared 自己四十；other 自身八；虚拟根包含全部可达对象，得到八十八。orphan 不在这些累计里，不能因为存在于输入字典就自动进入根保留量。

owned 的 retained 是三十二，cycle_a 为八，cycle_b 为四。你会看到四十、三十二、八之间有包含关系，不能把这些 retained 再相加当作堆总量。那会把同一批循环节点反复计入祖先。课程 case 有一个负向检查：所有 retained 相加大于八十八，证明这种总和不能当作独立容量。

拿 cache 的 shallow=8、retained=40 对比，才看见这个小容器留住了多少下游内容。它不意味着删除 cache 就必然让操作系统 RSS 立即下降四十；这里没有模拟分配器、GC 时机或页回收，更没有包含真实 VM 对象头。解释时应把“图上的保留载荷”与“机器内存减少”分开。

生产算法通常沿支配树由叶到根累计，避免对每个 owner 重复扫描所有对象。课程模块为了让公式直观，直接用支配集合判断每个目标属于谁，适合小图；输入上限就是这种选择的配套条件。不能把教学代码移到大堆上，再把超时归咎于数据质量。

## 只改一条边，观察保留关系怎样变化

做真正有对照的实验：保留全部对象与权重，只删除 `other → shared`。根列表仍为 cache 与 other，shared 仍然可达，所有可达载荷仍是八十八。变化的是 shared 只能经过 cache 到达，于是 cache 的 retained 从四十变成八十。

这个结果很适合检查错误实现。若你删除边后根总量也减了四十，说明把引用边误当成对象副本；若 cache 原来就八十，说明没有处理共享引用；若删除以后 shared 反而不可达，说明遍历漏掉了 cache 那条路径。三个错误都可能打印合法 JSON，却表达不同的坏算法。

再做一项反事实：从 cache 删除 owned 边，保留 cycle_a 与 cycle_b 互相引用。它们不会因为成环就自动成为根可达，owned 与整个环都会失去根路径。这个实验帮助你区分“环使引用计数有困难”和“带 roots 的可达性算法会不会无限循环”，不能把两种垃圾收集概念混成一个口号。

学生修改时只在合成 fixture 副本中做，不要去真实服务删除缓存引用来“验证教程”。我们验证的是图算法对受控干预的响应。要谈业务泄漏，还要获取真实授权快照、固定输入背景、对比多个时刻，并确认保留关系对应实际生命周期。

## 写一个不用支配算法的独立答案

怎样知道集合算法算对了，而不是自己证明自己？对于这张很小的图，可以写一个更慢但直观的参考：先计算原始可达集合，再假想移除某个对象，重新从根遍历；原来可达、移除后不可达的对象重量之和，就是这个对象在本图定义下的 retained。这个算法不读取 dominators，也不使用 idom，适合做独立对照。

下面函数使用前文的 objects、edges、roots，可直接放入同一个临时练习文件。它只用于已知的小图，规模由本课夹具控制，不提供生产级输入接口：

```python
def reachable_without(removed=None):
    seen = set()
    pending = list(roots)
    while pending:
        current = pending.pop()
        if current == removed or current in seen:
            continue
        seen.add(current)
        pending.extend(edges.get(current, []))
    return seen


before = reachable_without()
for owner in ("cache", "other", "shared", "owned"):
    lost = before - reachable_without(owner)
    print(owner, sum(objects[name] for name in lost))
```

预期标准输出依次为 `cache 40、other 8、shared 40、owned 32`，每项独占一行。这里是假想图删除，不会删除文件、JVM 对象或服务数据。与课程主算法的 retained 字段逐一比较，若某项不同，先画出移除后的剩余根路径，不要立刻修改期望去迁就实现。

注意参考算法也有前提：使用同一份强引用图、同一批根、同一种权重，且只比较原来可达的对象。若把 orphan 也算作“删除 cache 后不可达”，它原本就不可达，错误参考会多算十六。独立算法不等于天然正确，参考定义同样要经反例检查。

它比支配树累计慢得多，每个 owner 都重新遍历一次图；小样本可以接受，大堆不应该这样做。测试中的慢 oracle 与生产中的快算法可以承担不同角色：前者帮助确认语义，后者满足规模与资源要求。不要因为两个实现都叫 retained 就强迫它们使用同一套循环。

## 索引能恢复进度，不能替换快照身份

小图驻留内存，进程退出就丢失；真实 HPROF 解析可能耗时更长。生产用 SQLite 保存对象、引用和阶段元数据，处理到某些边界提交索引。恢复时不必把已经完整落盘的解析工作无条件再做一遍，但这不是允许任意文件继续使用同一个数据库。

输入摘要给索引绑定具体字节，索引 schema 版本绑定程序如何解释这些表。换输入仍复用旧对象 ID，会把两份快照拼成一个不存在的堆；换索引布局却继续按旧含义读列，也会生成貌似完整的坏图。因此先核对身份和版本，再依据实际实现拒绝或重建，不能把所有索引异常都吞掉继续输出。

即使有索引，后续支配计算仍会从表中构建内存对象图。不要把“使用 SQLite”宣传成“整个流程常数内存”或“可以分析任意大小堆”。对象、边、总工作量、子进程资源与临时磁盘都有上限，每层限制处理自己的消耗；索引改善可恢复性，不会取消这些规模前提。

设计恢复回归时也要区分位置：尚未完成对象记录解析、引用构建已提交、支配计算开始后被停止，留下的可重用状态不一样。测试应核对输入摘要、阶段与最终图是否一致，而不是只看第二次运行更快。速度可能来自系统缓存，不能单凭耗时变化证明真的恢复了正确阶段。

## 生产 HPROF 多出来的工作是什么

打开 `hprof.py / analyze_hprof`。它先验证并解析 HPROF 记录，把对象、字段布局、根与引用存入 SQLite 索引。索引按输入摘要绑定，并记录阶段完成情况；恢复时要确认还是同一份字节，不能用另一份快照接着旧索引往下算。这与我们的内存字典有相同身份需求，只是生产要把进度持久化。

建图还要理解强弱引用。实现不把 `java.lang.ref.Reference.referent` 当作强保留边，但对象的其他强字段仍参与图。这直接影响 retained，不能为了简单把每个地址字段都画成同等强度的箭头。数组、类布局、对象 ID 和字段载荷也都要按格式处理，不是从文本随便提取几个名字。

生产支配计算采用迭代 DFS 与直接支配节点算法，避免递归遍历栈溢出和平方级支配集合存储；同时限制对象、边、迭代与总工作量。课程集合算法让定义容易看见，生产算法让它在限定规模内可运行。理解两者的对应，比把某个算法缩写背下来更有用。

结果的 `sections.heap` 保留 size_basis、classes、dominators、leak_paths 与 limitations。权重使用 HPROF 字段和数组载荷，不含 VM 对象头、压缩引用差异和对齐；类间 retained 也不可直接相加。若页面把这个值简写成“真实 JVM 占用”，即使后端算法完全正确，结论仍然被最后的文案夸大了。
