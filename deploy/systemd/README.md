# Host Agent and maintenance timers

For an ordinary Ubuntu host, install `drop_agent`, `drop_collector_helper` and runtime libraries from the same release. Create a dedicated `drop` user and group with UID/GID 10001, then copy `agent.env.example` and `collector-helper.env.example` to separate files under `/etc/drop`, owned by root with mode 0640 and group drop. Set a stable Agent ID and configure only the business process UIDs this node may sample. Issue a unique client leaf certificate with CN `drop-agent-<AGENT_ID>`, verify the server's DNS name is in its certificate SAN, and give only the Agent service read access to that leaf key. Never copy the CA signing key or S3 access keys to this node.

Install `drop-helper-spool.service`, `drop-collector-helper.service` and `drop-agent.service` into `/etc/systemd/system`, and run `systemd-analyze verify` before enabling them. The Agent runs as UID/GID10001 with empty capability bounding and ambient sets. The separate root helper has PERFMON/SYS_PTRACE/DAC_READ_SEARCH/BPF and no TLS, database or object-storage credentials. DAC_READ_SEARCH is included to read a target UID's mode0600 RAW output; it does not grant write bypass. It remains a broad read capability within the helper's view, so target identity checks and its restricted filesystem view are still required. Reduce the helper's bounding set when BPF is unused. Its policy comes only from `collector-helper.env`, independently of the Agent's credential-bearing environment.

Prepare the dedicated host filesystem before starting either collection service; [HELPER_SPOOL.md](../HELPER_SPOOL.md) specifies the allowed paths and reuse checks. Production uses `/opt/drop-runtime/helper-spool`: a real 2GiB ext4 filesystem shared by private cache, target incoming files and scratch output, in addition to the helper's logical disk budget. This physical limit also bounds JVM/memray output written outside the helper's own child process. `COLLECTOR_HELPER_REQUIRE_BOUNDED_FS=true` must remain enabled. Both the runtime root and mounted filesystem root are root:drop mode0750; `cache` is root:root0700 and `incoming` is root:drop1770. The Agent and cooperative target must see the same absolute incoming path. Never mount the private cache into the Agent or make it group-writable.

Java attach and the native control adapter run cooperatively under the same UID as the ordinary, capability-free Agent. Their RAW task subdirectories stay on `incoming`; journal/state/LOG/MANIFEST remain in the Agent's private work directory. Java CPU explicitly uses async-profiler's ctimer engine and reports that limitation. The helper handles the collectors that actually need PERFMON, PTRACE or BPF. This does not grant the Agent permission to attach an arbitrary different-UID JVM.

Native gperftools/jemalloc applications must use the same release's schema2 adapter and a private control root on the bounded filesystem. The host example is `NATIVE_CONTROL_ROOT=/opt/drop-runtime/helper-spool/incoming/native-control`, UID10001/mode0700; Docker uses `/run/drop-helper-incoming/native-control`. Both Agent and adapter verify the filesystem, including intermediate profiler scratch files. The Agent creates only the permitted direct child safely; incorrect existing ownership/mode or a symlink fails closed. Do not retain the old `/run/drop-profilers` or `/tmp` scratch configuration, and do not treat a legacy adapter's response as quota enforcement.

For ordinary host deployment, enable/start in dependency order: spool, helper, then Agent. The helper unit requires the spool unit; the Agent starts after and wants the helper. The socket is root:drop mode0660 inside root:drop mode0750. IPC accepts typed collection/cancel operations, never arbitrary argv, paths, upload URLs or environment. Process identity checks pin start time, UID and PID namespace before and during collection. Acknowledged files are removed after the Agent fsyncs its recoverable copy; interrupted transfers have bounded retention. Analyzer download/temp limits are independent, so a collector accepting a RAW does not promise the small-host Analyzer will accept its size. Check current TaskKind and job budgets before a large heap collection. Java/Python attach still needs the target runtime's attach support; Go needs an explicitly enabled pprof listener; gperftools/jemalloc needs the native control integration.

For the Docker profile in `compose.helper.yml`, prepare the host filesystem first and set `DROP_HELPER_SPOOL_ROOT=/opt/drop-runtime/helper-spool` (staging: `/opt/drop-stage-full/runtime/helper-spool`). Its `helper_data` and `helper_incoming` named volumes bind `cache` and `incoming` separately on that same filesystem. Retain the existing deployment's complete Compose file list and append the helper overlay after its tools/perf overlays. Start the Agent container first, then the collector helper: the helper joins the running Agent's PID and network namespaces through `pid: service:agent` and `network_mode: service:agent`. The Agent has no dependency on the helper, avoiding a startup cycle; it can retry IPC until the socket is ready. The permission-init service only fixes the Agent's own persistent directory. This container setup does not use host PID/network namespaces or a Docker socket. Only the helper receives the optional BPF capability and read-only tracefs overlay.

Before changing the spool mount, quiesce collection, stop the helper and Agent, then prepare/verify the mount before restarting consumers. Do not unmount a filesystem while containers or host collectors use it. On Docker Agent restart/recreation, also recreate the helper **after** the Agent is running so it joins the new namespaces; Compose's `service_started` dependency alone does not repair an already-running helper's namespace references. Ordinary host services use the host namespaces and restart spool/helper/Agent in their dependency order. A failed spool preparation leaves completed image/metadata in place for review and retry; stopping the oneshot service does not unmount or delete anything. Docker itself does not require that unit, allowing the API/database control plane to start and report collection unavailability.

These instructions describe configuration and ordering, not a completed Linux mount, ENOSPC, systemd boot or production deployment acceptance. The 16 local spool regressions use fake commands and tiny temporary files; consult the current delivery matrix for separately recorded runtime evidence.

Container PID/mount/network namespace entry additionally needs an authorized runtime resolver and namespace permission. Configure `ALLOW_CONTAINERS` and the runtime executable only on approved collection nodes; a Docker socket grants daemon control even when the socket is mounted read-only. eBPF collectors need CAP_BPF/PERFMON, a supporting kernel/tracepoints and access to their trace filesystem. Supply those in a separate node policy and verify actual capability probes. Do not grant SYS_ADMIN or disable host-wide kernel controls to make a capability badge green.

The `core` full-tools image provides pinned profiler tools, real versions and executable hashes. It can also be used as a build/export source for a managed host package. Tool-specific `*_EXECUTABLE` / `*_SHA256` names are recorded in `contracts/task-kinds.json`.

After release deployment, install `drop-backup.*` and `drop-public-tls.*` and enable their timers. `backup-offsite.sh` uses an optional root-owned 0600 environment file and an existing protected rclone config. Without an independent destination, only the local backup is recorded as verified. Short-lived IP certificates require six-hour renewal checks and a successful external HTTPS probe; see the [official Certbot IP certificate instructions](https://letsencrypt.org/2026/03/11/shorter-certs-certbot).
