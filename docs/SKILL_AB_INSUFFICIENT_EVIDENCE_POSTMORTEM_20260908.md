# Skill A/B “证据不足”复盘（2026-09-08）

## 结论

截图中的两条诊断不是“刚创建就直接判证据不足”。它们都真实执行了 4 轮，分别持续约 163 秒和 184 秒。页面原来展示的“42/63 秒出现首条任意证据”只表示第一份材料通过或拒绝门禁的时间，不是总探索耗时，也不表示已经出现了支持根因的证据。

这组旧 Go pprof 采样只有 3 个有效样本，且集中在 `runtime.schedule`、`park_m` 等运行时空闲路径，没有捕获应用热点。其余系统、perf、持续采样和 eBPF 结果主要是 `NEUTRAL`、`ACCEPT_LIMITED` 或反证，没有一条满足“可支撑根因”的条件。因此最终保持 `INSUFFICIENT_EVIDENCE` 是正确的安全行为，不能为了 A/B 页面好看而强行生成根因。

## 为什么看起来像“没有探索”

原页面有两个表达问题：

1. 用“出现首条任意 Evidence 的时间”当作速度参考。`NEUTRAL`、`REJECT` 和 `ACCEPT_LIMITED` 也会被计入，所以它不能回答“多久找到支持证据”。
2. 页面按创建时间取最后一份 Report。多分支诊断中，后创建的证据不足报告可能遮住前面已经形成的可信报告。

页面现已改为分别展示：

- 首份门禁结果时间；
- 首条支持证据时间；
- 总探索耗时；
- 诊断轮次和工具路线；
- 按 `VERIFIED > PARTIAL_WITHOUT_COUNTER > INSUFFICIENT` 选择最佳报告，而不是盲取最后一份报告。

## 排查中发现并修复的系统问题

### 1. 陈旧诊断抢占新故障窗口

Worker 重启后曾恢复多条前几天遗留的非终态会话。旧会话继续向同一个 Agent 创建任务，导致新任务在 `PENDING` 中等待数分钟，真正采集时故障可能已经结束。

修复后，AUTONOMOUS 会话同时受两类预算约束：

- 工具调用和采集时长预算；
- 从 Diagnosis 创建时刻开始计算的端到端墙钟预算。

超过墙钟预算后，会话、未完成 Tool Call 和 Task 会转为 `CANCELLED`，写入 `diagnosis.expired` 事件，并保留审计记录。Worker 也不会再推进已终态会话。云端修复后，演示 Agent 的遗留活动任务从 12 条降为 0 条。

### 2. Java 方法名被误识别为服务名

Java 文件 I/O 问题中，范围解析器曾把 `FileChannel.force` 当成服务过滤条件，导致进程发现持续返回 `EMPTY`。现在：

- “进程名为 java”优先按进程快照绑定；
- 只有显式的“服务名为 X”或“X 服务”才产生服务过滤；
- 任意带点的方法名不再自动当作服务名。

### 3. 故障持续时间短于诊断超时

旧全量脚本允许故障只维持 100 秒、诊断却等待 900 秒，后几轮可能采到恢复数据。故障实验室单次安全上限是 300 秒，因此新脚本把有效诊断超时限制为 270 秒，故障死开关设为 300 秒，并始终在 `finally` 中主动停止。请求值和实际值都会写入报告，避免口径隐藏。

### 4. 长 Campaign 断线丢失报告

全量脚本现在每完成一个场景就原子写入 `RUNNING` 检查点，最终再覆盖为 `COMPLETED` 报告。SSH 断线不会再丢失已经完成的场景结果。

### 5. 反证文字误分类与工具/假设错配

`source-hotspot` 的诊断文本在同一句中同时写了“定位源码级热点函数”和“排除 I/O”。旧路由器只按整句关键词匹配，并且 I/O 分支优先，因此把“排除 I/O”误当成主故障方向。随后 LATS 回看一个尚未访问的 I/O 兄弟假设时，该假设原有的 eBPF 探针已经执行过，旧实现又把本轮剩余的 `py-spy` 强行替换上去。最终出现了一个很隐蔽但可复现的错误：`py-spy` 采到 4,449 个有效样本并定位到源码函数，却被用于验证“同步写盘路径过重”，所以只能得到中性证据。

修复分为两层：

- 分类只读取正向症状子句，显式忽略“排除、反证、不能单独解释”等对照子句；
- 持久化假设保留创建时的 `recommended_tool`，该工具已执行或当前不可用时，假设本轮不可执行，不能偷偷换成另一个证据域的采集器。

这不是降低证据阈值。它修的是“本轮到底在验证什么”，保证工具结果只与对应假设比较。

1. C++ perf 已采到 943 个样本，`cpp_cpu_hot_function` 约占 99.8%，但 TopN 是包含样本语义，同一条热调用栈中的多个父子帧都接近 100%。旧谓词把它们当成多个独立热点，并在“热点函数或系统调用”这个析取假设上错误地产生反证。修复后 Analyzer 将调用图的 `self_samples/self_percent` 合入证据元数据，谓词用叶子自采样判定 CPU 实际落点。

## 面试回答口径

可以这样回答：

> 证据不足不是超时的同义词，也不是为了兜底随便返回。系统会真实执行多轮工具调用，但只有目标、时间窗、完整性、分析质量和假设关联都通过门禁的材料才能支撑根因。我们复盘时发现页面把“首份任意门禁结果”误写成速度，又发现 Worker 会恢复陈旧会话造成新任务排队，因此补了支持证据时间、总探索耗时、最佳报告选择和诊断级墙钟截止。修复后用真实 Java 文件 I/O 故障重新跑通了 4 次工具调用、3 轮报告、eBPF SUPPORT Evidence 和清理闭环。

不能说“遇到证据不足就降低阈值”。阈值降低会把低样本、错时间窗或错目标的材料包装成根因，破坏整个 Evidence 可信链。
