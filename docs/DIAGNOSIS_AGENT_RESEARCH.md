# 性能诊断 Agent：公开方案调研与 Drop 设计取舍

日期：2026-10-20。依据用户提供的导师原文及测试开发 JD，AI 编排由本仓库独立实现。导师文档说明基础采集/分析链路和建议接口，不能据此声称存在可直接复刻的腾讯内部智能诊断 Agent。

## 查到的可借鉴方案

| 一手来源 | 实际定位 | 借鉴点与限制 |
| --- | --- | --- |
| [Grafana mcp-grafana](https://github.com/grafana/mcp-grafana) | 开源可观测性工具服务器，含 Pyroscope 查询及 RBAC/只读模式 | 借鉴查询权限和写操作隔离。MCP 是工具接口，不等于诊断决策和性能正确性；本次不直接引入整个 Grafana MCP |
| [Polar Signals sandwich 工具](https://www.polarsignals.com/blog/posts/2026/06/30/iteratively-explore-your-flame-graphs-with-the-mcp-sandwich-tool) | 商业持续 profiling 产品的官方技术说明 | 从热点表逐步展开调用者/被调用者，避免把整张火焰树塞给模型。借鉴交互和有界工具设计；不称其商业实现已开源 |
| [PerfAdvisor](https://github.com/leonhostetler/PerfAdvisor) | 面向 GPU/HPC profile 的开源诊断原型，MIT | 借鉴“确定性指标提取 → 工具补查 → 结构化假设”。作者明确说明分析未充分验证；不能直接套用 GPU 指标、任意 SQL 工具或其收益估计 |
| [PerfLab PerfAgent](https://github.com/PerfLab-io/perfagent) | Apache-2.0 Web trace 分析项目，围绕浏览器性能与交互 | 借鉴 trace、工具与报告的交互组织；其 Chrome trace/Core Web Vitals 与当前 Linux 服务端采集边界不同 |
| [PerfAgent 论文](https://arxiv.org/abs/2607.19653) | 2026-07 profiler 引导代码优化研究 | 借鉴性能反馈与行为正确性验证共同约束迭代。论文结果属于其 benchmark，不作为 Drop 的准确率、收益或上线证据 |

另需区别：名称含 agent 的 [dpsoft/perf-agent](https://github.com/dpsoft/perf-agent) 是 eBPF 采样器，[AgentSight](https://github.com/eunomia-bpf/agentsight) 主要观测 AI Agent 自身；二者不能直接等同于“让模型定位业务性能问题”的诊断 Agent。本次不替换已验收的 C++ 采样链路，也不照搬其他项目的高权限部署方式。

以上为设计模式参考，没有复制第三方实现代码、执行其安装脚本或把其 benchmark 数字写成项目指标。

## 选定方案

采用 Go 内置的有界工具调用循环，复用现有鉴权、PostgreSQL、任务状态与事件。DeepSeek 负责选择工具和组织假设；确定性程序负责读取数据、计算和验证。Python Analyzer 保持测量和解析职责，C++ Agent 保持受控执行职责，React 呈现证据和人机确认。

当前任务只需要少量工具和明确状态，不额外引入 LangGraph/Mastra 服务及第二套持久化。工具定义与执行器分离，未来需要给外部 IDE 使用时可以增加经过相同鉴权的 MCP 适配层；目前没有把未实现的 MCP 服务当作已交付能力。

实际执行链：

    授权完整结果 + 用户问题
      → 固定任务/采集attempt/分析job及run/输入哈希
      → 本地统计摘要（包含明确单位与栈类型）
      → DeepSeek选择受控只读工具
      → 校验工具、参数、预算、授权与版本
      → 持久化工具观测 → 模型继续判断
      → 校验JSON、真实证据编号、必要工具
      → 待验证假设 + 证据 + 缺失测量 + 复测草案
      → 用户独立确认复测 → 原采集/Analyzer链路
      → 对比结果页 → 针对新结果再诊断

诊断 success 只表示报告成功生成，不表示根因已经证实、修复已经成功或优化收益已经验收。复测与报告任务状态独立。

## 已落到代码的增强

1. 五个工具分别读取摘要、检查热点、检查质量、展开调用链和生成复测草案。摘要包含允许枚举内的测量单位；PROC_CPU 明确仅有进程/线程 CPU tick，不提供函数调用栈。
2. inspect_call_paths 接受热点 rank（1–10），只能在绑定任务的解析结果中查找。返回有限祖先、独立出现位置和 Top 被调用者；不跨任务、不查文件系统，不输出原符号或绝对路径。8MiB 输入预算、4096访问节点、64深、5个出现位置、6层祖先及3个被调用者；tree_truncated标记遍历预算，ancestors_truncated/callees_truncated/occurrences_truncated分别标记实际上下文省略，不能把配置上限当成本次已截断。递归 inclusive 不累加。
3. 所有工具观测有 E 编号及来源版本。结构化假设必须引用已存在证据；不存在的源码行、请求延迟和优化收益不会由测量程序补造。模型仍可能给出解释性错误，需要审阅和复测，JSON 校验不等于语义正确性证明。
4. 任意命令、模型 SQL、模型提供的目标 PID/URL、直接修改业务源码均不进入执行器。灵活度体现为问题驱动补查及同类采集器的可配置复测时长/频率；跨采集器的完整参数仍通过正常任务表单审阅。
5. 原符号在平台授权页面保留，模型只得到哈希及本地固定枚举语义线索。哈希是化名，不保证匿名化；问题文本也会出站，用户需明确确认不含敏感信息。

## 验收设计

| 场景 | 应观察到的行为 | 不应出现的行为 |
| --- | --- | --- |
| self/total占比不同、存在多级调用树 | 选中实际rank，调用路径来自同一输入；在UI可核对原符号 | 仅靠平表捏造父子关系 |
| PROC_CPU真实采集 | 说明线程CPU tick和缺少函数栈；建议按目标能力补充采集 | 把线程名说成源码函数 |
| CPU profile与堆/分配profile | 保留各自单位和测量含义 | 把字节当毫秒、把样本比例当P99 |
| 缺少火焰树、超出交互预算或截断 | 明确available=false/截断及限制 | 以“没返回”证明“没有问题” |
| 模型未知工具、额外参数、虚构E编号 | 固定失败码，不执行、不落成功报告 | 任意shell、任意SQL或跨目标操作 |
| 权限撤销、重新分析、抢占/过期租约、取消 | 旧worker不能继续提交 | 过期报告覆盖当前数据 |
| 用户确认复测及重复提交 | 复用目标身份，参数再校验；幂等任务与来源事件同事务 | 模型直接执行、重复创建采集 |

确定性部分用单元测试、真实PG并发/事务测试和浏览器流程验证；模型协议用明确测试响应覆盖异常；真实DeepSeek单独联调并标记输入来源；最后在用户指定腾讯云上执行真实采样、模型诊断、确认复测和结果对比。每一层的通过只证明其边界，互不替代。

## 后续能力的进入条件

- 自然语言从零选择采集器：需新建持久化诊断会话、目标能力快照、计划校验、明确采样成本及确认机制；当前版本只围绕已有完整任务及同类复测，不伪装成任意采样编排。
- 跨任务回退分析：需绑定两侧授权、kind/单位/来源、两侧分析版本，并由程序计算差异，模型负责解释；目前已有结果对比页，但没有宣称模型自动完成因果比较。
- 源码行定位：需可信版本映射、build-id/符号映射及源码访问权限，不能让模型按函数名猜行号。
- 自动修复：只应在独立代码沙箱和功能回归/性能复测门禁后再考虑，不在采集Agent或生产业务目录执行模型生成代码。
