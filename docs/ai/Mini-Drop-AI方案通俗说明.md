# Mini-Drop AI 诊断方案通俗说明

> 这篇文档写给第一次接触 Mini-Drop AI 方案的人。
> 不讲任务怎么下发、数据怎么上传等基础链路，只回答三个问题：
>
> 1. AI 到底是怎么查问题的？
> 2. 为什么它的结论比普通聊天回答更可信？
> 3. 项目里的几套测试到底分别测什么？

---

## 一句话先说明白

Mini-Drop 不让大模型直接猜根因。

它让大模型先列出几个“嫌疑人”，再调用系统允许的检查工具找证据。最后由程序核对证据，决定哪个嫌疑成立、哪个被排除，或者老实地说“目前还查不清”。

可以把它理解成看病：

- 大模型像会问诊的医生助手，负责提出可能性和安排检查；
- 采集工具像验血、CT 和心电图，负责得到真实数据；
- 后端规则像会诊标准，负责判断检查结果是否足以支持诊断；
- 测试集像考试题，用来检查系统会不会乱猜、漏查或越权操作。

核心原则只有一句：

> AI 可以提出猜想，但不能把猜想冒充事实。

## 1. 用一个例子看懂完整诊断过程

假设用户说：

> `order-service` 今天突然变慢，接口响应时间很高，帮我看看是不是 CPU 问题。

Mini-Drop 不会立刻回答“是某个函数导致的”。它会按下面的顺序调查。

### 第一步：先确认到底在查谁

系统先确认：

- 哪个服务变慢；
- 服务运行在哪台机器；
- 对应哪个进程；
- 异常发生在哪段时间；
- 用户想查的是 CPU、内存，还是下游调用。

这一步是为了防止查错对象。

例如，用户只说“订单服务变慢”，系统不能自己编造一个进程号，也不能随便挑一台机器开始采集。

### 第二步：列出几个可能原因

系统会形成几个候选原因，例如：

1. `order-service` 自己的代码占满了 CPU；
2. 同一台机器上的其他进程抢走了 CPU；
3. 订单服务本身没问题，是它调用的下游服务变慢了；
4. 磁盘或网络堵塞，看起来像 CPU 问题；
5. 当前信息太少，暂时无法区分。

这里故意保留第 5 项，因为系统不能被迫在几个错误答案中硬选一个。

### 第三步：给每个猜想安排检查方法

每个候选原因都必须回答两个问题：

- 如果它是真的，我们应该看到什么？
- 如果它是错的，我们应该看到什么？

例如，对“订单服务自己的代码占满 CPU”这个猜想：

**如果是真的，应该看到：**

- 订单进程的 CPU 明显升高；
- CPU 主要花在业务代码，而不是操作系统内核；
- 某个函数长期排在 CPU 消耗前列；
- 该函数变热的时间和接口变慢的时间基本重合。

**如果是错的，可能看到：**

- CPU 主要被另一进程占用；
- 真正变慢的是下游服务；
- 暂停可疑路径后，接口速度没有改善；
- 没做处理的对照机器也同时恢复了，说明改善可能来自流量变化，而不是我们的操作。

这就是项目文档常说的“可证伪假设”。讲人话就是：

> 不仅要想怎么证明自己是对的，还要提前说清楚什么结果会证明自己是错的。

### 第四步：选择检查工具

大模型只能从系统给出的工具名单里选，不能自己拼 Shell 命令。

例如可以选择：

- 查看一段时间内的 CPU 指标；
- 采集 CPU 火焰图；
- 查看内存增长趋势；
- 检查磁盘等待；
- 检查网络错误；
- 查看下游请求耗时；
- 对比修复前后的结果。

如果模型选了不存在的工具、返回格式不对、调用超时，系统会放弃这次模型规划，改用固定规则继续诊断，而不是让整次诊断失控。

### 第五步：执行检查，但不能随便动机器

操作按照风险分三档：

| 风险 | 讲人话 | 处理方式 |
|---|---|---|
| R1 | 基本只读或影响很小 | 满足条件时可以自动执行 |
| R2 | 可能影响被测服务 | 必须等人批准 |
| R3 | 风险很高或不适合自动化 | AI 只能建议，不能执行 |

例如，读取 CPU 指标通常风险较低；暂停一个测试程序可能需要审批；任意重启生产进程、修改生产配置或执行任意命令不允许 AI 自主完成。

所以“大模型建议做某件事”和“系统已经做了这件事”是两回事。

### 第六步：把采集结果变成可信证据

采集到一个文件，并不代表它立刻可以支持结论。

系统还要检查：

- 采集任务是否真的成功；
- 文件是否确实由这次任务产生；
- 文件内容有没有损坏或被替换；
- 文件大小和校验值是否一致；
- 分析程序是否是系统认可的版本；
- 数据是不是来自当前服务、当前进程和当前时间段；
- 报告中的数字能不能重新定位到原始分析结果。

可以把这套过程理解为给每份证据附上一张完整收据：

```text
谁采的
→ 什么时候采的
→ 在哪台机器采的
→ 对哪个进程采的
→ 原文件是什么
→ 谁分析的
→ 报告里的数字来自原文件哪一处
```

没有这张“收据”的数据，只能作为参考，不能拿来正式确认根因。

### 第七步：同时看支持证据和反对证据

系统不会只找对自己有利的信息。

例如它怀疑“本地 CPU 热点”，支持证据可能是：

- 订单进程 CPU 很高；
- 某个业务函数占据火焰图顶部；
- 函数变热和接口变慢发生在同一时间。

反对证据可能是：

- 下游服务的耗时更早开始升高；
- 本地 CPU 热点消失后，接口仍然很慢；
- 没有处理的另一台机器也同时恢复；
- CPU 实际主要消耗在内核或别的进程上。

最终可能得到三种容易理解的结果：

1. **证据比较完整，可以确认**；
2. **有一些支持，但缺少反向检查，只能说“可能”**；
3. **证据不足或互相矛盾，暂时不能确认**。

第三种不是系统失败，而是正常且重要的答案。好的诊断系统应该知道什么时候闭嘴。

### 第八步：生成建议，但建议也要能验证

如果证据支持某个原因，系统会给出处理建议，例如：

- 优化某个热点函数；
- 降低某段同步 I/O；
- 检查同机噪声进程；
- 扩容或修复下游依赖；
- 补采一项关键证据。

建议不能只写“建议优化代码”。它还应该说明：

- 为什么建议这样做；
- 预计哪个指标会改善；
- 怎么判断修复有效；
- 如果没有改善，下一步查什么。

### 第九步：修复后再查一次

系统会尽量在相同服务、进程和时间口径下重新采集，比较：

- 原来的热点是否消失；
- 热点占比是否明显下降；
- 接口响应时间是否恢复；
- 相关指标是否回到合理范围。

目前这部分主要使用固定幅度规则，例如热点下降约 30% 才认为改善明显。

它可以说明“修复后现象确实改善”，但还不是严格的统计学证明，因为当前没有完整处理流量变化、随机波动、置信区间等问题。

## 2. 大模型到底做什么，不做什么

### 大模型做的事

- 理解用户想查什么；
- 提出 1 到 3 个候选原因；
- 为候选原因写出支持条件和推翻条件；
- 从允许的工具中选择下一项检查；
- 根据已取得的结果，建议下一步调查方向。

### 大模型不做的事

- 不把自己生成的文字当成事实；
- 不自己编造服务、机器或进程；
- 不执行任意命令；
- 不绕过人工审批；
- 不直接宣布因果关系；
- 不使用测试集标准答案指导诊断；
- 证据不足时不能硬给根因。

### 当前实际边界

设计目标是让模型参与多个诊断场景的动态规划，但当前代码里，模型辅助最明确地用于 CPU 热点相关规划。其他不少场景仍主要使用固定规则。

因此，准确说法是：

> 当前已经实现“模型参与、规则兜底”的受限诊断，但还不是所有场景都由大模型自由地多轮调查。

## 3. “置信度 82%”是什么意思

页面上的置信度不是“这个根因有 82% 的概率是真的”。

它更像一张证据完整度评分表，考虑：

- 证据是否可靠；
- 是否有多个来源；
- 时间和对象是否覆盖完整；
- 是否有反对证据；
- 是否还有关键证据没采。

所以 `82%` 更合适的解释是：

> 按当前项目规则，这个结论得到的证据比较充分。

它不是经过大量线上事故校准出的统计概率，也不能直接拿来当生产准确率。

## 4. 怎么进一步验证“它真的是根因”

只看到“CPU 高”和“接口慢”同时发生，还不能证明 CPU 就是原因。

可能只是因为同一时间流量突然变大，两个指标一起升高。

Mini-Drop 为此增加了一种更强的验证方式：只改变一个因素，看问题是否跟着变化。

讲人话就是做一次小型 A/B 实验。

### 单机实验

如果只有一台可用机器，就按顺序观察：

```text
正常时
→ 出问题时
→ 做一个小改动后
→ 撤销改动、恢复后
```

例如暂时关闭测试程序中的 CPU 热点开关：

- 关闭后 CPU 和延迟都下降；
- 恢复开关后问题再次出现。

这能较强地支持该原因，但仍可能受到流量随时间变化的影响，所以系统只能给出“单机实验支持”，不能包装成严格双机对照。

### 双机对照

如果有两台条件相近的 Worker：

- Worker1 做一个改动；
- Worker2 不做改动；
- 两台保持相同负载；
- 同时观察相同指标。

例如：

```text
Worker1 关闭 CPU 热点后，P99 下降 60%
Worker2 没做处理，P99 只变化 4%
恢复 Worker1 的热点后，问题再次出现
```

这个结果比单纯的前后对比更有说服力，因为对照机器帮助排除了“所有机器刚好一起恢复”的可能。

### 当前做到哪一步

已经有：

- 实验方案；
- 人工批准或拒绝；
- 四个时间段的数据录入；
- 单机和双机两种判断规则；
- 结果和操作记录；
- CPU、内存、下游延迟三个可用模板。

还没有完全自动化：

- 现在主要由人关联已完成的任务和证据；
- 指标值目前需要按相同口径录入；
- 系统还不能自动跑完所有实验；
- 还不能自动从所有采集文件中提取实验指标；
- 完整 10 类实验尚未全部接通。

所以它现在是“可操作的实验判断 MVP”，还不是“全自动双机因果诊断平台”。

## 5. 项目里的测试集分别在测什么

项目里不止一套测试。它们像学校里的随堂测验、实验考试和真实实习，不能混成一个总分。

### 5.1 七个 Golden 场景：随堂测验

共有 7 个固定场景：

1. 服务自己代码的 CPU 热点；
2. 同一机器上其他进程抢 CPU；
3. 共享磁盘 I/O 争用；
4. 下游服务 CPU 热点；
5. 内存泄漏；
6. 网络丢包；
7. MySQL 锁等待。

它主要检查程序的固定逻辑是否被改坏，例如：

- 分类是否正确；
- 有没有找到预期类型的异常；
- 证据引用能不能重新找到原数据；
- 有没有安排反向检查；
- 有没有未经允许自动执行危险操作。

这套测试不调用真实大模型，输入和标准答案也是提前写好的。

因此，7 个场景全部通过只代表：

> 固定分析规则和报告检查没有回归。

它不代表：

> 面对从未见过的生产故障也能 100% 找对根因。

### 5.2 受控的 90 次实验：实验室考试

计算方式是：

```text
10 类故障 × 3 种诊断策略 × 每种重复 3 次 = 90 次
```

它会实际经历正常、故障、诊断和恢复等阶段，比 7 个固定场景更接近完整实验。

历史上有两批结果：

#### 第一批历史归档

- 计划和记录都是 90 次；
- 84 次完成；
- 6 次内存故障没有稳定触发，因此在故障确认阶段停止；
- 受约束混合策略平均分约 87.89%；
- 根因精确率约 86.67%；
- 没有证据却下结论的比例为 0%；
- 证据引用有效率为 100%；
- 应该采集的关键证据只覆盖了约 70%。

这 6 次失败没有被藏起来，也没有强行补上标准答案。

#### 修复内存实验稳定性后的历史重跑

- 90 次全部到达完成状态；
- 三种策略平均分约 90%；
- 根因精确率约 90%；
- 没有证据却下结论的比例为 0%；
- 证据引用有效率为 100%；
- 应该采集的关键证据仍只有约 70%。

正确说法是：

> 在这 10 类固定、受控故障里，历史运行取得了约 90% 的结果。

错误说法是：

> Mini-Drop 在真实生产中的准确率是 90%。

特别注意，“证据引用有效率 100%”和“关键证据覆盖率 70%”不是矛盾：

- 前者表示已经引用的证据都能找到，没造假；
- 后者表示本来应该采集的证据还有约 30% 没覆盖。

### 5.3 `ai_ops_v2`：组内统一考试

这是另一套独立数据，不是上面的 90 次受控实验。

它包含：

- 30 个案例；
- 90 次历史诊断运行。

历史基线大致是：

- 案例级严格根因准确率：46.7%；
- 运行级严格命中率：48.9%；
- 平均综合分：78.61/100；
- 该拒答时正确拒答：100%；
- 证据引用有效率：100%；
- 审计记录覆盖率：100%；
- 三次重复结果保持一致：36.7%；
- 不安全动作：0。

这套结果反映出：系统在安全、证据引用和拒答方面表现稳定，但严格根因命中和重复一致性还有明显提升空间。

目前仓库主要接入了它的目录、历史结果回放和页面展示，并不代表当前源码已经在云端重新注入并跑完这 30 个故障。

### 5.4 反事实实验测试集：验证“真的是它吗”

这套测试共有 10 类题目：

1. CPU 热点还是内核开销；
2. 内存泄漏还是有上限的缓存预热；
3. 同步 I/O 还是 CPU 计算慢；
4. 网络问题还是下游程序慢；
5. 锁竞争还是普通忙循环；
6. GC 压力还是真实内存泄漏；
7. 消费者变慢还是入口流量过大；
8. 下游变慢还是本地 CPU 热点；
9. 噪声邻居还是自身代码热点；
10. 两个因素同时变化，系统是否会拒绝乱下结论。

完整目标是每类正式重复 3 次，共 30 次。

当前只有 CPU、内存、下游延迟 3 类接通实验方案。如果做 MVP 评测，目标规模是 9 次。

这里的“9 次”和“30 次”都是设计目标，不能在没有实际运行记录时写成已经完成的成绩。

### 5.5 真实开源问题：真实实习

项目整理了 7 个真实开源问题候选，来源包括 Grafana、OpenTelemetry、Prometheus、Redis、Kubernetes 和 Envoy。

当前状态是：

| 内容 | 当前数量 | 说明 |
|---|---:|---|
| 候选问题 | 7 | 已整理题目和来源 |
| 页面可运行的简化机制 | 4/7 | 只复现核心机制，不一定运行完整上游项目 |
| 有稳定上游修复前后回放归档 | 1/7 | OpenTelemetry Python #4224 |
| 完成正式准入并评分 | 0/7 | 目前还没有正式成绩 |

“简化机制能运行”和“完整复现真实项目”不是一回事。

例如，用几十行测试程序模拟一个对象被强引用，只能证明我们复现了这个机制；只有固定真实项目版本、分别运行修复前和修复后代码、重复多次并保存原始数据，才算较完整的上游回放。

### 5.6 与成熟产品对比：同题比赛

计划对比的对象包括：

- Pyroscope：主要比火焰图和性能分析体验；
- RCAEval：主要比公开根因定位指标；
- HolmesGPT：主要比 AI 如何选择工具并逐步调查；
- OpenRCA：主要用于研究大规模监控数据下的工具选择和根因分析。

公平对比要求双方拿到：

- 相同的问题描述；
- 相同的监控数据；
- 相同的时间窗口；
- 相同的模型和工具预算；
- 看不到标准答案；
- 双方先交卷并冻结结果，再由评分器看答案。

目前的真实状态：

- Pyroscope 的性能分析能力对比已经实际运行；
- HolmesGPT 已启动，但外部模型鉴权返回 401，因此没有诊断成绩；
- RCAEval 和 OpenRCA 受环境或资源限制，还没有完成正式同题结果。

因此当前不能宣称 Mini-Drop 已经全面优于这些成熟产品。

## 6. 怎样看待“已经完成”

项目中的“完成”至少分四层：

| 层级 | 讲人话 | 能不能当正式成绩 |
|---|---|---|
| 代码完成 | 功能已经写出来 | 不能 |
| 本机测试通过 | 在开发机或内存数据库里通过测试 | 不能替代云端 |
| 云端三节点验证 | Control、Worker1、Worker2 真实运行并保存记录 | 能证明云端跑过，但还不一定完成正式准入 |
| 正式准入 | 输入、输出、标准答案读取顺序、评分、原始证据和校验值都完整 | 才能作为正式成绩 |

常见误解：

- 页面能打开，不等于诊断已经真实运行；
- 按钮能点击，不等于完整实验已经自动完成；
- 单元测试通过，不等于云端三节点通过；
- 历史报告通过，不等于当前代码重新通过；
- 历史 90 次成绩，不等于未知生产故障准确率；
- 显示 90% 置信度，不等于根因有 90% 的统计概率；
- 简化机制复现，不等于完整上游项目复现；
- 有历史运行记录，不等于已经完成正式准入。

## 7. 当前方案的优点和短板

### 已经比较扎实的部分

- 不允许大模型自己编造事实；
- 工具必须来自白名单；
- 高风险动作需要人工批准；
- 结论必须能追溯到真实采集结果；
- 会同时考虑支持和反对证据；
- 证据不足时允许不下结论；
- 测试标准答案在诊断完成前不可见；
- 历史失败会被保留，不会为了成绩改写成成功；
- 已有修复前后对比和双机实验的基本框架。

### 仍需补齐的部分

- 大模型动态规划目前主要集中在部分场景；
- 对“反对证据是否真正独立”的检查还需加强；
- 关键证据历史覆盖率只有约 70%；
- 置信度还只是规则分数，没有完成统计校准；
- 反事实实验目前还需要人工关联数据和录入指标；
- 完整 10 类反事实实验尚未全部接通；
- 真实开源问题正式准入仍为 0/7；
- 成熟产品同题对比只完成了一部分；
- 当前源码仍需用云端 Control + 两个 Worker 重新验收；
- 历史结果不能代替当前版本的运行证据。

## 8. 汇报时可以直接这样讲

> Mini-Drop 的 AI 不是直接猜根因。它先根据用户描述列出几个可能原因，并为每个原因说明“看到什么算支持、看到什么算推翻”。随后，它只能调用系统允许的检查工具。采集结果还要经过任务成功、文件完整性、对象和时间范围一致等检查，才能成为正式证据。最后由程序核对支持证据和反对证据：证据完整就确认，证据不完整就只说可能，互相矛盾或信息不足就明确不下结论。对于重要根因，还可以在一台机器上做前后对比，或用两台机器做实验组和对照组，只改变一个因素，看问题是否随之消失和恢复。这样做的重点不是让大模型更会说，而是让它的每个结论都能被检查、被推翻、被复现。

如果被问“成绩怎么样”，可以继续说：

> 项目有多套测试，不能混成一个数字。7 个固定场景主要检查代码规则有没有回归；历史 90 次受控实验在固定故障中取得约 90% 的结果，但关键证据覆盖率约 70%；另一套 30 案例的组内数据严格根因准确率为 46.7%，说明泛化和重复一致性仍需提高；反事实实验目前接通了 3 类模板，但还没有完成全自动 10 类、30 次正式运行；真实开源问题有 7 个候选，但正式准入和评分仍是 0/7。因此目前能证明的是受控环境下的工程能力，不能宣称未知生产故障准确率或全面领先成熟产品。

## 9. 术语翻译表

| 项目术语 | 讲人话 |
|---|---|
| Hypothesis | 一个待检查的可能原因 |
| Falsification | 主动寻找能证明这个猜想错了的信息 |
| Probe | 一次检查或采集动作 |
| Artifact | 采集任务产生的原始文件或结果 |
| Evidence | 经过来源和完整性检查、可以用于下结论的数据 |
| Evidence lineage | 这份数据从哪台机器、哪个任务、哪个文件、哪个分析结果来的 |
| Counter-evidence | 与当前猜想相反的证据 |
| Abstain | 信息不够时不乱猜，明确说无法确认 |
| Oracle | 测试题的标准答案，只能在系统交卷后用于评分 |
| Golden | 提前写好输入和预期结果的固定回归题 |
| Confidence | 按当前规则计算的证据充分程度，不是统计概率 |
| Causal Replay | 只改变一个因素，通过前后变化或双机对照验证根因 |
| Difference in Differences | 比较实验组变化和对照组变化之间的差距 |
| Formal Admission | 运行、证据、答案隔离、冻结、校验和评分都完整后的正式准入 |
