# 李明远独立 AI 亮点：资源自适应反事实根因验证

> 方案代号：Resource-Adaptive Causal Replay（资源自适应因果回放）
> 定位：在现有 Mini-Drop 循证诊断链路上，增加“通过受控实验验证根因”的能力。
> 边界：保留必要的人工审批、参数调整和诊断反馈，但不复制组员的“人工删除上下文”；也不复制“源码文件/函数/行级定位”。

## 1. 一句话说明

普通诊断只能说“CPU 高可能由某个热点函数导致”。本方案让 AI 设计一个低风险、单变量、可回滚的实验。服务器资源有限时，先在同一节点比较基线、故障、干预和恢复四个窗口；资源足够时，再增加独立对照节点。单机实验只输出较弱的“时间序列支持”，双机差分满足门槛后才确认因果关系。

用户最终看到的不是一句猜测，而是：

```text
根因：同宿主机 noisy-worker 抢占 CPU，导致 order-service P99 上升。
实验：仅停止 worker1 上的 noisy-worker 30 秒，worker2 不做处理。
结果：worker1 CPU steal 下降 71%，P99 下降 63%；worker2 指标无显著变化。
恢复：重新启动 noisy-worker 后，worker1 的异常再次出现。
结论：根因通过反事实实验验证，置信度 92%。
证据：baseline-17、incident-18、intervention-19、rechallenge-20。
```

## 2. 为什么这是独立亮点

三位同学解决的是三个不同问题：

| 方向 | 回答的问题 | 核心产物 |
|---|---|---|
| 人工干预与上下文删除 | 人如何纠正 AI，哪些上下文应保留或删除 | 修订记录、上下文版本 |
| 源码级定位 | 问题具体落在哪个文件、函数或代码行 | source location、patch candidate |
| **双机对照反事实验证** | **AI 提出的根因到底是不是真的** | **干预计划、对照实验、效应量、恢复证据** |

三个能力可以组合，但评分维度不重叠。源码定位可以告诉系统“怀疑函数 A”，反事实验证继续回答“禁用 A 的异常路径后，性能是否真的恢复”；人工干预可以纠正一次实验，但不是本方案的主要卖点。

这里的差异点不是“不要人工干预”。本方案同样要求人在高风险动作前审批，也允许人调整范围和纠正结论；区别在于它不提供删除历史上下文的能力，而是保留反证、审批与实验记录，重点评价根因能否被对照实验验证。

## 2.1 已落地范围（2026-08-23）

- 后端已实现实验目录、方案生成、人工批准/拒绝、四窗口裁决与事件审计接口；
- 前端已在统一 AI 诊断页接入 `资源自适应反事实根因验证` 卡片；
- 已接入 CPU 热点、内存持续增长、下游延迟 3 个轻量 MVP 模板，完整目录保留 10 类；
- 裁决由确定性差中之差门槛完成，不由大模型直接宣布因果关系；
- 当前由人关联已完成任务/证据并录入同口径指标，自动 Campaign 执行和产物抽取仍是下一阶段。

## 3. 用户价值

性能诊断最常见的误区是把“同时发生”当成“因果关系”：

- CPU 高时恰好看到 GC，不代表 GC 是根因；
- 服务慢且宿主机繁忙，不代表服务自身代码有问题；
- 下游调用慢，不代表网络故障，也可能是下游线程池耗尽；
- RSS 增长不一定是泄漏，也可能是有上限的缓存预热。

本方案通过“只改变一个因素并观察结果”减少误判，尤其适合噪声邻居、下游依赖、锁竞争、缓存增长和负载突增等容易混淆的场景。

## 4. 核心流程

```text
用户描述异常
  ↓
AI 确认服务、Agent、PID、时间窗
  ↓
生成多个可证伪假设
  ↓
选择当前证据最支持、且可安全验证的假设
  ↓
生成反事实实验计划
  ├─ 实验组：改变一个变量
  ├─ 对照组：保持原状
  ├─ 观测指标：CPU / RSS / P99 / I/O / queue lag 等
  ├─ 证实条件：什么变化可以支持假设
  └─ 证伪条件：什么结果会推翻假设
  ↓
安全预检与风险分级
  ├─ R1：可自动执行
  ├─ R2：等待人工批准
  └─ R3：禁止执行，只给出建议
  ↓
采集 baseline 快照
  ↓
执行白名单干预并采集 intervention 快照
  ↓
清理干预并采集 recovery 快照
  ↓
可选 rechallenge：再次引入故障，检查能否复现
  ↓
计算实验组与对照组的差分效应
  ↓
确认根因 / 推翻假设 / 证据不足
```

## 5. “双机对照”是什么

现有云端有 Control、Worker1、Worker2，可以把两个 Worker 当作实验组和对照组：

- 两台机器运行同一种服务和相同负载；
- Worker1 开启一个白名单故障或修复动作；
- Worker2 保持原状；
- 同时采集相同指标；
- 比较两台机器在相同时间窗中的变化。

如果只有一台机器，则退化为同进程的时间窗口对照：先采基线，再干预，再恢复。单机结果可以作为 `SUPPORTED`，双机加重新挑战（rechallenge）后才有资格进入更高等级的 `CAUSALLY_VERIFIED`。

## 5.1 为什么当前不把双机设成默认

云实验环境共三台 Ubuntu 主机，Control、Worker1、Worker2 均为 `2 核 4GB / 40GB`。这套资源足以演示控制面、两个 Agent 和轻量 fixture，但不适合每个 Worker 常驻完整微服务商城、可观测性全家桶和高负载发生器。资源打满还会制造新的 CPU 抢占与内存回收噪声，使实验失去解释力。

因此采用三级路径：

| 级别 | 执行方式 | 资源消耗 | 可输出结论 |
|---|---|---:|---|
| L0 历史证据回放 | 读取统一测试集、历史快照和 Golden Oracle 做离线评分 | 最低 | 诊断是否与标准答案一致 |
| L1 单机交叉实验 | 同一目标依次采集基线、故障、干预、恢复 | 低 | `SUPPORTED_SINGLE_NODE`，置信度最高 75% |
| L2 双机并行对照 | 两个 Worker 同负载，仅处理组改变一个变量 | 中 | 满足差中之差与恢复门槛后 `CAUSALLY_VERIFIED` |

默认演示走 L1；L2 只在两个 Worker 均空闲且负载可以对齐时启用。`CR-NOISY-001` 保留在完整测试目录，不作为首期默认案例，也不要求暂停实验机上的任意非白名单进程。

## 6. 关键数据模型

### 6.1 CausalExperiment

```json
{
  "experiment_id": "cexp-20260823-001",
  "diagnosis_id": "diag-001",
  "hypothesis_id": "hyp-002",
  "treatment": "stop_noisy_neighbor",
  "treatment_target": "worker1/noisy-worker",
  "control_target": "worker2/order-service",
  "primary_metric": "http.server.duration.p99",
  "secondary_metrics": ["host.cpu.utilization", "process.cpu.time"],
  "support_condition": "p99 decreases >= 30% only in treatment group",
  "refutation_condition": "p99 does not improve or control group changes equally",
  "cleanup_action": "restart_noisy_neighbor",
  "risk_level": "R2",
  "status": "PLANNED"
}
```

### 6.2 状态机

```text
PLANNED
→ SAFETY_CHECKED
→ BASELINING
→ INTERVENING
→ OBSERVING
→ RESTORING
→ VERIFYING_RECOVERY
→ VERIFIED / REFUTED / INSUFFICIENT_EVIDENCE / FAILED
```

无论在哪一步失败，都必须进入 `RESTORING`；清理失败则标记 `CLEANUP_FAILED` 并立即停止后续自动操作。

### 6.3 最终结论契约

```json
{
  "root_cause": "same-host noisy neighbor consumed shared CPU",
  "verdict": "CAUSALLY_VERIFIED",
  "confidence": 0.92,
  "effect_size": {
    "metric": "p99_latency_ms",
    "treatment_change_percent": -63.0,
    "control_change_percent": -4.0,
    "difference_in_differences": -59.0
  },
  "evidence_refs": ["snapshot-baseline", "snapshot-incident", "snapshot-intervention", "snapshot-recovery"],
  "counter_evidence_refs": ["control-worker2"],
  "limitations": ["experiment lasted 60 seconds"],
  "cleanup_verified": true
}
```

## 7. 因果裁决规则

第一版不需要宣称实现通用因果推断。采用可解释的工程规则：

1. **时间先后**：原因变化必须先于症状变化；
2. **单变量干预**：一次实验只允许改变一个主要因素；
3. **实验/对照差分**：实验组改善明显，对照组不能同步改善；
4. **效应量门槛**：变化必须超过噪声和预设阈值；
5. **可重复性**：正式用例至少重复 3 次；
6. **恢复验证**：撤销干预后系统必须恢复安全状态；
7. **反证优先**：命中证伪条件时必须推翻假设；
8. **允许拒答**：数据不足时返回 `INSUFFICIENT_EVIDENCE`，不能强行给根因。

后续可参考 DoWhy 的干预、反事实与 refutation API，或 PyRCA 的因果图方法，但第一阶段以真实、可复现、可审计的小实验为主，不为了“用了算法”增加黑盒复杂度。

## 8. 专属测试集

测试集定义见 [`benchmarks/causal_replay/cases.json`](../../benchmarks/causal_replay/cases.json)。首批 10 类：

| ID | 事故 | 主要混淆项 | 要验证的能力 |
|---|---|---|---|
| CR-CPU-001 | 用户态 CPU 热点 | 内核态开销 | 停止热点路径后 CPU/P99 是否下降 |
| CR-MEM-001 | 持续内存泄漏 | 有上限缓存预热 | 停止分配后 RSS 是否仍增长 |
| CR-IO-001 | 同步 I/O 延迟 | CPU 计算慢 | 切走磁盘写入后延迟是否恢复 |
| CR-NET-001 | 网络丢包/延迟 | 下游应用变慢 | 只恢复网络后调用链是否恢复 |
| CR-LOCK-001 | 锁竞争 | 普通忙循环 | 降低并发后锁等待是否下降 |
| CR-GC-001 | GC 压力 | 真正内存泄漏 | 降低分配率后暂停是否减少 |
| CR-QUEUE-001 | 消费者变慢导致积压 | 入口流量突增 | 恢复消费者后 lag 是否回落 |
| CR-DOWNSTREAM-001 | 下游依赖变慢 | 本地 CPU 热点 | 替换健康下游后 P99 是否恢复 |
| CR-NOISY-001 | 噪声邻居争抢 CPU | 自身代码热点 | 停止邻居后目标服务是否恢复 |
| CR-CONFOUND-001 | 负载与配置同时变化 | 两个相关因素 | 系统能否拒绝一次改两个变量 |

每个案例至少执行 3 次，共 30 次。它们是用户亮点测试，不替代团队统一基础测试集。

## 9. 统一团队对比方式

三位同学使用同一个事故输入、同一证据预算、同一时间窗和同一 Oracle，统一输出：

```json
{
  "case_id": "...",
  "root_cause": "...",
  "confidence": 0.0,
  "evidence_refs": [],
  "counter_evidence_refs": [],
  "abstained": false,
  "tool_calls": 0,
  "elapsed_ms": 0
}
```

再增加各自扩展字段：

- 人工干预方案：`context_revision_count`、`correction_acceptance`；
- 源码定位方案：`file`、`function`、`line`、`localization_rank`；
- 本方案：`intervention`、`control_group`、`effect_size`、`cleanup_verified`。

共同指标：根因准确率、证据有效率、正确拒答率、耗时、工具调用数。
本方案专属指标：

- 因果验证成功率；
- 混淆项排除率；
- 干预效应一致性；
- 故障清理成功率；
- 重复实验方差；
- 错误确认根因率。

## 10. 页面展示

AI 诊断页面新增“验证这个根因”卡片，不另建第二套诊断页面：

```text
候选根因：噪声邻居抢占 CPU
实验组：worker1/order-service
对照组：worker2/order-service
干预：停止 worker1/noisy-worker 30 秒（R2，待审批）

             基线       故障       干预后      恢复后
实验组 P99    82 ms      310 ms      108 ms      296 ms
对照组 P99    79 ms       84 ms       81 ms       83 ms

差分效应：-59%
清理验证：通过
结论：该根因通过反事实实验验证
```

页面必须显示每一步执行状态、命令摘要、风险等级、证据引用和清理结果，不能只展示最后一个百分数。

## 11. 实施顺序

### 阶段一：3 个案例 MVP

1. 扩展假设契约：增加 `testable_intervention`、`support_condition`、`refutation_condition`；
2. 新增 `CausalExperiment` 状态机；
3. 复用现有 Campaign 执行 baseline/fault/intervention/recovery；
4. 接入 CPU、内存增长、下游延迟 3 个轻量案例；
5. 页面展示四窗口和实验/对照差分；
6. 每个案例重复 3 次并保存 Evidence Snapshot。

### 阶段二：完整 10 类

1. 增加内存、I/O、网络、锁、GC、队列和混淆项案例；
2. 加入 rechallenge；
3. 输出 30 次专属评测报告；
4. 与无反事实验证的基础策略做消融对比。

### 阶段三：团队整合

1. 冻结团队统一输入/输出契约；
2. 合并三类亮点的扩展字段；
3. 同一批基础案例分别运行三套策略；
4. 各自专属测试只评价对应亮点；
5. 最后再跑组合策略，检查三种能力能否互相增强。

## 12. 汇报时的说法

> 我的方向不是再做一个聊天 Agent，也不是和组员重复做上下文管理或代码行定位。我关注的是性能诊断里最容易出错的一步：相关性不等于因果。系统会让 AI 把候选根因变成一个可证伪实验，在实验节点改变一个变量，用另一节点作对照，同时比较基线、故障、干预和恢复窗口。只有症状随原因可逆变化，而且清理成功，才确认根因；否则推翻假设或明确返回证据不足。这个能力可以直接复用我们已有的 Campaign、三节点环境和不可变证据链，并且能用 10 类、30 次专属实验量化评测。

## 13. 方案边界

- 不允许 AI 执行任意 Shell；只调用白名单故障开关和恢复动作；
- 不在生产环境自动执行 R2/R3 干预；
- 不把一次相关性变化写成因果结论；
- 不使用 Oracle 指导诊断，Oracle 只能在结果冻结后评分；
- 不保证所有故障都能安全做实验；不能实验时应返回证据不足和人工验证计划；
- 不把单机时间前后对比包装成双机随机对照实验。

## 14. 参考项目与取舍

- DoWhy：干预、反事实、根因归因和 refutation 思路；当前不把它作为在线必需依赖，避免为四窗口工程规则引入较重的数据科学栈；
- PyRCA：基于指标与因果图的根因分析；
- OpenTelemetry Demo：借鉴通过 feature flag 制造高 CPU、内存泄漏等可控故障；不在当前 `2C4G` 节点完整部署全部商城服务；
- Chaos Mesh：借鉴白名单、串行工作流、恢复动作和命名空间隔离；当前环境不是 Kubernetes 集群，因此不部署其 controller、daemon、dashboard 和 CRD。
