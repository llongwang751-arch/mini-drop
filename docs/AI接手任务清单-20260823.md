## 3. 已完成的主要工作

以下内容已经完成实现或已有历史证据，但必须区分“历史证据”和“本次当前源码重新验证”。不要把历史结果直接当成本次改动的通过结果。

### 3.1 AI 循证诊断主链路

已有链路：

```text
范围确认
→ 可证伪假设
→ 性能决策树
→ 白名单工具调用
→ TaskAttempt
→ VERIFIED Artifact
→ Evidence
→ 支持证据/反证裁决
→ 置信度与限制
→ 证据不足时 abstain
→ 修复后同范围复测
```

重要约束：

- 不猜测 Agent、PID、服务或时间窗；
- AI 结论必须引用成功的 `TaskAttempt` 和 `VERIFIED Artifact`；
- `evidence_refs` 与 `counter_evidence_refs` 是结论证据引用的唯一允许入口；
- 失败任务、未验证产物、任意字符串和手工自报快照不能作为正式证据；
- R1 可自动执行，R2 需要审批，R3 不允许 AI 自动执行；
- 故障注入必须白名单、可超时、`finally` 清理并验证恢复。

### 3.2 Evidence Snapshot 来源链

已完成任务拥有者、产物、字节级完整性、SHA-256、大小、诊断归属和 Analyzer lineage 的闭环。自动晋升为 `TRUSTED` 必须同时满足：

- 成功 `TaskAttempt`；
- Task-owned `Artifact`；
- 本地或 COS 字节重新计算后为 `VERIFIED`；
- SHA-256 和 size 一致；
- Diagnosis-owned Evidence；
- 晋升和 Snapshot 在同一事务中完成。

正式 AI 证据资格是：

```text
lifecycle_status == ACTIVE
trust_status == TRUSTED
superseded_by is None
```

### 3.3 结论失效与 Artifact 撤销

已经添加或重构：

- append-only conclusion invalidation；
- idempotent revalidation request；
- immutable `DiagnosisArtifactRevocationModel`；
- 独立 mutable `DiagnosisArtifactRevocationOutboxModel`；
- `20260823_0022` migration；
- revocation due/lease-recovery indexes；
- revocation list、claim、lease、ack、fail、backoff、dead-letter store 方法；
- `diagnosis_artifact_revoked` event payload；
- revocation dispatcher、worker、CLI flag；
- application lifespan 中独立的 task、artifact、revocation 三个 outbox worker。

撤销事实与投递状态必须保持分离：事实不可变，投递状态可以重试、租约回收和死信。

### 3.4 Artifact freeze 并发一致性

`freeze_diagnosis_artifact()` 已改为单一权威数据库事务：锁定 diagnosis，读取精确 latest conclusion，校验完整性和证据资格，确定性组装冻结 payload，并在并发插入冲突时保留不可变 winner。此前 artifact outbox 完整套件曾通过：

## 6. P0：继续闭合语义发布门禁

Revocation delivery 目前还不能自动证明语义安全。下一步需要设计并测试：

### 6.1 `SUPPRESSED` 语义状态

区分：

- `PUBLISHED`：已允许并完成发布；
- `SUPPRESSED`：语义上不再允许发布；
- `DEAD_LETTER`：投递、运行或字节完整性失败；
- `FAILED`：可重试的投递失败。

语义无效不能伪装成 transport dead-letter。历史 immutable conclusion JSON 和 hash 不得原地修改；应追加新的 invalidation/revalidation 事实。

### 6.2 三个语义门

至少检查三个时点：

1. claim-time：领取前确认 artifact/conclusion 仍可发布；
2. pre-delivery：调用下游前再次确认；
3. acknowledgement-time：ack 前确认没有发生 invalidation race。

所有门必须基于稳定 identity：diagnosis、artifact、conclusion hash、Evidence ID、review revision。

### 6.3 delivery-before-ack 竞态

如果下游已经收到 artifact-ready，但数据库 ack 之前 Evidence 被判无效，不能只把本地 outbox 改成 suppressed。必须明确补偿策略：

- 生成 immutable revocation fact；
- 创建 durable revocation outbox；
- 下游必须按 stable event identity 幂等处理撤销；
- 测试 delivery 成功、ack 失败、随后 invalidation 的完整时序。

### 6.4 重新生成结论的 Artifact identity

当前 `artifact:{diagnosis_id}` 的唯一 identity 与重新生成结论存在冲突。需要选择并记录一种明确方案：

- generation-aware artifact identity；或
- 明确的 artifact supersession 关系。

不能通过覆盖历史 JSON、修改历史 hash 或增加兼容字段掩盖冲突。

优先顺序：

每个产品必须拿到相同：

- 公开事故描述、拓扑和时间窗；

- 可见数据源与工具 contract；
- 模型、参数、system prompt、user prompt；
- token、byte、tool-call、wall-clock budget；
- 评分规则；
- 诊断输出冻结前不可见的 private Oracle。

严格执行：

```text
公开输入冻结
→ 产品诊断
→ 输出冻结并绑定 source_run_id/input_hash
→ 评测器读取 private Oracle
→ 统一评分
```

历史结果中：

- Mini-Drop 曾在机制和 abstention 上更强；
- llongwang 结果曾在证据有效性、必需证据请求和 evidence-gap detection 上更强；
- 工具调用和字节数差异不能直接解释为效率差异；

- 产品覆盖面不同，不能用接近的总分宣称完整产品更强。

## 9. 评测输出和报告结构

每条运行必须可按以下层级追溯：

```text
Case
→ Repetition
→ Benchmark track
→ Scoring dimension
→ Aggregate
```

至少输出以下状态：

- `SCORED`：输入、输出、冻结、Oracle 读取和评分完整；
- `UNSCORED`：运行完成但准入或 evaluator 条件不足；
- `RECEIVED_AWAITING_EVALUATOR`：结果已收取，等待隐藏评测器；
- `NOT EXECUTED`：没有真实运行；
- `INTERRUPTED` / `FAILED`：运行或环境失败，保留原因。

至少包含：

- manifest；
- source identity；
- test-set identity；
- environment identity；
- raw results；
- input/output/hash；
- admission boundary；
- acceptance boundary；
- 分维度分数；
- 聚合结果；
- 人工 A 评分或明确缺失；
- 未解决风险。

不要让旧报告中的过时运行次数、候选数量或产品归属覆盖机器可读事实。机器可读 manifest 和冻结原始结果优先。

## 10. P1：当前源码回归与云端三节点验证

用户已明确：后续联调和验收直接使用云端三节点，不再默认执行本地验证。

因此口径必须是：

- 本机测试：`LOCAL DEVELOPMENT VERIFICATION`；
- 云端控制节点 + 两个 worker：`CLOUD THREE-NODE VERIFICATION`；
- 原生物理机能力证明：`PHYSICAL-MACHINE CERTIFICATION`；
- 满足准入、评分、哈希和证据包后才是 `FORMAL ADMISSION`。

本机测试可以帮助开发，但不能代替云端三节点验收，也不能代替 Formal Admission。

云端操作顺序：

1. 先核对 host key、当前 release 和 Git commit；
2. control PostgreSQL 先备份；
3. 新建 verified bundle 和新 release 目录；
4. 只从审查后的 commit/bundle 发布；
5. 校验 Compose config；
6. 控制并发构建；
7. 显式执行 migrations；
8. 只启动需要的服务，不执行 `docker compose down`；
9. 验证 HTTPS、SSE、Agent heartbeat、系统指标任务、Campaign、AI 范围确认和失败路径；
10. 保存每个 run ID、服务端 timeline、数据库/Artifact hash、日志摘要和恢复结果；
11. 不覆盖 active release，保留 rollback。

需要验证的云端场景：

- control、worker1、worker2 各自只能采集本机 PID；
- 三个 outbox worker 独立运行；
- artifact publication 和 revocation 不互相饥饿；
- 网络超时、HTTP 5xx、无效响应和 `ACCEPTANCE_UNKNOWN` 语义正确；
- 重启后旧 generation 的 command/event/completion/replay 被拒绝；
- 数据库并发和 late callback 不破坏 ownership/fencing；
- Evidence invalidation 能触发正确的 artifact revocation。

14. 运行云端 golden path 和 failure path；
15. 只有证据包完整后，才更新 Formal Admission 状态。

## 14. 最终完成定义

本项目只有在以下条件全部满足时，才能说本阶段闭合：

- revocation outbox 的状态、租约、重试、死信和事件契约有真实测试；
- semantic suppression 和 delivery race 有明确实现与测试；
- 至少一个真实 PR 具备固定 base/fix、重复回放、三段证据和冻结诊断结果；
- 成熟产品对照使用相同公开输入和预算，Oracle 在输出冻结后才使用；
- 报告能区分 SCORED、UNSCORED、AWAITING_EVALUATOR 和 NOT EXECUTED；
- 当前源码已提交并可从 clean commit/bundle 重建；
- 云端 control、worker1、worker2 的实际运行证据已保存；
- 数据库、Artifact、事件、日志和报告 hash 可互相追溯；
- 没有凭据、临时包或生成物进入 Git；
- 所有未完成能力和环境阻塞仍被明确列出。

在这些条件满足前，不得宣称“完整真实 PR 评测已完成”“成熟产品全面优于对照”“云端三节点 Formal Admission 已通过”或“线上准确率等于历史受控 Campaign 分数”。
