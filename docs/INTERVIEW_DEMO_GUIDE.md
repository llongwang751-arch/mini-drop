# Mini-Drop 面试演示手册

> 目标：让你不依赖历史截图，在网页上随时制造一个受控故障，展示多轮 Agent 调查、LATS 探索树、真实采集、火焰图、人工干预、Skill 复用与不复用对照。
>
> 当前页面入口：`https://120.24.187.205/ai-diagnosis`。发布版本和最新线上验收结果以 [`PROJECT_CONTEXT.md`](PROJECT_CONTEXT.md) 和 [`RESTART_HANDOFF.md`](RESTART_HANDOFF.md) 为准，不以本文中的截图或历史会话为准。

## 1. 先记住两条演示链

Mini-Drop 故意把“算法完整性”和“真实机器取证”分开，因为它们证明的事情不同。

| 演示链 | 页面入口 | 能证明什么 | 不能证明什么 |
|---|---|---|---|
| 完整 LATS 冻结回放 | AI 诊断 → 验证与 A/B → 故障广场 → 完整 LATS 冻结回放 | Selection、Expansion、Evaluation、Simulation、Reflection、Backpropagation、剪枝和停止能在可复位环境中完整执行 | 当前云主机真的有故障，或产生了真实 Task、Artifact、Evidence |
| 实时受控故障诊断 | AI 诊断 → 验证与 A/B → 故障广场 → 启动并诊断 | 页面启动白名单故障，Agent 真实调用 Collector，形成新的 Task、Artifact、Evidence 和 Report | 实时环境不可回滚，不能声称所有兄弟分支处于完全相同的现场 |

冻结回放显示 `FULL_LATS / FROZEN_REPLAY`；真实故障显示 `BUDGETED_LATS / LIVE_PROGRESSIVE`。面试时先讲清这条真实性边界，会比把所有流程都叫“完整 LATS”更可信。

当前线上版本目录为 `/opt/mini-drop-releases/20260908T094648Z`，已用页面同款 API 顺序跑通故障广场全部 21 条真实诊断链。关闭 Skill 与开启 Skill 都会重新采集现场证据；正式展示仍应从故障广场新建会话，证明不是复用旧案例。最新 Java GC 场景同时产出 allocation Profile 和独立 `jvm_gc_metrics` CONTROL Evidence；历史旧报告仍保持当时“缺少独立计数器”的限制，不做回写。

## 2. 演示前两分钟检查

1. 打开 `https://120.24.187.205/ai-diagnosis`。
2. 点击右上角 **访问凭据**，输入并保存 API Key。共享屏幕时不要展示明文，也不要把 Key 写进文档、命令历史或截图。
3. 页头显示 **实时事件已连接**，表示 SSE 正常；显示 **轮询兜底中**时页面仍能使用，但状态更新会稍慢。
4. 打开 **采集与任务 → 任务面板**，确认至少一个 Agent 为“在线”。
5. 回到 **AI 诊断 → 验证与 A/B → 故障广场**，看卡片是否显示可用。
   默认“推荐”会依次显示 Go、Java、C++、Python 各一个案例；也可点击“全部、Go、Java、C++、Python”筛选。筛选后的数量应为 Go 4、Java 5、C++ 5、Python 7。
6. 正式演示优先选 `120 秒`。`30 秒`适合检查按钮，`60 秒`适合快速走通，`120 秒`更容易形成三轮取证。
7. 演示结束主动点击 **停止**。自动停止是安全兜底，不应替代主动清理。

如果某一种语言的卡片不可用，先读卡片上的“不可用原因”。不要连续刷新，更不要第一反应重启整台云服务器；Python、Go、Java、C++ 四组实验室彼此隔离，一组不可用不应拖垮其他组。

## 3. 故障广场：21 个可重复场景

卡片只向浏览器暴露 `scenario_id` 和 30/60/120 秒时长。真实 URL、命令、Agent、PID 和默认参数都在服务端白名单里，最长 300 秒并自动停止。页面不能借故障广场执行任意 shell，也不能把实验室指向生产环境。

### 3.1 Python 与基础实验室：7 个

| 场景 | 现象 | 典型取证 | 演示重点 |
|---|---|---|---|
| CPU 计算热点 | 单进程 CPU 持续升高 | 系统指标、perf、py-spy | 区分业务热点、I/O 等待和同机争抢 |
| Python 源码热点 | 业务函数成为稳定热点 | 系统指标、py-spy | 定位到 Python 文件、函数和行号 |
| 进程内存增长 | RSS/PSS 持续上升 | 系统指标、smaps | 区分对象保留、页缓存和宿主机压力 |
| 同步写入压力 | 写入量和 I/O wait 上升 | 系统指标、eBPF I/O | 一次 I/O wait 不能直接证明根因 |
| 同机噪声邻居 | 宿主机忙，目标自身无主导热点 | 系统指标、perf | 比较目标进程与同机其他进程 |
| 入口负载饱和 | 到达率高于完成率，拒绝和延迟上升 | 系统指标、perf | 区分流量饱和、代码热点、下游等待 |
| 生产消费队列堆积 | 生产速率高于消费速率 | 系统指标 | 观察队列趋势和停止后的消退 |

### 3.2 Go：4 个

| 场景 | 现象 | 典型取证 | 演示重点 |
|---|---|---|---|
| Go 服务 CPU 热点 | CPU 持续升高 | 系统指标、Go pprof、perf | 区分业务计算、运行时开销和系统等待 |
| Go 网络等待与下游慢响应 | 请求延迟升高，CPU 未必饱和 | 系统指标、Go pprof | 对照阻塞栈、本地计算和恢复窗口 |
| Go 堆内存持续增长 | heap in-use 与 RSS 同向增长 | 系统指标、smaps、Go heap profile | 区分对象保留、页缓存、短命分配和 swap |
| Go 同步文件写入 | 写入量与块设备等待升高 | 系统指标、eBPF I/O、Go pprof | 交叉验证同步写、阻塞栈与 CPU 反证 |

### 3.3 Java：5 个

| 场景 | 现象 | 典型取证 | 演示重点 |
|---|---|---|---|
| Java 分配风暴与 GC 压力 | 堆呈锯齿，GC 和延迟抖动 | 系统指标、smaps、async-profiler | 区分短命对象、长期保留与纯 CPU 热点 |
| Java 锁竞争 | 阻塞与上下文切换增加 | 系统指标、async-profiler、perf | 定位 `ReentrantLock/park`，排除 GC 与 I/O |
| Java 下游依赖慢响应 | 请求线程等待，本地 CPU 中低 | 系统指标、async-profiler | 本地资源正常不等于下游正常 |
| Java 堆外内存持续增长 | RSS 上升，但 Java 堆解释不了 | 系统指标、smaps、async-profiler | 对比 heap、DirectByteBuffer 与匿名映射 |
| Java 同步文件写入 | `FileChannel.force` 带来 I/O 等待 | 系统指标、eBPF I/O、async-profiler | 排除 GC、锁、CPU 和下游等待 |

### 3.4 C++：5 个

| 场景 | 现象 | 典型取证 | 演示重点 |
|---|---|---|---|
| C++ 计算热点 | 稳定计算函数占用 CPU | 系统指标、perf、持续 perf | 区分业务循环、锁自旋和系统调用 |
| C++ 互斥锁竞争 | mutex/futex 等待增加 | 系统指标、perf、持续 perf | 分开看计算热点与阻塞热点 |
| C++ 有界内存保留 | 匿名内存分阶段增长 | 系统指标、smaps | 观察 RSS/PSS 趋势和停止后的释放 |
| C++ 同步文件写入 | write/fdatasync 与 I/O wait 上升 | 系统指标、eBPF I/O、perf | 交叉排除计算、锁和内存压力 |
| C++ 下游响应变慢 | socket 等待，端到端延迟上升 | 系统指标、perf、持续 perf | 区分本地计算、锁、文件 I/O 与下游 |

每个场景由服务端要求至少 3 个有报告的诊断轮次，典型顺序是“低开销系统初筛 → 运行时或内核专项取证 → 寻找反证并观察恢复”。上限仍受诊断预算控制，不能为追求轮数无限运行。

页面轮次表示“第几次真实选择、取证并形成 Report”，不是节点最初在哪一层生成。LATS 回溯到早先的 sibling 时，树的父子位置保持不变，但该节点及其工具、证据和报告会显示新的执行轮次；因此能同时看见真实树结构和连续的第 1～4 轮调查。

## 4. 推荐的 15 分钟演示顺序

| 时间 | 页面操作 | 你要讲清楚的事情 |
|---:|---|---|
| 0～2 分钟 | 浏览故障广场和安全说明 | 四种语言、六类故障、安全白名单和自动停止 |
| 2～5 分钟 | 新建完整 LATS 冻结回放 | 树搜索不是静态流程图，且可复位、可重放 |
| 5～10 分钟 | 选一个场景，120 秒，启动并诊断 | 页面制造故障，形成真实 Task/Artifact/Evidence/Report |
| 10～12 分钟 | 探索树全屏、查看评分、展开事件 | 选择、观察、反思、回传与转向如何可解释 |
| 12～13 分钟 | 在树节点发起人工干预 | 人能改变方向，但意见不能冒充证据 |
| 13～15 分钟 | Skill A/B 和 Skill 示例与沉淀 | Skill 改变路线，Evidence 必须重新采集 |

只有 5 分钟时，优先演示：**Go 服务 CPU 热点 → 启动并诊断 → 对话 → 探索树 → 查看评分 → 寻找反证 → Go pprof 火焰图**。如果更想展示源码文件、函数与行号，再选择 **Python 源码热点**。

## 5. 演示完整 LATS 冻结回放

### 5.1 点击步骤

1. 进入 **验证与 A/B → 故障广场**。
2. 找到 **完整 LATS 冻结回放**。
3. 点击 **新建回放会话**。
4. 打开新生成的 `insight_replay_*` 会话。
5. 切换到 **探索树**，点击 **全屏查看探索树**。

### 5.2 讲解顺序

1. 根节点是问题，不是预先写好的答案。
2. 扩展产生多个候选分支，并进行语义去重。
3. 选择使用 UCT，在“历史回报较高”和“尚未充分探索”之间取舍。
4. 模拟从冻结快照取得观察，每个兄弟 rollout 前都有重置证明。
5. 反思决定继续、转向、剪枝或停止。
6. 价值回传更新访问次数、累计奖励和平均回报 Q。
7. 刷新后树仍存在，说明它来自服务端事件，不是一次性前端动画。

冻结回放中的真实工具调用、Task、Artifact、Evidence 和 Report 应为 0。这里的“观察”是冻结 fixture，不是当前云机器证据。

## 6. 演示真实多轮诊断

### 6.1 从故障卡创建新诊断

1. 选一张状态可用的故障卡。
2. 阅读 **目标运行时、建议轮次、调查阶段、预期信号、推荐采集、关联 Skill**。
3. 选择 `120 秒`。
4. 点击 **启动并诊断**。
5. 页面跳入新的诊断会话。记录本次短会话 ID，不要复用历史截图。

第一次推荐“Go 服务 CPU 热点”，因为它已经完成 Skill 开/关、四轮诊断、Go pprof 火焰图和报告引用验收；想突出源码行号时选择“Python 源码热点”，想展示 native perf 时选择“C++ 计算热点”，想展示 JVM allocation Profile、Skill 路线持续沿用和带限制结论时选择“Java 分配风暴与 GC 压力”。Java 锁竞争、Go 文件 I/O 或 C++ 下游慢响应可用于展示跨运行时、跨证据域规划，但目前不能宣称这些未单独出具 live 报告的场景已经完成根因验收。

### 6.1.1 Java GC 压力的页面验收脚本

1. 在故障广场选择 **Java 分配风暴与 GC 压力**，时长选择 `120 秒`，点击 **启动并诊断**。
2. 在新会话确认目标进程类型为 Java，服务端签发的 Agent/PID 绑定只读；不要手工填写历史 PID。
3. 打开 **探索树**，观察共同的系统初筛之后，Skill 路线引导到内存 Profile 和 JVM allocation Profile。Skill 命中只是 Prior，不是 Evidence。
4. 在任务或证据详情中打开 JVM Profile。有效结果应显示采集器 `java_async`、allocation 事件、非零样本和 `Hotspot`；空火焰图不能通过门禁。
5. 查看结论：允许显示“带限制完成 / `PARTIAL_WITHOUT_COUNTER`”，同时明确已有 JVM 支持证据、仍缺独立计数器。最后一次非关键 perf 失败可以保留在树中，Agent 应选用当前最好且受支持的报告收尾，而不是伪造成功。
6. 回到故障广场点击 **停止**；状态应变为未运行。正式面试每次都新建会话，不展示下面的历史验收 ID 冒充现场结果。

Java 这组 A/B 的第一项工具都可能是系统指标，这是刻意保留的共同低风险基线，不代表 Skill 没有作用。页面对比时看完整路线：关闭组为“系统指标 → perf → eBPF I/O → JVM Profile”，开启组为“系统指标 → 内存 Profile → JVM allocation Profile → perf”；再看是否命中 JVM Profile、支持证据数和最终状态。

### 6.2 三轮应该看到什么

| 轮次 | Agent 的工作 | 页面观察点 |
|---:|---|---|
| 第 1 轮 | 低成本初筛，判断 CPU、内存、I/O、网络或运行时大方向 | 范围、初始假设、系统指标、预算 |
| 第 2 轮 | 运行时/内核专项采集，定位函数、阻塞点或资源趋势 | Tool Call、Task、Artifact、专项 Evidence |
| 第 3 轮 | 主动找反证，必要时跨域重规划，并看停止后的恢复 | 被否定分支、方向切换、新证据、恢复窗口 |

如果证据不支持当前假设，正确行为不是把它硬写成结论，而是保留这条分支及其观察和反思，再探索未覆盖的 CPU、内存、I/O、网络、运行时或依赖域。所有“其他未知原因”会按语义合并为一个开放世界兜底，避免同义卡片刷屏。

## 7. 探索树与评分怎么讲

切到 **探索树** 后，先指向树上方的 **Skill 调查路线**。开启 Skill 且命中时，这条虚线泳道会实时显示：候选召回、类别纠偏、完整 `SKILL.md` 加载、当前探针、第 N 轮沿用，以及证据/人工改向后的偏离或退出。点击任一阶段可查看来源文件、SHA-256、加载章节和命中依据；真实工具节点会标记“Skill 路线第 N 步 · 已采用”。

面试时可以这样说：

> Skill 是非证据调查先验，所以放在 LATS 树旁边而不是伪装成证据节点。它建议先查什么；实际 Tool Call、Observation、Reflection 和 Evidence 才进入 LATS 事实链。检索是进程内 BM25 加本地哈希 n-gram/领域概念特征，不依赖 Elasticsearch 或向量数据库；命中后才加载完整 Skill 文档。

1. 默认选择 **树状结构**，从根问题沿父子线看分叉、剪枝、回溯和当前最佳路径。
2. 长文字较多时切到 **轮次路径**，按轮读“为什么转向、用了什么工具、拿到什么证据”。两种视图来自同一份树，不会新建会话。
3. 可拖动画布；右上角按钮依次用于缩小、放大、复位和全屏。
4. 点击节点内 **查看评分**。点击与拖拽已分离，短按打开弹窗，拖动仍移动画布。

| 评分字段 | 正确解释 | 常见误解 |
|---|---|---|
| 访问次数 | 该分支真正参与选择和回传的次数 | 模型提到它的次数 |
| 平均回报 Q | `value_sum / visits`，表示历史环境奖励均值 | 报告置信度或故障概率 |
| 先验概率 | 规划阶段对候选的倾向；只有 PUCT 直接使用 | Evidence 强度 |
| UCT/PUCT 分数 | 本次选择时平衡利用与探索的排序分 | 根因可信度 |
| 本轮奖励 | Observation 经门禁/评估产生的有界反馈 | 模型自评分 |

没有记录的数字应显示“未记录”，不能补成 0。Q、UCT 与最终报告置信度是三类不同数值。

## 8. 事件为什么看起来重复

LATS 每次迭代都会发生“选择 → 模拟/执行 → 观察 → 反思 → 回传”，所以不同迭代中出现同类事件是正常的。页面按 **第 N 次搜索迭代**分组，默认只显示中文摘要；点 **查看原始事件信息**才看到稳定的内部事件名，例如 `lats.node_selected`。

以下才算需要去重：

- 同一事件 ID 被重复返回；
- 同一轮、同一对象、相同语义和相同内容的重复写入；
- 同一轮出现多个仅措辞不同的“其他未知原因”。

以下不能删除：

- 不同轮次对同一分支的重新选择；
- 新 Observation 后的再次反思和回传；
- 数值发生变化的访问次数、Q、奖励或树版本。

## 10. 演示 Skill 启用与关闭对比

页面顶部先展示离线量化卡：540 条受控根因回放中，关闭 Skill 为 42.78%，启用 Skill 为 70.74%；其中固定的 500 组同题同两次工具预算对比为 41.20% 对 68.40%，提升 27.20 个百分点，改善 136 组、退化 0 组、关键采集器提前 187 组。配对差值的 bootstrap 95% 区间为 `[23.2, 31.2]` 个百分点，双侧精确符号检验 `p=2.295887e-41`。这里证明的是“路线策略在项目内受控真值集上的效果”，不是 540 次公网真机注入。随后再用双会话对比证明两条真实路线确实执行；需要统计性线上结论时使用独立的服务端随机实验面板。

### 10.1 点击步骤

1. 在支持对比的故障卡点击 **Skill A/B**，或进入 **验证与 A/B → Skill A/B**。
2. 检查“两组共用问题”。
3. 点击 **启动真实对比**。
4. 对照 **Skill 启用组**和 **不使用 Skill 组**。
5. 查看 Skill 激活、工具调用、证据总数、门禁接受构成、诊断轮次、首条证据时间、真实路线和报告。
6. 点击 **打开该诊断**分别查看两条探索树。
7. 返回验证中心，在 **本浏览器的 A/B 对比历史**中重新打开刚才的两条 ID。

浏览器只保存 AUTO/DISABLED 两条 Diagnosis ID；刷新或返回后，状态和指标从服务端重新读取，不会在本地伪造 Evidence。清除站点数据、无痕窗口或换设备后，本地入口历史不会同步，但服务端诊断记录仍可从“诊断案例”打开。

### 10.2 正确解释结果

- `AUTO` 允许检索已发布 Skill，`DISABLED` 绕过 Skill；两组都必须重新采集当前 Evidence。
- Skill 命中只改变候选 Prior 和探针顺序，不会复制历史根因。
- “支持、反证、中性、受限”都是门禁接受的有效分类，不能只统计支持证据。
- Scope、进程、故障负载、时间窗不一致时，页面显示“当前不是严格同范围实验”；此时只能比较路线，不能宣称准确率或速度提升。
- 单次双会话仍不是统计实验。不要用一次耗时或一次成功率代替长期结果。

### 10.3 服务端随机实验

1. 在 **验证与 A/B** 的持久化实验区新建实验，配置 `AUTO` 比例、每臂最小标注数、最小效果、显著性阈值和安全护栏。
2. 输入稳定的实验单元键和分层键，由服务端带盐哈希分流；页面不能选择自己进入哪一臂，原始单元键也不会保存。
3. 等真实 Diagnosis 到终态后，由人工或受控 Oracle 标注根因是否正确。没有标签就只统计完成率、验证率和工具次数，不统计准确率。
4. 点击评估，查看两臂准确率、效果百分点、两比例 z 检验、95% 置信区间、样本量和安全护栏；后台也会在出现新标签时追加长期快照。
5. 只有满足全部门槛才显示 `ROLLOUT_RECOMMENDED`。具备审批权限的人仍需明确批准；批准记录不等于系统已经修改 Prompt、代码、权限或生产流量。

面试解释：离线 500 组配对实验回答“在固定合同和相同工具预算下是否提升”；服务端随机实验回答“真实流量长期是否仍提升”。两者的样本、标签来源和可宣称范围不同。

## 12. 演示基础采集与火焰图

### 12.1 手工创建采集

1. 在故障广场只点击 **启动故障**。
2. 打开 **采集与任务 → 任务面板 → 新建性能采集**。
3. **目标 Agent**：选择在线采集节点。
4. **可信进程快照**：选择当前新鲜进程，不要复制历史 PID。
5. **采集器**：Python 常用 py-spy，Go 常用 pprof，Java 常用 async-profiler，C/C++ 常用 perf；低开销初筛使用系统指标。
6. **时长（秒）**：控制本次采样窗口。
7. 点击 **开始采集**，打开新任务详情。

选择 `continuous_perf` 时会多出：

| 输入框 | 含义 |
|---|---|
| 窗口（秒） | 原始 Profile 的轮转窗口，单窗最多 900 秒 |
| CPU 触发阈值（%） | 0 表示立即采集；大于 0 时达到阈值才开始 |
| 连续命中次数 | 避免一次尖峰误触发 |
| 等待上限（秒） | 等待触发的最长时间，0 表示最多等到任务结束 |
| 保留层级 | 短期、标准、延长三种保留策略 |

### 12.2 任务详情讲解顺序

1. **采集状态**从待处理、执行、上传、分析到完成。
2. **分析状态**与采集状态分开；材料上传成功不等于分析成功。
3. **Attempt**是一次真实执行，重试会创建新的 Attempt。
4. **产物**列出原始文件、manifest、火焰图、TopN、调用关系图等。
5. **火焰图**横向宽度代表样本占比，纵向代表调用深度，不是时间轴。
6. **TopN**展示热点函数；点击或悬停可与火焰图对照。
7. 空 Profile 会给出质量错误，不会伪造一个看似成功的空火焰图。
8. **进入 AI 诊断**只负责导航；从故障广场“启动并诊断”才能自动形成 Scope → Task → Artifact → Evidence → Report 闭环。

## 13. 证据不足不等于没有故障

看到“证据不足”时按顺序检查：

1. 故障是否仍在运行，是否因时长过短已经停止。
2. 当前 binding 是否仍对应同一个存活进程。
3. Task 是否完成，Analysis 是否成功。
4. Artifact 是否有有效样本，而不是空 Profile。
5. Evidence 是否通过目标、时间、来源、hash 和质量门禁。
6. 当前分支被反证或不可观测后，是否还有预算进入跨域自由探索。
7. 是否已经达到最少轮次、最大轮次、工具预算或时间预算。

工具失败、权限不足、Agent 离线和审批拒绝表示“不可观测”，不是科学反证。只要预算与允许工具还在，Agent 应转向新的证据域；真正耗尽后才带限制结束。

## 14. 常见问题速查

### 页面一直刷新或闪烁

正常情况下使用 SSE；只有事件流断开才进入后台轮询。先看页头“实时事件已连接/轮询兜底中”，再检查 API 会话、反向代理 buffering 和 EventSource。不要用浏览器手动刷新替代状态流。

### 页面停在“准备中”

依次看 Agent 在线状态、进程发现、Diagnosis Worker 消费和诊断事件。不要连续点击“继续推进”，避免制造重复请求。

### 火焰图为空

常见原因是采样窗内没有有效样本、perf/ptrace 权限不足、符号缺失或分析失败。它代表可观测性不足，不代表业务假设为假。

### “查看评分”点不开

确认点击节点内文字按钮，而不是拖动画布；也可切到全屏树后再点。若仍失败，记录浏览器控制台错误和当前 Diagnosis ID，不要只发整页截图。

### 返回验证中心后 A/B 历史不见了

同一浏览器会按保存的两条 ID 恢复。无痕窗口、清站点数据或换设备会丢本地入口，但服务端案例仍在“诊断案例”里。

### 某种语言所有卡片不可用

看卡片的实验室状态和不可用原因。它通常是对应 Go/Java/C++ demo target 未部署或不可达，不需要重启 PostgreSQL、MinIO 或整台服务器。

### 为什么事件中仍有英文

页面主标题、状态、工具和说明中文优先；`LATS`、`CPU`、`JVM`、`eBPF`、`py-spy`、函数名、内部事件码等技术标识在“查看技术详情/查看原始事件信息”中保留，便于审计和查日志。

## 15. 一分钟架构讲稿

> Mini-Drop 是一套证据驱动的 Linux 性能诊断系统。React 页面只访问 Go API；Go API 负责鉴权、范围选择和任务编排；C++ Control 管理 Agent 心跳、租约和任务下发；Linux 上的 C++ Agent 只执行白名单 Collector；原始 Artifact 进入 MinIO，PostgreSQL 保存 Task、Attempt、状态、Evidence、事件、记忆和审计；Python Analyzer 生成火焰图、TopN 和调用图；Diagnosis Worker 使用 LangChain `create_agent` 与 LangGraph 运行多轮规划、Agentic RAG、LATS 和 Skill 路线复用。模型没有任意 shell 权限，结论必须引用当前会话通过门禁的新 Evidence。

再补一句：

> 冻结回放证明可复位的完整 LATS；实时故障证明真实工具和证据链。Skill 是路线记忆，不是历史答案。
