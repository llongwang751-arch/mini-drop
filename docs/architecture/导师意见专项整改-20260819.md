# 导师意见专项整改（2026-08-19）

## 1. 本轮整改目标

本轮只处理导师对 AI 诊断提出的关键问题：固定决策树过于僵化、证据不足就停止、成功经验无法复用、诊断过程像黑盒、源码定位不足、测试结果只有百分比而缺少过程。

## 2. 已完成整改

### 2.1 从固定树升级为“受约束的自适应取证”

- 新增 `server/app/diagnosis/next_probe_planner.py`。
- AI 根据当前假设、已有证据、缺失证据、目标 Agent 能力和历史成功路线选择下一项探针。
- AI 只能从 Probe Registry 已注册探针和当前目标列表中选择，不能生成任意命令。
- R2 探针继续经过审批，人工拒绝是硬门禁；模型不可用时回退到确定性规划。
- 规划结果必须给出取证目的、选择原因、预期现象和证伪条件。

### 2.2 证据不足后自动进入下一轮，而不是直接结束

- `INSUFFICIENT_EVIDENCE` 报告会触发下一轮假设和工具规划。
- 已尝试工具会被排除，最多自动规划 3 轮，防止无限循环。
- 若 Agent 离线、能力不匹配或预算耗尽，系统明确记录停止原因。
- 前端决策路径显示 `planner.insufficient_replanned`、`adaptive_probe_planned` 等事件。

### 2.3 成功路线形成可审计的经验反馈

- VERIFIED 报告会记录 `diagnosis.route_learned`。
- 历史成功路线只影响后续候选工具排序，不会自动注册新工具、绕过审批或覆盖证据规则。
- 自适应规划器会同时看到实时证据缺口和历史路线先验。

### 2.4 诊断过程对用户透明

前端技术细节的“决策路径”会展示：

1. 为什么提出当前假设；
2. 为什么选择该采集器；
3. 预期采到什么；
4. 什么结果会推翻假设；
5. 为什么继续、重规划或停止。

### 2.5 热点函数到源码行的复核入口

- Python 使用 AST，Go 与 C/C++ 使用保守的函数定义扫描器。
- 只扫描管理员通过 `MINI_DROP_SOURCE_ROOTS` 配置的目录。
- 诊断报告保存 `source_context`，前端“源码定位”页展示文件、函数、起止行和循环/锁/I/O 等复核信号。
- 源码映射只是复核线索，不单独作为根因证据。

### 2.6 评测从“只看 100%”升级为可追溯过程

- Golden 评测新增独立 HTML 报告，展示标准答案、系统输出和每项判定。
- 增加“诊断分析覆盖率”，定义为分类、证据校验和反证规划三段均完成，而非简单统计模型调用次数。
- 90 次策略 Campaign HTML 展示三种策略对比、逐次得分、根因命中情况和缺失证据。
- Oracle 只在诊断完成后的评分阶段加载，规划输入中不包含标准答案。

生成命令：

```bash
python scripts/run_diagnosis_eval.py --output-dir reports/mentor-remediation
python scripts/diagnosis_benchmark.py evaluate reports/benchmark/official-90/submissions.json \
  --require-complete --output reports/benchmark/official-90/evaluation.json
```

第二条命令除 JSON 外会自动生成同名 HTML 文件。

### 2.7 独立的 OTel orchestrator-backed live subset

- 新增 `scripts/run_live_subset.py`，只覆盖 `T1-CPU-001` 与 `T1-MEM-001`。
- 每个案例按 3 种策略、3 次重复执行，共 18 个唯一 execution ID；每个案例/重复共享一个有界故障窗口，共 6 个 raw manifest。
- CPU 与内存窗口都先完成 baseline task，再开启 incident；诊断结论来自 `/api/v1/diagnoses` 的真实终态数据，不从 `CASE_RUNTIME`、`SUPPORTED_TAGS` 或 Oracle 拼装。
- 三策略 submission 采用原子分组发布。fixture 无信号、PID 变化、清理失败或内存恢复失败时保留 manifest，但不发布无效 submission，也不静默重跑覆盖失败。
- Oracle 仅在 18 次诊断终态冻结后由 evaluator 读取；最终门禁要求 18 个 ID 完整唯一、6 个 manifest 可追溯且全部清理成功。
- 当前状态是实现与聚焦回归完成，尚未执行云端正式 18-run，因此没有把它写成已完成的现场结果，也没有修改历史 `reports/benchmark/official-90`。

## 4. 仍需环境验收的边界

- 源码定位需要在部署环境配置源码只读目录，并用真实带符号采样产物验收。
- eBPF、perf、async-profiler 的最终真实性仍以原生 Linux Worker 为准。
- 自适应路线效果需要结合真实故障 Campaign 持续观察，不能仅依据 Golden 全通过宣称生产准确率。
- OTel 18-run live subset 仍需在云端原生 Linux 完成只读预检、CPU/MEM smoke、warmup、6 个正式窗口和最终报告门禁；当前测试结果不能替代该验收。
- 本轮没有让 AI 自动执行修复；系统输出修复建议，变更仍由人工确认。
