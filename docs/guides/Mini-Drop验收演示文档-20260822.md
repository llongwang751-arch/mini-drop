# Mini-Drop 验收演示文档：基础链路、AI 循证诊断与统一测试集

> 适用项目：`D:\tx\mini-drop`  
> 云端入口：<https://47.112.10.137/>  
> 云端发布目录：`/opt/mini-drop-li-mingyuan-release-6af735f`  
> 文档日期：2026-08-22  
> 推荐演示时长：20～25 分钟；完整验收约 60～90 分钟  
> 重点：AI 不是直接猜根因，而是完成“确认范围 → 生成可证伪假设 → 决策树取证 → 证据裁决 → 结论验证”。

## 1. 这次验收到底要证明什么

验收不是只证明“网页能打开”，而是分四层证明：

| 层级 | 要证明的内容 | 最低通过证据 |
|---|---|---|
| 服务层 | Web、API、Server、数据库、Analyzer 等组件已启动 | 首页和 `/api/healthz` 返回 `200`；核心容器健康 |
| 采集层 | 任务确实下发到 Agent，原始数据确实被采集 | Task `DONE`、TaskAttempt `SUCCEEDED`、Artifact `VERIFIED` |
| AI 层 | AI 会确认范围、提出假设、选择工具、引用证据并控制结论边界 | 非零置信度结论或可解释的 `INSUFFICIENT_EVIDENCE`；存在 `evidence_refs` |
| 评测层 | 不是拿预填答案演示，而是先制造故障、再诊断、最后才看标准答案 | baseline/incident/recovery 三段快照、隐藏 Oracle、恢复清理、独立运行 ID |

验收时反复强调一句话：

> Mini-Drop 的目标不是让大模型替工程师“猜”，而是把性能诊断变成一条有范围、有工具权限、有原始证据、有反证、有置信度、可复测的工程流程。

## 2. 系统原理：一句话背后的真实链路

### 2.1 基础采集链路

```text
Web 创建任务
  ↓
Go API 做认证、参数校验和协议转发
  ↓
Python Server 保存任务、状态迁移和审计记录
  ↓
C++ Control Plane 把任务下发给指定 Agent
  ↓
目标主机上的 Agent 对指定 PID 执行 perf/eBPF/py-spy 等采集
  ↓
原始产物上传 MinIO，元数据写 PostgreSQL
  ↓
Python Analyzer 生成火焰图、TopN、趋势图或延迟直方图
  ↓
Web 展示结果
```

### 2.2 AI 循证诊断链路

```text
用户描述现象
  ↓
AI 确认服务、环境、Agent、PID、故障时间窗
  ↓
生成多个“可被证据支持，也可被证据推翻”的候选假设
  ↓
性能决策树选择区分度最高的采集器
  ↓
策略引擎检查参数、风险、预算和是否需要人工审批
  ↓
Agent 真实采集，Analyzer 生成结构化证据
  ↓
证据裁决：支持证据 + 反证 + 时间一致性 + 完整性
  ↓
证据足够：输出根因、置信度、evidence_refs、限制和修复建议
证据不足：明确拒答，并开启下一轮取证
  ↓
修复后按相同口径复测
```

### 2.3 关键名词的人话解释

| 名词 | 人话解释 |
|---|---|
| Agent | 安装在被观察机器上的“采集工人”。它保持心跳、领取任务、执行采集器并上传结果；每台机器通常部署一个。 |
| PID | 进程编号。必须填写所选 Agent 所在机器能看到的 PID，不能把另一台机器的 PID 填进来。 |
| Collector | 采集工具，例如 perf、eBPF、py-spy、async-profiler、pprof。不同工具回答不同问题。 |
| TaskAttempt | 一次具体执行尝试。Task 是需求，TaskAttempt 才是 Agent 真正执行过的记录。 |
| Artifact | 采集产生的文件，例如 perf.data、火焰图 JSON、系统指标 JSON。 |
| `VERIFIED` | 产物经过哈希和完整性检查，可以作为诊断证据。 |
| 可证伪假设 | 不只是“可能是 CPU”，而是同时写清支持条件和推翻条件，例如“若热点集中在 1～3 个业务函数则支持；若内核态占比更高则推翻”。 |
| 性能决策树 | 先判断 CPU/内存/I/O/网络/依赖等故障域，再选择能区分候选根因的工具，避免固定命令行。 |
| `evidence_refs` | 结论引用的证据 ID。点击或查询后应能回到真实任务、快照或产物。 |
| Oracle | 测试集中的标准答案。诊断完成前 AI 看不到，结束后才由评测器揭示并对比。 |
| Campaign | 一次完整实验：基线 → 制造故障 → 确认异常 → 采集 → AI 诊断 → Oracle 对比 → 清理恢复。 |
| 反证门禁 | 只要关键证据缺失或存在可信反证，就不让系统输出确定根因。 |
| `INSUFFICIENT_EVIDENCE` | 证据不足，不是根因结论，也不是系统故障；表示系统选择停止编造。 |

## 5. 演示一：真实故障 Campaign——最重要的一条端到端链路

这一段最适合当作主线，因为它能稳定产生真实异常，也能得到完整诊断和标准答案对比。

### 5.1 页面点击步骤

1. 左侧点击 **AI 诊断**。
2. 左侧工作区点击 **方法与测试集**。
3. 在主区域找到 **真实故障 Campaign（先制造故障，再评测）**。
4. 先选择 **Python 进程 CPU 热点**。
5. 确认卡片标签包含：
   - `CPU_HOTSPOT`
   - `R1`
   - `自动清理`
   - `T1-CPU-001`
6. 点击 **一键制造故障并评测**。
7. 不要重复点击；等待页面依次推进八个阶段。

### 5.2 八个阶段分别在做什么

| 阶段 | 系统实际动作 | 现场讲解文案 |
|---|---|---|
| 1. 安全预检 | 检查目标健康、故障开关存在且可回滚 | “第一步不采集，先确认目标和清理开关可用，避免实验留下脏状态。” |
| 2. 基线快照 | 在无故障状态记录 CPU/RSS/延迟等指标 | “没有基线就只能看到高，不能证明是故障造成的变化。” |
| 3. 真实注入 | 调用白名单接口启动有限时、可回滚的忙循环 | “页面没有执行任意 shell，只调用注册过的故障开关。” |
| 4. 异常确认 | 比较故障快照和基线，确认指标确实变化 | “如果指标没变，系统不会继续把它当成有效故障。” |
| 5. 任务取证 | 创建 Mini-Drop 采集任务，由 Agent 执行并上传产物 | “这一步复用了基础采集链路，不是 AI 自己编数据。” |
| 6. 循证诊断 | 决策树结合证据输出根因、置信度、推理链和引用 | “AI 的每个结论必须挂到真实快照或任务证据上。” |
| 7. Oracle 对比 | 诊断结束后才读取标准答案并评分 | “标准答案和诊断过程隔离，避免把答案提前喂给模型。” |
| 8. 恢复验证 | `finally` 关闭故障，采集恢复快照并检查回落 | “即使中间失败，也会进入清理；恢复快照证明环境真的回到正常状态。” |

### 5.3 页面上必须看到的通过证据

Campaign 完成后展开并核对：

- 状态：`COMPLETED`；
- 三段快照：`baseline_snapshot`、`fault_snapshot`、`recovery_snapshot`；
- CPU 故障窗口明显高于基线，恢复窗口重新回落；
- 关联 Task 状态 `DONE`；
- TaskAttempt 存在且成功；
- Artifact 标记 `VERIFIED`；
- Analyzer Job 成功或显示该场景无需独立 Analyzer Job；
- AI 根因：`SELF_CODE_CPU_HOTSPOT`；
- 置信度为非零；
- `evidence_refs` 至少引用快照和任务证据；
- Oracle 对比：根因命中 `PASS`、证据完整 `PASS`、恢复清理 `PASS`。

数值不要背死。CPU 基线、故障和恢复会随云服务器负载变化，验收看的是“基线低 → 故障明显升高 → 恢复回落”的相对关系。

### 5.4 建议现场讲解文案

> 我先不让 AI 直接回答，而是启动一个受控 CPU 故障。系统先采正常基线，再开启真实忙循环，确认异常确实发生，然后通过 Agent 创建采集任务。AI 只能使用这条链路生成的快照和已校验产物。诊断完成后评测器才揭示 Oracle，最后无条件停止故障并验证 CPU 回落。因此这里展示的不是预填答案，而是一条能重复、能失败、能清理、能审计的实验链路。

### 5.5 其他九个 Campaign 怎么选

完整测试目录包含 10 类场景：

| 页面场景 | 故障类型 | 期望根因 |
|---|---|---|
| Python 进程 CPU 热点 | CPU_HOTSPOT | SELF_CODE_CPU_HOTSPOT |
| Python 进程内存持续增长 | MEMORY_LEAK | SELF_CODE_RETAINED_MEMORY |
| Python 进程同步 I/O 写入 | IO_LATENCY | SELF_CODE_SYNC_IO |
| 下游服务响应变慢 | DOWNSTREAM_LATENCY | DOWNSTREAM_SERVICE_LATENCY |
| 依赖边网络延迟 | NETWORK_LATENCY | DEPENDENCY_EDGE_NETWORK_LATENCY |
| Java 服务手动 Full GC 压力 | GC_PRESSURE | MANUAL_FULL_GC_PRESSURE |
| Python 源码级热点函数 | SOURCE_HOTSPOT | DOMINANT_SOURCE_HOT_FUNCTION |
| 同宿主机噪声邻居 | NOISY_NEIGHBOR | SAME_HOST_NOISY_NEIGHBOR |
| 流量洪峰导致容量饱和 | LOAD_SATURATION | HOMEPAGE_TRAFFIC_SATURATION |
| 生产消费失衡导致队列积压 | QUEUE_BACKLOG | PRODUCER_CONSUMER_IMBALANCE |

现场时间有限时只跑 CPU；完整验收再补内存、下游延迟和噪声邻居，覆盖自身代码、依赖边和同宿主机三类根因。

## 6. 演示二：自然语言 AI 诊断——证明它不是固定命令行

### 6.1 创建会话时输入什么

1. 切回 **AI 诊断 → 诊断工作台**。
2. 点击 **新对话**。
3. 输入下面这句话：

```text
订单服务最近 5 分钟 CPU 飙高，请定位原因
```

4. 点击 **发送**。

预期状态为 `NEEDS_CLARIFICATION`。这是正确行为，因为当前只知道现象，不知道采哪台机器、哪个进程和哪个时间窗。

### 6.2 “AI 需要确认诊断范围”怎么填

优先点击右上角 **使用在线演示目标**，系统会从在线 Agent 和候选进程中填入可用目标。然后逐项检查：

| 字段 | 演示输入 | 注意事项 |
|---|---|---|
| 服务 | `order-service` | 业务标签，可按实际服务修改 |
| 环境 | 选择 `demo` | 不要把测试环境写成 production |
| 在线 Agent | 选择页面推荐的在线 Agent | Agent 必须与 PID 位于同一主机 |
| 目标 PID | 使用按钮自动选择的候选 PID | PID 每次启动可能变化，不要照抄历史数字 |
| 开始时间 | 当前时间往前 5 分钟 | 覆盖告警/故障窗口 |
| 结束时间 | 当前时间 | 必须晚于开始时间 |

点击 **确认范围并开始取证**。

如果没有候选 PID：先到 **任务 → 任务面板** 查看在线 Agent 和候选进程；不要随便填 `1`，也不要把 control 主机的 PID 配给 worker Agent。

### 6.3 六步诊断条怎么讲

1. **理解问题**：抽取服务、现象、时间窗。
2. **确认范围**：绑定 Agent、PID 和环境，防止采错机器。
3. **生成假设**：至少覆盖用户态热点、内核态开销、锁竞争/自旋和 unknown 兜底。
4. **决策树取证**：优先选能区分候选根因的采集器。
5. **证据裁决**：检查支持证据、反证、完整性和时间一致性。
6. **结论验证**：输出根因、置信度、证据引用、限制和复测建议。

专家模式下重点展示每个假设都包含：

- 决策依据；
- 期望观察；
- 证伪条件；
- 当前状态（待验证/支持/被推翻）；
- unknown 兜底。

### 6.4 工具审批怎么操作

当出现 `perf CPU 采样` 等工具卡时，先核对：

- Agent 是否正确；
- PID 是否正确；
- 采样时长是否合理；
- 风险等级；
- 是否显示 `REQUIRE_APPROVAL`。

确认无误后点击 **批准并执行**。拒绝时点 **拒绝**，拒绝理由会进入审计，AI 应选择其他取证路径。

批准后：

1. 工具卡状态从等待审批进入创建/执行；
2. 左侧打开 **任务 → 任务面板**，能找到关联 Task；
3. 等 Task 到 `DONE`；
4. 返回 AI 页面点击 **继续推进**；
5. 系统读取成功 TaskAttempt 和 VERIFIED Artifact，生成证据裁决。

### 6.5 如何判断得到了“真正的结论”

真正结论至少同时显示：

- 具体根因，不是泛泛的“CPU 高”；
- 非零置信度；
- `evidence_refs`；
- 支持证据；
- 反证或替代解释；
- 诊断限制；
- 修复建议和复测方案。

如果显示 `INSUFFICIENT_EVIDENCE` 和 0%：

1. 这不是根因结论；
2. 先检查关联 Task 是否 `DONE`、TaskAttempt 是否成功、Artifact 是否 `VERIFIED`；
3. 点击 **继续推进** 让系统切换下一轮取证；
4. 若系统确实漏读了页面已有证据，选择 **已有证据被遗漏**；
5. 若采集方向错误，选择 **诊断方向错误**；
6. 若证据确实不够，选择 **确认证据不足**。

现场需要稳定展示完整根因时，以第 5 节的真实 Campaign 结论为主；自然语言会话用于证明范围确认、假设、工具治理和多轮诊断。

### 6.6 修复前后验证怎么用

1. 保存修复前 Task 和指标；
2. 人工修改服务或关闭故障，AI 不直接改生产代码；
3. 用相同 Agent、采集器、时长和负载创建修复后 Task；
4. 在修复验证区选择前后两条任务；
5. 点击比较；
6. 检查 CPU、延迟、RSS 或热点函数是否改善。

关键原则：前后对比必须保持采集口径一致，否则下降可能来自负载变化，而不是修复有效。

## 7. 演示三：基础任务链路——证明 AI 证据来自真实采集

![任务面板](../images/tutorial-v2/01-task-dashboard.png)

### 7.1 点击和输入

1. 左侧点击 **任务 → 任务面板**。
2. 选择 **快速可视化**。
3. 先选 **系统指标**，它对环境要求最低。
4. 选择在线 Agent，例如当前在线的 `li-mingyuan-worker-1` 或页面实际显示的 Agent。
5. 从候选进程选择 PID。
6. 采样时长输入：

```text
15
```

7. 点击 **创建并查看结果**。

### 7.2 观察状态机

```text
PENDING → RUNNING → UPLOADING → ANALYZING → DONE
                                        └→ FAILED
```

每次状态迁移都应有时间和 reason：

- `PENDING`：数据库已创建任务；
- `RUNNING`：Control 已下发，Agent 正在采集；
- `UPLOADING`：产物正在上传；
- `ANALYZING`：Analyzer 正在解析；
- `DONE`：分析和完整性检查通过；
- `FAILED`：必须指出失败步骤和原因。

### 7.3 详情页通过标准

- 总状态 `DONE`；
- 采集状态 `SUCCEEDED`；
- 分析状态 `SUCCEEDED`；
- TaskAttempt 存在；
- Artifact 非空且 `VERIFIED`；
- 可下载原始文件；
- 系统指标页面能看到 CPU/负载/线程/FD/网络等维度。

然后再演示 **CPU 火焰图**：选择忙碌目标 PID，时长 15～30 秒。通过标准是火焰图不为空、TopN 有热点函数，并能点击帧下钻或联动高亮。

## 12. 常见失败怎么处理

### 12.1 Campaign 卡在某一步很久

真实 Campaign 包含采样、分析和大模型响应，数分钟属于可能范围。先看阶段是否仍在推进，不要重复点击。

control 上查看日志：

```bash
cd /opt/mini-drop-li-mingyuan-release-6af735f
docker compose --env-file deploy/env/cloud-control.env \
  -f docker-compose.cloud-control.yml \
  logs --tail=200 campaign-agent diagnosis-worker server analyzer
```

### 12.2 `python-hotspot` 无法解析

说明 Campaign 目标服务没启动或不在同一 Compose 网络：

```bash
docker compose --env-file deploy/env/cloud-control.env \
  -f docker-compose.cloud-control.yml \
  up -d python-hotspot downstream-service network-proxy java-hotspot campaign-agent server web
```

### 12.3 `task has no completed TaskAttempt`

该 Task 没有成功执行尝试，不能作为证据。回任务详情，选择 `DONE` 且 TaskAttempt 为 `SUCCEEDED` 的任务。

### 12.4 AI 一直停在范围确认

检查服务、环境、在线 Agent、正整数 PID、开始时间、结束时间六项是否完整；结束必须晚于开始。按 `Ctrl+F5` 后重新填写，避免旧前端轮询覆盖表单草稿。

### 12.5 结论一直是 0%

0% 通常表示没有被接受的支持证据。检查：

1. 采集任务是否完成；
2. Artifact 是否 `VERIFIED`；
3. 采集时间是否覆盖故障时间；
4. 采集器是否能区分当前候选；
5. 是否需要点击 **继续推进** 开启下一轮。

### 12.6 eBPF 或 perf 失败

Windows Docker Desktop 常受 WSL2 内核、PID 命名空间和权限限制。最终 perf/eBPF 验收放到云端原生 Linux；检查 tracefs、BPF/PERFMON、ptrace 和目标 PID 可见性。
