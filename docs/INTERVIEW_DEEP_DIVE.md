### 1.2 一道题怎么被追到五层

以“为什么要做 Outbox”为例：

1. **功能层**：创建任务后为什么不能直接发消息？——讲清数据库提交与远程发送之间的失败窗口。
2. **实现层**：写哪几张表？在哪个事务？——定位 Task、状态事件、Outbox 的原子提交。
3. **并发层**：两个 dispatcher 怎么抢？——锁、租约、重领、幂等。
4. **反例层**：消息已经发送，标记成功前崩溃怎么办？——仍可能重复，消费者必须去重。
5. **取舍层**：为什么不用 Kafka？十万节点还用表队列吗？——先说当前规模，再说迁移条件和保留的语义。

能把“为什么”说清是起点；能主动提出反例，才说明你知道方案的适用范围。

### 2.3 九十秒项目介绍示例

“Mini-Drop 是一个面向 Linux 多节点的性能诊断项目，想解决的是：采到了很多数据，但很难把异常、目标进程、取证过程和结论连起来。基础链由 Go API 接收任务、C++ Control 和 Agent 执行白名单采集，原始产物进入 MinIO，状态与审计进入 PostgreSQL，Python 做分析。

AI 部分使用 LangChain 与 LangGraph 提出调查假设，再由后端检查目标绑定、策略和预算后取证。报告必须引用有效证据；采集失败只能说明可观测性不足，不能当成反证。Skill 提供可复用路线，实时搜索采用有预算的 LATS 适配。

我会重点展开自己实际理解和参与的两个难点：任务重试下的一致性，以及诊断结论如何受证据约束。项目已有三个 Agent 和受控场景验收，但没有大规模生产准确率或容量结论。”

**如果被问“你自己做了什么”：** 区分亲手设计、借助 AI 生成、自己审查和复现的部分。给出一个能现场改代码、解释失败测试的模块；不要把本手册变成虚构的个人经历。

## 3. 架构与职责：Q01—Q10

### Q01【P0】为什么这个项目有价值？现成监控平台不够吗？

**回答要点：** 监控擅长发现趋势，profiling 擅长展示栈，Mini-Drop 尝试连接“异常 → 假设 → 受控取证 → 证据裁决 → 报告”。价值是可追溯的诊断过程，不是声称替代所有监控产品。用一个 CPU 热点例子走完整链，再说明 I/O 归因不足时要停在“尚未定位”。

**追问：** 用户是谁？没有 AI 能不能用？——用户可理解为开发／性能排障人员；基础采集可独立使用。没有 AI 时少了自动规划，不应丢掉采集和审计能力。

**容易失分：** 只说“接了大模型，智能化程度更高”，说不出用户省下了哪一步。参见 [学习手册](PROJECT_LEARNING_GUIDE.md)。

### Q02【P0】为什么同时用 Go、C++、Python？

**回答要点：** Go 管公开请求与并发连接；C++ 接近 Linux 采集与原生工具；Python 适配分析和 Agent 生态。这是职责与生态的权衡，不是三种语言越多越先进。代价是协议生成、错误码、部署版本、观测和排障复杂度都增加。

**追问：** 单人项目会不会过度设计？如果重做呢？——先承认复杂度。可以保留进程边界而简化语言数量，比较开发维护成本后再决定，不凭语言口号说性能更好。

**源码落点：** [Go API](../apiserver/internal/httpapi/server.go)、[Control](../native/control/src/main.cpp)、[Diagnosis Agent](../server/app/drop_insight/diagnosis_agent.py)。

### Q03【P0】从点击“采集”到看到火焰图，完整链路是什么？

**回答要点：** 请求校验与进程绑定 → Task／事件／Outbox 落库 → Control 调度 → Agent 领取并建立尝试 → 白名单 Collector 运行 → 产物上传并报告 → AnalysisJob 校验输入血缘与分析 → 展示 Artifact／TopN／图。每个箭头都要能讲失败状态和恢复入口。

**追问：** 哪一步最慢？——不能脱口而出数据库；分别量排队、采样窗口、上传、分析、模型与前端读取耗时。CPU 采 15 秒，本身就有时间下界。

**源码落点：** [任务仓库](../apiserver/internal/repository/postgres.go)、[Agent 主循环](../native/agent/src/main.cpp)、[分析 Worker](../server/app/analysis_jobs.py)。

### Q04【P0】基础采集和 AI 诊断有什么区别？

**回答要点：** 基础采集由人选目标和工具；AI 诊断先确认范围，提出可证伪假设，选择探针，再消费同一条基础链的结果。AI 多出来的是规划、记忆、搜索和证据裁决，而不是获得了另外一套高权限 shell。

**追问：** AI Worker 挂了能不能继续采？——从架构职责上基础链独立，但实际可用性还受公共入口、Control、数据库和部署健康依赖影响；不能简单承诺任何故障都无影响。

**不要答：** “基础链确定，AI 链就可以不确定地随便执行。”

### Q05【P0】Task、Attempt、AnalysisJob 为什么不能一张表解决？

**回答要点：** Task 表达用户意图；Attempt 记录某次执行身份、授权与结果；AnalysisJob 绑定某批输入和分析器版本。重采样与重新分析不是同一件事，混在一起会覆盖失败历史，也难解释迟到结果属于哪次尝试。

**追问：** 新版分析器能分析旧产物吗？——可以作为设计上的再分析，但应产生新的分析作业及版本血缘，不能无痕覆盖旧结论。

**源码落点：** [模型](../server/app/models.py)、[分析作业仓库](../server/app/repositories/analysis_job_repo.py)。

### Q06【P1】为什么文件放 MinIO，元数据放 PostgreSQL？

**回答要点：** 大产物适合对象存储；状态、关系、权限、事件和索引适合关系库。两者没有天然同一个事务，所以要有上传、登记、校验、可用状态的明确顺序，并能识别“对象有了但登记失败”“登记了但对象缺失”。hash 证明字节一致，不能证明采样对象正确。

**追问：** 孤儿对象怎么清理？——提出保留期、引用检查、可恢复删除与审计方案，并明确不是本次已经实现的自动治理能力。

**源码落点：** [上传器](../native/agent/src/artifact_uploader.cpp)、[产物校验](../server/app/artifact_integrity.py)。

### Q07【P0】状态机到底解决什么问题？

**回答要点：** 状态机定义允许的迁移、触发者和终态，避免乱序回报把取消任务改回运行。采集成功与分析成功分开：有原始文件不一定有可用图，有报告也不等于故障修复。

**追问：** 页面出现两个状态冲突怎么办？——先查各状态的含义、权威来源和更新时间，不能靠前端把红色改绿色；找 Task、Attempt、AnalysisJob 与事件的一致性。

**源码落点：** [状态机](../server/app/state_machine.py)、[Go 状态合同](../apiserver/internal/taskstatus/statuses.go)。

### Q08【P1】共享数据库是不是破坏服务边界？

**回答要点：** 当前是多进程协作、共享领域数据的工程，不宜包装成完全解耦微服务。共享库便于事务与诊断审计，但表结构、迁移和写入约束耦合明显。需要明确每类状态的写入入口、版本兼容和约束，而不是“谁都能改”。

**追问：** 未来拆库怎么办？——先列跨表不变量；拆开后用事件和补偿替代部分本地事务，接受更复杂的一致性与恢复成本。不得承诺拆库后仍原样拥有跨库原子性。

### Q09【P1】为什么不用 Redis／Kafka／Kubernetes？

**回答要点：** 当前节点数与吞吐没有证明必须引入这些设施。PostgreSQL 的事务、表队列与持久事件能覆盖当前需求；Docker Compose 管理现有部署。新设施应解决测出来的瓶颈，而不是提高简历名词密度。

**追问：** 面试官指定用 Kafka 怎么设计？——保留数据库事务 Outbox，异步发布到分区日志；按合适的业务键确定顺序域，消费者仍幂等。Kafka 不自动解决数据库与外部副作用一致性。

**事实边界：** 上述扩展是方案讨论，不是当前主线已部署。

### Q10【P2】扩到一万 Agent，最先改哪里？

**回答要点：** 先做容量模型。假设每 Agent 每 5 秒心跳，一万节点约 2,000 次／秒；这是计算示例，实际频率看配置。评估 TLS/gRPC、Control 线程、数据库心跳写放大、快照大小与 SSE 读放大，再决定分片、批量写、心跳与任务领取解耦。

**追问：** 可以把心跳全放缓存吗？——存活视图可容忍短时近似，任务执行权和审计事实不能因此丢失。先分清数据语义，再选存储。

**设计要求：** 租户限额、带抖动的重连、每节点采样预算、压测停止阈值；不把一万节点说成现有能力。

## 4. 分布式可靠性：Q11—Q20

### Q11【P0】用户点一次，浏览器重试两次，如何只创建一个任务？

**回答要点：** 用调用者与幂等键定义请求身份，保存规范化请求参数；相同键相同参数返回原 Task，相同键不同参数拒绝。唯一约束兜底并发，不能只用“先查再插”。没有提供幂等键时当前实现保留普通创建语义。

**追问：** trace ID 变了算参数变化吗？——链路追踪字段不应改变任务业务身份。空键也不能全部存空字符串造成唯一键碰撞。

**源码：** [resolveIdempotentTask 与创建事务](../apiserver/internal/repository/postgres.go)、[参数回归](../apiserver/internal/repository/postgres_test.go)。

### Q12【P0】Task 提交成功，但发消息前进程死了怎么办？

**回答要点：** 当前创建逻辑在一个 PostgreSQL 事务里写 Task、状态事件和 Outbox。dispatcher 可以从持久 Outbox 继续发布，因此不依赖 API 进程在提交之后活着。

**追问链：** 提交前死？三者一起回滚。提交后发送前死？重领 Outbox。发送成功标记前死？可能再发，靠幂等消除重复业务效果。

**不要答：** “用了 Outbox 就是端到端 exactly-once。”

**源码：** [创建事务](../apiserver/internal/repository/postgres.go)、[Outbox dispatcher](../server/app/outbox_dispatcher.py)。

### Q13【P0】两个 Worker 同时领取同一条记录呢？

**回答要点：** 在事务内选择可领取行并加锁，当前 Outbox 领取使用 `FOR UPDATE SKIP LOCKED`，随后写 owner、期限和状态。执行网络调用时不应持有长事务。SKIP LOCKED 让其他消费者跳过被锁记录，提高并发领取能力，但不保证严格 FIFO，也不是通用一致查询。见 [PostgreSQL SELECT](https://www.postgresql.org/docs/16/sql-select.html)。

**追问：** Worker 领完死了？——靠租约过期重领。长期占锁的任务会饥饿吗？——需要观察最老待处理年龄，不能只看吞吐。

**源码：** [claim_outbox_messages](../server/app/repositories/outbox_repo.py)。

### Q14【P0】有租约为什么还要 fencing token？

**回答要点：** A 停顿导致租约过期，B 接管后 A 又恢复。租约只表达谁“应该执行”，不能让 A 的 CPU 自动停止。代次 token 随接管递增，写入时要求 token、owner、期限匹配，拒绝旧执行者更新。

**追问：** 远程系统不检查 token 呢？——那只能保护检查 token 的边界；外部副作用还需要幂等键或接收端约束。不能把数据库防旧写扩大成所有外部操作 exactly-once。

**源码：** [报告副作用 claim／renew／complete](../server/app/drop_insight/service.py)，搜索 `effects_fencing_token`；不同子系统的所有权机制不必完全相同。

### Q15【P0】采集成功，结果上报网络断了，要重新采吗？

**回答要点：** 优先重试已完成结果的上报，而不是重跑有成本的采集。原生 Agent 的结果 Outbox 保存执行身份、产物和错误信息，重启后可继续投递。接收端仍要校验 Attempt 与授权，防止迟到结果挂到新尝试。

**追问：** 本地写到一半断电？——检查序列化版本、长度边界、临时文件与持久化顺序；原子 rename 和 fsync 解决不同层的问题，不能只靠“有文件”。

**源码：** [result_outbox.cpp](../native/agent/src/result_outbox.cpp)、[结果 Outbox 测试](../native/agent/tests/result_outbox_test.cpp)。

### Q16【P0】超时重试到底怎么分层？

**回答要点：** 区分请求没发出、执行状态未知、工具明确失败、结果质量不足和模型输出不合法。读取可有界重试；创建和派发需要幂等；采样重做会产生新窗口，不能伪装成同一次观测。指数退避、抖动、最大次数与总 deadline 配合使用。

**追问：** 五层各重试三次？——最坏放大很大，重试所有权应尽量集中，每层消耗同一总预算。gRPC deadline 不等于自动撤销服务端已经完成的副作用。见 [gRPC Deadlines](https://grpc.io/docs/guides/deadlines/)。

### Q17【P1】用户取消采集，为什么不能只改数据库状态？

**回答要点：** 需要控制路径到达 Agent，停止对应 Collector 及其受控进程组，处理上传／上报竞态，并让服务端拒绝不合法的迟到状态迁移。取消请求成功与工作已停止是两个时点。

**追问：** 误杀目标业务怎么办？——停止的是采集器拥有的子进程组，不是未经区分地 kill 目标 PID。核对进程身份和进程组归属。

**源码：** [process_runner.cpp](../native/agent/src/process_runner.cpp)、[Agent 主循环](../native/agent/src/main.cpp)。

### Q18【P0】事件流重连如何补漏？

**回答要点：** 事件持久化，客户端保存已消费游标，重连从游标之后读取。诊断 SSE 使用该 Diagnosis 的 sequence，不是墙上时钟；前端按事件身份去重、不能把别的会话混进来。浏览器原生 EventSource 的 `Last-Event-ID` 是协议机制，自定义 fetch 流则要自己管理重连。见 [SSE 标准](https://html.spec.whatwg.org/multipage/server-sent-events.html)。

**追问：** 超过事件保留期？——返回可识别的游标失效并加载快照，是应设计的恢复路径；不要假设无限保留或声称当前已实现所有过期策略。

**源码：** [streamDropInsightEvents](../apiserver/internal/httpapi/server.go)。

### Q19【P1】慢消费者和背压怎么处理？

**回答要点：** 分开处理任务积压、模型调用积压、产物上传积压和页面事件积压。限队列、限并发、设超时、记录最老消息年龄；可合并的是展示刷新，不能随便丢关键业务事件。当前 SSE 周期性读库，连接变多会放大数据库读取。

**追问：** 为什么不无限加 Worker？——数据库连接数、同机采样干扰、模型配额和对象存储带宽都可能先饱和。扩容要根据瓶颈与预算，不只看队列长度。

### Q20【P1】怎么设计故障注入来证明可靠性？

**回答要点：** 在“提交前／提交后”“领取后／写结果前”“上报成功／本地确认前”分别终止测试进程，观测恢复后 Task、Attempt、事件、产物是否重复或缺失。加入并发接管、旧 token 回写、乱序响应与重复上传。

**追问：** 为什么 SQLite 测试不能证明 PostgreSQL 竞争正确？——SQLite 的锁与并发模型不同，部分 `FOR UPDATE` 在本地不起同样作用；要在隔离 PostgreSQL 实例里验证竞争。

**已有证据：** [PostgreSQL 并发测试](../tests/test_drop_insight_report_effects_postgres.py)。本文设计的其他注入点不能自动算成已跑过。

## 5. PostgreSQL：Q21—Q30

### Q21【P0】ACID 分别如何落到这个项目？

**回答要点：** 原子性对应 Task／事件／Outbox 同进退；一致性对应外键、唯一键和业务状态不变量；隔离性定义并发事务能看到什么；持久性依赖日志刷盘等机制与实际配置。ACID 的 C 不等于 CAP 的一致性。

**追问：** commit 返回就永不丢？——仍取决于存储可靠性、持久化配置、同步复制策略与故障范围。单机成功不能推出机器永久损坏后无丢失。

**项目练习：** 画出 Q12 的事务，标出 MinIO 上传在哪个边界之外。

### Q22【P0】PostgreSQL 的 MVCC 是什么？与 MySQL 怎么区分？

**回答要点：** 多版本让查询依据快照决定可见数据，降低常见读写冲突。PostgreSQL 以堆元组版本和事务可见性为核心，旧版本由 VACUUM 等机制处理；不要直接讲成 InnoDB 的 undo 链加 ReadView。普通查询不阻塞普通写入，不代表 DDL、锁定读与写写永不冲突。见 [PostgreSQL 事务隔离](https://www.postgresql.org/docs/16/transaction-iso.html)。

**追问：** 长事务为什么害人？——旧快照可能持续需要旧版本，垃圾回收受阻，表和索引膨胀；可能还占连接或锁。

### Q23【P0】四种隔离级别，PostgreSQL 实际有什么差别？

**回答要点：** PG 默认 Read Committed，通常每条语句取得新快照；Read Uncommitted 在 PG 中表现为 RC。Repeatable Read 使用事务级快照，PG 的 RR 不出现幻读，但仍可能有序列化异常。Serializable 进一步检测不能串行化的并发并可能中止事务，调用方需重试整个事务。见 [PG 16 隔离级别表](https://www.postgresql.org/docs/16/transaction-iso.html)。

**追问：** 两个调度器都读到“还能派一个任务”然后各插一条呢？——单靠快照读可能破坏跨行不变量，需要约束、锁定公共资源行或可串行化事务等设计。

**不要答：** “RR 完全等于串行化”“PG 默认 RR”“PG 用间隙锁解决所有幻读”。

### Q24【P0】行锁、表锁、死锁与乐观锁怎么选？

**回答要点：** 悲观锁先占有冲突资源；乐观方案用 `UPDATE ... WHERE version = old_version` 检测并发失败。数据库的行锁不表示没有表级锁参与；PG 的锁模式与命名要按自身文档解释。死锁是循环等待，统一加锁顺序、缩短事务，并处理数据库终止事务后的重试。见 [PG Explicit Locking](https://www.postgresql.org/docs/16/explicit-locking.html)。

**追问：** 乐观锁失败一直重试行吗？——高竞争下可能活锁／放大负载，需要次数上限和退避，甚至改为串行处理。

### Q25【P0】为什么唯一约束比“先查一下”更可靠？

**回答要点：** 两个事务都可能读到不存在，只有数据库冲突仲裁能覆盖最终竞争。当前分析幂等键含 Task、Attempt、分析器类型／版本和输入 checksum，同一文件不同分析版本不应误去重。重复请求还要检查参数是否一致，不能所有冲突都当成功。

**追问：** NULL 和空字符串有什么差别？——业务上未提供幂等键与提供空键不能混成一个身份；唯一约束的 NULL 行为应按实际建表定义确认。

**源码：** [分析幂等键](../server/app/repositories/analysis_job_repo.py)、[模型约束](../server/app/models.py)。

### Q26【P0】给任务列表和事件列表设计索引。

**回答要点：** 先写查询：等值过滤哪些字段、按什么排序、取多少条，再选组合索引。示例：按 Agent 查询最近任务可讨论 `(agent_id, created_at DESC, id DESC)`；按 Diagnosis 游标追事件可讨论 `(diagnosis_id, sequence)`。这些是设计示例，是否已有要看 migration，不能当现有清单。

**追问：** 为什么不每个字段建一个？——索引增加写放大和存储，多个单列索引不必然等价于目标排序的联合索引。B-tree 适合常见等值／范围；GIN 适合某些复合值检索，不是所有 JSON 字段都必须建 GIN。见 [PG 索引类型](https://www.postgresql.org/docs/16/indexes-types.html)。

### Q27【P0】SQL 慢，如何用 EXPLAIN 定位？

**回答要点：** 先看总耗时、锁等待和连接等待，再看估计与实际行数、扫描方式、排序、循环次数和 buffer 命中／读取。`EXPLAIN ANALYZE` 会实际执行语句，写语句尤其要在安全测试事务／环境内处理。Seq Scan 不自动代表坏计划，小表或低选择性可能合理。见 [PG EXPLAIN](https://www.postgresql.org/docs/16/using-explain.html)。

**追问：** 有索引为什么还慢？——可能取行过多、随机 IO、统计信息失真、深 offset、回表／排序或锁等待；不要只答“强制索引”。

### Q28【P1】心跳频繁 UPDATE 会对 VACUUM 有什么影响？

**回答要点：** UPDATE 产生旧版本，持续心跳会形成写入和回收压力。监控死元组、autovacuum、长事务与表膨胀，再评估降低写频率、拆分热字段或合并状态写。普通 VACUUM 回收可复用空间，通常不会把文件直接缩回最小；VACUUM FULL 会重写并有更强锁影响。见 [PG Routine Vacuuming](https://www.postgresql.org/docs/16/routine-vacuuming.html)。

**追问：** 能直接清历史行救性能吗？——先检查数据保留与引用，清数据不是代替定位；线上不能无审批破坏证据。

### Q29【P1】WAL、Checkpoint、备份与复制分别做什么？

**回答要点：** WAL 先记录可恢复的变更，再让数据页持久化；数据库 Checkpoint 限定恢复工作的起点与脏页推进，它不是 LangGraph Checkpoint。备份提供独立恢复材料，复制提供副本，但误删也可能复制过去。见 [PG WAL](https://www.postgresql.org/docs/16/wal-intro.html)。

**追问：** 项目已经做到 PITR 吗？——已有一次独立恢复验证，不据此声称持续 WAL 归档、任意时点恢复或异地高可用已经完成。追问 RPO、RTO 时，先定义目标再讲方案。

### Q30【P0】latest_metrics 为什么是 JSON？JSONB 更好吗？

**回答要点：** 当前 migration 新增的是可空 JSON 字段，表示 Agent 心跳观测；未上报保留 NULL。JSON 保存输入文本形式，JSONB 采用分解表示、支持更丰富的索引操作，也有转换和写入成本。若只整块读写小对象，不能仅为“高级”强制迁移；频繁过滤特定指标时再比较结构化列与 JSONB。见 [PG JSON Types](https://www.postgresql.org/docs/16/datatype-json.html)。

**追问：** schema 变了为什么旧镜像不能直接回滚？——旧 Python 不认识新的 Alembic head，应用启动检查会失败。需要兼容式迁移与配套镜像，而不只是加一列 SQL。

**源码：** [新增指标迁移](../server/migrations/versions/20260910_0008_agent_latest_metrics.py)。

## 6. 操作系统与性能诊断：Q31—Q40

### Q31【P0】进程、线程、协程各是什么？

**回答要点：** 进程通常是地址空间与资源隔离单位；同进程线程共享大量资源，各有执行上下文与栈；协程的调度依赖语言／运行时。CPU 最终执行的是被调度的线程。一个进程整体 CPU 高，要进一步到线程和栈，而不是只记一个 PID。

**追问：** 上下文切换为什么有成本？——寄存器与调度状态切换、缓存局部性破坏等；是否切地址空间影响不同。线程并非没有切换成本，协程也不保证永不陷入内核。

**项目关联：** Agent 启动 Collector 子进程时要管理其生命周期；不能让诊断器产生的进程反过来被选为故障目标。[进程快照实现](../native/agent/src/process_snapshot.cpp)

### Q32【P0】用户点选 PID 847，几秒后它退出、PID 被复用了怎么办？

**回答要点：** PID 是可复用的局部编号，不是持久身份。快照携带进程启动 ticks、PID namespace、boot_id、generation 等信息，服务端绑定目标，执行前再次验证。快照“可信”表示来源与身份可检查，不是断言进程有故障。

**追问：** 核对完到采样间仍退出呢？——这是 TOCTOU 窗口；应失败并重新发现，不能自动换到同号新进程。可讨论 pidfd 等更强句柄，但没有查到项目使用时不能说已实现。

**源码：** [ProcessCandidate 字段](../native/agent/include/process_snapshot.h)、[心跳合同](../proto/healthcheck.proto)。

### Q33【P0】CPU 高就一定是计算热点吗？CPU 不高就没有性能问题吗？

**回答要点：** 先确定口径：单进程还是整机、单核百分比还是总核归一化、采样窗口多长。高 CPU 可能是业务计算、GC、忙等、系统调用等；低 CPU 的高延迟可能来自锁、磁盘、网络、队列和配额限流。Load Average 与 CPU 使用率不是一回事。

**追问：** 只看到一张火焰图怎么证明用户请求慢由它导致？——补同窗口请求延迟、吞吐、队列、线程状态和对照实验；栈占比只描述采样分布。

**训练：** 分别画“高 CPU 高延迟”“低 CPU 高延迟”两棵排查树，写每个分支需要什么证据。

### Q34【P0】perf 怎么采样？为什么 99 Hz 采 15 秒不一定有 1485 个样本？

**回答要点：** perf 基于选定事件进行计数或采样，实际样本受进程运行时间、事件、调度、权限和丢样影响。频率不是样本数承诺；99 Hz 常用于降低与整周期活动同步的风险，但不保证消除偏差。cycles 与 cpu-clock 事件语义不同，回退必须留记录。见 [perf_event_open](https://man7.org/linux/man-pages/man2/perf_event_open.2.html)。

**追问：** 为什么不能按 perf.data 大小判断成功？——头部和元数据也占字节；当前修复检查实际 `PERF_RECORD_SAMPLE`，仍须由分析器检查样本质量。

**源码：** [perf_collector.cpp](../native/agent/src/perf_collector.cpp)、[perf_samples.h](../native/agent/include/perf_samples.h)。

### Q35【P0】火焰图的横轴、宽度、高度、颜色分别是什么？

**回答要点：** 一般火焰图的框宽对应样本权重／占比，高度体现调用栈深度；横向排布通常不是时间轴。颜色的意义由具体渲染规则决定，不能默认红色就是更慢。区分 inclusive 与 self：包装函数包含子调用的时间，不能把它的累计占比直接解释成函数自身消耗。基础解释见 [Brendan Gregg 的 Flame Graphs](https://www.brendangregg.com/flamegraphs.html)。

**追问：** 最宽函数一定值得优化吗？——先看事件类型、self、可优化比例、业务重要性和测量误差。优化后分母也可能变化，比例降低不自动等于绝对耗时降低。

**项目关联：** 当前已有 self 已知时避免用包装帧累计比例冒充热点的修复。[分析器](../analyzer/mini_drop_analyzer/hotmethod_analyzer.py)

### Q36【P0】虚拟内存、RSS、PSS、堆内存有什么区别？

**回答要点：** 虚拟地址空间是进程可寻址范围，不等于实际占用 RAM；RSS 是当前驻留页，含堆、栈、代码与映射等；PSS 按共享情况分摊；语言堆只是其中一部分。RSS 上升可能来自缓存、映射、碎片或运行时保留，不能单凭它确认泄漏。

**追问：** free 之后 RSS 为什么没立刻降？——分配器可能保留页供复用，释放对象与归还内核不是一件事。结合 smaps、堆对象趋势、业务稳态和运行时指标定位。

**源码：** [proc_collectors.cpp](../native/agent/src/proc_collectors.cpp)、[自身指标](../native/agent/include/self_metrics.h)；字段来源见 [proc stat](https://man7.org/linux/man-pages/man5/proc_pid_stat.5.html)。

### Q37【P0】CPU 与 IO 速率怎么从累计计数算出来？

**回答要点：** 当前采 Agent 自身：`CPU%=100×Δ(utime+stime)/CLK_TCK/Δt`；`RSS_MB=驻留页数×页大小/1024²`；`读KB/s=Δread_bytes/1024/Δt`，写同理。时间间隔用单调时钟，首个样本无差分窗口，计数回退或读取失败不能填 0。这里 CPU 以一核为 100%，多线程进程可以超过 100%。

**追问：** `read_bytes` 等于应用 read() 的字节数吗？——不是；存储层读写与字符／系统调用级计数口径不同，页缓存命中会影响它们。见 [proc IO](https://man7.org/linux/man-pages/man5/proc_pid_io.5.html)。

**源码：** [self_metrics.h](../native/agent/include/self_metrics.h)。实测磁盘速率为 0 可以完全正常。

### Q38【P0】eBPF 观察到磁盘慢，为什么不能直接定位到目标进程？

**回答要点：** 先看探针位置、过滤条件和 attribution。块层 I/O 可能包含其他进程、异步写回与内核活动，事件触发线程未必就是原始业务发起者。当前案例明确是宿主机块设备观察且未归属目标，只能作背景信号。

**追问：** eBPF verifier 通过是否代表安全、低开销、归因准确？——不代表；程序可加载与业务语义正确是不同问题，采样量、探针范围和环境权限都要评估。验证器职责见 [内核 eBPF verifier 文档](https://docs.kernel.org/bpf/verifier.html)。

**项目修复：** 主机未归属 I/O → `ACCEPT_LIMITED`，对进程假设为 `NEUTRAL`。[门禁实现](../server/app/drop_insight/evidence.py)、[eBPF Collector](../native/agent/src/ebpf_io_collector.cpp)

### Q39【P0】锁竞争、死锁、忙等怎么区分？

**回答要点：** 竞争可能仍在进展但排队；死锁需要形成无法自行解开的等待关系；忙等反复检查条件可能消耗 CPU。先采线程状态与等待栈，结合锁持有时长、队列和吞吐判断。CPU profile 不完整覆盖 off-CPU 等待。

**追问：** 四个死锁必要条件？——互斥、占有且等待、不可剥夺、循环等待；再讲项目怎样通过一致锁顺序、超时和取消降低风险。超时检测失败不能自动证明存在死锁。

**场景答法：** “线程等锁”还要追问锁的持有者在干什么，例如持锁调用远程依赖才是更具体的瓶颈。

### Q40【P1】Docker 如何隔离？为什么容器内看到的 PID 和宿主机不同？

**回答要点：** namespaces 隔离视图，cgroups 限制／统计资源，两者职责不同。PID namespace 导致同一进程在不同视角编号不同；本项目为采宿主机进程使用相应部署配置，因此要更严格核对目标和采集权限。CPU 配额与 throttle 可能使进程延迟升高，即使整机还有空闲。见 [cgroup v2](https://docs.kernel.org/admin-guide/cgroup-v2.html)。

**追问：** 容器限制 1GB，Go 配了更大的内存目标会怎样？——可能先触及 cgroup 限制；语言 GC 目标不能覆盖所有原生／内核内存，更不是容器限额替代品。

## 7. 计算机网络：Q41—Q48

### Q41【P0】打开项目 HTTPS 页面，到完成一次 API 请求发生什么？

**回答要点：** 域名场景先 DNS；当前直接 IP 访问则没有该域名解析步骤。随后路由／连接建立、TLS 身份校验与密钥协商、HTTP 请求、代理转发、鉴权、业务与存储、响应。连接复用时不必每次重做整个流程。

**追问：** 请求慢如何分段？——DNS／连接／TLS／首字节／下载，与服务器排队／处理时间分别测；浏览器慢不一定是数据库慢。证书对 IP 地址的身份校验也要正确，不能把关闭校验当生产方案。

**项目路径：** 浏览器只连接公共 Go API 入口，内部 RPC 与 Agent 通信是另外的链路。

### Q42【P0】TCP 三次握手、四次挥手、TIME_WAIT 有什么意义？

**回答要点：** 握手同步序列号并确认双向通信条件；关闭方向独立，因此常见四段关闭，但实际报文可合并，不能背成固定包数。TIME_WAIT 帮助处理旧连接残留报文和最终确认丢失场景。见 [TCP RFC 9293](https://www.rfc-editor.org/rfc/rfc9293.html)。

**追问：** TIME_WAIT 多就调小超时？——先查是否短连接爆发、是否缺连接池、主动关闭在哪端和端口是否真的耗尽；不能见到状态多就乱改内核参数。

### Q43【P0】TCP 可靠是否意味着接口可以不做幂等？

**回答要点：** TCP 保证连接内字节流的可靠有序传输，不知道业务事务是否提交。服务端成功提交但响应丢失，客户端超时重试仍会产生重复业务请求。流量控制保护接收方缓冲，拥塞控制应对网络承载能力；两者也不能解决业务重试语义。见 [TCP 标准](https://www.rfc-editor.org/rfc/rfc9293.html)。

**追问：** TCP 粘包怎么解决？——它是字节流没有应用消息边界，需要长度前缀、分隔符或协议框架；当前 gRPC／HTTP 已定义消息格式，不能按一次 recv 等于一次任务处理。

### Q44【P0】TLS、mTLS、API Key 分别验证什么？

**回答要点：** TLS 提供通信机密性／完整性和服务端身份认证机制；mTLS 还要求客户端证书身份。API Key 是应用层凭据，不能替代链路加密；有效客户端证书也不自动意味着有权采任意 PID。证书有效期、信任链、目标身份和权限绑定分开检查。见 [TLS 1.3 RFC](https://www.rfc-editor.org/rfc/rfc8446.html)。

**追问：** TLS 1.3 怎么讲？——密钥协商、证书签名验证、派生会话密钥，再用对称加密保护数据；不要把旧式 RSA 密钥交换流程当所有 TLS 版本统一答案。

### Q45【P0】为什么页面进度用 SSE，而不是 WebSocket？

**回答要点：** 这里主要是服务端向页面推事件，用户操作仍走 HTTP，SSE 的单向文本事件流足够。WebSocket 更适合持续双向通信，但也要自建鉴权、重连、游标与应用消息语义。SSE 不自带业务持久化，这由项目事件表负责。

**追问：** SSE 为什么页面半天不更新？——查服务端 flush、代理缓冲、连接超时和浏览器解析；本项目设置 `text/event-stream`、禁止缓存／代理缓冲提示，并发 keepalive。见 [SSE 标准](https://html.spec.whatwg.org/multipage/server-sent-events.html)。

**代码事实：** 当前诊断 SSE 每秒查一次库、每次最多 200 条，20 秒 keepalive；这是读代码时的实现，不是通用协议常量。[server.go](../apiserver/internal/httpapi/server.go)

### Q46【P1】gRPC 与 HTTP JSON 的取舍是什么？

**回答要点：** gRPC 配合 protobuf 提供显式合同与生成客户端，适合当前内部跨语言 RPC；公开 HTTP JSON 方便浏览器使用。序列化尺寸与性能不是唯一考虑，调试、兼容、错误码、deadline 与代理也有成本。

**追问：** Proto 加字段怎么兼容？——使用新字段号，不重用删除字段的编号；理解默认值与 presence，新增可选能力不能强制老 Agent 立即提供。`self_pstats` 缺失与实测全 0 就是实际例子。

**源码：** [proto 入口](../proto/README.md)、[HealthCheck 合同](../proto/healthcheck.proto)。

### Q47【P0】select、poll、epoll 的区别？ET 为什么容易漏事件？

**回答要点：** 前两者通常要反复提交／检查描述符集合；epoll 维护关注集合并通知就绪事件，适合大量连接但不保证任何负载都更快。ET 只在状态变化通知，通常配非阻塞 IO，持续处理直到 EAGAIN；LT 条件持续满足时会继续通知。epoll 是就绪通知，不是“数据已经异步读进用户缓冲”。见 [epoll 手册](https://man7.org/linux/man-pages/man7/epoll.7.html)。

**追问：** Go HTTP 服务要手写 epoll 吗？——通常 runtime／网络库封装了这些机制。要懂机制，但不能声称本项目自己实现了高性能网络库。

### Q48【P1】心跳在线是否证明节点可用？

**回答要点：** 心跳只证明某一时点特定通信成功，不能证明 Collector 能运行、磁盘可写、对象可上传或模型可调用。阈值过短会在网络抖动时误判，过长则故障发现慢；需分别展示存活、能力和真实任务结果。

**追问：** 网络分区如何避免两边都干活？——心跳是检测线索，真正写入授权还需要服务端身份、租约／尝试约束。采用超时只能怀疑失联，不能证明远端进程已经停止。

**项目例子：** 修复指标时入口健康曾通过，但心跳写库失败；见 Q81 与 Q85。

## 8. Go／C++／Python 与运行时：Q49—Q56

### Q49【P0】Go 的 G、M、P 是什么？为什么 goroutine 不是越多越好？

**回答要点：** G 是 goroutine，M 是操作系统线程，P 是执行 Go 代码所需调度资源。并发任务最终受 CPU、内存和下游承载限制。为每个事件无限创建 goroutine，会形成队列、内存与连接压力。

**追问：** 如何找 goroutine 泄漏？——看数量趋势和阻塞栈，排查无人接收的 channel、未取消的请求、遗漏的 ticker 和永远等不到的 WaitGroup。结合 pprof 而不是只改 GOMAXPROCS。

**项目关联：** SSE 长连接要响应 `r.Context().Done()` 并停止 ticker。[HTTP 服务](../apiserver/internal/httpapi/server.go)

### Q50【P0】channel、mutex、atomic 怎么选？

**回答要点：** channel 适合传递工作／所有权和同步，mutex 适合保护共享不变量，atomic 适合小范围原子状态；没有“用了 channel 就不可能数据竞争”。同一不变量涉及多个字段时，单个 atomic 不够。

**追问：** 什么是 happens-before？——它约束同步可见性，不是墙上时钟的先后。讲一次 mutex 解锁／加锁或 channel 同步关系，再说不满足关系时为什么不能靠 sleep 保证正确。见 [Go Memory Model](https://go.dev/ref/mem)。

**训练：** 手写 Q90；用 race detector 辅助发现数据竞争，但它不能证明所有业务竞态都不存在。

### Q51【P0】context 取消能让后台任务一定停止吗？

**回答要点：** context 是协作式取消信号，调用链必须传递并检查，阻塞调用也要支持取消。HTTP 请求返回不等于外部采集任务已结束；持久任务的生命周期不应简单绑定到浏览器是否在线。

**追问：** SQL 超时、RPC 超时、任务采样时长怎么配？——用户操作 deadline 与长任务预算分开，内部短调用继承剩余预算。取消后仍需处理已发生的事务和迟到回报，不承诺“自动回滚远程世界”。

### Q52【P1】Go GC 为什么可能影响延迟？GOGC 与内存限制怎么理解？

**回答要点：** GC 通过回收不可达对象管理内存，但标记与分配辅助工作消耗 CPU；分配率高、活对象多会影响吞吐和延迟。GOGC 与内存目标是在 CPU／内存之间取舍，不是“一调大就快”。运行时内存限制是软目标，不能保证进程 RSS 或 cgroup 一定不超限。见 [Go GC Guide](https://go.dev/doc/gc-guide)。

**追问：** 怎么优化？——先看分配热点与对象存活，缩短持有、减少无效拷贝，再考虑池化；sync.Pool 不是永久缓存，乱池化也可能保留大对象。

### Q53【P0】C++ Agent 如何保证异常路径释放资源？

**回答要点：** 用 RAII 管理文件描述符、锁、子进程句柄等，拥有权清晰。`unique_ptr` 表达独占，`shared_ptr` 有引用计数成本且循环引用需处理；智能指针不能自动管理任意外部资源，必须封装正确 deleter。

**追问：** 采集超时，进程已经创建但父函数抛异常呢？——检查每个退出分支是否收子进程、关管道、回收临时状态，并保留失败结果供上报。

**源码：** [process_runner.cpp](../native/agent/src/process_runner.cpp)、[artifact_uploader.cpp](../native/agent/src/artifact_uploader.cpp)。

### Q54【P1】Python GIL 会让整个系统只能单线程吗？

**回答要点：** 对启用 GIL 的 CPython 构建，多个线程通常不能同时执行 Python 字节码，但阻塞 IO、释放 GIL 的扩展和多进程另当别论；现代 Python 还存在 free-threaded 构建，不能不问版本与构建方式就下结论。异步 IO 也不是 CPU 并行方案。参见 [Python free threading 官方说明](https://docs.python.org/3/howto/free-threading-python.html)。

**追问：** 为什么 Agent 适合 Python？——模型／工具库生态与大量 IO 等待是理由，不等于重 CPU 分析必须全在单个事件循环内做。当前 Analyzer 与 Diagnosis Worker 已是独立进程角色。

**避免套话：** “GIL 导致所有 Python 代码都没有竞态”错误；跨进程、数据库与业务逻辑依旧有竞争。

### Q55【P1】Java、Go、Python、C++ 的 Profile 能混着解释吗？

**回答要点：** 原生 perf、py-spy、Go pprof、JVM async-profiler 的采样来源、符号、事件和单位不同。都可能画成火焰图，但不能统一解释为 CPU 百分比；墙钟、分配、锁等待等事件要按实际报告类型看。

**追问：** JVM GC 怎么判断？——结合堆／分配趋势、GC 时间和请求延迟；看到一次 GC 不是故障。Go 看分配与活堆，Python 看解释器栈与原生扩展，C++ 还要考虑符号与栈展开条件。

**源码：** [语言 Collector](../native/agent/src/language_collectors.cpp)、[pprof 分析器](../analyzer/mini_drop_analyzer/pprof_analyzer.py)。

### Q56【P1】前端显示错了为什么也是后端面试题？

**回答要点：** UI 是数据合同的消费者。后端返回空对象、前端 `?? 0` 会制造“实测零”；报告缺少归因范围，页面就可能把阶段性发现标为根因。正确做法是传达状态、单位、范围、时间与失败原因，让展示保留语义。

**追问：** 切 Agent 后旧请求晚回来呢？——忽略迟到结果、清除旧 PID 选择，提交时再校验目标来自当前新鲜快照。不能只在前端隐藏旧值而不做服务端约束。

**源码：** [agentMetrics.js](../web/src/utils/agentMetrics.js)、[TaskCreatePanel](../web/src/components/TaskCreatePanel.jsx)。

## 9. Agent／RAG／Skill／LATS：Q57—Q72

### Q57【P0】你这是 Agent，还是一个套了模型的工作流？

**回答要点：** 固定工作流预先规定路径；Agent 可以根据观察调整计划和工具选择。本项目把可变规划放在模型与搜索中，把身份、预算、状态机、证据门禁留在确定性后端。它是受约束的 Agent 系统，不是无限自由执行者。

**追问：** 哪一步确实由模型决定？——指出 Scope 候选选择和 Diagnosis 假设／探针提案，展示 MODEL 或 LANGGRAPH_AGENT 的持久记录；确定性兜底要说清。不能只展示漂亮树就证明真实模型参与。

**源码：** [diagnosis_agent.py](../server/app/drop_insight/diagnosis_agent.py)、[Runtime 文档](AGENT_RUNTIME.md)。

### Q58【P0】模型调用工具时，谁真正执行？如何防参数幻觉与越权？

**回答要点：** 模型产生结构化语义提案，后端解析 schema，校验工具白名单、参数、范围、绑定、权限、预算和会话版本，再映射 Collector。工具提案被接受不等于采样已成功，更不等于证据成立。允许列表外工具、任意 shell 和改绑 PID 都不能靠 Prompt 自觉约束。

**追问：** 模型写出合法 JSON 就安全吗？——不安全；结构合法只过第一关，还要语义和授权检查。批准后等待太久，也应重新检查授权是否仍有效。

**源码：** [工具目录](../server/app/drop_insight/tools.py)、[Harness](../server/app/agent_runtime/harness.py)、[领域服务](../server/app/drop_insight/service.py)。

### Q59【P0】ReAct、Plan-and-Execute、LATS 有什么区别？

**回答要点：** ReAct 强调推理与行动观察交替；Plan-and-Execute 先形成较显式的计划再执行／重规划；LATS 把候选探索、评估、反馈与树搜索结合。前者简单但可能局部打转，显式计划容易遇到环境漂移，搜索提高探索能力也增加成本。见 [ReAct 论文](https://arxiv.org/abs/2210.03629)、[LATS 论文](https://arxiv.org/abs/2310.04406)。

**追问：** 为什么不每轮让模型想十条？——真实探针耗时且会影响环境，候选数与实际执行数必须受预算限制。本项目默认候选 Top-K 和真实诊断轮数不是无限展开。

**注意：** 可以保存可审计的结构化理由，不应把模型生成的长篇解释当作真实因果证明或可直接验证的内部思维。

### Q60【P0】LangChain 与 LangGraph 分别承担什么？

**回答要点：** 项目使用 `langchain.agents.create_agent` 与 LangGraph Checkpoint 能力承载工具循环、消息与恢复。业务的 Task、Evidence、Report、权限和副作用语义仍由领域服务负责。框架负责图执行，并不替你定义业务正确性。

**追问：** 为什么不用一个 while 循环？——简单原型可以；恢复、线程隔离、状态投影和人机交互复杂后，自建也要实现这些能力。选框架是减少通用运行时工作，不是获得天然可靠性。

**源码：** [Agent 入口](../server/app/drop_insight/diagnosis_agent.py)、[运行时声明](../server/app/agent_runtime/runtime.py)。

### Q61【P0】有 Checkpoint 就不会重复调用工具吗？

**回答要点：** Checkpoint 保存图状态，持久化到哪里决定重启后能否恢复；执行中断可能落在外部操作成功、状态尚未确认的窗口，业务仍需幂等与结果对账。内存 Checkpoint 不能跨进程重启保留消息。见 [LangGraph Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)。

**追问：** PG Saver 不可用怎么办？——当前可降级内存以保留服务，但必须显示 requested 与 actual backend 不同、状态 DEGRADED。业务 Evidence 已落库的部分不能因模型短期消息丢失而被删除。

**项目落点：** [Agent Runtime 的健康与恢复约定](AGENT_RUNTIME.md)。

### Q62【P0】短期上下文、长期 Memory、Skill 和 RAG 怎么区分？

**回答要点：** 上下文是当前调用送入模型的内容；Checkpoint 保存线程执行状态；用户 Memory 在本项目是显式保存的偏好；Skill 是可复用诊断路线；Knowledge RAG 提供背景知识。Evidence 则是本次目标与时间范围内的观测，这几类不能互相冒充。

**追问：** 用户说“上次就是 GC”，能直接当长期根因吗？——不能。可以作为待验证线索，不能自动写成通用事实或覆盖本轮证据。用户偏好还需要按 principal 隔离。

**源码：** [operator_memory.py](../server/app/drop_insight/operator_memory.py)、[记忆策略](../server/app/agent_runtime/memory.py)、[SKILLS](SKILLS.md)。

### Q63【P0】上下文超长，压缩时必须保留什么？

**回答要点：** 保留目标身份／范围、用户约束、当前假设、已执行动作与结果引用、否定发现、失败与停止条件、剩余预算。大原始产物留外部存储，通过有上限的摘要与引用进入上下文；模型上下文裁剪不能删除数据库审计事实。

**追问：** 摘要写错怎么办？——把摘要作为派生内容，关键参数和证据从结构化事实回查；不能让一段模型总结成为唯一真值。当前窗口策略有消息和 token 限制，但不据此声称实现了万能长期记忆。

**源码：** [memory.py](../server/app/agent_runtime/memory.py)、[context.py](../server/app/agent_runtime/context.py)。

### Q64【P0】你说 Agentic RAG，到底检索了什么？

**回答要点：** 本项目每轮规划从 `knowledge/catalog.json` 与 Markdown 检索，给出知识 ID、来源 hash、短摘录、所需证据和限制；记录为 `planner.knowledge_retrieved`，明确不是本次 Evidence。它影响下一步怎么查，不直接证明现在是什么故障。

**追问：** 没有向量数据库还算 RAG 吗？——RAG 是检索增强生成的方式，不要求特定数据库。当前目录小，确定性本地检索便于审计；应该用召回质量和延迟决定是否换基础设施。

**源码：** [retrieval.py](../server/app/agent_runtime/retrieval.py)、[Knowledge 目录](../knowledge/catalog.json)。

### Q65【P0】BM25 与向量检索各有什么弱点？项目实际用了哪种向量？

**回答要点：** BM25 偏词项匹配，受措辞与分词影响；学习型 embedding 擅长部分语义相似，但可能漏掉精确错误码、版本和否定条件。项目 Knowledge 与 Skill 是不同检索入口；Skill 使用 BM25、512 维确定性哈希特征和结构上下文评分，不是调用 embedding 模型得到的语义向量。

**追问：** 哈希冲突怎么办？为什么不全部取最高分？——哈希会丢信息，要以评测看误激活；硬兼容门禁、最低分和前两名过近时弃权一起使用。对 13 条目录先解释简单方案价值，不虚构海量向量优化经验。

**源码／合同：** [Skill 机制](SKILLS.md)、[Skill 目录](../skills/catalog.json)。

### Q66【P0】Skill 与普通 Prompt 模板有什么区别？如何沉淀？

**回答要点：** Skill 在这里包含适用范围、检索词、探针顺序、预期观察、反证与停止条件。候选需要经过质量／评测与发布门禁，负反馈可能隔离或回滚；新会话还必须重新取证。它是路线记忆，不是历史根因复制粘贴。

**追问：** 只要用户点“结论正确”就能上线吗？——人工反馈不是唯一安全条件；候选、门禁评测、发布是不同状态。需检查当前条件与 API，不把按钮点击等同于直接生产生效。

**源码：** [Skill 文档](SKILLS.md)、[Skill 页面](../web/src/components/SkillEvolutionPanel.jsx)。

### Q67【P1】为什么要渐进加载 Skill？hash 有什么用？

**回答要点：** 先用 catalog 轻量元数据召回，命中后才加载相应 Markdown，减少上下文负担。文件边界、编码、长度和结构验证降低错误内容进入规划的风险；hash 让本次 activation 对应到当时路线版本，方便复盘。

**追问：** hash 一样就可信？——hash 只说明内容一致，不说明内容正确或来源有权限。仓库发布物与外部工具内容的信任等级也不同。

**项目细节：** 正文加载有目录边界和 128 KiB 等限制；修改源 Skill 后由加载器生成摘要，不能手改派生 hash。[builtin_skills.py](../server/app/drop_insight/builtin_skills.py)

### Q68【P0】手写 UCT／PUCT，并说清参数影响。

**回答要点：** 常见 UCT 形式：`score = Q + c × sqrt(ln(N_parent) / N_child)`；未访问节点需单独处理。Q 表示平均价值，探索项鼓励较少访问节点。PUCT 常见形式以 prior 调整探索：`Q + c × P × sqrt(N_parent)/(1+N_child)`。这是便于讲解的常见形式，实际代码还会处理边界和预算。

**追问：** c 大小如何影响？Q 来自哪里？——c 大更愿探索；项目价值来源要区分模型先验、确定性评估和真实观察反馈，不能说 Q 是诊断正确概率。

**源码：** [lats.py](../server/app/drop_insight/lats.py)；搜索选择、回传和均值函数。论文概念参考 [LATS](https://arxiv.org/abs/2310.04406)。

### Q69【P0】FULL_LATS 和 BUDGETED_LATS 的核心差别是什么？

**回答要点：** 真实服务器时间会前进，负载也会变，不能保证兄弟分支从同一环境起点执行。实时路径因此诚实标为预算化搜索。独立冻结回放保存 observation 快照，每次 rollout 可 reset／verify，才满足更严格的可重复环境语义。

**追问：** 冻结回放能证明生产效果吗？——不能。它验证搜索、回传、事件恢复和 UI 展示，不创建真实 Task、Artifact、Evidence 或 Report；snapshot 中引用不是本次生产采集。

**源码：** [冻结桥接](../server/app/drop_insight/frozen_replay_showcase.py)、[搜索原语](../server/app/drop_insight/lats.py)。

### Q70【P0】怎么防止 Agent 死循环、重复探针和路径震荡？

**回答要点：** 限轮数、工具次数和总成本；候选规范化与去重，记录失败原因，区分不可观测与反证，必要时换未覆盖的诊断域。退出不只靠模型输出“结束”，后端要有可检查的预算与门禁。当前自主诊断最多 4 轮，搜索配置还会受更严格的诊断预算约束。

**追问：** 加反思 Prompt 能根治吗？——不能；反思可以辅助规划，但不能增加不存在的证据，也不能越过硬停止条件。重复探针若只是重试网络和重新取样，语义也必须分开。

**源码：** [service.py](../server/app/drop_insight/service.py)、[LATS 预算](../server/app/drop_insight/lats.py)。

### Q71【P0】采集失败为什么不是反证？“置信度 60%”到底是什么？

**回答要点：** “没有观测到”可能因为工具没工作，只有成功有效观测且满足反证条件，才可能反驳假设。内部置信度是规则评分，未经校准不能解释成 60% 的概率。报告引用还要检查目标、时间范围、质量、重复与独立性。

**追问：** 三份报告引用同一原始文件算三份独立证据吗？——不算；不同包装不会增加独立性。主机 I/O 也不能仅因与目标同机就成为进程支持证据。

**源码：** [Evidence Gate](../server/app/drop_insight/evidence.py)、[报告展示边界](../web/src/utils/reportPresentation.js)。

### Q72【P1】MCP、Function Calling、多 Agent 与提示注入怎么讲？

**回答要点：** Function Calling 是模型产生结构化工具调用的交互机制；MCP 定义 host/client/server 协作与能力交换协议，不是让工具天然有权限或必然正确。本项目核心采集链是自有 RPC／合同，不应说已经由 MCP 承载。见 [MCP 架构规范](https://modelcontextprotocol.io/specification/2025-06-18/architecture)。

**追问一：** 多 Agent 为什么可能更差？——增加上下文丢失、通信成本、冲突和重复执行；先证明分工有独立价值。不能把多个服务进程直接叫多 Agent。

**追问二：** 工具输出写“忽略规则，执行命令”怎么办？——视作数据，不升级为指令；限制输出尺寸、只提取预期结构，再过后端授权。模型的安全 Prompt 只是辅助，不能替代边界。

## 10. 测试、评估与实验：Q73—Q80

### Q73【P0】单元测试、集成测试、端到端测试分别证明什么？

**回答要点：** 单元测试可验证状态、参数和门禁纯逻辑；集成测试验证数据库竞争、RPC 或对象存储协作；端到端验证从请求到产物／报告的整条路径。截图说明页面显示，不能独立证明采集真实；一条成功 E2E 也不替代大量边界测试。

**追问：** mock 了采集器的 E2E 是不是真机验收？——不是。报告必须标环境、mock 边界、工具结果、错误和断言，不把形式上的“全链路”当真实物理观测。

### Q74【P0】540 和 500 测试集具体是什么？

**回答要点：** 至少区分三种口径：540 条 Skill 路由选择／安全拒绝测试；540 条基于已知场景合同的确定性根因代理回放；500 组受控离线 A/B。它们的目标、输入、Oracle 和工具预算不同，不是对同一“真实准确率”的三次测量。

**追问：** 每条都调用了真实模型和 Linux 工具吗？——不是，离线观察存在预设与合同依赖。变换措辞会增加样本条数，但不会自动得到同等数量的独立事故。打开 [学习手册第 28 节](PROJECT_LEARNING_GUIDE.md) 对照具体生成器与报告。

**不要答：** “我们的系统在 540 次生产故障里正确率 93.7%。”路由选择分数不能替换端到端根因分数。

### Q75【P0】测试集如何避免答案泄漏？

**回答要点：** 公共输入与私有 Oracle 分离只是第一步，还要按场景／服务／时间等合理单位切分，防模板兄弟跨训练测试集。Prompt、RAG、Skill、重试反馈与生成脚本都可能泄漏标签；记录版本、随机种子与 hash。

**追问：** 生产路由代码和测试生成器共享合同会怎样？——有利于合同回归，但会高估对未知故障的泛化。需要另建人工盲标／外部事故集，再报告结果，不能靠换 seed 自证独立。

**项目边界：** 现有数据集适合受控回归；独立生产泛化仍未验证。

### Q76【P0】Agent 应该评哪些指标？

**回答要点：** 分层评：目标选择正确率、合法工具率、执行成功率、有效证据率、根因正确／拒答质量、证据引用完整性、安全违规、时延与 token／工具成本。区分“回答了且正确”与“总体成功”，避免只在成功子集统计。

**追问：** 证据不足时拒答会拉低准确率吗？——需同时报告覆盖率、选择性正确率和高风险误判率；不能奖励无证据猜测，也不能用总拒答刷安全分。

**练习：** 设计 2×2 表分别统计“应回答／应拒答”与“实际回答／拒答”，再给已回答部分人工判分。

### Q77【P0】Skill A/B 怎么做才公平？

**回答要点：** 保持模型版本、目标、负载、预算和评价协议一致，只改变待比较因素；记录随机分配和实际执行路径。两臂共用一台正在变化的机器会相互干扰，应考虑顺序随机、隔离或可重置复现。同一请求重复跑也不是天然独立样本。

**追问：** 当前六条在线 A/B 能说明什么？——证明随机分配、执行、标注和统计链工作过；AUTO 2、DISABLED 4 的样本不能支撑效果提升，系统返回 NOT_READY。最低样本门槛也不等于统计功效充分。

**源码：** [skill_experiments.py](../server/app/drop_insight/skill_experiments.py)。

### Q78【P1】LLM-as-a-Judge 有什么问题？

**回答要点：** 裁判模型可能偏好长度、措辞、位置或自身风格，也可能忽略错误引用。使用结构化量表、盲化／交换顺序、确定性证据校验和人工抽检；报告裁判一致性，不以单个模型分数代替真值。

**追问：** 为什么项目还用规则门禁？——某些不变量可确定验证，如 Artifact 存在、范围匹配、质量状态。模型评价可补充解释质量，不能批准违反权限或证据来源的结论。

**边界：** 这是评估设计知识，不代表当前已部署了一套经过标定的裁判模型系统。

### Q79【P0】十分钟 1,200 次读取通过，容量是多少？

**回答要点：** 只能说该次负载与时间窗下的结果。平均约 2 次读取／秒，四路并发与公网延迟要一起说明；不是 CPU 采集压力、模型并发或容量上限。容量测试需控制负载、渐增并发，观测错误率、P95/P99、资源与队列。

**追问：** QPS 提升但 P99 爆了算成功吗？——不算满足原延迟目标。注意闭环压测在响应变慢时自动少发请求可能低估排队；负载模型和采集方式应写入报告。

**项目边界：** 长期 soak 和容量上限压测仍未完成，不把本题方案当已验收指标。

### Q80【P0】“问题已解决”需要哪些证据？

**回答要点：** 明确实施了什么修复，在可比负载与时间窗下比较业务延迟／错误率／吞吐、资源与关键栈，检查副作用，并保留前后版本。根因定位、修改代码、停止故障注入、修复复测是不同事件。

**追问：** TopN 热点没了就好了？——热点比例是相对量，可能因为负载停了或换了瓶颈；当前自动对比主要是 TopN，不能代替完整业务验收。无复测记录必须显示未验证。

**源码：** [FixVerificationPanel](../web/src/components/FixVerificationPanel.jsx)、[最近验收边界](../reports/ai-diagnosis/截图问题修复与验收-20260910.md)。

## 11. 真实问题复盘：Q81—Q86

本节来自仓库已有记录，不是为了面试编造的事故。以下“复盘答法”应按自己真实参与程度使用；若是 AI 辅助定位／实现，也可以坦诚说明自己负责了哪些复核。

### Q81【P0】为什么三个 Agent 的 CPU、RSS、IO 曾经全是 0？

**复盘答法：** “我先查显示值是不是实测值。发现 Go 列表接口返回空 metrics，前端缺失回退成 0；更上游 Agent 和 Control 也没有打通自身统计。修复必须覆盖 `/proc/self` 差分、心跳字段、数据库迁移、Control 入库、Go 读取和前端缺失语义，不能只改界面。”

**追问链：** 0 与 NULL？→ 采样首窗口？→ CPU 单核口径？→ 数值新鲜度？→ 三个节点版本一致吗？

**结果与边界：** 三节点上报 RSS 非零、指标时间新鲜，二进制 hash 一致；空闲 IO 为 0 仍正常。证明的是 Agent 自身指标链，不是被诊断业务没有资源问题。[验收](../reports/ai-diagnosis/usability-final-20260910.json)

### Q82【P0】为什么 CPU 火焰图采集失败？你怎么证明不是前端问题？

**复盘答法：** “原始结果为 cycles 与 cpu-clock 都没有有效样本，所以没有可画的 CPU 火焰图。先核对 PID、进程名、业务负载、权限和产物，而不是修改页面假装成功。代码后来按真实 sample record 判定，保留 NO_PERF_SAMPLES 并提示补负载或选等待类工具。”

**追问链：** 没样本是空闲还是权限？→ 为什么 fallback 也没用？→ 为什么文件大小不可信？→ 重采是否新观测？

**边界：** 对具体任务若缺权限日志／时段状态，不能武断认定唯一原因；当前历史负向任务用于验证失败展示，不是性能故障被修复。[修复说明](../reports/ai-diagnosis/截图问题修复与验收-20260910.md)

### Q83【P0】报告置信度 60%，为什么最后改成“尚未定位根因”？

**复盘答法：** “检查 Evidence 元数据后发现它只描述宿主机块设备，没有归属到目标进程。旧分数没有满足因果范围要求，所以先修后端证据门禁，再修报告投影。历史审计不无痕改写，页面明确说明旧引用的限制。”

**追问链：** hash 正确为什么证据还错？→ 同机相关性为何不等于因果？→ 有没有基线？→ 需要什么新探针？

**结果与边界：** 新门禁为 ACCEPT_LIMITED／NEUTRAL，重新校验报告为证据不足；原队列根因仍未验证。这个案例更适合展示“知道什么时候不能下结论”。[实际重验](../reports/ai-diagnosis/usability-host-io-gate-20260910.json)

### Q84【P1】为什么 Java 有产物但页面图是空的？

**复盘答法：** “采集、分析和展示成功是三个状态。历史 Java async-profiler HTML 与现有渲染方式不匹配，后来采用受限数据解析，由已有 D3 组件绘制，并防止旧请求晚到覆盖新任务。”

**追问链：** 为什么不直接执行产物里的 JavaScript？→ XSS／沙箱？→ 数据格式兼容？→ 怎么区分解析失败和零热点？

**结果与边界：** 已有 Java 真机产物和页面验收记录，具体帧数只是那份产物的属性，不是所有 Java Profile 都固定如此。[前轮验收](../reports/ai-diagnosis/后续完善与验收-20260909.md)、[前端绘图](../web/src/components/FlamegraphViewer.jsx)

### Q85【P0】最值得讲的一次发布问题是什么？

**复盘答法：** “指标功能发布时漏了数据库字段，心跳写入失败；补迁移后，Windows 交叉编译的 Linux API 二进制又缺可执行权限，旧 Python 镜像还不认识新 migration head，导致直接整组回滚失败。恢复采用带执行权限的 API 和兼容新 schema 的 Worker，保留新增列与数据。”

**追问链：** 为什么健康检查没挡住？→ 有没有迁移预检？→ 为什么应用回滚不等于数据回滚？→ 如何避免下次？

**改进方向：** 发布检查覆盖启动、心跳入库、真实 API 和任务链；构建中固定执行权限；使用兼容式 schema 变更与明确的镜像组合。已执行与未来改进要分别说，不能说“发布从未影响服务”。[完整时间线](../reports/ai-diagnosis/截图问题修复与验收-20260910.md)

### Q86【P0】模型余额恢复了，为什么仍不能保证诊断成功？

**复盘答法：** “余额解决 provider 可调用，不保证计划合法或证据充分。模型曾把采集失败设成反证条件，因此把语义检查前移到提案接受前，对该类错误最多给一次纠正机会，持续无效则明确兜底。专用运行时探针也要进入有限候选，避免预算耗尽在通用探针。”

**追问链：** 为什么不用无限重试？→ 如何计成本？→ 兜底后还叫模型诊断吗？→ 怎么证明真实模型参与？

**结果与边界：** 先前 Java／Python／Go／C++ 四条新链路 4/4、16 次工具完成，有模型规划记录；是小规模受控验收，不是生产准确率。[真实模型验收记录](../reports/ai-diagnosis/后续完善与验收-20260909.md)

## 12. 手写代码与 SQL：Q87—Q92

以下是练习题，不会在云端执行。算法答案给核心思路、复杂度与边界，面试时要自己补完整输入输出。SQL 使用教学表 `jobs`，不是让你直接修改生产表。

### Q87【P0】从百万条栈样本里求 Top-K 热点函数。

**解法：** 用哈希表按函数身份累计权重，再用大小为 K 的最小堆保留候选；若有 M 个不同函数，累计 O(N)，选取 O(M log K)，内存 O(M+K)。不能把带权样本当每条都权重 1；函数重名要考虑模块／符号身份。

**追问：** 数据流无限大，内存有限？——讨论近似 heavy hitter 算法与误差；若要求精确，则需外存／分区聚合。不要把近似算法输出叫精确 Top-K。

**自测：** K=0、K>M、同名不同模块、并列权重、负权重非法、空输入、跨时间窗是否允许合并。

### Q88【P0】实现一个 LRU 缓存，get／put 都 O(1)。

**解法：** 哈希表定位节点，双向链表保存新旧顺序；访问移到头，超容量删除尾并同步删哈希。使用哨兵头尾降低空表分支。

**追问：** 加 TTL、并发与租户隔离？——TTL 和 LRU 是不同淘汰条件；并发要保护哈希与链表这一整体不变量；key 需要包含租户／范围／版本。不可把一个进程的旧诊断结论缓存给另一个目标。

**自测：** 容量 0／1、覆盖已有键、访问改变淘汰顺序、删除后无悬挂节点。说明不带 TTL 的练习并非项目已实现的通用缓存。

### Q89【P1】合并重叠的采样时间窗。

**解法：** 按起点排序，逐个维护结果的最后一个区间，重叠就扩展终点，否则追加，O(N log N)。先约定半开区间 `[start,end)`，相邻是否合并取决于业务：时间覆盖可合并，但不同 Agent／PID／事件类型不能仅因时间相邻就合并。

**追问：** 跨时区、时钟回拨、无时区时间怎么办？——存储明确 UTC／时区，时长计算使用合适时钟；拒绝无效窗口。项目证据还需保留原始采样边界与来源，合并展示不能抹掉它们。

### Q90【P0】设计固定并发的 Go Worker Pool，支持取消。

**先讲合同：** N 个 Worker 消费有界队列；生产者负责关闭输入；worker 不共同关闭同一个通道；任务要接收 context；谁等待结束、谁收集错误都明确。以下为教学核心，不是生产调度器替代代码。

```go
type Job func(context.Context) error

func Run(ctx context.Context, n int, jobs <-chan Job) error {
    if n <= 0 { return fmt.Errorf("worker count must be positive") }
    ctx, cancel := context.WithCancel(ctx)
    defer cancel()
    var wg sync.WaitGroup
    var once sync.Once
    var firstErr error
    for i := 0; i < n; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            for {
                select {
                case <-ctx.Done():
                    return
                case job, ok := <-jobs:
                    if !ok { return }
                    if err := ctx.Err(); err != nil { return }
                    if err := job(ctx); err != nil {
                        once.Do(func() { firstErr = err; cancel() })
                        return
                    }
                }
            }
        }()
    }
    wg.Wait()
    if firstErr != nil { return firstErr }
    return ctx.Err()
}
```

**追问答案：** 生产者也必须监听取消，否则队列没人读时可能阻塞；job 若忽略 context，Run 仍可能等待很久。示例约定 job 非 nil、不 panic；生产实现还需决定 panic 策略、错误聚合、任务持久化和重试归属。原子／同步正确不等于业务 exactly-once。

**自测：** 空队列关闭、N=0、首个任务失败、外部取消、慢任务不响应取消、生产者忘关通道。

### Q91【P0】手写并发领取、过期旧写保护和游标分页 SQL。

**教学前提：** `jobs(id, status, owner, lease_until, generation, created_at)`，其中 generation 非空且初始 0；SQL 中参数由调用方绑定。领取事务应很短，提交后再做外部工作。

```sql
BEGIN;
WITH candidate AS (
  SELECT id
  FROM jobs
  WHERE status = 'PENDING'
     OR (status = 'RUNNING' AND lease_until < now())
  ORDER BY created_at, id
  LIMIT 1
  FOR UPDATE SKIP LOCKED
)
UPDATE jobs AS j
SET status = 'RUNNING', owner = $1,
    lease_until = now() + interval '30 seconds',
    generation = j.generation + 1
FROM candidate AS c
WHERE j.id = c.id
RETURNING j.id, j.generation;
COMMIT;

-- 完成时必须携带领取时的 owner 与 generation。
UPDATE jobs
SET status = 'DONE', lease_until = NULL
WHERE id = $1 AND owner = $2 AND generation = $3
  AND status = 'RUNNING' AND lease_until > now();
-- 影响 0 行表示失去权限或状态已变，不能当成功。
```

**分页题：** 假设顺序为时间倒序、ID 作为稳定次序，对后续页可写：

```sql
SELECT id, created_at, status
FROM jobs
WHERE (created_at, id) < ($1, $2)
ORDER BY created_at DESC, id DESC
LIMIT $3;
```

**追问答案：** 首屏无游标条件；排序字段要非空且语义稳定；并发新增时这不是跨页一致快照；租户过滤必须包含在查询中。`now()` 在 PG 中取事务起点，长事务不适合用它推断实时租约，故领取／完成使用短事务。需要严格一致视图时另设计 snapshot／固定截止点。语法与锁行为参考 [PG SELECT](https://www.postgresql.org/docs/16/sql-select.html)。

### Q92【P1】怎么把乱序树事件还原成探索树？

**解法：** 先按会话与事件身份去重，根据约定顺序处理；用 node_id → node 哈希表，父节点未到时暂存待连接孩子。检测重复 ID、未知父节点、自环和有向环。若只是二叉树平衡题，则后序遍历返回高度或失败标记，O(N)，不要与通用 DAG 的验证混为一谈。

**追问：** 中途断线再收到旧事件会不会多一条边？——事件身份、节点身份与 effect key 各有去重层；领域事实与前端投影要分开。最终从持久事件重建，应与正常实时处理结果一致。

**项目延伸：** 出生深度与实际执行轮次不同；回溯旧 sibling 仍可能发生在新的真实取证轮次。[Runtime 的树语义](AGENT_RUNTIME.md)

## 附录 A. 大模型基础加练：Q93—Q100

这部分补 Agent 应用岗的模型基础。讲理论时同时指出“本项目调用模型，没有自行训练基础模型”。若面试目标是算法／训练岗位，还需更系统地准备数学、训练与实验，不靠这八题覆盖全部。

### Q93【P0】Token 是什么？为什么字符数不等于 Token 数？

**回答要点：** Token 是 tokenizer 输出的离散单元，可能对应子词、字符或字节片段；中文、英文、代码、错误堆栈和特殊符号的比例不同。预算要包含系统指令、工具描述、历史消息、检索片段、工具结果和预留输出，不能只数用户输入。

**追问：** 128K 上下文能放心塞满吗？——容量上限不保证有效利用率和低延迟；长上下文增加成本，也可能稀释关键约束。项目应优先结构化事实、来源引用、去重与有边界的摘要。

**项目连接：** Q63 的消息裁剪与 Q67 的渐进加载都是实际节省上下文的方法。

### Q94【P1】Attention 中 Q、K、V 是什么？为什么有除以根号 d？

**回答要点：** 可用 `Attention(Q,K,V)=softmax(QKᵀ/√d_k)V` 解释：Q 和 K 计算相关权重，V 提供被加权的信息；缩放控制点积量级。多头允许不同表示子空间参与建模，不能把每个头机械地命名成某个固定语义功能。见 [Attention Is All You Need](https://arxiv.org/abs/1706.03762)。

**追问：** decoder-only 为什么要 causal mask？——生成当前位置只能依赖允许看到的前缀，避免训练时偷看未来。普通全注意力的序列两两交互使长输入有较高成本，但实际推理性能还受实现和硬件影响。

### Q95【P0】temperature、top-p 怎么影响输出？设 0 就不幻觉了吗？

**回答要点：** 温度改变 logits 到采样概率的集中程度；top-p 约束累计概率候选集合。降低随机性不等于事实正确，更不保证跨运行绝对逐字一致，服务实现与计算也可能影响结果。

**追问：** 诊断系统该怎么调？——结构化、安全敏感任务优先稳定输出与后端校验，再用固定评测比较不同设置；不要用“低温”替代 Evidence Gate。具体可用参数与含义应按实际 provider／模型文档核实。

### Q96【P0】RAG、SFT、LoRA 分别解决什么？

**回答要点：** RAG 在推理时取外部知识，适合可更新、可溯源内容；SFT 用监督样本改变模型行为／能力；LoRA 是低秩参数适配方法，可用于某些微调训练，不是和 SFT 完全并列的业务任务。概念参考 [RAG 论文](https://arxiv.org/abs/2005.11401) 与 [LoRA 论文](https://arxiv.org/abs/2106.09685)。

**追问：** 为什么不微调一个“永远懂本项目”的模型？——成本、更新、数据质量与安全边界都需要权衡；训练不能替代实时系统观测。当前项目没有训练基础模型或实施 LoRA 的验收记录，不能说自己完成过。

### Q97【P1】如果把知识库扩到十万篇，怎么做分块、召回和重排？

**回答要点：** 先按文档结构和语义单元分块，保留标题、来源、版本、权限与父子关系；召回后可重排、去重与补上下文。块太小丢上下文，太大占预算且噪声多；overlap 也会带来重复。精确错误码、版本与向量语义需要共同评测。

**追问：** 只看最终答案分数够吗？——分别看相关段 Recall@K、排序质量、权限过滤、引用正确性与最终任务效果；召回错与生成错要分开诊断。不能用调大 K 掩盖所有问题。

**边界：** 这是扩展设计；当前本地小目录没有部署十万文档向量检索和 reranker。

### Q98【P0】结构化输出是否意味着可以直接执行？

**回答要点：** 约束解码／JSON schema 可以减少格式错误，但合法字段仍可能是错误 PID、过大时长、已过期绑定或不合适工具。模型输出要经过业务语义、授权、时间与预算检查；参数默认值也应由服务端决定并可审计。

**追问：** 模型老是输出无效计划怎么办？——先分类错误，给有界反馈或切换确定性兜底，记录实际来源与成本；不要循环到碰巧合法才算成功。当前仅对特定反证语义错误给最多一次纠正，不代表所有错误都统一重试。

### Q99【P1】模型慢，怎么拆分延迟？KV Cache 和 Prompt Cache 一样吗？

**回答要点：** 用户等待可拆为排队、检索、模型首 Token、生成、工具执行与后处理；流式首 Token 快不代表整个诊断完成快。KV cache 通常复用自回归计算中的键值状态；provider 的 Prompt Cache／前缀缓存是服务层复用机制，条件、计费和可见性因实现而异。

**追问：** 把动态 PID 放在提示最前面会怎样？——可能降低稳定前缀复用机会；但优化缓存不能让过期目标或越权上下文复用。先测 token、缓存命中与端到端耗时，再比较方案，不编造收益数字。

**项目边界：** 本项目主要是调用模型服务；没有据此证明自己实现了 KV cache 引擎或特定模型推理优化。

### Q100【P0】如果换一个更便宜的模型，怎么决定能不能上线？

**回答要点：** 固定任务集、版本、工具预算和评分规则，比较合法计划率、目标选择、有效证据率、安全拒绝、端到端成功、尾延迟与成本。人工检查高风险失败，做灰度和明确回退条件；便宜模型多调用几轮可能总成本更高。

**追问：** 能用大模型判小模型回答然后直接上线吗？——只能作为一部分评估，需结合确定性门禁、真实观察与人工抽检；沿用 Q78 的裁判偏差控制。充值恢复可用性也不能代替换模回归。

**串题练习：** 用 Q100 串起 Q58 的工具安全、Q70 的预算、Q76 的分层指标与 Q77 的公平实验，讲成一个十分钟系统设计回答。
