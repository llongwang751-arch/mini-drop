2026-10-01用户要求恢复CPU、内存、I/O、网络等性能诊断主线。4个工程缺陷仍单独展示，不能替代21类性能实验或合并为AI根因成绩。默认进入“性能故障实验”并显示全部21类，保留运行时筛选、启停与历史成绩；进入页面不会自动注入。

## 六种结果

| 结果 | 必须具备的依据 |
|---|---|
| 本次检查正常（已检查范围） | 已准入系统证据，目标Agent/PID/启动时间一致，至少5样本/1秒，有有效CPU和RSS趋势且未超观测阈值 |
| 证据不足，暂时无法判断是否正常 | 身份、采样或必要指标缺失；缺失不能当作0 |
| 已发现性能异常，原因待确认 | CPU、内存趋势或业务性能信号异常，即使没有SUPPORT或最终报告也不能显示正常 |
| 已验证性能观测，根因仍待确认 | 报告验证测量合同，范围为BOUNDED_OBSERVATION；还需要干预验证 |
| 性能路径已定位，根因仍待确认 | 已验证有界观测明确具体CPU热函数、HTTP/下游调用耗时路径或目标同步I/O路径；不证明因果或同负载修复 |
| 因果根因已验证 | 可信支持与独立对照完整，有针对候选原因的可比干预；采样比例下降或停止注入不能直接升级 |

默认初筛阈值：进程CPU低于50%（单核口径，可超过100%）、窗口RSS增量低于8MiB。业务HTTP在身份有效且有请求时参与检查：平均耗时低于500ms、近期P95低于1000ms、失败率低于5%。这是初筛阈值，不是业务SLO；页面明确未检查磁盘操作延迟、丢包/重传、内存限额和全部业务接口。

会话状态与检查结果独立：INSUFFICIENT_EVIDENCE表示没有证明假设，不能自动解释为正常或故障。取消、失败不能产生正常检查结果。

原完整批次为`reports/ai-diagnosis/fault-plaza-strict-21-deployed-20260930.json`，不可修改成绩。只读复盘由`scripts/audit_fault_plaza_failures.py`生成。`contracts/performance_audit.json`钉住21份文件SHA，`scripts/build_performance_audit.py`生成网页索引并校验。

| 旧包装器分类 | 数量 | 实际含义 |
|---|---:|---|
| 通过旧链路检查 | 7 | 链路通过不等于因果根因通过 |
| 证据不足被当作链路失败 | 9 | 要求终态COMPLETED，混入诊断结果要求 |
| 缺支持结论被当作链路失败 | 2 | 要求指定采集器产生SUPPORT，混入结论覆盖要求 |

归档记录18/21能够对应Task、Attempt、Artifact SHA、Analyzer与Evidence，仅3项目标不一致。这是归档内部一致性复盘，不是重新下载校验，更不是18类根因通过。原因果成绩仍0/21，其中4项有验证观测。

## 本轮修复

1. 取消性能信号关键词覆盖。HTTP路径慢不能覆盖“网络队列/丢包/重传”，写入量不能覆盖“fsync延迟”，队列深度不能覆盖“持续增长”。只支持完整数值判据，例如`downstream_latency.average_latency_ms >= 100`；缺字段、复合描述和非法值不覆盖槽位。
2. 新规则计划在持久化前选择可执行观察，模型获得字段、数值语法与范例。旧假设不重写。报告显示满足判据的实际数值及范围，不把猜测当作具体根因。
3. 计算循环有进展不直接触发CPU高占用。保留内存绝对量与窗口增长分开，不据此猜测泄漏。
4. 网络/下游累计平均值通过首尾请求计数换算新增请求窗口平均耗时，不再拿历史平均值峰值当恢复窗口延迟。无新请求、计数重置或首尾不完整时保持未知。
5. 新生成普通运行时Profile发现也标为有界观测，避免旧路径以VERIFIED直接显示因果根因；已持久化报告保持原样。

注册表支持13个信号域，不代表13类因果根因验收通过，也不代表已经采集全部性能原因。

真实办公助手检查发现服务端的`ACCEPT_NEUTRAL`：有效且通过Analyzer校验，但不支持根因假设。正常结果与归档链复盘均须接纳这种可信中性观测；同时仍校验schema、Analyzer、目标、时间与非降级标记。首次复盘漏算1项而得到17/21，纠正后为18/21；首次复盘材料保留，原因果0/21与原链路7/21不改。

## 剩余性能案例的关键条件

| 方向 | 已有测量 | 仍需要的证据与对照 |
|---|---|---|
| CPU/源码 | CPU ticks、运行时Profile、源码映射 | 固定请求输入、针对热点的算法/配置干预，比较输出质量、耗时与CPU；闲置线程栈占比不是CPU占用 |
| 内存/堆外 | RSS/PSS、保留量 | 多窗口生命周期与释放对照，区分瞬态分配、保留平台、增长和限额压力 |
| I/O/同步写 | 目标读写计数、宿主块设备直方图 | 目标归属的操作耗时/等待栈、操作次数和持久性结果，宿主I/O不能冒充目标fsync瓶颈 |
| 网络/下游 | HTTP路径窗口耗时 | 独立依赖侧处理计时、连接/传输计时；丢包/重传需要真实TCP计数或可归属捕获，不用人为sleep冒充 |
| 锁 | JVM锁Profile、应用等待计数 | 持锁者/等待者、等待耗时，以及同输入缩小临界区前后的正确性与延迟 |
| GC | 分配Profile、独立JVM计数 | 停顿分布、堆行为、针对分配路径的干预；普通GC计数不是Full GC次数 |
| 队列/入口 | 到达、完成、拒绝、积压 | 固定到达负载、服务能力、全部请求/错误/排队时间；停止生产不是提高消费能力的修复 |
| 噪声邻居 | peer身份与CPU ticks | 目标调度等待/节流/PSI及隔离干预，peer活动本身不能证明争抢 |

新性能因果实验先声明目标身份、输入SHA、请求数量、到达率、并发、资源条件、候选原因、干预与标准，再记录基线/故障/干预后三个独立窗口。保留全部请求与失败，业务质量不得下降。控制快照是独立验收，不能直接塞进Agent Evidence。完成这些证据之后才统计新因果成绩。

本轮首先修复判定、计划、观测语义和验收口径。尚未证明全部21类因果根因，不删除旧案例、不制造通过成绩，也不重跑用户已接受的一小时压测。

## 部署验证

### 数值判据与路径定位候选

`observation_verifier.py` 输出 `performance-observation-verification.v1`：`checked_ratio` 表示已测量判据占比，`matches` 表示各条件是否成立。异常窗口中 `x >= 100` 成立、`x < 100` 不成立，两者均可已检查；不把“不成立”改成独立CONTROL。完整期望成立且无反证成立才验证观测；有效反证为REFUTED，冲突窗口为CONFLICTING_OBSERVATIONS，缺测为INSUFFICIENT_OBSERVABILITY，不支持语法为UNSUPPORTED_PLAN。不可跨产物拼接完整覆盖。内存收缩的负增量保留为真实测量，缺失不当作0。

报告持久化保留原匹配覆盖率与独立对照标记，以 `matched_verification_status` 留存原匹配状态；观测验证独立于因果验收。`bottleneck-localization.v1` 仅在新有界验证通过时定位性能路径。CPU须有已注册的Profile+独立系统CPU合同；HTTP耗时不能说明丢包或传输原因；I/O须明确TARGET_APPLICATION_SYNC_IO。`scripts/evaluate_performance_localization.py` 独立统计3类路径，旧21成绩不覆盖。

Go 应用增加 `io_operation_duration_ms_total`，与成功操作计数在同一锁内快照，测量open/write/sync/close，不计循环休眠和获取I/O工作锁的等待。Analyzer用累计耗时差/成功操作数差求窗口均值，计数重置、缺测、无新操作保持未知。计划在验收前钉住平均至少10ms且至少5次操作；实际快磁盘未达阈值应报告未发现该异常，不能加sleep或降低阈值凑通过。其范围不是单独fsync延迟或块设备延迟。
