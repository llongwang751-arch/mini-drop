# Mini-Drop 真实业务测试集与成熟产品对照方案

> 状态：页面化云端验证版 0.2.0（2026-08-20）
> 原则：先复现，再评分；公开输入与隐藏 Oracle 分离；没有运行证据就保留意见。

## 1. 结论先说

现有 10 类统一用例和 90 次策略 Campaign 已经能检查工程链路、证据引用、安全门禁和三种策略差异，但还不能单独证明 Mini-Drop 能处理真实生产缺陷。缺少的是：

1. 来自真实开源项目的故障与修复版本；
2. 同一故障在成熟产品和 Mini-Drop 上的同题对照；
3. 不泄漏答案的隐藏标准答案；
4. 基线、故障、修复后三段快照；
5. 对“证据不足”和“上游也不确定”的校准测试。

本轮新增 `benchmarks/real_world/`，把 7 个真实 PR 整理成候选挑战集，并为其中 4 个案例实现低资源机制级页面执行适配器。已按可信发布流程部署并获得服务端 run 证据时，页面才会执行 baseline → incident → diagnosis → verification → Oracle comparison；本地代码和构建验证不能替代该云端证据。尚未完成 7 个上游仓库的完整 base/fix 编译与 A/B，因此案例仍是 **candidate**，不能称为“完整上游 Golden 已跑通”。

当前必须区分三种数字：

- 候选案例：7；
- 页面机制级执行适配器：4；
- 上游完整仓库 base/fix A/B：0。

## 2. 为什么要分三层测试

| 层级 | 解决的问题 | 当前载体 | 能证明什么 | 不能证明什么 |
|---|---|---|---|---|
| A. 确定性工程回归 | API、状态机、证据格式、权限、评分器是否稳定 | 现有 10 用例 × 3 策略 × 3 次 | 系统能稳定执行和评分 | 真实根因定位能力 |
| B. 真实缺陷挑战 | 能否从真实症状和采样证据定位到机制/代码位置 | `benchmarks/real_world/` | 真实 PR 上的证据推理与反证能力 | 跨系统普适性（案例仍少） |
| C. 公共基准/产品对照 | 与公开论文基线和成熟产品相比处于什么位置 | RCAEval、OpenRCA、HolmesGPT、Pyroscope | 可比较的 Top-K、成本、覆盖率或 Profiling 体验 | 各产品能力并不完全等价 |

三层不能互相替代。合成用例适合每天回归，真实 PR 适合验收深度，公开基准适合对外比较。

## 3. 首批真实 PR 候选集

### 3.1 分级规则

- **Golden 候选**：PR 已合并；根因、故障表现和修复方式清楚；能够固定 base/fix revision；本地至少重复 3 次且症状稳定。
- **Challenge 候选**：PR 仍开放，或只有设计解释但缺少稳定复现结果。用于考察候选生成和证据边界，不计入正式 Golden 准确率。
- **Abstention（保留意见）题**：上游本身也不能确认完整因果链。正确行为不是猜一个根因，而是说明缺少什么证据并设计 A/B 实验。
- **拒收**：未合并、无稳定复现、无可核对证据且无法形成反事实验证的案例。

## 4. 公共数据集与成熟产品怎么选

### 4.1 RCAEval：统一离线根因定位基准

[RCAEval](https://github.com/phamquiluan/RCAEval) 提供 9 个数据集、735 个真实故障案例、11 类故障和 15 个 RCA baseline，覆盖 Online Boutique、Sock Shop、Train Ticket，并包含 metrics/logs/traces 的不同组合。它最适合回答：Mini-Drop 的服务/指标根因 Top-K 能否达到公开基线水平。

接入方式：

1. 先接 RE1 的小样本，只测 metrics 到根因服务/指标；
2. 再接 RE2，加入 logs/traces；
3. 用同一输入分别跑 RCAEval baseline 和 Mini-Drop；
4. 输出 Top-1、Top-3、Avg@5、运行时间和证据引用率。

边界：RCAEval 是离线遥测 RCA，不包含 Mini-Drop 的 perf/eBPF 进程采集、人工审批和修复后验证。因此“RCAEval 分数高”不等于 Mini-Drop 全链路更完整。

### 4.2 OpenTelemetry Demo：真实业务故障环境

[OpenTelemetry Demo](https://opentelemetry.io/docs/demo/) 是多语言电商微服务，官方提供可切换的故障场景。[Feature Flags 文档](https://opentelemetry.io/docs/demo/feature-flags/) 包含高 CPU、内存泄漏、GC、队列积压、下游不可达、流量洪峰和慢图片链路等故障。

它最适合做 Mini-Drop 的端到端业务演示：

```text
正常负载 -> baseline 快照
打开一个官方故障开关 -> incident 快照
Mini-Drop 诊断并引用证据
关闭故障开关 -> verification 快照
Oracle 在诊断结束后评分
```

仓库已经固定到提交 `3684411da9a4dc3e77cddfef929a630d6f5af6c5`，预检确认 10 个适配器定义齐全；但当前 Docker Desktop Linux Engine 未启动，而且真实 OTel 场景还缺显式在线 Agent 与 collector 能力确认，因此不能把预检的 `fixture_ready` 误写成“真实诊断已跑通”。

### 4.3 HolmesGPT：成熟 AI SRE Agent 对照

[HolmesGPT](https://github.com/HolmesGPT/holmesgpt) 是 CNCF Sandbox SRE Agent，支持从 Prometheus、Grafana、数据库、日志和 Trace 等工具迭代调查，并强调只读访问和 RBAC。它适合对照：

- 工具选择是否合理；
- 多轮调查是否会主动收缩范围；
- 大遥测输出是否先在服务端过滤；
- 结论是否有证据与操作边界。

它不直接替代 Mini-Drop 的进程级 perf/eBPF 控制面，也没有本项目的隐藏 Oracle 评分流程。公平对照必须让两者使用相同事故窗口、相同可见遥测、相同模型和工具预算。

### 4.4 Grafana Pyroscope：持续 Profiling 对照

[Pyroscope](https://grafana.com/docs/pyroscope/latest/get-started/) 可用 Docker 或二进制启动，支持持续 Profiling、时间窗口查询和火焰图探索。它最适合比较：

- 火焰图交互；
- 时间窗口回看；
- profile 查询延迟；
- 函数级钻取体验。

它不是 AI 根因诊断系统，所以比较时只比较 Profiling 能力，不把“没有 AI 诊断”算成质量 0 分。

### 4.5 OpenRCA：LLM 工具调用研究对照

[OpenRCA](https://github.com/microsoft/OpenRCA) 适合研究 LLM 如何从大量 metrics/logs/traces 中选择工具和定位根因。它的环境要求较高，优先用于设计和离线结果对照，不作为当前演示的首个依赖。

## 5. 公平的同题对照协议

每个产品必须拿到相同的：

1. 事故描述、服务拓扑和时间窗；
2. baseline / incident / verification 三段遥测；
3. 可调用数据源；
4. LLM 型号、温度和最大 Token（若产品使用 LLM）；
5. 工具调用次数与墙钟时间预算；
6. 隐藏 Oracle，且诊断阶段不可见。

统一输出至少包含：

```json
{
  "case_id": "RW-OTELPY-4224",
  "product": "mini-drop",
  "predicted_root_cause_id": "<evaluator-only submission field>",
  "scope": {"service": "...", "process": "...", "function": "..."},
  "evidence_refs": ["snapshot://...", "artifact://..."],
  "counter_evidence_refs": [],
  "abstained": false,
  "confidence": 0.82,
  "duration_seconds": 31.5,
  "tool_calls": 5,
  "cost": {"input_tokens": 0, "output_tokens": 0}
}
```

评分维度：

- 根因 Top-1 / Top-3；
- 服务、实例、进程、函数、源码位置的定位深度；
- 必需证据覆盖率和证据引用有效率；
- 反证是否实际执行；
- 信息不足时是否正确 abstain；
- 修复前后验证是否支持结论；
- 时间、工具调用数和模型成本；
- 高风险动作未经审批的次数（应为 0）。

## 6. 实际执行顺序

### 6.0 云端页面验收流程（需先取得实际云端 run 证据）

访问云端 Mini-Drop，填写 Mini-Drop 访问密钥后进入：

`AI 诊断 → 方法与测试集 → 真实开源缺陷：页面化云端复现与成熟产品对照`

实现已配置 4 个机制级案例适配器；只有实际部署后返回服务端 run ID 的执行才可计为云端运行：

| Case | 页面实际执行的机制 | baseline / incident / verification |
|---|---|---|
| RW-GRAFANA-123359 | 指针身份作为队列键导致去重失效 | 10 / 600 / 10 个队列项 |
| RW-OTELPY-4224 | bound method 强引用导致 Reader/Exporter 存活 | 0 / 600 / 0 个存活对象 |
| RW-K8S-138571 | 大集群周期性 full sync 放大 dataplane 操作 | 150 / 9000 / 150 次操作 |
| RW-ENVOY-42752 | 非 debug 模式仍逐 chunk 求值日志表达式 | 0 / 4000 / 0 次求值 |

部署后的页面在用户点击“在云端运行”后依次展示安全预检、基线、故障注入、异常确认、诊断、Oracle 对照和恢复验证。Oracle 只在诊断结束后读取。只有取得独立 run ID、服务端时间线和三段快照的实际记录，才能证明执行发生在云端服务，而非 AI 会话沙箱。

另外 3 个案例在页面中保留题面和来源，但按钮禁用并标记“尚无执行适配器”，防止把未复现案例伪装成成功。

## 8. 导师要求还有哪些遗漏

结合“循证医学、性能决策树、测试集、真实开源缺陷对照”的要求，项目现在仍有以下缺口：

1. **完整上游复现覆盖不足**：机制级执行适配器已实现 4/7，但本阶段未重新执行云端验收，真实 PR 完整仓库 A/B 仍是 0/7。
2. **成熟产品对照未落数据**：目前只有协议和产品选型，没有同题结果。
3. **源码/指令级下钻仍不完整**：多数路径止于函数，未稳定落到源码行或指令。
4. **工具失败后的动态改道需要更多证据**：目前有 fallback，但真实 Campaign 中需统计改道成功率。
5. **现有 90 次评测的必需证据覆盖率仍偏低**：正式报告约为 70%，需优先提升，而不是只追求根因命中率。
6. **置信度校准仍需加强**：完成态校准约 63%–70%，K8s #140886 这类题用于专门检查是否会过度自信。
7. **修复建议与修复后验证需绑定**：建议必须给出可测的 counterfactual，不能只输出泛化优化建议。
8. **数据集版本治理**：上游 PR 状态变化、提交变化或环境变化时必须发新版本，旧结果不可覆盖。

## 9. 仓库入口

```powershell
# 校验真实业务候选集
python scripts/real_world_benchmark.py validate

# 生成不含 Oracle 的公开执行计划
python scripts/real_world_benchmark.py plan `
  --output reports/benchmark/real-world/public-plan.json

# 对某个产品的统一输出评分
python scripts/real_world_benchmark.py score product-result.json `
  --output reports/benchmark/real-world/product-score.json

# 运行相关自动测试
python -m pytest -q tests/test_real_world_benchmark.py
```

标准答案位于 `benchmarks/real_world/private/oracles.json`，它只能由评测器在诊断完成后读取，不得进入模型上下文、Prompt 或页面请求。
