## 今天做了什么

今天主要在收拾 Mini-Drop 的 AI 诊断链路和云端环境。之前功能虽然铺得比较多，但真正在页面上操作时，还是会碰到范围不明确、测试集读取失败、演示目标连不上这些问题，所以我今天没有继续堆新功能，先把几个影响演示的地方处理掉。

### 1. 把 AI 诊断的范围确认补完整了

我先重新走了一遍 AI 诊断页面。用户只输入“订单服务最近 5 分钟 CPU 飙高”时，系统其实不知道要查哪台机器、哪个进程。如果这时直接让模型给结论，结论大概率是在猜。

我把这一段改成了先确认范围。现在 AI 会要求补充服务、环境、Agent、PID 和故障时间段，页面也会加载真实的在线 Agent 和候选进程。信息没补齐时，会停在 `NEEDS_CLARIFICATION`；范围确认后，才继续生成假设和采集计划。

这一版看起来多了一步，但我觉得是必要的。至少系统不会拿一个不存在的 PID 或错误主机继续往下跑。

### 2. 处理了云端几个会卡住演示的问题

今天排查云端时，发现 Python 演示目标出现过容器名称解析失败，Server 找不到 `python-hotspot`。我检查了 Compose 网络和健康检查，修复后，Server 在容器内可以正常访问目标的 `/health` 接口。

外部测试集也有两个问题：压缩包里带中文目录，原来的读取逻辑依赖固定路径；云端还有一个可选目录没有访问权限。现在后端会按文件结构和后缀找测试集，不再死认某一个目录。测试集也挪到了 `benchmarks/external`，跟着 Server 镜像构建，云端接口可以正常读取。

### 3. 重新跑了一次真实 CPU 故障实验

我用白名单 Campaign 跑了一次完整的 CPU 热点实验，不是直接往数据库塞一份假结果。流程是先记正常状态，再启动热点进程，确认 CPU 确实上升，然后让 Mini-Drop 创建采集任务、分析产物并做 AI 诊断。诊断结束后才读取 Oracle 对答案，最后停掉故障进程，再确认 CPU 恢复。

这次运行的结果：

- 基线 CPU 约 0.30%；
- 故障期间约 96.33%；
- 清理后约 0.29%；
- Task、TaskAttempt 和 Analyzer 都执行成功；
- 产物完整性校验通过；
- 系统判断为 `SELF_CODE_CPU_HOTSPOT`，置信度 0.91；
- 与 Oracle 一致，故障进程也完成了清理。

这次实验对我比较有帮助。以前我更多是在看页面和接口，现在至少把“制造故障、采集、诊断、对答案、恢复”这一整条链路实际走了一遍。

### 4. 检查了统一测试集

目前外部测试集是 30 个场景，每个场景跑 3 种策略，共 90 次记录。我补看了版本、SHA-256、每次运行状态和 Oracle 对比，确认页面展示的数据有对应的后端记录，不是只显示一个 100% 的汇总数字。

后面还需要继续检查这些场景的难度和数据质量。90 次全部跑完只能说明评测流程能运行，不能直接说明 AI 已经达到生产效果。
