## 2. 准确率收口

### 2.1 case-08：区分“修复未生效”和“原始根因已定位”

case-08 的公开证据只能证明：清理后仍有 64 个节点可从根对象到达，Map 条目没有减少，`release_verified=false`。这些数据足以否定“修复已经成功”，但没有分配点、保留路径或源码位置，不能证明原始缺陷属于哪个组件。

系统增加了两层约束：

- Prompt 明确区分修复结果判定和原始根因定位；
- 代码语义护栏检查 `release_verified`、清理后残留对象以及独立因果证据。只有修复失败而没有因果证据时，强制 `not_enough_evidence=true`、`root_location=unknown`。

真实模型回放结果：

| 项目 | 结果 |
|---|---|
| 模型是否实际调用 | 是 |
| 修复是否验证成功 | 否 |
| 是否承认证据不足 | 是 |
| 原始根因位置 | `unknown` |
| 保留的有效判断 | 对象在清理后仍被保留，修复未生效 |

这不是把所有结论改成“证据不足”。如果证据中另外包含 `allocation_site`、`retention_path`、`causal_symbol` 或 `causal_source_location`，系统仍允许给出明确根因位置。

### 2.2 case-01：记录为样本可判定性问题

case-01 的公开证据只显示条件分支约占 7.4% 自耗时且 P99 稳定，私有答案却要求定位到未在公开证据中出现的“关闭功能仍逐块求值”机制。仅凭公开输入无法唯一推出该机制。

处理原则：

- 不读取私有答案后硬编码规则；
- 不为提高分数伪造源码级结论；
- 将其记录为测试样本的证据充分性缺陷；
- 后续应补充源码差异、调用栈或运行时计数器，再纳入根因准确率统计。

## 3. Linux 云端真实 Campaign

四个实验均执行完整链路：安全预检 -> 基线快照 -> 白名单故障注入 -> 异常确认 -> 真实任务采集 -> 循证诊断 -> Oracle 对照 -> `finally` 清理 -> 恢复快照。

| 场景 | Campaign ID | 任务状态 | 根因 | 置信度 | Oracle 对照 | 清理恢复 |
|---|---|---|---|---:|---|---|
| Python CPU 热点 | `campaign_20260824_141405_d0186f` | DONE | `SELF_CODE_CPU_HOTSPOT` | 0.90 | 通过 | 成功 |
| Python 内存持续增长 | `campaign_20260824_141417_5e10b4` | DONE | `SELF_CODE_RETAINED_MEMORY` | 0.87 | 通过 | 成功 |
| Python 同步 I/O | `campaign_20260824_141432_673847` | DONE | `SELF_CODE_SYNC_IO` | 0.76 | 通过 | 成功 |
| 下游服务响应变慢 | `campaign_20260824_141447_ceeeb3` | DONE | `DOWNSTREAM_SERVICE_LATENCY` | 0.93 | 通过 | 成功 |

这四项不是离线填写标准答案：Campaign 会实际控制演示进程、采集基线/故障/恢复三段快照，诊断完成后才读取 Oracle 做比较，无论中途哪一步失败都会执行清理。

## 4. 本轮修复

云端首次 CPU Campaign 暴露了一个真实调度问题：Agent 仍在处理前序任务时，新任务只等待 18 秒，故障又在 8 秒后自动停止，导致任务领到时故障窗口已经结束。

修复后：

- Campaign 等待采集任务的默认超时改为 30 秒，并限制在 5 到 120 秒；
- 故障保护时间至少覆盖“任务等待超时 + 5 秒”；
- 超时参数非法时安全回退到默认值；
- 增加对应回归测试。
