# 性能测试：测什么、看什么指标、用什么工具

> 更新：2026-11-05。本文记录在本仓库实际执行过的性能相关测量、本轮新增的 HTTP 负载测试、
> 指标口径与工具选择。数字均可追溯到 `docs/evidence/` 下的收据；本文不预测容量。

## 1. 之前到底测过什么

被问“做过性能测试吗”时，容易把四件不同的事混成一件。它们对象不同，结论不能互相替代：

| 已有测量 | 对象 | 实际做法 | 证据 |
| --- | --- | --- | --- |
| 采集扰动验证 | 平台自己的采样器对被测进程的影响 | 固定 CPU 工作负载，不采样/49Hz/99Hz 各三次交错，记录 P50/P95/P99、吞吐、目标 RSS 与 profiler CPU | [scripts/quality/performance](../scripts/quality/performance/README.md) |
| Core 心跳基线 | C++ Server 的 gRPC 注册与心跳 | 10/25/50 个合成 mTLS 身份，每身份 10 次心跳，共 850 次测量心跳、0 失败 | [心跳收据](evidence/jd-quality-20261023/core-heartbeat.json)、[说明](../scripts/benchmarks/README.md) |
| Analyzer 解码吞吐 | 解析器在固定容器规格下的处理能力 | 整容器 512MiB、swap 0，10k/50k/100k 三档解码，100001 拒绝 | [交付矩阵](DELIVERY_MATRIX.md) |
| 前端渲染 | 浏览器侧首屏与稳定性 | Lighthouse 桌面档：性能 99、LCP 619.5ms、CLS 0.0697、TBT 0 | [Lighthouse 收据](evidence/guide-20261020/final/lighthouse.json) |

**缺口很具体：没有任何一条测量覆盖“用户在公网上打开页面、登录、翻任务列表”这条 HTTP 链路。**
上面四项分别测的是采样开销、gRPC 控制面、解析器吞吐和前端渲染，没有一项回答
“20 个人同时用，接口还快不快”。本轮补的就是这一层。

## 2. 测的对象是接口，但不只是接口

把“性能测试”理解成“压接口”会漏掉一半瓶颈。本仓库按四层分开测，因为它们的失败模式不同：

| 层 | 具体对象 | 典型瓶颈 | 谁来测 |
| --- | --- | --- | --- |
| 边缘 | 网关 TLS 终结、静态资源、gzip、缓存头 | `gateway` 只有 `cpus: 0.15`，`web` 只有 `0.3` | Locust（本文） |
| HTTP API | 登录后读接口、认证中间件、序列化 | `api` `cpus: 0.5`、`mem_limit: 256m` | Locust（本文） |
| 数据与存储 | PostgreSQL（`cpus: 0.5`）、MinIO / 存储后端 | 连接数、锁等待、慢查询 | 需要服务器本机指标 |
| 异步链路 | 采集派发、Analyzer 租约、SSE 推送 | 轮询频率、派发退避、长连接数 | 需要专门的有界客户端 |

所以答案是：**接口是主要压测对象，但必须同时看它下游的数据库与它上层的网关配额**。
只压接口而不看 cgroup 配额，得到的延时数字无法归因。

## 3. 需要关注什么指标

### 3.1 延迟：看分位数，不看平均值

| 指标 | 为什么看它 |
| --- | --- |
| P50 | 典型体验。空载下本套件测得 44ms，基本等于公网 RTT + 一次 nginx 处理 |
| P90 / P95 | 交互可接受度的常用门槛；“每 20 次里有 1 次慢于它” |
| P99 | 长尾。平均值会把 1% 的 2 秒请求稀释成“看起来还行” |
| max | 只用来发现离群（例：GC、连接重建、慢查询），不作为验收线 |

**平均值单独出现时不能作为结论**：1% 的请求耗时 2 秒、99% 耗时 40ms，平均值仍会显示约 60ms。

### 3.2 吞吐与错误

| 指标 | 口径 |
| --- | --- |
| RPS / 有效吞吐 | 只统计成功请求；失败要单独给 |
| 错误率 | 按状态码分类：4xx 是契约行为（401/403/409/429），5xx 才是平台故障 |
| 超时率 | 独立计数，不能并入 5xx |
| 限流命中（429） | 说明负载超过了产品自己设定的配额，属于发现，不属于故障 |

**闭环压测的陷阱**：固定并发用户时，系统变慢会让客户端自然降低发压速率，于是 RPS 下降而延迟
看起来没爆。所以必须**同时**报告 RPS 与延迟，并说明负载模型是闭环（固定并发）还是开环（固定到达率）。
本套件是闭环，因此它证明的是“这个并发下没退化”，**不能**用来宣布最大 QPS。

### 3.3 资源与服务端（本轮缺，需服务器权限）

容器 CPU 使用与 **cgroup 节流次数**（`cpu.stat` 的 `nr_throttled`）、RSS 相对 `mem_limit`、
load average、`iowait`、磁盘 IOPS、网络收发、打开的文件描述符；PostgreSQL 的连接数、等待事件、
慢查询、锁等待；Go 的 goroutine 数、GC 停顿、5xx 计数与 SSE 连接数。

本轮没有该主机的 SSH 凭据，这些字段在收据里是 `null` 并写在 `not_measured` 中，**不用客户端
延迟去反推资源占用**。

### 3.4 正确性

性能测试不应只看得快不快：401 不能变成 200、`total` 与实际条数要对得上、分页越界要返回空页而不是
全量。压测期间状态码分布（见收据 `status_counts`）就是这道检查的第一层。

## 4. Locust 还是 JMeter

**结论：本项目用 Locust。** 理由按重要性排序：

| 维度 | Locust | JMeter | 对本项目的意义 |
| --- | --- | --- | --- |
| 形态 | Python 脚本，测试即代码 | `.jmx` XML + GUI | 脚本能进 PR、能 diff、能在 CI 里跑；JMX 改一行要开 GUI |
| 认证流程 | `requests` 里设 Cookie 和 `X-CSRF-Token` 即可 | 要串联 Cookie Manager + JSON Extractor + 变量 | 本项目是 Cookie 会话 + CSRF 双要素 |
| 报告 | 内建 P50/P95/P99 + CSV/HTML | 更丰富的报告模板 | 我们要的是分位数，两者都够 |
| 环境 | 与仓库现有 Python 质量工具链一致 | 需要 JVM | 少一套运行时 |
| 扩展 | worker 横向扩压 | 线程模型，单机内存开销大 | 本项目并发量级很小，够用 |
| 协议 | 只有 HTTP | 支持 JDBC/JMS/LDAP 等 | 本项目只压 HTTP，gRPC 已有独立 Go 工具 |

代价也要说清楚：

- **Locust 走 HTTP/1.1，浏览器走 HTTP/2。** 真实浏览器多路复用，本轮数字对浏览器偏保守。
- **单进程吞吐有限**（gevent），打到饱和点前客户端会先成为瓶颈。本轮实测客户端 CPU 占用极低，
  50 RPS 以内不构成限制；真要找拐点应换 k6（Go 单二进制）或在服务器本机发压。
- **长连接不适合它。** SSE `/tasks/:id/events/stream` 需要单独的有界客户端统计事件速率和连接数。
- **JMeter 更合适的场景**：要出 GUI 报告给非开发同学看、团队已有 JMX 资产、需要 JDBC 压数据库。

## 5. 本轮实测（公开层，无需账号）

执行时间 2026-11-05 01:00（UTC+8），对象 `https://82.157.81.79`，发压机为开发机（公网）。
负载：2 → 5 → 10 → 20 个虚拟用户，20/30/30/30 秒，只读，思考时间 1–3 秒。

| 端点 | 请求数 | 平均 RPS | P50 | P95 | P99 | max |
| --- | --- | --- | --- | --- | --- | --- |
| `GET /` | 120 | 1.09 | 44ms | 60ms | 150ms | 163ms |
| `GET /<spa-route>` | 75 | 0.68 | 44ms | 95ms | 160ms | 158ms |
| `GET /assets/*` | 152 | 1.38 | 91ms | 210ms | 240ms | 305ms |
| `GET /api/v1/auth/providers` | 104 | 0.95 | 44ms | 96ms | 180ms | 180ms |
| `GET /api/v1/tasks`（无 Cookie，应 401） | 63 | 0.57 | 44ms | 83ms | 200ms | 199ms |

合计 515 个请求、0 失败、0 个 5xx、0 次限流，传输 33,117,507 字节。收据：
[公开层收据](evidence/perf-http-20261105/public-step-receipt.json)。

可以下的结论和不能下的结论：

- **可以**：在这个量级下，TLS 入口、静态资源和认证拒绝路径没有退化；`/` 与 API 的 P50 同为
  44ms，说明网关与 Go 处理在 20 并发下**小于测量分辨率**，不是瓶颈；静态资源 P95 210ms 主要来自
  传输 165KB（gzip 后）的正文，不是服务端计算。
- **不能**：这一档不能说平台能扛多少 QPS。20 个虚拟用户带思考时间只有 4.7 RPS，离饱和很远；
  也不能据此说“接口 44ms 很快”——44ms 里绝大部分是公网 RTT（本机到该主机 TLS 建连约 89ms）。
  容量见下一节。

### 5.1 能压到多少（同一晚的容量探针）

交互式节奏只能证明“没退化”，回答不了“上限在哪”。为此另跑三组：只打小正文端点
（`--exclude-tags assets`，避免测到本机下行带宽）、缩短思考时间、逐级加人。
全部 0 失败、0 个 5xx、0 次限流，跑完立刻恢复（`GET /` 137ms）。

| 档位（稳态窗口） | 稳态 RPS | P50 | P95 | P99 | 最慢 | 失败 |
| --- | --- | --- | --- | --- | --- | --- |
| 25 用户，思考 0.1–0.3s | 95（峰 101） | 44ms | 77ms | 217ms | 390ms | 0 |
| 50 用户，思考 0.1–0.3s | 194（峰 200） | 44ms | 77ms | 178ms | 750ms | 0 |
| 100 用户，思考 0.1–0.3s | 327（峰 398） | 44ms | 89ms | **736ms** | 1600ms | 0 |
| 100 用户，思考 0.05–0.15s（单发压进程） | 386（峰 **639**） | 50ms | 97ms | **1920ms** | 3800ms | 0 |
| 100 用户，同负载拆成 2 个发压进程 | 325（合计） | 68ms | **500–660ms** | 3400–3800ms | 5012ms | 0 |

怎么读这张表：

1. **无损区间约 200 RPS**：50 用户档 P95 77ms、P99 178ms，和 25 用户档没差别。
2. **300–400 RPS 开始长尾劣化**：P95 还停在 90ms 左右，P99 从 0.2 秒涨到 0.7–1.9 秒。
   P95 好、P99 坏，说明是一小部分请求在排队，而不是整体变慢。
3. **再加压只涨延迟不涨吞吐**：最后一组把发压能力翻倍（两个进程各 50 用户），
   总吞吐反而从 386 掉到 325，P95 从 97ms 恶化到 500–660ms。发压机不是瓶颈，
   **瓶颈在服务端这一侧**。
4. **退化表现是变慢而不是报错**：全程没有 5xx，也没有超时。容器 CPU 配额被打满后
   请求在队列里等，而不是把错误甩给客户端——这是 cgroup 限流的行为，也意味着
   “看错误率判断容量”会误判。

所以答案分三层，不能合并成一句：

- **已实测的可用区间**：≤200 RPS 无损；300–400 RPS 可用但尾部到秒级；≥400 RPS 吞吐饱和。
- **瓶颈位置（强推断，非定论）**：网关 `cpus: 0.15`、web `0.3`、api `0.5` 是首要嫌疑，
  因为每个请求都要穿过这三跳，而响应体只有 156–855 字节。**但没有拿到
  `cpu.stat` 的 `nr_throttled`，所以只能写“指向”，不能写“已证明”。**
- **对业务的意义**：这是个团队内部诊断平台，真实并发是“几个人同时在排查”。
  400 RPS 已经远超需求，容量不是风险；真正值得知道的是**墙在网关 CPU 配额上**，
  它是个可配置项，而不是代码结构问题。

仍未测：登录后业务读路径的容量阶梯（已测 20 用户交互式量级，见 6.1）、
服务器本机发压与指标采样、SSE 长连接并发、长时间稳定性。

## 6. 认证层怎么跑

登录限流是 10 次/15 分钟/IP，所以套件**不**让每个虚拟用户各登录一次，而是先换 ≤8 个真实会话，
再让 N 个虚拟用户轮转复用。凭据只从两行文件或环境变量读取，不落参数、不落日志、不写进收据，
会话池用完即删。

```bash
# .local/loadtest/account.txt：第一行用户名，第二行口令（.local/ 已在 .gitignore）
python scripts/quality/loadtest/run.py --host https://82.157.81.79 \
  --profile api-step --sessions 4 --insecure --out .local/loadtest/api-step
```

要拿到服务端 CPU 与 PostgreSQL 指标，需要在 82.157.81.79 本机发压
（`--host http://127.0.0.1:18080` 或反向代理内的服务名），同时采 `docker stats`、
`cgroup cpu.stat` 与 `pg_stat_activity`。SSH 凭据已于 2026-11-07 具备，但本轮认证层
仍在工作站侧发压（与公开层同源、可对比），服务器本机发压与指标采样仍未执行。

### 6.1 认证层实测（2026-11-07）

使用管理员账号（来自服务器 secrets，凭据不入库）执行同一 `api-step` 阶梯
（2→5→10→20 虚拟用户，20/30/30/30 秒，4 个预登录会话轮转复用，只读接口）：

| 路径 | P50 | P95 | P99 | 最慢 |
| --- | --- | --- | --- | --- |
| `GET /api/v1/overview` | 52ms | 160ms | 230ms | 231ms |
| `GET /api/v1/tasks` | 48ms | 90ms | 180ms | 227ms |
| `GET /api/v1/tasks/:id` | 54ms | 110ms | 210ms | 211ms |
| `GET /api/v1/tasks/:id/events` | 49ms | 69ms | 87ms | 87ms |
| `GET /api/v1/tasks/:id/result` | 49ms | 56ms | 93ms | 93ms |
| `GET /api/v1/quality/runs` | **110ms** | **200ms** | 220ms | 219ms |
| `GET /api/v1/agents` | 47ms | 68ms | 260ms | 256ms |
| 其余（auth/me、schedules、providers、401 路径等） | 45–47ms | 60–150ms | 60–240ms | ≤244ms |

合计 773 请求、6.98 RPS、**0 失败、0 个 5xx、0 次限流**，最差端点 P95 200ms、P99 260ms，
四项门槛（无 5xx、失败率 ≤1%、P95 ≤800ms、P99 ≤2000ms）全部通过。收据
[auth-step](evidence/perf-http-auth-20261107/auth-step-receipt.json)、[负载模型](evidence/perf-http-auth-20261107/auth-step-meta.json)。

怎么读：

- 登录后读接口 P50（45–54ms）与公开层同级——认证中间件加 PostgreSQL 单查询的开销
  在 20 并发下仍小于测量分辨率（公网 RTT 主导）。
- `quality/runs` 是唯一 P50 过百的端点（110ms/20 用户）：它按 SHA 逐条读回 14 条质量摘要，
  是明确的 PostgreSQL 重查询端点，也是后续加压时最先值得单独看的一个。
- 结论仍只覆盖"20 个带思考时间的虚拟用户"量级；登录后路径没有做 25/50/100 用户容量阶梯，
  不能把公开层的 400 RPS 结论外推到认证层——它碰 PostgreSQL（`cpus: 0.5`），墙只会更低。
- 服务器本机采样（`docker stats`、`nr_throttled`、`pg_stat_activity`）仍未执行，
  延迟不能归因到具体容器配额。

认证链路的**工具**本身已用本机 mock 端到端验证过（换 2 个会话、轮转复用、读 9 类接口、
`409 RESULT_NOT_READY` 按契约计为通过、收据正常合成），所以缺的只是账号和服务器指标，
不是代码路径。mock 的延迟数字没有任何参考价值，不作为证据收据。

## 7. 边界

- 本套件**没有**写接口开关。创建任务被串行槽位（容量 1）约束，写请求另有 60 次/分钟限流，
  用压测撞限流得到的是限流器性质，不是平台容量。
- 单次上限 100 虚拟用户、600 秒、8 个会话，越界拒绝启动。这是有界实验，不是浸泡测试，
  也不能证明长时间稳定性。
- 生产是 4C8G、29 个容器的小机队，且承担演示环境职责。压测期间应避免并行构建、
  镜像构建或大规模采集等重任务——历史记录里曾出现并行重任务把宿主 I/O 压到 ~91%、
  SSH 停在 banner 阶段的情况（[开发日志](../DEVELOPMENT_LOG.md)）。

## 8. 复现与回归

```bash
cd scripts/quality/loadtest && python -m unittest test_loadtest   # 11 项离线测试
python scripts/quality/loadtest/run.py --host <url> --profile public-step --insecure --out <新目录>
```

单元测试只验算统计合成、越界拒绝与凭据解析，**不能**证明平台性能；性能结论只认实际执行的收据。
