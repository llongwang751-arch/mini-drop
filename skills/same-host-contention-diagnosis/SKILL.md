# 同机资源争抢循证诊断

## 目标
区分目标进程自身计算热点与同宿主机其他进程造成的 CPU 争抢，避免把主机繁忙误判为业务代码问题。

## 输入契约
- 必填：`agent_id`、目标进程绑定、`environment`、`start_time`、`end_time`。
- 可选：容器配额、宿主机基线、同机进程清单、吞吐与延迟。
- 同机进程信息只能来自授权 Agent 的只读快照。

## 适用与停止条件
- 适用：宿主机 CPU 饱和、目标延迟升高，但目标自身热点不明显或 CPU 时间不匹配。
- 目标和宿主机时间窗不一致、同机进程不可见或采样严重丢失时停止强归因。
- 若目标调用栈存在稳定热点，应回到 CPU 热点路线而非坚持噪声邻居假设。

## 取证顺序
1. 比较宿主机总 CPU、目标进程 CPU、负载和调度指标。
2. 对目标执行短时 perf，判断是否存在足以解释现象的自身热点。
3. 观察同机进程 CPU ticks 与上下文切换，寻找竞争来源及反证。
4. 停止受控邻居负载后复测目标延迟、可运行队列和 CPU 分配。

## 结论门槛
- 同机争抢要求宿主机饱和、目标自身无主导热点、其他进程占用增长且恢复窗改善。
- 目标热点要求其 CPU 与栈样本集中，不能仅用宿主机总 CPU 下结论。
- 同机进程不可见时只能报告“疑似资源争抢”，不能点名责任进程。

## 必需证据与反证
- 支持证据：主机与目标 CPU 时序、运行队列、目标 perf、同机进程计数、恢复窗。
- 反证：目标自身稳定热点、主机未饱和、竞争进程无变化或停止邻居后现象不恢复。

## 安全边界
- 只读观察授权范围，不终止、降权或修改其他进程和容器。
- perf 持续时间、频率和并发必须通过本地预算。
- Skill 不携带旧主机的 PID、结论或 Evidence。

## 输出契约
输出 `root_cause`、`confidence`、`evidence_refs`、`counter_evidence_refs`、`limitations` 和 `next_action`；任何责任进程必须有本次快照引用。

## 回归门禁
- 噪声邻居正例必须通过目标栈反证和停止后的恢复验证。
- 业务热点、I/O 等待和配额节流反例不得归入同机争抢。
- 进程身份漂移或快照过期时拒绝复用旧 PID。
- Skill A/B 两组都必须独立产生本次 Evidence。
