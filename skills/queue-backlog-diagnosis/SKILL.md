# 队列堆积循证诊断

## 目标
判断队列增长来自入口突发、消费能力下降、消费者代码热点还是下游等待，并用恢复窗验证方向。

## 输入契约
- 必填：`agent_id`、受服务端证明的目标绑定、`environment`、`start_time`、`end_time`。
- 可选：生产速率、消费速率、队列深度、最老消息年龄、消费者数量与发布版本。
- 业务指标必须来自本次服务端发现或采集，不接受模型自行补齐。

## 适用与停止条件
- 适用：队列深度或排队时延持续增长、消费吞吐下降、任务超时。
- 队列指标不在时间窗内、目标消费者无法绑定或只有单个瞬时点时停止根因归因。
- 生产和消费恢复平衡后仍不退积压时，应转查毒消息、重试风暴或外部依赖。

## 取证顺序
1. 采集系统及进程指标，并比较生产速率、消费速率和队列深度趋势。
2. 若消费者 CPU 同窗升高，受控采样热点；若 CPU 不高，转查等待、重试和下游延迟。
3. 检查入口突发、消费者数量变化和同机资源竞争作为反证或替代解释。
4. 停止注入后观察生产消费差值与积压消退速度，形成闭环。

## 结论门槛
- 速率失衡必须由连续窗口的生产率高于消费率和队列增长共同支持。
- 消费者热点需要目标 CPU 与调用栈证据，不能只凭队列增长推断。
- 下游等待需要低本地 CPU、等待路径或依赖延迟证据共同支持。
- 缺少恢复窗或业务计数器时只能给出受限结论。

## 必需证据与反证
- 支持证据：生产/消费计数、队列深度、目标系统指标、专项栈或依赖观测、恢复窗。
- 反证：队列深度稳定、消费率不低、消费者 CPU 正常且无等待、停止注入后仍无变化。

## 安全边界
- 只读采集，不清空队列、不扩缩容、不修改并发和重试参数。
- 所有专项探针必须通过会话预算与 Agent 能力门禁。
- Skill 只复用经验证的取证次序，绝不复用旧案例结论或证据。

## 输出契约
输出 `root_cause`、`confidence`、`evidence_refs`、`counter_evidence_refs`、`limitations` 和 `next_action`，并明确区分入口、消费者和下游三个责任域。

## 回归门禁
- 正例必须至少经过速率对比、资源或等待专项证据和恢复验证三轮。
- CPU 热点、入口突发与下游等待反例不得被同一路线强行归因。
- 缺失业务计数器时必须显式降级，不能生成虚构的队列指标。
- A/B 开启组可命中该路线，关闭组必须独立规划并重新采集。
