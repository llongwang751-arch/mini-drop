# Python Runtime 循证诊断

## 目标
区分 Python 用户态热点、GIL 或线程调度问题、事件循环阻塞与系统层开销，并生成可回溯到采集任务和原始栈的结论。

## 输入契约
- 必填：`agent_id`、受服务端快照证明的进程绑定、`environment`、`start_time`、`end_time`。
- 可选：服务名、Python 版本、发布版本、吞吐和历史基线窗口。
- 不接受模型自行猜测的 PID；进程启动时间、PID namespace、可执行文件身份和 Agent 必须与最新快照一致。

## 适用与停止条件
- 适用：Python 服务 CPU 持续升高、吞吐下降、延迟升高、疑似 GIL 竞争或 busy loop。
- PID 已退出、py-spy 无法附加、样本量不足、时间窗错位或产物完整性失败时停止归因。
- Python 栈没有热点但系统 CPU 仍高时，转入 perf 或系统指标路径，不把未知内核开销归因给 Python 代码。

## 取证顺序
1. 使用 py-spy 对已证明身份的目标进程做短时只读采样，生成 speedscope、火焰图和 TopN。
2. 检查样本量、热点集中度、线程分布、GIL 相关栈和事件循环调用链。
3. 必要时补采系统指标，确认目标进程 CPU 与故障时间窗一致。
4. Python 栈不能解释现象时，受控降级到 perf 以区分用户态、内核态和调度开销。
5. 修复或关闭故障开关后复测，验证热点占比、CPU 或延迟是否回落。

## 结论门槛
- 用户态热点：有效样本集中在少数 Python 函数，且函数、文件、行号可定位。
- GIL 或线程竞争：多个线程的等待/运行分布和相关栈共同支持，不能仅凭“多线程”下结论。
- 事件循环阻塞：主要样本稳定落在同步阻塞或长耗时回调，并与延迟窗口一致。
- 只有一次采样且没有恢复窗时，必须在报告中保留限制，不把相关性包装成修复已验证。

## 必需证据与反证
- 支持证据：原始 speedscope、样本总量、TopN、火焰图、目标身份绑定和时间窗。
- 反证：样本均匀、热点在解释器外、目标进程 CPU 正常、修复后热点不回落或采集错误率过高。

## 安全边界
- 只调用注册过的只读采集工具，不执行任意 Shell、代码修改、重启或业务参数变更。
- py-spy、perf 的持续时间、采样率、并发、主机数和产物大小必须同时通过会话预算与 Agent 本地预算。
- 采集产物只能上传到 task/attempt 作用域的短期授权对象键。

## 输出契约
必须输出 `root_cause`、`confidence`、`evidence_refs`、`counter_evidence_refs`、`limitations` 和 `next_action`；函数级结论必须引用已验证的 TopN 或火焰图 Evidence。

## 回归门禁
- Python CPU 正例应优先选择 py-spy，并能从真实 Artifact 生成 Evidence 和报告。
- 内核热点、IO 等误导反例不得套用 Python 用户态热点结论。
- py-spy 不可用时允许受控降级到 perf，但必须降低置信度并记录降级原因。
- 进程身份漂移、空样本、Hash/Schema 失败或工具调用失败时，不得把该证据计为支持。
