# CPU 热点循证诊断

## 目标
回答“CPU 为什么升高”，并用基线、故障、恢复三个时间窗验证结论，而不是只凭一次火焰图猜测。

## 输入契约
- 必填：`agent_id`、`pid`、`environment`、`start_time`、`end_time`。
- 可选：服务名、发布版本、请求量、历史基线窗口。
- PID 必须属于所选 Agent；故障时间窗必须覆盖用户看到的异常。

## 适用与停止条件
- 适用：目标进程 CPU 持续升高、吞吐下降或延迟上升。
- PID 已退出、样本为空、采集器降级或时间窗错位时停止归因，返回“证据不足”。
- 只有主机 CPU 高、目标进程 CPU 不高时，转查噪声邻居或系统负载。

## 取证顺序
1. 采集主机与目标进程 CPU，确认异常与目标 PID 同窗出现。
2. 受控执行 perf 采样，生成火焰图、热点函数 TopN 和用户态/内核态占比。
3. 检查样本是否集中在少数业务函数，并检查 syscall、锁等待和调度开销等反证。
4. 停止故障或应用修复后重复采集，确认 CPU 与热点占比回落。

## 结论门槛
- 用户态热点：目标进程 CPU 同窗升高，热点函数样本集中，并在恢复窗显著回落。
- 内核开销：内核调用链占比显著，且与 I/O、网络或内存行为一致。
- 锁竞争：锁相关栈、线程等待和上下文切换同时异常。
- 不满足闭环时必须拒答，不把“CPU 高”直接写成“代码热点”。

## 必需证据与反证
- 支持证据：CPU 时间序列、perf 栈样本、热点 TopN、恢复窗复测。
- 反证：热点分散、样本主要来自内核、目标 PID CPU 正常、恢复后热点未变化。

## 安全边界
- 只调用注册过的只读采集工具。
- perf 必须审批并限制频率与持续时间。
- 不自动重启进程、不修改业务参数、不执行任意命令。

## 输出契约
必须输出 `root_cause`、`confidence`、`evidence_refs`、`counter_evidence_refs`、`limitations` 和 `next_action`。每条结论必须能跳转到原始任务、快照或产物。

## 回归门禁
- 相似正例可以复用取证顺序；syscall、锁等待等误导反例不得套用代码热点结论。
- perf 不可用时降级并降低置信度，不伪造调用栈。
- 必须比较基线、故障、恢复三阶段，旧版本误迁移时隔离当前版本。
